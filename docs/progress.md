### Как запустить

Разработка (инфраструктура в Docker, api/worker и web на хосте):

```bash
bash infra/scripts/generate-secrets.sh
pnpm install && docker compose up -d --wait
pnpm db:migrate && pnpm db:seed && pnpm dev
```

Установка целиком в контейнерах (ADR-0044):

```bash
bash infra/scripts/generate-secrets.sh --mode app
docker compose --profile app up -d --build --wait
docker compose exec api kchs init --admin-email admin@example.org
docker compose exec api kchs seed        # демо-данные, по желанию
```

Демо-данные: администратор `admin`, сотрудники `user001…user060` (пароли — N2 в
`05-risks-and-open-questions.md`); почта разработки — mailpit.

### Найдено и исправлено при закрытии фазы

Безопасность:

- Вложение сообщения обсуждения открывало автору чужой файл: связь `attachment` создавалась без
  проверки прав на файл, а по ADR-0042 она открывает файл читателям объекта (89c6572).
- Шлюз MFA обходился: коррелированный подзапрос Drizzle в списке выборки сравнивал столбец сам с собой.
- Повышение привилегий через управление ролями, захват учётной записи через восстановление,
  вход с неподтверждённой настройкой (2274d59).
- Разрыв наследования не закрывал поддерево: роль пространства, ACL предков, вложенные копии (0f9d0e9);
  утечки по матрице типов объектов (a96dcb2).
- Уведомление об упоминании раскрывало объект получателю без доступа (14f64bf).
- Внутренние маршруты движка были доступны через прокси (fddbe19).

Работоспособность:

- Лимит входа по одному адресу блокировал организацию за NAT после десятого входа за минуту (709e300);
  429 приходил английским текстом плагина.
- Файлы в поиске находил только администратор (5230c10).
- Подписанные ссылки S3 не работали в контейнерах: адрес подменялся после подписи (d061285).
- Реакции писались мимо outbox, правки и реакции не доходили до соседей (89c6572); список сообщений
  с вложением падал на схеме ответа.
- Из пространства можно было убрать последнего администратора (50d32f7).
- Обрезка «недавних» была написана, но не вызывалась — таблица росла без предела (knip).
- Брошенные события не доставлялись повторно (5bf0129); задание могло уйти в очередь до коммита (c1de5aa).
- Сбой отправки комментария был молчаливым и терял текст (a157c58).

### Принятые решения (ADR)

- ADR-0025…0034 — см. предыдущие записи (расширения в `extensions`, свой образ Postgres,
  отметка после подписчика, ISO-время, тестовая база, типизированный клиент, порт справочника,
  токен гостевой ссылки, «от имени» заголовком, почта сразу и дайджестом).
- ADR-0035 — у каждой очереди заданий один исполнитель.
- ADR-0036 — задание ставится в транзакции и уходит в очередь после коммита.
- ADR-0037 — собственный переводчик в `@kchs/i18n` вместо i18next.
- ADR-0038 — нативное перетаскивание и перенос с клавиатуры.
- ADR-0039 — SchemaForm без react-hook-form.
- ADR-0040 — политика безопасности: системные настройки, кэш процесса, шлюз незавершённой настройки входа.
- ADR-0041 — импорт пользователей из Excel.
- ADR-0042 — вложения: закрытая системная папка и доступ через связь `attachment`.
- ADR-0043 — строгий CSP с nonce запроса.
- ADR-0044 — установка: `kchs init`, образ api одним бандлом, web — единственная точка входа.
- ADR-0045 — наблюдаемость: OpenTelemetry по запросу, Alloy, бюджеты API профилем k6.

## Фаза 1 — Данные и аналитика

Ветка `phase/1-data`, начата 18.09.2026. **Все семь сценариев приёмки фазы проходят в e2e, демо-
датасеты на 5 млн строк загружаются сидом, бюджет запросов выдержан (k6).** Эпики P1-E01…P1-E10
закрыты в объёме приёмки; отложенное — ниже.

**Сделано (в ветке):**

- Контракты фазы: датасет, импорт, QuerySpec, ChartSpec, дашборд; события `dataset.*`,
  `chart.updated`, `dashboard.updated`; очередь `data`.
- P1-E01 — датасет как объект реестра; таблицы `ds.t_*`, история `ds.h_*`, версии; правка схемы с
  пробным отчётом смены типа (ADR-0047); `kchs_query` читает только таблицы строк (ADR-0048);
  строки: чтение через компилятор с политиками, правка с `_ver` и 409, история (ADR-0051).
- P1-E02 — анализ и нормализация в движке (CSV/TSV/XLSX/XLS/JSON/NDJSON/GeoJSON, кодировки,
  локали, геометрия; 1 млн строк CSV ≈ 9 с), загрузка воркером (replace/append/upsert/sync),
  мастер импорта в 4 шага.
- P1-E03 — экран датасета: DataGrid (ADR-0050) с поиском, сортировкой и правкой ячеек, редактор
  схемы, профиль столбца, версии, импорты; слой `DatasetAccess` — политики строк и столбцов.
- P1-E04 — компилятор `packages/query` (выражения, QuerySpec → SQL, политики, 616 тестов),
  выполнение под `kchs_query` с тайм-аутом и кэшем Redis по версиям.
- P1-E05 S01 — «Исследование»: фильтры, разрезы с интервалами, меры, сортировка, лимит, автозапуск.
- P1-E06 S01, S03 (часть) — `chart-spec` и `Chart` (ADR-0049), графики и дашборды — объекты
  реестра; данные — с правами смотрящего, плитка без доступа — «нет доступа».
- Попутно: доступность панели вкладок и пустой таблицы (axe чистый), имя автора в письмах
  уведомлений, устойчивость e2e к данным общего стенда.

- Политики строк и столбцов (ADR-0055): API для `manage+`, фильтр проверяется компилятором,
  событие `dataset.policies_changed`, вкладка «Доступ» с выбором принципала и конструктором
  фильтра; поле из политики не удаляется и не меняет тип на несовместимый.
- P1-E03 S01 — добавление строк вставкой из буфера (ниже последней строки и «Добавить строки»);
  S03 — карточка строки: поля с правкой по месту, история, удаление, новая строка формой;
  S04 — экспорт CSV/XLSX/JSON/GeoJSON заданием `exports` с политиками на момент выполнения,
  до 1 млн строк, XLSX собственным потоковым писателем (ADR-0056).
- P1-E04 S04 и P1-E05 S02 — сырой SQL (libpg-query, белые списки, подзапросы-политики,
  ADR-0052), SqlEditor на CodeMirror 6 и экран «SQL-лаборатория» (способность `data.sql`,
  ошибки с позицией, ADR-0059).
- P1-E06 S02 — показатели: определение, окна периодов, сравнения, пороги, один путь значения,
  плитка-показатель и TV-режим дашборда (ADR-0058).
- P1-E10 (часть) — детерминированный генератор демо-данных в движке: территории, справочники,
  5 млн происшествий, гидропосты, объекты и зоны риска, манифест загрузки (ADR-0054).
- Безопасность: пользовательские запросы к данным без подмены роли `kchs_query` ролью приложения
  (в продакшене конфигурация без `DATABASE_QUERY_URL` не загружается); поиск принципалов больше
  не находит заблокированных по логину; удаление обычного поля датасета больше не падает с 500.
- P1-E06 S03 — детализация плитки дашборда до строк (условия графика, фильтры дашборда и
  выбранный элемент, политики смотрящего) и перекрёстный фильтр по привязке плитки.
- P1-E01 S04 — откат датасета к прежней версии новой версией «Откат» (ADR-0062): история строк
  помечается номером версии, отменяются правки и импорт «дополнить»; замена, синхронизация и

### P5-E04, часть «вход и каталог» (ADR-0098)

- **Каталог LDAP/AD.** Настройка подключения (адрес, StartTLS, проверка сертификата, учётная
  запись чтения, корни и фильтры поиска), соответствие полей записи полям карточки, сопоставление
  групп каталога с ролями. Синхронизация сотрудников, подразделений и должностей всегда строит
  план изменений и только потом применяет его — предпросмотр «что изменится» это тот же код без
  записи. Уволенный в каталоге или пропавший из него блокируется, локальная учётная запись с тем
  же логином каталогу не отдаётся. Журнал синхронизаций с разбором каждого прогона. Расписание —
  одно повторяемое задание в час, интервал задаёт администратор. Вход по паролю каталога — привязка
  (bind) в том же `AuthService.login`: блокировка после серии неудач, аудит и политика сессий
  прежние.
- **Единый вход OIDC.** Authorization Code + PKCE через `openid-client`, состояние входа —
  одноразовая строка в базе (`state` хэшем, проверочный код зашифрован), JIT-создание сотрудника,
  сопоставление claims и групп с ролями, завершение сессии провайдера при выходе. Секрет клиента
  наружу не возвращается.
- **Ключи входа (passkeys).** Регистрация в профиле, самостоятельный вход и подтверждение второго
  фактора, список и отзыв. Ключ с подтверждением личности входит сам и засчитывается как второй
  фактор наравне с TOTP; ключ без подтверждения — только второй фактор.
- **Экраны.** Администрирование: «Каталог (LDAP/AD)» и «Единый вход» с кнопкой «Проверить
  соединение», предпросмотром и журналом синхронизаций. Профиль: «Ключи входа». Экран входа:
  кнопки «Войти через <IdP>» и «Войти по ключу» — только если способ настроен.
- **Тесты.** 47 интеграционных проверок в `directory-sso.test.ts` и `passkeys.test.ts`; внешних
  служб не требуют: каталог, поставщик OIDC и ключ входа поднимаются поддельными, а клиентские
  библиотеки настоящие. Негативные: чужой и повторный `state`, подменённый `nonce`, просроченный
  код, отключённый в каталоге и исчезнувший из каталога сотрудник, отозванный ключ, повтор ответа
  устройства, чужой адрес сайта, чужой ключ на чужом вызове входа.
- **Не сделано в этой части эпика**: IMAP-регистрация входящих, ONLYOFFICE, CalDAV.

### P5-E02 и P5-E06 (часть): публичный API, вебхуки, интеграции, конфигурация

Ветка `phase/5-platform`, ADR-0097.

**Токены публичного API.** `kchs_<префикс>_<секрет>`: в базе только хэш,
видимый префикс ищет строку, сравнение по SHA-256 в постоянное время. Токен
строит контекст своего владельца и дальше проходит обычный `authorize()` —
прав не расширяет. Область доступа выводится из тега маршрута (`read:` для
`GET` и `POST` с `readOnly`, иначе `write:`), список закрыт по умолчанию:
незнакомый тег, отсутствие тега и пути `/me`, `/auth`, `/internal`, `/admin`,
`/share`, `/hooks` токенам недоступны. Режим администратора и замещение токену
не достаются, незавершённая настройка входа владельца закрывает токен целиком,
у токена свой счётчик запросов. Экраны — «Мои токены» в профиле и «Токены API»
в администрировании.

**Документация API.** `/api/docs` собирается на сервере по текущему OpenAPI:
без скриптов и внешних библиотек, стиль — отдельным файлом того же
происхождения (CSP установки разрешает только свои файлы, ADR-0043).
Спецификация приведена в порядок: описания разделов, обе схемы аутентификации
по умолчанию, служебные маршруты вне `/api/v1` из неё убраны; тест требует у
каждой операции тега, краткого описания и ответов.

**Массовые и длительные операции.** `POST /objects/batch-get` был, помечен
`readOnly`; добавлен `POST /datasets/{id}/rows/batch` — вставка, изменение и
удаление одной транзакцией, больше 500 операций или `async` даёт `202` с
`jobId`. Задание выполняется правами поставившего (`buildUserCtxFor`), а не
системы: иначе массовая правка обходила бы политики строк.

**Вебхуки.** Исходящий — объект реестра с фильтром по типам и пространствам и
владельцем `run_as`; наружу уходит только то, что видит владелец подписки, и
никогда домены `job`, `webhook`, `token`. Подпись
`sha256=HMAC(секрет, "<timestamp>.<тело>")`, повторы 30 с … 6 ч до суток,
серия отказов отключает подписку, есть журнал доставок и ручной повтор. Адрес
проверяется до запроса (только внешний, без перенаправлений). Входящий
`POST /hooks/{id}/{secret}` только публикует `webhook.received`: знание
секрета не даёт доступа к данным, а неизвестная интеграция, выключенный вход и
неверный секрет отвечают одинаково.

**Интеграции.** Объект `integration` с зашифрованными секретами (наружу — лишь
имена ключей), статусом, журналом синхронизаций и проверкой связи; права —
способность `automation.manage`. Встроенные SMTP и Telegram остались в
переменных окружения и показываются в общем списке только для чтения — общий
учёт получен, работающее не сломано.

**Пакет конфигурации.** Реестр разделов в ядре (`kernel/config-package`),
поставщики — `integrations`, `webhooks`, `processDefinitions`. Импорт идёт
через предпросмотр различий с отметкой конфликтов (запись правили здесь после
выгрузки пакета); секреты в пакет не едут. Раздел `documentTypes` объявлен, но
не поддержан: журналам регистрации нужен стабильный ключ (вопрос N42).

**Найдено и исправлено по ходу:** секрет токена в base64url содержит «_», и
разбор через `split('_')` отбрасывал действующий токен — нашли негативные
тесты.

**Проверки:** `pnpm lint`, `pnpm typecheck`, `pnpm deps:check`, `pnpm knip`,
`pnpm i18n:check`, `pnpm i18n:literals`, `pnpm test`; интеграционные в слоте 11
(`access-matrix`, `integrations-tokens`, `integrations-webhooks`,
`integrations-config`, `api-docs`, `data-rows-batch`). Сквозной сценарий —
`apps/web/e2e/integrations.spec.ts` (прогон при слиянии).

**Осталось:** правила автоматизации и расписания (параллельная ветка); разделы
пакета конфигурации сверх трёх (после N42); проверка связи для IMAP, LDAP и
OIDC появится вместе с самими интеграциями в P5-E04.
**Сделано:**

- P5-E02 (часть «правила и расписания») — правила автоматизации (ADR-0096). Правило — объект
  реестра `rule` с определением «когда / если / то»: триггеры `event` (тип каталога или префикс
  домена + отбор по полям конверта), `schedule` (cron с поясом), `webhook` (входящий вызов с
  секретом в адресе), `manual` (кнопка у объекта), `metric` (значение показателя по расписанию);
  условия и шаблоны `{{…}}` — язык выражений платформы (`@kchs/query/expr`), получатели и
  исполнители — язык назначений маршрутов (`@kchs/process`). Семнадцать действий: `notify`,
  `create_task`, `update_fields`, `set_status`, `assign`, `create_document`, `start_process`,
  `add_link`, `add_tag`, `post_message`, `create_event`, `send_email`, `send_telegram`,
  `webhook`, `ai_task`, `wait`, `stop` — чужие модули только через `public.ts`.
- Исполнение — задание очереди `automation` от имени служебного пользователя правила (`run_as`);
  администратор системы недопустим, а запуск пропускается, если `run_as` не видит объект события:
  условия и шаблоны не вычисляются, уведомление не уходит. Журнал `rule_runs` с логом шагов и
  диагностикой, идемпотентность по `(ruleId, eventId)`, дедупликация по ключу в окне, лимит
  запусков в час, защита от циклов (событие правила несёт `causationId` и источник `automation`,
  правило не идёт от собственных событий, глубина цепочки ≤ 5), ошибка — событие
  `rule.run_failed` и уведомление владельцу.
- Тестовый прогон «что бы произошло» на последних событиях из outbox — под правами `run_as`,
  без выполнения действий; галерея шаблонов правил; справочник конструктора (события каталога с
  полями полезной нагрузки, поля карточек типов, опубликованные маршруты).
- Единый планировщик (`kernel/schedules`): регулярные задания объявляются `declareSchedule` и
  ставятся одним проходом при старте воркера; обслуживание, таймеры маршрутов и задания модулей
  переведены на него; расписания правил по cron — собственные планировщики BullMQ по состоянию
  правила. Экран «Расписания» в администрировании: ближайший запуск, последний результат,
  история, переключатель и «выполнить сейчас».
- Веб: список правил по пространствам с включением, конструктор «когда / если / то» во вкладке
  (подсказки каталога, проверка на лету, лимиты, вкладка JSON), история запусков с шагами,
  тестовый прогон, галерея шаблонов при создании, кнопки ручного запуска у объекта в
  контекст-панели.
- Тесты: модульные (выражения и шаблоны, дерево условий, отбор триггером, проверка определения)
  и интеграционные на настоящих шине, очереди и воркере, включая негативные — правило с
  ограниченным `run_as` ничего не делает с чужим объектом, уведомление не уходит тому, кто не
  видит объект, правило не запускается от собственных событий, лимит и идемпотентность.
  Спецификация e2e — `apps/web/e2e/automation-rules.spec.ts` (прогон при слиянии).

## Известные ограничения

- Архивирование пространства не сделано: содержимое не лежит под пространством в `object_ancestors`,
  заморозка только объекта пространства оставила бы содержимое изменяемым — нужен отдельный проект
  (архив по `space_id` с восстановлением по отметке времени).
- Способности системных ролей только читаются; свои роли (`roles.manage`) — позже.
- Таджикская локаль покрыта на 6,5 % ключей (324 из 5008; недостающие берутся из русской) — тексты
  фаз 1–3 ждут перевода и вычитки носителем.
- Наблюдаемость: нет экспортёров метрик Postgres/Redis/MinIO/Meilisearch, Alertmanager (правила есть,
  доставки нет), трасс движка; экран «Здоровье» пока не читает метрики.
- Производительность, замеченная при профилировании: каждый запрос обновляет сессию (`touchSession`),
  `GET /objects/:id` проверяет доступ дважды — в бюджете, но стоит поправить до фазы 1 под нагрузкой.
- Поле даты-времени `SchemaForm` и формы объявлений работают в поясе браузера, а не профиля пользователя.
- Сборка web — один бандл больше 500 кБ; разбиение по экранам — вместе с модулями фазы 1.
- Партиционирование `activities`, `notifications`, `query_runs` — до появления объёмов.
- Заголовки карточек дизайн-системы — не заголовки (`div`), навигация скринридером по виджетам
  «Мой день» — по тексту.
- Мягко удалённая строка датасета держит значение ключа (уникальный индекс полный): новая строка с
  тем же ключом отклоняется, откат, возвращающий занятый ключ, — тоже (409).
- В PDF страницы базы знаний встроенные объекты (график, карта, таблица датасета, показатель,
  список задач) заменяются ссылкой: печатная форма строится сервером с закрытой сетью (вопрос N36).
- Перестройка чанков `page_chunk` при смене прав идёт по поддереву страницы (до 500 страниц за
  событие); смена прав самого пространства до страниц не доходит — то же ограничение, что у
  индекса объектов (содержимое не лежит под пространством в `object_ancestors`).
- Ключ входа (passkey) отзывает только его владелец в своём профиле: кнопки «отозвать все ключи
  сотрудника» у администратора нет (вопрос N45). Учётной записи каталога ссылка восстановления
  доступа не поможет — локального пароля у неё нет.
- Синхронизация каталога не переносит руководителей подразделений и территории: `manager` и
  `territoryId` остаются за администратором оргструктуры.

**Первая волна влита (20.09.2026)** — четыре ветки подряд: база знаний, вход (каталог, единый
вход, ключи), публичный API с вебхуками и интеграциями, правила автоматизации с расписаниями. При
слиянии найдено и починено:

- блоки страницы базы знаний читались ключами документа тетради — страница открывалась пустой,
  хотя содержимое было (ключи корневых типов стали параметром функций совместного документа);
- `Field` дизайн-системы не связывал подпись с полем: у поля не было доступного имени ни для
  программы чтения с экрана, ни для сценариев;
- правило автоматизации нельзя было создать из галереи (сервер требовал служебного пользователя
  ещё до того, как его есть где указать) — черновик теперь сохраняется выключенным;
- тег `automation` не попадал в области доступа токенов и в документацию API, а тестовые типы
  объектов для маршрутов кончились: перечень заменён типами будущих фаз;
- **страницы Входящих теряли дела**: список отсортирован по важности и сроку, а курсор хранил одно
  лишь время открытия — часть дел не показывалась вовсе; курсор теперь повторяет порядок целиком,
  а экран догружает страницы кнопкой «Показать ещё» (раньше список молча обрывался на пятидесяти);
- полоса «весь день» в сетке календаря росла без предела: на дне с десятками проекций сроков она
  занимала весь экран, и часы уезжали за нижний край — видно три ряда, остальное по кнопке «ещё N».

Сквозные сценарии веток (знания, автоматизация с расписаниями, токены с вебхуками и пакетом
конфигурации, каталог с единым входом и ключами) написаны ветками, приведены к действительности и
прогнаны на стенде. Сценарий с ключом входа теперь заводит свою сессию и снимает ключ запросом в
`finally`: общая сессия сотрудника одна на прогон, а оставшийся ключ делает учётную запись
двухфакторной и ломает вход остальным проверкам.

**Моя часть второй волны фазы 5 (20.09.2026)** — администрирование установки (P5-E06) и ассистент
экраном:

- **возможности установки** (ADR-0115): модуль объявляет свой флаг рядом с типами объектов, ядро

  Выключаются только листья: знания, чаты, встречи, карты, отчёты, правила, публичный API,

Найдено и починено в своём коде первой волны (нашла ветка форм и алертов, спасибо ей): правило

бейдж качества доведён до каталога датасетов (колонка и значок в карточке списка).

**Вторая волна фазы 5 влита (20.09.2026)** — четыре ветки подряд:

- **формы сбора данных и алерты** (ADR-0103, ADR-0104): форма — объект реестра над публичным API
  датасетов, отправка ложится строкой с `_import_id`, контроль сдачи — матрицей «назначения ×
  периоды» с делами, напоминаниями и эскалацией; алерт на показатель считает порог, изменение в

- **пайплайны, внешние БД и ГИС-службы** (ADR-0106…0108): восемнадцать шагов раскладываются в один
  `QuerySpec` и идут обычным компилятором — политики строк и столбцов остаются одни на платформу;
  внешние базы подключаются интеграцией с шифрованными секретами, выборка — объект `source` с
  загрузкой через staging; WMS и WMTS встали видами базовой карты, WFS и ArcGIS REST — слоем-ссылкой;
- **офисный редактор и почта канцелярии** (ADR-0112, ADR-0113): ONLYOFFICE службой профиля `office`,

Слияние: миграции веток пересобраны поверх моих (состав объектов сверен), словари сведены
трёхсторонним слиянием, домены событий, палитра команд и разделы администрирования — вручную.
Сквозные сценарии всех четырёх веток прогнаны на стенде; в сценарии deck.gl пришлось выключить
кластеризацию слоя (кластеры рисует MapLibre — так задумано), в сценарии почты — заменить `or` в
строгом режиме, а тестовому типу объекта маршрутов снова искать свободный ключ: ветки заняли
`form`, `alert`, `pipeline` и `source`.

**Классификация при регистрации (P5-E05, ADR-0126)**: по тексту скана ассистент документа
предлагает вид — но не свободным ответом, а ключом из видов, заведённых в этой установке и
видимых человеку; вместе с видом показывается журнал регистрации и похожие документы по смыслу
(ADR-0099). Применяет предложение человек и только в черновике: после регистрации вид уже связан
с номером. Обучение на исправлениях (хранить, что предложили и что приняли) — следующей историей.
