# 0182. Ядро не знает модули по именам: реестры и признаки типа объекта

Статус: Принято
Дата: 2026-10-05

## Контекст

Ядро держало словарь модулей строками (находка 12 разбора,
`04-delivery/07-architecture-hardening.md`):

- **Аудит.** `AUDIT_ACTIONS` содержал действия документов, дел, журналов, поручений,
  интеграций, вебхуков, токенов, файлов, справки и почты.
- **Уведомления.** Режимы доставки по умолчанию были заданы для категорий модулей:
  `tasks`, `documents`, `chat.*`, `meetings`, `calendar`, `data`.
- **«Входящие».** Ядро задавало кнопки видов дел поручений и сопоставление видов дел
  модулей с областями замещения (`SCOPE_BY_KIND`).
- **Лента активности.** Ядро записывало загрузки и версии файлов.
- **Поиск и вкладки.** Подписчики поиска и realtime слушали `file.text_extracted` и
  `file.previewed`.
- **Обсуждения.** Вложение проверялось сравнением типа с `'file'`.
- **Потоки событий.** `KNOWN_DOMAINS` — жёсткий список доменов, который правился при
  каждом новом модуле.

Каждый новый модуль поэтому правил ядро. Это шло против `02-platform-kernel.md` §1 («ядро
ничего не знает о конкретных типах, кроме этого описания») и делало общие файлы ядра
местом постоянных конфликтов слияния.

## Решение

Модуль объявляет свой словарь в `register*ObjectTypes` или `register*Feature`. Эти функции
выполняются в любой роли процесса раньше подписчиков ядра и HTTP. Ядро держит только своё.

- **Действия аудита.** Модуль объявляет константы у себя
  (`modules/<m>/domain/audit-actions.ts`) и регистрирует их `registerAuditActions(owner,
  actions)` (`kernel/audit/registry.ts`). В `AUDIT_ACTIONS` остались действия ядра и
  обязательные действия безопасности из 17-security.md §6: вход, второй фактор, пароли,
  сессии, роли, замещения, оргструктура, допуск, режим администратора — справочник по
  ADR-0178 входит в ядро. Каталог действий с владельцами отдаёт
  `GET /admin/audit/actions` (способность `admin.audit.read`) — администратору и SIEM.
  Значения действий не менялись, журнал прежних записей остаётся читаемым.
- **Категории уведомлений.** `registerNotificationCategory(category, defaults)`
  (`kernel/notifications/service.ts`). Ядро задаёт режимы `inbox`, `mention`,
  `discussion`, `object` и `system`, модули — свои; значения прежние. Список категорий
  по-прежнему задаёт контракт `NOTIFICATION_CATEGORIES`.
- **Виды дел «Входящих».** `registerInboxKind(kind, {actions, delegationScopes})`
  (`kernel/inbox/actions.ts`) — кнопки по умолчанию и области замещения вида.
  - Движок процессов объявляет `approve`, `sign`, `register` и `revise`.
  - Механизм ознакомления — `acknowledge`.
  - Модули — `resolve`, виды поручений, `respond_invite` и `review_protocol`.
  - Не объявленный вид получает кнопку «Открыть» и только область `all`.
- **Признаки типа объекта** (`ObjectTypeDefinition`):
  - `attachable` — объект можно прикрепить к сообщению обсуждения;
  - `reindexOn` — события модуля, после которых устаревает поисковый документ объекта;
  - `refreshOn` — события модуля, после которых открытая вкладка перечитывает поле
    (событие → `changedFields`).

  Подписчики поиска и realtime ядра собирают объявленные события при регистрации: типы
  объектов к этому времени уже зарегистрированы. Файл объявляет
  `reindexOn: ['file.text_extracted']` и `refreshOn` для превью и текста. Датасет
  объявляет `reindexOn: ['dataset.schema_changed']`: подписи полей входят в его
  поисковый документ, а правка схемы публикует только это событие. Теперь они доходят до
  поиска — это продолжение ADR-0170.
- **Лента активности.** Загрузки и версии файла пишет подписчик модуля files через
  `recordModuleActivity`, как это уже делают задачи, календарь и документы.
- **Домены событий** для подписчиков «*» — `EVENT_DOMAINS` из каталога событий
  `@kchs/contracts`. Событие вне каталога не публикуется (`publishEvent`), поэтому других
  потоков у шины не бывает.
- **Проверка.** `apps/api/src/kernel/vocabulary.test.ts` ищет в коде ядра строки с типами
  объектов и доменами событий модулей; она падает на любом новом совпадении. Модульным
  словом считается тип из `OBJECT_TYPES`, не зарегистрированный ядром, и домен каталога,
  не опубликованный кодом ядра и не входящий в словарь безопасности справочника.
  Обоснованные совпадения перечислены в тесте:
  - имена столбцов `source`, `token`, `event`;
  - поле записи потока `event`;
  - виды шагов маршрута `task` и `call` из `@kchs/process`;
  - исход ожидания `event`;
  - ключ журнала `document.confidential_access` — доступ к объекту с грифом (ADR-0080);
    переименование разорвало бы журнал.

## Альтернативы

- **Реестр активности по образцу аудита.** Модули и так пишут свою ленту через
  `recordModuleActivity`, второй механизм ничего бы не дал.
- **Переименовать модульные ключи аудита** (например, `document.confidential_access` в
  `object.confidential_access`). Тогда журнал аудита разделился бы на прежние и новые
  записи одного смысла, и поиск по действию перестал бы находить старые.
- **Вычислять события поиска и вкладок лениво при каждом событии.** Подписка шины
  строится по типам подписчика при запуске потребителей. Объявление в типе объекта дешевле
  и проверяется тестом.

## Последствия

- Новый модуль не правит ядро ради своих действий аудита, категорий уведомлений, видов
  дел и событий поиска. `vocabulary.test.ts` ловит возврат к строкам.
- Подписчик `files-activity` — новая группа потребителей. После обновления установки она
  начинает с новых событий (ADR-0171), поэтому записи ленты о файлах, загруженных в
  момент обновления, могут не появиться.
- Подписчик поиска ядра теперь читает поток `dataset`. Переиндексация датасета на каждое
  изменение схемы — одна запись Meilisearch.
- Тесты:
  - `kernel-vocabulary.test.ts` — каталог аудита, режимы категорий, виды «Входящих»,
    переименование подписи поля доходит до поиска;
  - `vocabulary.test.ts` — словарь ядра;
  - `domains.test.ts` — домены из каталога.
