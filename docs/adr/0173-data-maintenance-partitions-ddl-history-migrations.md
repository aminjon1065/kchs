# 0173. Обслуживание данных: партиции аудита, ожидание блокировок DDL, срок хранения истории, сверка миграций, старт реплик

Статус: Принято
Дата: 2026-10-05

## Контекст

Разбор архитектуры (`04-delivery/07-architecture-hardening.md`, находка 9) нашёл в данных
проблемы, которые проявились бы через месяцы работы пилота или при нескольких репликах:

- Партиции `audit_log` создаёт только миграция `0001_hardening` — на месяц установки −1…+3.
  Функцию `ops.ensure_month_partition` миграция объявила «для задания обслуживания», но
  задания не было. Через три месяца записи аудита легли бы в `audit_log_default`, а потом
  создать партицию месяца с такими строками Postgres уже не даёт.
- Попутно найдено: права по умолчанию для таблиц `kchs_migrator` и `GRANT … ON ALL TABLES`
  при синхронизации привилегий давали `kchs_app` UPDATE и DELETE на каждой партиции
  `audit_log`. Родитель был закрыт, но журнал правился и удалялся в обход него, через
  партицию. Это нарушает неизменяемость аудита (`17-security.md` §6).
- DDL таблиц датасетов (`modules/data/infra/physical.ts`) ждёт блокировку без предела.
  Правка схемы или подмена таблицы при импорте, ждущая конца долгого запроса или
  выгрузки, ставит за собой в очередь всех читателей: тайлы, запросы и грид датасета
  встают целиком.
- История строк `ds.h_*` хранится бессрочно. У лент она включена по умолчанию, а лента
  правит строки на каждом прогоне.
- Мигратор записывает хэш миграции, но не сверяет его. Правка применённой миграции задним
  числом проходит молча, и база с кодом расходятся.
- При старте каждой реплики способности системных ролей удалялись и вставлялись заново
  без транзакции. Запросы в этот момент получали ложный 403.
- Приведение таблиц датасетов к текущему виду при старте (индексы ключа ADR-0160, номер
  версии в истории ADR-0062) шло на всех репликах разом. Две перестройки одного индекса
  ловили deadlock — это проверено тестом.

## Решение

1. **Партиции журнала аудита.** `ensureAuditPartitions` (`shared/db/partitions.ts`)
   обеспечивает партиции на текущий и три следующих месяца, а также на каждый месяц,
   строки которого оказались в `audit_log_default`.
   - Строки месяца без партиции переносятся в неё в той же транзакции: партиция по
     умолчанию отсоединяется, строки переходят с прежними `id` и временем, она
     присоединяется обратно. Мы выбрали самоисцеление, а не ошибку в журнале: долгий
     простой обслуживания не должен оставлять установку без партиций.
   - Месяц создаётся под транзакционной advisory-блокировкой с `lock_timeout` 10 с.
   - Создаёт владелец таблицы, `kchs_migrator`. Это делает мигратор при каждом старте и
     ночное задание `maintenance:audit.partitions` через `withMigratorConnection`.
     Приложению аудит по-прежнему доступен только на добавление.
2. **Аудит только на добавление и через партиции.** При синхронизации привилегий и после
   создания партиций с каждой партиции `audit_log` снимаются INSERT, UPDATE, DELETE,
   TRUNCATE, REFERENCES и TRIGGER для `PUBLIC`, `kchs_app`, `kchs_audit` и `kchs_readonly`
   (`AUDIT_PARTITIONS_APPEND_ONLY`). Вставка идёт через родителя: при маршрутизации строки
   Postgres права партиции не проверяет. Чтение остаётся, его просит `pg_dump` резервной
   копии (она работает ролью `kchs_app`).
3. **Ожидание блокировок DDL — 5 с.** DDL таблиц датасетов выполняется под
   `lock_timeout = 5s`, после DDL ожидание возвращается к значению сеанса. Это поле,
   индекс, ключ, смена типа, история, удаление таблиц и подмена при импорте.
   - Занятая таблица — 409 «Датасет сейчас занят… повторите через несколько секунд».
   - Подмена таблицы при импорте повторяется на месте до трёх раз с растущей паузой
     (`retryWhileBusy`) и только потом отдаёт ошибку повтору задания.
   - Окончательное удаление из корзины идёт по объекту. Занятый датасет остаётся в
     корзине до следующего прохода и не держит остальные.
4. **Срок хранения истории строк.** В настройках датасета появилось
   `historyRetentionDays`: целое 1…3650, `null` — бессрочно.
   - Умолчания: у обычных датасетов — бессрочно (правки людей редки, их история ценна).
     У датасетов лент — 90 дней: их ставит создание ленты, а уже установленным —
     миграция `20261005084732_feed-history-retention`.
   - Ночное задание `maintenance:data.history-prune` удаляет историю всех версий,
     созданных раньше срока, целиком: по индексу `dataset_version`, пачками по 10 000, не
     больше 50 пачек на датасет за проход. Строки таблиц до ADR-0062 без номера версии
     удаляются по времени правки.
   - Версия либо хранит всю историю, либо ни одной строки. Поэтому откат к оставшимся
     версиям верен, а к удалённым недоступен с причиной «история строк этой версии удалена
     по сроку хранения (N дн.)».
   - Поле «Срок хранения истории, дней» есть в настройках таблицы датасета.
5. **Сверка миграций.** Мигратор сверяет хэш каждой применённой миграции с файлом. При
   расхождении запуск останавливается с `EditedMigrationError`: в тексте ошибки — файлы и
   команда обновления хэша на случай, если правка намеренная и база ей уже соответствует.
   Миграции, которых нет в этой версии кода (база новее кода), дают предупреждение в
   журнале. Правило выпуска миграций — expand/contract
   (`04-delivery/01-project-structure.md`, `15-admin-operations.md` §2).
6. **Старт нескольких реплик.**
   - Роль и её способности сверяются в одной транзакции: недостающие добавляются, лишние
     удаляются. Роль на чистой базе создаётся `ON CONFLICT DO NOTHING`.
   - Приведение таблиц модулей к текущему виду идёт под сессионной advisory-блокировкой на
     отдельном соединении (`withAdvisoryLock`).
   - Ключи блокировок платформы собраны в `shared/db/advisory.ts`.

## Альтернативы

- **Функция `SECURITY DEFINER` для партиций, вызываемая ролью приложения.** Она дала бы
  `kchs_app` право создавать таблицы от имени владельца. У api и так есть учётная запись
  мигратора (миграции при старте), и отдельное соединение проще и уже.
- **Ошибка в журнале и метрика вместо переноса строк из `audit_log_default`.** Установка
  требовала бы ручного вмешательства, а перенос — одна короткая транзакция.
- **`lock_timeout` на всю транзакцию правки схемы.** Тайм-аут задевал бы строковые
  блокировки метаданных (`objects`, `datasets`), и их ошибки не превращались бы в понятный
  409.
- **Удаление истории по времени правки, а не по версиям.** Версия могла бы остаться с
  частью истории, и откат к ней дал бы неверные строки.

## Последствия

- Ограничено только ожидание блокировки. Сама смена типа крупного столбца
  (`ALTER … TYPE`) держит таблицу всё время перезаписи. Перезапись теневым столбцом —
  отдельная задача, если понадобится.
- Импорт в режиме «заменить» при долгом чтении таблицы ждёт до трёх попыток (около 30 с),
  затем повторяется заданием (до пяти попыток). Раньше он ждал без предела и держал всех
  читателей.
- Чистить историю чаще раза в сутки и раньше срока нельзя, это ночное задание. Отключается
  оно, как и остальные, на экране «Расписания».
- Тесты: `db-maintenance.test.ts` (мигратор, партиции, права на партиции, старт реплик),
  `data-schema.test.ts` (занятая таблица), `data-rollback.test.ts` (срок хранения и
  откат), `data-feeds.test.ts` (умолчание лент), `retry-busy.test.ts`.
