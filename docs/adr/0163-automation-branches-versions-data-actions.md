# 0163. Правила автоматизации: ветка «иначе», группы условий в форме, версии, файл одного правила, запуск пайплайна и импорта

Статус: Принято
Дата: 2026-09-25

## Контекст

Владелец включил «отчёты и автоматизацию» в «закончить разработку» (05-risks §5). В руководстве
26 «Чего пока нет» числились:
- конструктор условий знал только плоское «и»: вложенные группы, пришедшие из API или пакета,
  показывались одной строкой со скобками, ветки «иначе» не было;
- не было копии правила, версий, отката и переноса одного правила (только весь набор через
  «Конфигурацию»);
- тестовый прогон был только у триггера «Событие»;
- у строк-правил на экране «Расписания» не было истории;
- действия `run_pipeline` и `run_import` были отложены до пайплайнов (ADR-0096, ADR-0106).

## Решение

1. **Ветка «иначе» — поле контракта `otherwise`** (`RuleDefinition`, по умолчанию `[]`).
   - Условие не выполнено и ветка пуста — запуск «Пропущено», как раньше.
   - Непустая — выполняются её действия; шаг журнала несёт `branch: 'otherwise'`.
   - Ветка выбирается один раз и запоминается в контексте запуска: продолжение после `wait`
     идёт по той же ветке.
   - Ключ повтора у «иначе» свой (`otherwise:<ключ>`): её запуск не глушит следующий по «то»
     (ADR-0128 не меняется).
   - Без условий ветка не выполняется никогда — «Проверка» предупреждает.
   - Миграции данных не нужно: старые определения читаются с пустой веткой.
2. **Конструктор условий — дерево.** Группа «Выполнены все условия» / «Выполнено любое из»,
   вложенные группы до трёх уровней, флажок «не» у строки и у группы. Модель контракта
   (`and` / `or` / `not`) не менялась: форма переводит её в узлы и обратно без потери смысла.
   Под деревом — условие одной строкой.
3. **Версии правила — таблица `rule_versions`.**
   - Версию пишут создание, правка определения (название, описание, «когда», «если», «то»,
     «иначе», лимиты, служебный пользователь), копия, импорт и откат.
   - Включение и выключение версией не считаются.
   - Откат делает определение старой версии новой версией. Состояние «включено» остаётся
     текущим: откат не включает и не выключает правило.
   - Миграция заводит первую версию каждому существующему правилу.
4. **Копия правила** — в том же пространстве, выключенная, с пометкой «(копия)» на языке каждой
   подписи. Ключ правила теперь берётся из хвоста идентификатора: у UUIDv7 начало — время, и
   правила, созданные в одну миллисекунду с одним названием, получали бы один ключ.
5. **Файл одного правила** (`RuleExport`, формат `kchs.rule`):
   - без привязок к установке — служебный пользователь снят, правило выключено;
   - без секретов — пуст секрет подписи вебхука и заголовки, похожие на ключи
     (`authorization`, `token`, `secret`, `key`, `cookie`, `password`).
   - Импорт проверяет схему, создаёт правило выключенным; занятый ключ заменяется новым.
   - Идентификаторы показателей, пайплайнов и объектов расписания переносятся как есть: на
     другой установке их надо поправить — ошибку покажет «Проверка» или запуск.
6. **Действия с данными** — через публичный API модуля данных (`DataRuns`):
   - `run_pipeline` (`pipelineId`) — прогон пайплайна заданием, `authorize(run_as, 'run')`,
     источник прогона `rule`;
   - `run_import` (`sourceId`) — синхронизация источника (внешняя база, лента),
     `authorize(run_as, 'sync')`.
   - Идентификатор — литерал или шаблон `{{…}}`; литерал проверяется при сохранении.
   - Правило не ждёт конца прогона: прогон виден в журнале пайплайна или источника.
7. **Тестовый прогон для всех триггеров:**
   - «Расписание» — один запуск «сейчас» (с объектом расписания, если он задан);
   - «Показатель» — значение сейчас под правами служебного пользователя и условие триггера;
   - «Входящий вызов» — последние `webhook.received` с ключом правила;
   - «Кнопка у объекта» — последние изменённые объекты нужных типов, видимые служебному
     пользователю.
   В итоге указана ветка, которая выполнилась бы.
8. **История на экране «Расписания»:** у строки-правила кнопка «История» открывает журнал
   запусков правила с шагами — тот же, что в конструкторе.

## Альтернативы

- **«Иначе» вторым правилом с обратным условием.** Отвергнуто: два правила расходятся при
  правке, у них разные лимиты и ключи повтора, в журнале не видно, что это одно решение.
- **Версии как снимки внутри `rules.definition`.** Отвергнуто: определение раздувается,
  а история нужна отдельно от текущего состояния и с автором.
- **Секреты в файле правила под паролем.** Отвергнуто: файл правила — для переноса
  логики. Секреты заводятся на новой установке заново.

## Последствия

- Контракт `automation-rule.md` дополнен полем `otherwise` и действиями `run_pipeline`,
  `run_import`; API — версиями, копией, файлом правила.
- Форма показывает и правит группы любой глубины (правило из пакета или API); добавить новую
  группу можно до третьего уровня, глубже — на вкладке «JSON».
- Согласование изменений правила (черновик → проверка → включение) не делалось: версии и
  «Проверка» закрывают откат, а выключенная копия служит черновиком.
