# 0048. Роль `kchs_query` читает только таблицы строк датасетов

Статус: Принято
Дата: 2026-09-18

## Контекст

`05-data-model.md` (Решено): роль пользовательских запросов `kchs_query` имеет `SELECT` на
`ds.*`, а единственный путь к ней — компилятор запросов и переписыватель SQL. Права по
умолчанию схемы `ds` (`infra/compose/postgres/init/00-roles-and-db.sh`) открывают
`kchs_query` любую новую таблицу роли приложения. Кроме таблиц строк `ds.t_*`, приложение
создаёт в `ds` служебные таблицы: историю строк `ds.h_*`, staging импорта `ds.s_*` и таблицу
замены `ds.t_*_n` (ADR-0046).

В истории лежат прежние значения строк целиком: политики столбцов (скрытие, маскирование)
к ней не применяются, потому что компилятор обращается только к таблицам строк. Если
переписыватель SQL когда-нибудь пропустит ссылку на такую таблицу, роль не должна её читать.

## Решение

Таблице строк право `SELECT` для `kchs_query` (и `kchs_readonly`) выдаётся явно — независимо
от роли, создавшей таблицу. У истории, staging и таблицы замены права `kchs_query` явно
отзываются сразу после создания. Проверка — интеграционный тест: у `kchs_query` есть право
только на `t_*` датасета.

## Альтернативы

- Сузить права по умолчанию схемы `ds` в скрипте инициализации: изменение затронуло бы уже
  развёрнутые стенды и всё равно потребовало бы явной выдачи прав таблицам строк.
- Отдельная схема для служебных таблиц: больше изменений в `physical.ts` и миграциях ради
  того же результата.

## Последствия

- «`kchs_query` имеет `SELECT` на `ds.*`» уточняется: на таблицы строк `ds.t_*`.
- Новые служебные таблицы в `ds` должны отзывать права `kchs_query` при создании.
