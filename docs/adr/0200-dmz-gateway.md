# 0200. Шлюз DMZ: белый список маршрутов из таблицы контрактов, второй рубеж в api, только токен снаружи

Статус: Принято
Дата: 2026-10-12

## Контекст

Концепт-нота КЧСиГО 2.0 (§6.5, §9.3, приложение C) и разбор
`docs/04-delivery/08-architecture-concept-note-and-signatures.md` §5.1:

- внутренний контур закрыт из интернета, у серверов Комитета нет входящего доступа;
- партнёры подключаются к опубликованным каналам: API Комитета по токену (уровень 3),
  входящие вебхуки, в дальнейшем — проверка подписи по QR, CAP-лента предупреждений,
  приём координат;
- входящие каналы доступны только через шлюз в публичном контуре (DMZ), токены — с
  ограниченными правами, обращения журналируются, частота ограничивается.

До этого наружу смотрел один Caddy установки (`infra/compose/caddy/Caddyfile`) со всем
приложением: вход, сессии, SPA, realtime. Ставить его в DMZ — значит открыть интернету всё.
Нужно было решить:

- где объявляется, что маршрут открыт снаружи, и как не вести второй список руками;
- чем фильтровать на границе и чем страховать фильтр;
- что делать с cookie, CSRF, гостевыми ссылками и замещением снаружи;
- как не потерять адрес клиента за двумя прокси;
- WAF и лимиты частоты на границе.

## Решение

1. **Объявление — в таблице маршрутов контрактов.** У `RouteContract` (ADR-0188) появился
   признак `exposure: 'public'` — маршрут без входа, нужный партнёрам снаружи. Сейчас он у
   двух маршрутов: `POST /hooks/:integrationId/:secret` (входящий вебхук интеграции) и
   `POST /hooks/rules/:id/:token` (вебхук-вход правила). Регистратор маршрутов не примет
   `exposure` у маршрута не с `auth: 'public'`.

   Маршруты публичного API по токену **не перечисляются**: снаружи открыт маршрут, которому
   токен API получает область по существующему правилу ADR-0097 (тег → ресурс, метод и
   `readOnly` → чтение или запись, закрытые префиксы и теги). Одно правило внутри и снаружи
   — список не расходится с действительностью и не ведётся руками.

   Закрыто снаружи всегда, при любых признаках: `/auth`, `/me`, `/admin`, `/internal`,
   `/share`, `/office`, `/print`, маршруты обратного вызова движка, маршруты
   `auth: 'public'` без `exposure`. Объявить открытым снаружи маршрут входа или маршрут с
   сессией — ошибка конфигурации: генератор и тест падают.

   Публичному маршруту пункта 2 плана (`GET /verify/:id`) достаточно записи в таблице:
   `'GET /verify/:id': { exposure: 'public', … }` и регистрации с `auth: 'public'`; затем
   `pnpm --filter @kchs/api dmz:gen`.
2. **Белый список шлюза генерируется.** `pnpm --filter @kchs/api dmz:gen` собирает
   приложение без запуска сервера (как `openapi:gen`), берёт реестр маршрутов и пишет
   `infra/compose/caddy/dmz-routes.caddy` — три именованных матчера Caddy на выражениях CEL,
   по строке на шаблон пути с его методами:
   - `@kchs_dmz_closed` — закрытые маршруты, общие пути которых с открытым шаблоном
     маршрутизатор отдаёт им (буквальный сегмент сильнее параметра: `GET /meetings/guest/:token`
     рядом с открытым `GET /meetings/:id/…`); шлюз отвечает на них 404 раньше остальных;
   - `@kchs_dmz_public` — без входа;
   - `@kchs_dmz_token` — по токену; шлюз требует `Authorization: Bearer …`, иначе 401.

   Параметр пути — один сегмент (`[^/]+`), точка — классом `[.]`, путь — точное совпадение
   от начала до конца. CI сверяет файл с таблицей (`dmz:gen --check` в задании
   интеграционных тестов), а тест `dmz-gateway.test.ts` ещё и проверяет каждый маршрут
   реестра: по сгенерированному файлу, так же, как Caddy, снаружи проходит путь маршрута,
   только если маршрут открыт.
3. **Конфигурация шлюза — руками, отдельно от списка.** `infra/compose/caddy/dmz.Caddyfile` и
   `infra/compose/dmz.yml` для хоста DMZ:
   - срезает `Cookie`, `X-CSRF-Token`, `X-Kchs-On-Behalf-Of`, `X-Kchs-Share-Token`,
     `X-Kchs-Job-Token`; `Set-Cookie` обратно не уходит — снаружи работает только токен;
   - ставит `X-Kchs-Zone: dmz` поверх присланного клиентом;
   - передаёт запрос Caddy установки (`KCHS_DMZ_UPSTREAM`) с его именем в `Host`;
   - ограничивает тело (`KCHS_DMZ_MAX_BODY`, по умолчанию 20 МБ);
   - пишет журнал обращений; учётные данные Caddy не пишет, секрет вебхука в пути
     маскируется (ADR-0122);
   - свой центр сертификации внутреннего контура — файлом в `caddy/dmz-upstream`;
   - контейнер только для чтения, без привилегий.

   Отдельный файл списка, а не весь Caddyfile из генератора: заголовки, транспорт и журнал
   правит администратор, а список — только таблица маршрутов.
4. **Второй рубеж — в api.** Запрос с `X-Kchs-Zone: dmz` проходит, только если маршрут
   открыт снаружи по тому же расчёту (`requestExternalAccess`), иначе 404; маршрут по
   токену без токена — 401: сессия, гостевая ссылка и cookie печати снаружи не
   принимаются. Белый список могли ослабить на хосте DMZ — api этого не допустит.
   Заголовок может прислать и клиент изнутри, но он только сужает доступ.
5. **Адрес клиента за двумя прокси.** Caddy установки получил глобальное
   `trusted_proxies static {$KCHS_TRUSTED_PROXIES}` (по умолчанию `127.0.0.1/32`, то есть
   никого): адрес шлюза записывают туда, и тогда `X-Forwarded-For` от шлюза сохраняется, а
   api (`TRUST_PROXY=uniquelocal`) видит адрес партнёра. Без этого все партнёры для лимитов и
   журнала были бы одним адресом шлюза, а лимит недействительных токенов по адресу —
   общим.
6. **Частота и WAF.** Лимиты частоты — у api: на токен (`API_TOKEN_RATE_LIMIT_PER_MINUTE` и
   лимит токена), на недействительные токены по адресу, у вебхуков — на интеграцию
   (ADR-0097). В образе `caddy:2-alpine` нет модулей rate limit и Coraza; собирать свой
   образ через xcaddy ради них — хрупко для 2–3 администраторов Комитета. WAF (Coraza с
   набором OWASP CRS) — следующим шагом, когда понадобится, отдельным образом шлюза.

## Альтернативы

- **Список открытых маршрутов руками в Caddyfile.** Отклонено: он разошёлся бы с таблицей
  при первом новом маршруте; генерация и сверка в CI это исключают.
- **Шлюз пропускает префиксы `/api/v1/*`, всё решает api.** Отклонено: тогда вся
  поверхность API — вход, администрирование — доходит до процесса приложения, и защита
  держится на одном рубеже.
- **Отдельный продукт API-шлюза (Kong, APISIX).** Отклонено: ещё одна система с базой
  конфигурации для малой команды; ключи и области уже ведёт платформа.
- **Роль `gateway` того же образа api в DMZ.** Отклонено: процесс с кодом платформы в
  публичном сегменте и очередь между контурами сложнее Caddy и не дают защиты сверх
  второго рубежа в api.
- **`path` Caddy с `*`.** Отклонено: `*` в конце — совпадение по префиксу, и
  `/datasets/*` пропустил бы любой вложенный путь. Регулярное выражение с якорями точнее.
- **Список в одном матчере `path_regexp`.** Отклонено: Caddy допускает одно регулярное
  выражение на именованный матчер; CEL позволяет строку на маршрут.

## Последствия

- Контракты: `RouteContract.exposure`, `RouteExposure`. Реестр маршрутов api хранит теги,
  `readOnly` и `exposure`; регистратор проверяет `exposure` против `auth`.
- api: `modules/integrations/domain/gateway.ts` — расчёт доступа снаружи, генерация и разбор
  списка; `src/dmz-cli.ts`, скрипт `dmz:gen`; зависимость `gateway` у плагина
  аутентификации.
- Инфраструктура: `infra/compose/dmz.yml`, `caddy/dmz.Caddyfile`, `caddy/dmz-routes.caddy`
  (генерируется), `caddy/dmz-upstream/`; у web — `KCHS_TRUSTED_PROXIES`.
- CI: `dmz:gen --check` и `caddy validate` шлюза и установки — в задании интеграционных
  тестов.
- Снаружи не работает то, что отдаёт подписанные ссылки хранилища (`/files/:id/download`,
  сессии загрузки): адрес MinIO внутренний. Обмен файлами с партнёрами — выгрузками и
  отчётами по почте или отдельным публичным хранилищем; решается вместе с каталогом
  каналов (п. 9 плана).
- Документация API (`/api/docs`) снаружи закрыта: партнёр читает её в тестовой среде
  (вопрос владельцу).
- Почта: MX и фильтр спама — в DMZ, ящики и IMAP — внутри; шлюз почты — отдельная служба
  хоста DMZ, описана в `31-admin-mail.md`.
