# 0118. Helm-чарт S2: свои манифесты зависимостей, секреты без значений по умолчанию, KEDA для очередей

Статус: Принято
Дата: 2026-09-20

## Контекст

`15-admin-operations.md` §3 (статус **Рекомендовано**) описывает S2: Helm-чарт `infra/helm/kchs`
с развёртываниями `api`, `worker`, `engine`, `web`, данными через операторы, Ingress с TLS,
отдельным сервисом UDP для LiveKit и секретами из внешнего менеджера. Чарта не было: до фазы 5
установка жила только в `infra/compose` (S1, ADR-0044).

При составлении чарта пришлось решить четыре вопроса, ответы на которые документ не даёт.

1. **Встроенные зависимости.** Чарт должен разворачиваться и в тестовом кластере, где никаких
   управляемых служб нет. Обычный путь — subcharts (Bitnami postgresql, redis, minio). Но
   Postgres нам нужен не любой: PostGIS 3.5, pgvector и бутстрап ролей `kchs_app`,
   `kchs_migrator`, `kchs_query`, `kchs_readonly`, `kchs_audit` с их привилегиями и лимитами
   (`05-data-model.md`, `17-security.md` §4) — всё это уже есть в образе `kchs/postgres`
   (`infra/compose/postgres`), и воспроизводить его поверх чужого чарта значит держать
   бутстрап в двух местах.
2. **Секреты.** Чарт с паролями по умолчанию — обычная причина установок с `postgres/postgres`
   наружу. Нужен способ не дать такой установке даже отрендериться.
3. **Масштабирование worker.** `HorizontalPodAutoscaler` умеет только метрики ресурсов пода и
   внешние метрики через адаптеры. Глубина очереди — не то и не другое: это метрика
   приложения, `kchs_queue_jobs{queue,state}` (ADR-0045).
4. **UDP медиасервера.** В S1 LiveKit публикует диапазон 50000–50100/udp. У `Service`
   Kubernetes диапазонов нет — порты перечисляются по одному.

## Решение

1. **Зависимости тестового кластера — свои манифесты, а не subcharts.** `postgres.embedded`,
   `redis.embedded`, `s3.embedded` (MinIO с заданием создания бакетов) и
   `meilisearch.embedded` — четыре StatefulSet'а на тех же образах, что в compose S1. Чарт не
   имеет зависимостей (`Chart.yaml` без `dependencies`), `helm dependency update` не нужен,
   закрытый контур обходится своим реестром образов. Промышленная установка выключает их и
   получает адреса управляемых служб. Разница между путями — только адрес: прикладные
   развёртывания одинаковы.
2. **Паролей по умолчанию нет.** Обязательные ключи секрета объявлены через `required`: без
   них `helm template` падает. Два пути — `secrets.existingSecret` (внешний менеджер) или
   `Secret` чарта из файла значений вне репозитория. Секрет помечен
   `helm.sh/resource-policy: keep`: удаление релиза не должно уносить `KCHS_MASTER_KEY`, иначе
   зашифрованные им данные (секреты интеграций, TOTP) станут нечитаемыми. Строки подключения
   собираются в spec пода подстановкой `$(ПЕРЕМЕННАЯ)` kubelet из адреса и пароля; для паролей
   со спецсимволами и сложных DSN есть `postgres.urlsFromSecret` и `redis.urlFromSecret`.
   Проверку «чарт без секретов не рендерится» делает CI.
3. **Очереди — KEDA.** `worker.autoscaling.mode: keda` создаёт `ScaledObject` с триггером
   `prometheus` по запросу
   `sum(kchs_queue_jobs{queue=~"…",state=~"waiting|prioritized"})`, порог — заданий на
   реплику. Тот же механизм для движка по его очередям (`QUEUE_RUNTIME`, ADR-0035).
   `minReplicaCount ≥ 1`: метрику отдаёт сам воркер, на нуле реплик её неоткуда взять.
   Что нужно в кластере: KEDA (CRD `keda.sh/v1alpha1`) и Prometheus, собирающий `/metrics`
   api и worker (порт 9464; `observability.serviceMonitor.enabled` для Prometheus Operator).
   Запасной путь без KEDA — `mode: cpu`, обычный HPA; он грубее и это сказано в README и NOTES.
4. **UDP — один порт мультиплексора.** В кластере LiveKit настраивается на `rtc.udp_port`
   (по умолчанию 7882) и публикуется отдельным `Service` типа `LoadBalancer` с
   `externalTrafficPolicy: Local` (сохраняет адрес клиента — иначе кандидаты ICE неверные),
   мимо Ingress; сигнальный канал WebSocket — обычным HTTPS через свой Ingress.
5. **Миграции — хук, кроме встроенного Postgres.** `kchs migrate` идёт заданием
   `pre-install,pre-upgrade`, чтобы `helm upgrade --wait` не катил поды на старой схеме. При
   `postgres.embedded.enabled` хук невозможен (StatefulSet создаётся вместе с релизом, то есть
   позже pre-install), поэтому задание становится обычным ресурсом с именем по номеру ревизии
   и ждёт базу в `initContainer` с `pg_isready`. Корректность в обоих случаях обеспечивает
   advisory lock самих миграций (ADR-0044).
6. **Конфигурация Caddy переехала в образ web.** `apps/web/Dockerfile` копирует
   `infra/compose/caddy/Caddyfile` в `/etc/caddy/Caddyfile`; в compose его по-прежнему
   перекрывает том с тем же файлом (поведение S1 не изменилось), а в кластере web настраивается
   только окружением (`KCHS_DOMAIN=:8080`, `KCHS_API_UPSTREAM`, `KCHS_STORAGE_ORIGIN`,
   `KCHS_MEDIA_ORIGIN`). Альтернатива — копия Caddyfile внутри чарта для ConfigMap: две копии
   CSP-заголовка, который и так помечен «меняйте только здесь» (ADR-0043). `web.caddyfile`
   остаётся как переопределение для контуров со своими маршрутами.

## Альтернативы

- **Subcharts Bitnami.** Postgres всё равно пришлось бы подменять своим образом и бутстрапом
  ролей, а остальные три дали бы зависимость от чужого реестра и от чужих схем значений в
  закрытом контуре. Для четырёх одиночных служб стенда это дороже, чем 400 строк манифестов.
- **Оператор CloudNativePG прямо в чарте.** Правильный путь для промышленной установки, но он
  требует установленного оператора и в тестовом кластере ставит «кластер ради одного пода».
  Чарт сознательно не решает за администратора, каким оператором поднимать базу.
- **HPA по внешним метрикам через prometheus-adapter** вместо KEDA: то же требование к
  кластеру (адаптер вместо KEDA), но настройка размазана между `configMap` адаптера и чартом.
  KEDA описывает триггер целиком в релизе.
- **`hostNetwork: true` для LiveKit** вместо мультиплексора: работает и сохраняет диапазон
  портов, но привязывает медиасервер к узлам и их портам и конфликтует с любым другим
  использованием 50000–50100 на узле.
- **Перечислить 101 порт UDP в Service**: манифест на сотню строк, лимиты облачных
  балансировщиков (у части провайдеров — десятки портов на правило).
- **Задание миграций всегда обычным ресурсом** (без хука): теряется гарантия «схема обновлена
  до выката» при `helm upgrade --wait`.

## Последствия

- Новая обязательная переменная окружения api должна попасть не только в `x-app-env` compose,
  но и в `configmap-env.yaml` чарта (несекретная) или в `kchs.appSecretEnv` (секретная), иначе
  установка S2 разойдётся с S1. Это же относится к новому бакету и новой очереди.
- Для полного S2 в кластере должны быть: контроллер Ingress, cert-manager (или готовый
  секрет TLS), KEDA, Prometheus, оператор Postgres и распределённое хранилище. Чарт их не
  ставит и не проверяет — отсутствие KEDA видно по несозданному `ScaledObject`.
- Встроенные зависимости годятся только для стенда. Это сказано в `values.yaml`, README и
  выводится в NOTES после установки.
- Проверено `helm lint`, `helm template` и `kubeconform` на трёх наборах значений (Helm 3.19 и
  4.3). Развёртывание в настоящем кластере — при первой установке S2: у исполнителя кластера
  нет, и поднимать его на машине с общим стендом нельзя.
