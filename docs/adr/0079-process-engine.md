# 0079. Движок процессов: чистая модель переходов, исполнение в ядре, таймеры в базе, расширения модулей

Статус: Принято
Дата: 2026-09-19

## Контекст

P3-E01 S01–S02 и сценарии приёмки фазы 3 №2 («маршрут с параллельным согласованием, замечаниями,
новой версией и повторным согласованием только отклонивших; сроки в рабочих днях с праздником в
календаре; просрочка → эскалация») и №6 («worker перезапущен посреди маршрута — процесс
продолжается»). ADR-0012 выбрал собственный лёгкий движок; контракт — `contracts/process-definition.md`
(Решено по структуре), ядро — 02-platform-kernel.md §10, маршруты документов — 08-documents.md §3–4,
делегирование — 03-access-model.md. Таблицы `process_*` были заготовлены в фазе 0 и не
использовались; рабочие дни — `BusinessCalendar` (коммит 81559e8), Входящие с копиями заместителям и
реестром действий — ADR-0060.

Открытыми оставались: где живёт модель, как описаны точная семантика кворумов, замечаний и
повторного согласования, как устроены таймеры, чтобы перезапуск worker ничего не терял, как
документы (вторая волна) расширяют движок, не заставляя ядро знать о них, кто видит маршрут и объект,
что значит `role_in_space`, как подтверждается подпись вторым фактором и какой способностью
закрыты определения.

## Решение

1. **Два слоя.** `@kchs/process` — чистый пакет без базы: zod-схема ProcessDefinition, проверка
   определения, разбор и резолвер выражений назначений против интерфейса справочника, модель
   состояния экземпляра и переходы (`startProcess`, `assignStep`, `decideStep`, `completeStep`,
   `addStepAssignee`, `delegateStep`, `reassignStep`, `cancelProcess`, `availableActions`), контракты
   HTTP API движка. Переход — чистая функция: состояние и событие → новое состояние и работа
   (`resolve` — определить назначенных, `run` — выполнить автоматический шаг, `wait` — начать
   ожидание). Ядро (`kernel/process`) исполняет работу, сохраняет разницу состояний и по ней
   открывает и закрывает Входящие, ставит таймеры, публикует события, вызывает хуки модуля.
   Схема определения лежит в `@kchs/process` (как допускает contracts/README.md), а не в
   `@kchs/contracts`: ей нужен язык выражений, а контракты API движка лежат рядом с ней.
2. **Условия — язык выражений платформы.** Разборщик `@kchs/query` научился составным ссылкам
   (`object.fields.amount` — узел `path`; компилятор запросов их отклоняет), а вычисление над
   данными в памяти (`evaluateExpression`, семантика SQL: `null` поглощает, условие — строгое
   `true`) и проверка без вычисления (`checkEvaluable`) доступны подпутём `@kchs/query/expr` без
   libpg-query. Корни: при запуске — `object`, `var`, `author`, `initiator`; в шаге `condition` —
   ещё `steps.<ключ>.outcome`; в фильтре `wait` — ещё `event`.
3. **Семантика шагов** (дополняет контракт, совместимо):
   - Кворум согласования: `all` — все, `any` — один, `n` — n (не больше числа назначенных).
     Параллельный режим: **отклонение** завершает шаг сразу, как только одобрение стало
     невозможным; **замечания** ждут ответов всех — автор получает все замечания одним возвратом.
     Последовательный режим прерывается на первом ответе, после которого кворум недостижим. Режим
     `any` — решает первый ответ. Итог шага: `approved`, иначе `rejected`, если было отклонение,
     иначе `remarks`; и отклонение, и замечания идут в `onReject` (по умолчанию `end:rejected`;
     `continue` — дальше по маршруту; `end:<исход>` — завершить).
   - Подпись: все назначенные подписывают (параллельно или по очереди); отказ завершает шаг сразу
     и идёт в `onReject`.
   - Возврат (`return`): элемент Входящих `revise` автору (или `to`); «отправить повторно» —
     новый круг и правило `reapproval`; «отозвать» — маршрут отменён с исходом `withdrawn`.
   - **Повторное согласование только отклонивших** (`rejecters_only`): при следующей активации
     того же шага согласования одобрившие прошлый круг засчитываются (`carried`, без Входящих);
     решают не одобрившие — и отклонившие, и не успевшие ответить; добавленные согласующие прошлого
     круга остаются; передавший шаг засчитывается, если одобрил получивший. Шаг, одобренный
     целиком, засчитывается сразу. Подпись повторяется всегда.
   - Параллельные ветви — упорядоченные списки ключей; шаги ветви идут по порядку и не имеют
     `next`; `condition`, `return`, `end` в ветвях запрещены; вложенные параллельные шаги
     разрешены. `join: any` снимает остальные ветви. Отклонение внутри ветви с переходом на шаг
     верхнего уровня снимает все активные шаги.
   - Проверка определения: ссылки, места шагов в ветвях, достижимость, путь к завершению от
     каждого шага, циклы только через `return` (граф без шагов `return` ацикличен), выражения.
     Публикация дополнительно проверяет зарегистрированные исполнители шагов модулей и ожидаемые
     события.
4. **Назначения.** Резолвер сохраняет порядок выражений (очередь последовательного режима),
   убирает повторы и неактивных. `unit:<id>` и `author.unit` в роли людей — сотрудники
   подразделения и вложенных (как принципал `unit:`); `unit_head(...)` — буквально глава;
   `manager(x)` — как в модели доступа. Добавлены совместимые формы: запись через вызов
   (`role_in_space('legal')`, `field('responsible')`), `unit_head('КОД')` — подразделение по коду,
   `initiator`, `step.assignee` (только в таймерах: не ответившие на просроченном шаге).
   `role:<ключ>` — роль без ограничения и роль, ограниченная пространством объекта.
   **`role_in_space:<ключ>`**: для ролей участника пространства (`viewer`…`admin`) — участники
   пространства объекта с ролью не ниже указанной; для остальных ключей — сотрудники с ролью,
   ограниченной пространством объекта (`user_roles.space_id`), а если таких нет — с той же ролью
   без ограничения («юрист пространства, иначе юрист организации»). Порт справочника получил
   основное подразделение, сотрудников подразделения, подразделение по коду, членов группы,
   обладателей роли с пространством и фильтр активных — реализует модуль identity.
5. **Пустые назначения.** Шаг решения без назначенных при запуске — ошибка 400 с путём шага:
   маршрут не стартует. На ходу (оргструктура изменилась) шаг ждёт: инициатор получает
   уведомление, администратор маршрутов переназначает (`POST …/reassign`). Ознакомление без
   назначенных выполняется сразу.
6. **Исполнение и хранение.** Экземпляр закреплён за версией определения; в `context` —
   переменные, выбор инициатора, применённые условия запуска, круг, счётчик шагов. Каждая
   активация шага — строка `process_steps` (назначенные с решениями в `assignees`, круг, ветвь,
   предыдущий шаг, итог, таймеры, ожидаемое событие). Все переходы экземпляра — под `SELECT … FOR
   UPDATE` строки экземпляра: решения, таймеры и события идут по очереди. Один идущий маршрут
   определения на объект (частичный уникальный индекс). Решения и изменения состава — строки
   `process_step_actions` (кто, от чьего имени, комментарий, файлы, подтверждение вторым фактором) и
   аудит `process.decision`.
7. **Таймеры — состояние в базе.** Срок шага решения — `BusinessCalendar.deadline(активация, N)`
   (конец N-го рабочего дня в поясе установки); моменты — напоминание утром рабочего дня перед
   сроком, утром в день срока и просрочка в конце дня срока — пишутся в строку шага, ближайший — в
   `next_timer_at`. На каждый шаг одно отложенное задание `process.timer` очереди `process-timers`
   (worker, ADR-0035) на ближайший момент; обработчик под блокировкой отмечает сработавшие моменты
   (`firedAt`) и ставит задание на следующий. Обход `process.timers-sweep` раз в пять минут
   подхватывает моменты, задание которых потеряно (очередь очищена, worker лежал), — из базы.
   Просрочка — событие `process.step_overdue` с не ответившими и получателями эскалации по
   `timers` определения; напоминание — `process.step_due_soon`. Ожидание `wait`: момент
   (`durationWorkingDays`, `until` — дата, момент, `var:`, `field:`) — тем же таймером, событие —
   подписчиком по списку ожидаемых событий (по умолчанию `object.updated`, `object.linked`,
   `process.finished`; модули добавляют `registerProcessWaitEvent`) об этом же объекте с фильтром.
8. **Входящие и действия.** Шаг решения открывает элемент каждому ждущему (`approve`, `sign`,
   `acknowledge`, новые виды `register` и `revise`) с дедупликацией по шагу и пользователю;
   `InboxService` делает копии заместителям (области замещения расширены на новые виды). Кнопки
   исполняет `registerInboxActionHandler` — один путь для Входящих, Telegram и API; элемент знает
   свой шаг (`InboxActionItem.processStepId`). Копия заместителя действует от имени получателя;
   через API — заголовок «от имени» в пределах области замещения. Замечания требуют комментарий
   или файл, отклонение и отказ — комментарий; комментарий и файлы решения становятся сообщением
   `decision` в обсуждении объекта (файлы — вложениями, прикрепить можно только свой файл, как в
   обсуждениях).
9. **Подпись с подтверждением.** Новый порт ядра `kernel/second-factor` (`enrolled`, `verify`),
   реализация — identity: только TOTP (`AuthService.verifyTotp`, повтор кода отклоняется), без
   резервных кодов. Код вводит тот, кто действует; без подключённого второго фактора — 422; пять
   неверных кодов за 15 минут — 429. Действие Входящих получило признак `requiresSecondFactor`:
   веб спрашивает код в диалоге действия; Telegram такие действия показывать не должен.
10. **Расширения модулей** (ядро не знает о документах): `registerProcessObjectProvider` — данные
    типа объекта (автор, подразделение автора, пространство, поля для `field:` и
    `object.fields.*`, сводные свойства `object.<имя>`), изменение поля (`set`), разрешение запуска
    из общего API и хуки в транзакции перехода: активация шага (заморозка версии), каждое решение
    (лист согласования, подпись версии), завершение шага (статус), завершение маршрута;
    `registerProcessStepHandler` — исполнители `register` (номер), `task` (поручение; модуль
    завершает шаг `ProcessService.completeStep`), `call` по действию; отменённый шаг — `cancel`
    исполнителя. Без поставщика данные берутся из реестра (автор — создатель, поля — `meta`), а
    запуск — только модулем.
11. **Права.** Маршрут и его линию видит тот, кто видит объект; решает назначенный или его
    заместитель; не участник шага, не видящий объект, получает 404. Производное право участника
    шага видеть объект подключает модуль в политике своего типа:
    `withProcessParticipants(policy, { afterStep: 'view' | 'none' })` — `derive`, `visibleSql` и
    новое поле политики `principals` (принципалы для поискового индекса и `readPrincipalsFor`:
    иначе участник не нашёл бы документ поиском — возражение ADR-0060 к политике вместо ACL).
    Изменение состава участников публикует `acl.changed` — пересчёт индекса и комнат realtime.
12. **Определения и способность.** `process_definitions`: у ключа один черновик (частичный
    уникальный индекс) со следующим номером; опубликованная версия неизменна. API —
    `/process-definitions` (список, маршрут, версия, создание, черновик, проверка, публикация,
    предпросмотр «кто будет назначен» на примере объекта) под новой способностью
    **`processes.manage`** (системный администратор; документы второй волны могут выдать её
    канцелярии): маршруты общие для документов, базы знаний и автоматизации, поэтому ни
    `documents.journals.manage`, ни `automation.manage`, ни широкая `admin.system` не подходят.
    Определения — конфигурация, а не объекты реестра (как роли и календарь); экземпляры —
    часть своего объекта.
13. **События и последствия**: `process.started`, `step_activated`, `step_decided`,
    `step_completed`, `step_assignees_changed`, `step_due_soon`, `step_overdue`, `finished`,
    `definition_changed` (домен `process`). Подписчики ядра: уведомления (назначение по типу
    шага, напоминания, просрочка и эскалация, решения автору, пустой шаг, завершение), лента
    активности объекта, обновление открытой вкладки (`object.updated` с полем `process`), ожидание
    событий, отмена маршрутов объекта в корзине.

## Альтернативы

- **Машина состояний прямо в ядре с записью в базу на каждом шаге** — отклонено: семантику
  кворумов, ветвей и повторного согласования нельзя было бы проверить быстрыми тестами без базы.
- **Отдельное отложенное задание на каждый момент шага** (напоминания и просрочка) — отклонено:
  реестр заданий рос бы втрое, а устаревшие задержки после повторной передачи в очередь срабатывали
  бы невпопад; одно задание на ближайший момент и обход по базе проще и надёжнее.
- **Только обход по расписанию без заданий** — отклонено: минутная точность и лишняя нагрузка;
  контракт требует отложенных заданий.
- **Участники шагов — записями ACL, как у поручений (ADR-0060)** — отклонено: запись ACL не знает
  своего источника, снятие права по окончании шага отняло бы явно выданный доступ, а выдача с
  меньшим уровнем понизила бы его; политика типа с принципалами для поиска закрывает то же.
- **`role_in_space` как только роль участника пространства** — отклонено: пример контракта
  (`legal`, `finance`) — функциональные роли; как только роль, ограниченная пространством, —
  отклонено: пришлось бы назначать юриста в каждом пространстве.
- **Отклонение, ждущее ответов всех** (как замечания) — отклонено: жёсткое «нет» задерживало бы
  возврат автору на сроки остальных согласующих.
- **Схема определения в `@kchs/contracts`** — отклонено: контракту нужен разборщик выражений, а
  пакет контрактов — лист графа зависимостей.

## Последствия

- Документы (вторая волна) запускают маршрут `ProcessService.start` в транзакции «отправить на
  согласование», регистрируют поставщика данных `document` с хуками (заморозка версии, лист
  согласования, статусы) и исполнителей `register`/`task`/`call`, подключают
  `withProcessParticipants` в политике `document`, о завершении узнают хуком `onFinished` или
  событием `process.finished`. Конструктор маршрутов (P3-E01 S03) работает поверх
  `/process-definitions`, проверки и предпросмотра; определения можно проверять и в браузере —
  `@kchs/process` не тянет базу и libpg-query.
- Сроки шага — общие для шага (у последовательного согласования — на всю очередь); напоминания и
  просрочка — только у шагов решения (у поручений шага `task` — свои сроки модуля).
- Изменение оргструктуры не пересчитывает назначенных активного шага; пустой шаг ждёт
  переназначения. Роли для `role_in_space` (кроме ролей пространства) назначаются ролями
  пользователей с ограничением пространством — своих ролей пока нет (отложено с фазы 0).
- Уведомления процесса не фильтруются по праву видеть объект (эскалацию получает руководитель,
  которому объект может быть не виден): модуль с грифами сам решает, что показывать.
- Отложено: уведомления заместителям о новых шагах (у них копии во Входящих), шаблоны
  уведомлений шага `notify` (ключи `processes.templates.*` добавляют модули), кнопки Telegram для
  действий с кодом второго фактора, экран «Процессы».
