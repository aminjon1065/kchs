# 0087. Конструктор маршрутов: определение — единственная правда, схема списком с группами, проверка сервером, справочник модулей

Статус: Принято
Дата: 2026-09-19

## Контекст

P3-E01 S03 и 08-documents.md §4: маршруты согласования, подписи, регистрации и ознакомления
настраивает канцелярия, а не разработчик. Конструктор — «визуальный (список шагов с вложенными
параллельными группами), с проверкой определения и предпросмотром „кто будет назначен“ для примера
документа». Движок процессов (ADR-0079) уже даёт API определений: черновик, проверка, публикация,
версии, предпросмотр. Открытые вопросы реализации:

- как показать граф (`next`, `onReject`, ветви условий, возвраты) списком и не потерять шаги;
- где правда о маршруте при правке, как не разойтись с проверкой сервера;
- как конструктору узнать, что зарегистрировали модули: поля объекта для `field:`, события для
  `wait`, исполнители `register`/`task`/`call`;
- как показывать назначенных (`user:<id>`, `unit:<id>`) словами, а не идентификаторами.

## Решение

1. **Определение — единственная правда.** Конструктор держит `ProcessDefinition` целиком и правит
   его чистыми функциями (`apps/web/src/features/processes/model.ts`, unit-тесты): вставка после
   шага и в ветвь, новая ветвь, удаление со сшивкой `next` и начала (ссылка отклонения на удалённый
   шаг сбрасывается к умолчанию, прочие ссылки остаются — их покажет проверка), сдвиг в линии и в
   ветви, переименование ключа во всех ссылках (`next`, `onReject`, ветви, `else`, группы, таймеры,
   условия запуска). Вставка шага даёт разумные значения по умолчанию (согласование —
   руководителем подразделения автора, 3 рабочих дня), чтобы черновик сохранялся без ошибок формы.
2. **Схема — раскладка графа списком.** Основная линия идёт от первого шага по `next`;
   параллельная группа показывает ветви внутри карточки (колонками, если хватает ширины, иначе
   друг под другом — container query); остальные шаги — цепочками ниже в порядке обнаружения по
   переходам отклонения и условий, затем недостижимые; у цепочки — «переход сюда: при отклонении
   «…»». Шаги без `next` (условие, завершение) — последние в линии; завершение вставляется только в
   конец, условие — только перед шагом; в ветвь — без условий, возвратов и завершения (ADR-0079).
3. **Проверка — сервером, на лету.** Каждое изменение (с задержкой 400 мс) уходит в
   `POST /process-definitions/validate`; ответ с проблемами раскладывается по шагам (`steps.<ключ>…`)
   и разделам настроек (переменные, эскалация, условия). Карточка показывает число ошибок,
   инспектор — их текст, вкладка «Проверка» ведёт к месту. Публикация закрыта при ошибках.
   Предпросмотр назначений — `POST /process-definitions/preview` с текущим определением, выбранным
   объектом типа маршрута, значениями переменных и выбором инициатора.
4. **Справочник модулей — `GET /process-catalog`** (способность `processes.manage`): типы
   объектов с поставщиком данных маршрута и их поля (`ProcessObjectProvider.fieldHints` —
   необязательный, у документа — поля карточек), можно ли запускать общим API, события для `wait`
   (`registerProcessWaitEvent`), исполнители шагов модулей. Ядро не знает о документах — справочник
   собирает то, что модули зарегистрировали.
5. **Назначенные словами.** Частые формы (`unit_head(author.unit)`, `manager(author)`, `author`,
   `role:`, `role_in_space:`, `var:`, `field:`, `chosen_by_initiator`, в эскалации
   `manager(step.assignee)`) распознаются и подписываются словарём; люди, подразделения и группы —
   именами через `GET /principals/describe?keys=user:<id>,…` (identity, до 100 ключей, только
   именованные принципалы — те же, что пикер ищет всем сотрудникам). Прочие выражения показываются
   как есть и проверяются сервером; меню «Добавить» даёт быстрые формы, поиск сотрудника,
   подразделения или группы, роль, переменную, поле и произвольное выражение.
6. **Место и права.** Раздел консоли «Маршруты процессов» (виден со способностью
   `processes.manage`) — список с опубликованной версией, черновиком и числом идущих, создание
   (ключ подсказывается транслитерацией названия, шаблон «согласование и завершение» или
   «согласование → подпись → регистрация»); конструктор — вкладка оболочки `process-designer` с
   параметром `key`, отдельным чанком (нужен только администратору маршрутов). Несохранённые
   изменения — точка на вкладке. JSON — вкладка для редких конструкций; текст применяется при
   выходе из поля, если похож на маршрут (ключ и тип объекта не меняются). История версий
   позволяет взять старую версию за основу черновика.

## Альтернативы

- **Графический редактор узлов и стрелок (canvas).** Отклонено: проект задаёт список с группами;
  канцелярии привычнее последовательность шагов, чем граф; доступность и мобильная версия canvas
  дороже; редкие переходы (условия, возвраты) видны цепочками ниже.
- **Собственная модель конструктора с преобразованием в определение при сохранении.** Отклонено:
  два представления расходятся, JSON-вкладка и проверка сервера работали бы с разными данными.
- **Проверка на клиенте тем же `validateDefinition`.** Отклонено: публикация ещё проверяет
  исполнители модулей и события, известные только серверу; пакет `@kchs/process` со схемами и
  разборщиком выражений утяжелил бы оболочку. Веб берёт из пакета только типы.
- **Поля объекта для подсказок — из схемы карточек документов напрямую.** Отклонено: ядро не
  читает таблицы модулей; поставщик маршрута сам знает свои поля.

## Последствия

- Новые API: `GET /process-catalog`, `GET /principals/describe`; необязательный
  `ProcessObjectProvider.fieldHints`. Контракт `ProcessDefinition` не менялся.
- Поставщик документов (вторая волна) может отдать поля карточек через `fieldHints` — конструктор
  предложит их в назначениях и покажет подписи.
- Выбор маршрута при отправке документа и связь «тип документа → маршрут по умолчанию» —
  карточка типа и отправка на согласование (ADR-0083); конструктор только создаёт и публикует
  маршруты.
- Не сделано: перетаскивание шагов мышью (сдвиг — командами «Выше/Ниже»), визуальное сравнение
  версий маршрута, подсказки выражений условий с автодополнением.
