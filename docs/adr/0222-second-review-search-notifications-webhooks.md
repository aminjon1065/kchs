# 0222. Второй внешний разбор: поиск, уведомления, вебхуки, Входящие, документы, рабочее пространство, движок

Статус: Принято
Дата: 2026-10-14

## Контекст

Второй внешний разбор проекта (`04-delivery/07-architecture-hardening.md` §3.4б). Все находки
проверены по коду и подтвердились:

- поиск индексирует по одному объекту, полная переиндексация идёт `OFFSET` без порядка, векторы
  пишутся запросом на кусок;
- `notify()` обрабатывает получателей по одному и доставляет внутри цикла;
- `setDue` пересчитывает счётчики Входящих до фиксации транзакции;
- вебхуки читают таблицу подписок на каждое событие, а адрес проверяется одним разрешением DNS,
  запрос же идёт со вторым;
- справочник людей запрашивается дважды подряд при запуске правила;
- правка темы карточки документа поднимает версию объекта на 2;
- рабочее пространство сохраняется после восстановления и при непостоянных полях;
- кэш колоночных копий движка вытесняет по `st_atime` и может удалить читаемый файл, словарь
  замков растёт, клиент Redis отмены не закрывается.

## Решение

### Поиск (`kernel/search`)

- `indexObjects` готовит пачку вместе: строки, грифы (`effectiveConfidentialityMany`) и теги
  (`TagService.namesMany`) — запросом на пачку, права и содержимое модуля — с параллелизмом 4
  (`shared/concurrency.ts`, `mapLimited`). В Meilisearch пачка уходит одной задачей
  `addDocuments` и одной `deleteDocuments`. `indexObject` — пачка из одного.
  Замер (60 папок, слот тестов): было 442 мс и 60 вызовов, стало 58 мс и 1.
- `reindexAll` идёт курсором по `id` с `ORDER BY`, как `reindexSpace`. Тест с правкой всех строк
  во время прохода: было 6 повторов, стало 0 повторов и 0 пропусков.
- Фильтр статуса в `hitsForObjects` — `inArray` по выражению `meta->>'status'`.
- Векторы (`indexEmbeddings`, `indexChunks`) пишутся одним `INSERT … ON CONFLICT DO UPDATE` с
  `excluded.*`. Укороченный текст без правок теперь тоже убирает лишние куски.

### Уведомления (`kernel/notifications`)

- Получатели обрабатываются пачкой: настройки по категории, проверка повтора события
  (ADR-0171), окно агрегации, вставка — запрос на пачку. Счётчик агрегации — атомарное
  `aggregate_count + 1`. Режимы каналов, тишина (ADR-0140), срочное без агрегации (ADR-0168) и
  пропуск автора не изменились.
- Доставка идёт после записи всех строк: письма «немедленно» — один `deliverEmail(ids)`,
  внешний канал — одна пачка сообщений на канал. Строки, сводки объектов и кнопки дел
  (`InboxService.openActionsFor`) читаются на пачку, отметка `external_sent_at` — одним `UPDATE`.
- Сбой письма одному получателю не останавливает письма остальным (и в дайджесте).
- Замер (30 получателей, Telegram и почта): было 603 мс и 29 вызовов канала, стало 149 мс и 1.

### Входящие (`kernel/inbox`)

- `setDue` в транзакции только сбрасывает кэш, пересчёт и realtime — `afterCommit`. Тест
  воспроизводил устаревшее «просрочено» (0 вместо 1).
- `invalidateCounts` сбрасывает кэш одной командой и пересчитывает пользователей параллельно,
  не больше 8 сразу.

### Вебхуки (`modules/integrations`)

- Доставка идёт через общий диспетчер `shared/net/outbound.ts` (`outboundDispatcher`). Адрес
  проверяется в момент соединения, то есть проверяется тот адрес, с которым соединяемся.
  Подмена записи DNS после предварительной проверки (DNS rebinding) запрос внутрь не уводит.
  Host и SNI — имя из адреса, перенаправления не выполняются, прокси — как у `outboundGet`.
- Политика одна: предварительная проверка `checkOutboundUrl` использует тот же
  `outboundAddressDenied` (частные сети и loopback — по `WEBHOOKS_ALLOW_PRIVATE_ADDRESSES`).
  Служебные адреса — метаданные облака, «этот узел», multicast — закрыты всегда (N166).
- Активные подписки — кэш процесса на 5 с. Изменение подписки сбрасывает его после коммита, а
  в других процессах — событием `webhook.*` или объекта-вебхука у подписчика шины (N165).
  Доставка подписке, удалённой за время кэша, не ломает подписчика: нарушение внешнего ключа —
  пропуск и сброс кэша.
- Тест подменяет DNS (проверка — внешний адрес, соединение — loopback). На старом коде запрос
  доходил до loopback, теперь — «Имя указывает во внутреннюю сеть».

### Автоматизация, документы

- `buildScopeData` обращается к справочнику за именем инициатора один раз.
- Правка карточки документа — одно `ObjectService.update` (название и `meta` вместе): версия
  +1 вместо +2. Событие `object.updated` — только при смене темы.

### Рабочее пространство (web)

- Сохраняется только изменившийся снимок: сериализованный `snapshot()` сравнивается с
  последним сохранённым. `restore()` задаёт новую точку отсчёта. Якорь обсуждения и стек
  закрытых вкладок в снимок не входят и запроса не порождают.
- Оболочка показывается после загрузки профиля (`app.tsx`), поэтому восстановление берёт
  сотрудника из загруженного `/me`, без второго `fetchQuery`. Снимок вкладки из
  `sessionStorage` (перезагрузка, ADR-0188) после восстановления досылается — keepalive мог не
  дойти (N168).

### Движок

- Вытеснение копий Parquet — по `st_mtime`, который кэш ставит сам (`os.utime`) при каждой
  выдаче файла.
- Выданные запросу копии отмечены читаемыми до конца запроса (`_acquire_local` / `_release`,
  отпускаются и при ошибке), вытеснение их не трогает.
- Замок скачивания уходит вместе с вытесненной копией.
- Клиент Redis отмены закрывается при остановке (`close_cancel_client` в `lifespan`).

## Альтернативы

- Кэш подписок в Redis с pub/sub — лишняя зависимость. Подписчик шины и так получает событие
  об изменении.
- Соединение по заранее разрешённому адресу (pin) вместо проверки в момент соединения — то же
  закрытие окна, но проверка в момент соединения уже есть в общем клиенте и работает с прокси.
- Сохранять рабочее пространство на каждое изменение, а лишние запросы срезать на сервере —
  сеть и база всё равно нагружаются.

## Последствия

- Миграций нет, контракты и события не менялись.
- `WEBHOOKS_ALLOW_PRIVATE_ADDRESSES=true` больше не открывает служебные адреса (метаданные
  облака 169.254.0.0/16, 0.0.0.0/8, multicast). Частные сети и loopback по-прежнему открывает.
- Внешний канал получает уведомления одного `notify()` пачкой. Сбой адаптера канала теряет
  пачку, а не одно сообщение. Адаптеры Telegram и push ошибки по сообщению ловят сами.
- e2e, которые задевает изменение: поиск, уведомления и Входящие, вебхуки (`integrations`),
  карточка документа, `workspace.spec.ts`, колоночная аналитика.
