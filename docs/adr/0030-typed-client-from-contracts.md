# 0030. Типизированный клиент из `packages/contracts`, а не из OpenAPI

Статус: Принято

Контекст: `04-delivery/03-backlog.md` (P0-E01 S04) требует типизированный клиент,
скомпилированный из OpenAPI. При этом сервер описывает маршруты zod-схемами из
`packages/contracts`, и те же схемы доступны клиенту напрямую — монорепо на
одном языке.

Решение: веб-клиент использует типы `@kchs/contracts` напрямую через тонкую
обёртку `shared/api/client.ts` (cookie-сессия, CSRF, problem+json, обработка
401). OpenAPI остаётся источником правды для внешних интеграций и Python-движка
и публикуется по `/api/openapi.json`; команда `pnpm --filter @kchs/web api:types`
генерирует `openapi.gen.ts` для сверки.

Альтернативы:
- `openapi-typescript` + `openapi-fetch` как единственный путь: типы проходят
  через JSON Schema и теряют часть выразительности zod (уточнённые строки,
  дискриминированные объединения), появляется шаг генерации в цикле разработки.
- `tRPC`: отклонён проектом (18-tech-stack.md) — нужен один REST для интеграций.

Последствия: несовпадение контракта и реализации ловится компилятором сразу,
без шага генерации. Ответы всё равно проверяются zod-схемами на сервере, поэтому
расхождение «тип клиента ↔ фактический ответ» невозможно. Для внешних
потребителей OpenAPI остаётся обязательным и проверяется в CI.
