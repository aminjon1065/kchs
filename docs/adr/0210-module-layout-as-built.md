# 0210. Шаблон модуля — по фактическому устройству, с проверкой в CI

Статус: Принято
Дата: 2026-10-13

## Контекст

`04-delivery/01-project-structure.md` (Решено) описывал модуль так: `module.ts`, `public.ts`,
`schema.ts`, `domain/`, `infra/`, `http/`, `jobs/`, `events/`, `__tests__/`, и «репозитории —
единственное место SQL модуля». Разбор укрепления (`07-architecture-hardening.md` §3.4)
показал, что шаблон не соблюдён ни в одном модуле:

- запросы Drizzle к своим таблицам живут в сервисах `domain/` (183 файла), отдельного слоя
  репозиториев нет;
- `infra/` есть у трёх модулей — у тех, где правда есть инфраструктура: физическое хранение
  датасетов (`data`), тайлы и слои (`gis`), адаптеры внешних систем (`integrations`);
- маршруты — `http.ts` или каталог `http/`; задания и подписчики регистрируются в
  `module.ts` и лежат в `domain/`;
- тесты — в `apps/api/test` (интеграционные) и рядом с кодом (`*.test.ts`).

Переделать 24 модуля под репозитории — недели работы без пользы для пользователя и с риском
регрессий. Важно не где лежит запрос, а чьи таблицы он трогает и как строится SQL — а это
уже проверяет CI.

## Решение

1. **Шаблон модуля — фактическое устройство:**
   - `module.ts` — регистрация: типы объектов, маршруты, подписчики, задания, расписания;
   - `public.ts` — публичный вход, когда модуль нужен другим модулям;
   - `schema.ts` — таблицы модуля (ADR-0178);
   - `domain/` — сервисы, инварианты и запросы Drizzle к своим таблицам, задания и
     подписчики;
   - `http.ts` или `http/` — маршруты по таблице контрактов (ADR-0188);
   - `infra/` — адаптеры внешних систем и физическое хранение (DDL, COPY, тайлы);
   - `providers/` — поставщики внешнего сервиса за портом модуля (сейчас — ИИ).
2. **Правило «SQL только в репозиториях» заменяется проверяемыми инвариантами:**
   - модуль трогает только свои таблицы и `objects`, таблицы ядра — через сервисы и порты
     (`scripts/table-owners.mjs`, ADR-0178, ADR-0184);
   - текст SQL как есть — только в `modules/data/infra`, `shared/db`, `packages/query` и
     адаптере внешней СУБД (`scripts/raw-sql.mjs`, ADR-0184); остальное — шаблон `sql` с
     параметрами и построитель Drizzle;
   - между модулями нет колец, чужой модуль — только через `public.ts`
     (`scripts/module-cycles.mjs`, dependency-cruiser, ADR-0181).
3. **Новая проверка `scripts/module-layout.mjs`** в `pnpm deps:check`: у каждого модуля есть
   `module.ts` и `domain/`, каталоги верхнего уровня — только из шаблона. Новый модуль сразу
   получает общий вид, а новый вид каталога требует правки шаблона и этого ADR.
4. **Крупный файл делится по швам** (этап 4 укрепления): разные сущности, шаги мастера,
   регистрации групп маршрутов — отдельными файлами в том же каталоге.

## Альтернативы

- **Перевести модули на репозитории.** Отклонено: объём без пользы для пользователя; таблицы и
  сырой SQL уже под контролем CI.
- **Оставить описание как есть.** Отклонено: документ «Решено» расходится с кодом и вводит в
  заблуждение исполнителя нового модуля.

## Последствия

- `04-delivery/01-project-structure.md` и `02-architecture/01-overview.md` описывают
  фактический шаблон; правило «репозитории — единственное место SQL» снято.
- `pnpm --filter @kchs/api deps:check` проверяет устройство модулей.
