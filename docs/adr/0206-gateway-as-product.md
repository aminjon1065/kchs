# 0206. Шлюз как продукт: учёт подключений, датасет «Подключения», стабильные ключи журналов и шаблонов, каталог каналов, порт ЭДО

Статус: Принято
Дата: 2026-10-12

## Контекст

Концепт-нота КЧСиГО ред. 2.0 (компонент 4, приложение C) описывает шлюз обмена как продукт для
партнёров: 16 каналов с паспортами, документация и тестовая среда. Показатель концепт-ноты —
«не менее двух партнёров на уровнях 0–2». Разбор `docs/04-delivery/08-architecture-concept-note-and-signatures.md`
§8, §9 и пункты 9–10 плана свёл это к четырём вещам:

- у токена API есть только `last_used_at` и `last_used_ip`. Кто, каким каналом и сколько
  передаёт, не видно. Нечем мерить показатель концепт-ноты;
- пакет конфигурации (ADR-0097) не переносит типы документов: карточка типа ссылается на журнал
  по UUID, а стабильного ключа у журналов нет (вопрос N42). Песочница и рабочий контур не могут
  обмениваться настройкой документооборота;
- каталог каналов — это содержание, а не код. Нужно решить, где он живёт и как ставится;
- адаптер государственной системы ЭДО ждёт её интерфейса. Нужно, чтобы модуль документов уже
  сейчас знал, куда ставить отправку.

Ограничения: модули по слоям без колец (ADR-0181), таблицы у владельца (ADR-0178), события
через outbox (правило 3), горячий путь API не должен получить запись в базу на каждый запрос.

## Решение

1. **Учёт подключений — две таблицы модуля интеграций.**
   - `integration_connections` хранит подключение: что подключено (`subject_id`), канал, вид,
     название, владельца токена, «с какого времени», последнюю передачу и последнюю ошибку.
   - `integration_usage_daily` хранит суточные счётчики по дню установки (`TZ`): запросы
     (передачи), записанные строки, ошибки.
   - Каналы: `api`, `webhook_in`, `mail_in`, `feed`, `database`, `form`, `webhook_out`, `edms`.
2. **Запросы токенов считаются в Redis, а не в базе.**
   - Аутентификация токеном делает один `HINCRBY kchs:usage:pending "<день>|<токен>"` без
     ожидания ответа.
   - Задание `integrations.usage-flush` раз в минуту атомарно переименовывает хэш в снимок,
     прибавляет счётчики одной транзакцией (`ON CONFLICT … + excluded`) и удаляет снимок.
   - Упавший сброс оставляет снимок, следующий запуск его досчитывает. Блокировка `SET NX`
     не даёт двум воркерам сбрасывать одновременно.
   - Почему не upsert на каждый запрос: горячая строка токена под блокировкой и запись WAL на
     каждый вызов API. Почему не память процесса: реплик api несколько, память теряется при
     перезапуске.
   - Цена решения: при потере Redis пропадает до минуты счётчиков. Если сбой придётся между
     фиксацией и удалением снимка, минута посчитается дважды. Для телеметрии это допустимо;
     для расчётов с партнёрами учёт не предназначен.
3. **Остальные каналы — из событий.**
   - Подписчик `integrations-usage` получает события:
     - `source.synced` и `source.failed` — лента или источник из внешней БД; канал определяет
       новое необязательное поле `kind` в нагрузке;
     - `form.submitted` — сдача формы;
     - `webhook.received` — входящий вызов интеграции или правила;
     - `mail.received` — письмо из ящика IMAP;
     - `webhook.delivered` и `webhook.failed` — исходящий вебхук;
     - `dataset.rows_changed` и `dataset.imported` от сессии `token:<id>` — строки,
       записанные по токену.
   - Таких событий на порядки меньше, чем запросов, поэтому подписчик пишет в базу сразу.
   - Запись счётчиков — телеметрия, а не предметное состояние. Событий она не публикует, как
     `ApiTokens.touch`.
   - Счётчики старше 400 дней удаляет суточная очистка журнала доставок.
4. **Системный датасет «Подключения» (`connections`).**
   - Представление `ds.sys_connections` даёт строку «подключение × сутки» за последние 60 дней.
     Дни без передач входят в него, пропуски видны нулями.
   - Выпущенные, но не использованные токены тоже входят: «выдан и молчит».
   - Поля:
     - кто: `connection`, `kind`, `owner`;
     - каким каналом и с какого времени: `channel`, `since`;
     - объём за день: `requests`, `rows`, `errors`;
     - своевременность: `last_at`, `hours_since_last`, `stale` (молчит дольше суток);
     - полнота: `completeness` — доля дней с передачами за 30 дней;
     - состояние: `status`.
   - Политика строк: управляющие интеграциями (`automation.manage`) видят всё, владелец токена —
     свои строки, остальные — ничего.
   - Показатели и дашборд «Интеграции» заводит сид в «Общем», идемпотентно по `meta.systemKey`.
     Модуль интеграций ниже модуля данных по слоям и создавать показатели сам не может.
   - Показатели дашборда:
     - активные подключения за 30 дней — это показатель концепт-ноты;
     - запросы за сутки;
     - строки за сутки;
     - молчащие подключения;
     - полнота.
5. **Стабильный ключ журналов и шаблонов (N42).**
   - Столбец `key` добавлен расширением: заполнение, затем `NOT NULL` и уникальность.
   - Журналы стартового набора получают ключи из кода (`incoming`, `outgoing`…). Остальные
     журналы и шаблоны получают транслитерацию названия; совпадения различает хвост из id.
   - Ключ не задан — сервер берёт `keyFromName` с суффиксом `_2`, `_3`.
   - Ключ правится в справочнике журналов. Занятый ключ — 409.
   - Вид ключа совпадает с ключом типа: `^[a-z][a-z0-9_]*$`, от 2 до 64 символов.
6. **Пакет конфигурации переносит журналы, типы и шаблоны по ключам.**
   - Разделы `journals`, `documentTypes`, `documentTemplates` дал модуль документов.
   - Ссылки внутри пакета — ключи:
     - журнал нумерации типа — `journalKey`;
     - типы журнала — `typeKeys`;
     - тип шаблона — `typeKey`;
     - маршрут — ключ определения процесса (раздел `processDefinitions` уже был);
     - подразделения — по коду.
   - Файл DOCX шаблона до 2 МБ едет в пакете base64 с sha256. Новое вложение заводится, только
     если хэш изменился.
   - Люди не переносятся. Сотрудник «резолюции — конкретному сотруднику» остаётся местным;
     новый тип с таким правилом приезжает без него.
   - Применение идёт в порядке каталога разделов: маршруты → журналы → типы → шаблоны.
   - Провайдер раздела может объявить второй проход `relink`. После всех записей он ставит
     ссылки на записи, приехавшие в том же пакете позже: журнал ссылается на новый тип.
7. **Каталог каналов — содержание пакета ЧС, а не код платформы.**
   - Шаблон страницы «Паспорт канала» (`channel_passport`) — общий для платформы. Разделы
     шаблона: назначение, состояние, формат, пример, порядок доступа, ответственный, описание API.
   - Раздел «Каналы обмена» с 16 паспортами по приложению C ставит пакет ЧС (как ADR-0128). Он
     ложится в пространство «Общее» с ключами `meta.packKey = emergency.channels.*`. Повторная
     установка досоздаёт недостающее, правки не трогает.
   - Состояние указано честно на дату выпуска. «Создаётся проектом»:
     - MS SQL и ClickHouse;
     - приём координат;
     - CAP-лента Комитета;
     - картослужбы Комитета;
     - песочница.
   - Ответственных назначает Комитет.
8. **Порт `EdmsExchange` без реализации.**
   - Интерфейс адаптера: `send` с ключом идемпотентности, необязательные `status` и `recipients`.
     Ошибка `EdmsError(retryable: false)` повтором не лечится.
   - Таблица `edms_sends`: пакет отправки (`payload`), адресат, ключ идемпотентности, состояние,
     попытки, следующая попытка, внешний id, ошибка.
   - `EdmsSends.enqueue` вызывает модуль документов в своей транзакции. Без адаптера вызов
     отказывает 409, чтобы отправка не висела в очереди молча. Пакет собирает модуль
     документов: интеграции документы не читают.
   - `processDue` берёт строки с `SKIP LOCKED`. Паузы между попытками: 1, 5, 15, 60, 180, 720 и
     1440 минут. После восьмой попытки отправка получает состояние `failed`.
   - События `edms.send_queued`, `edms.sent`, `edms.send_failed`. Передачи пишутся в канал `edms`
     журнала подключений.
   - Обработчик задания зарегистрирован. Расписание объявит адаптер, когда появится интерфейс
     системы. До этого обмен идёт письмом с подписанным экземпляром (ADR-0198).
   - **Дополнение 14.10.2026 (ADR-0219).** Госсистема закрыта, интерфейса не будет. Порт
     работает провайдером «ручной обмен» (`MANUAL_EDMS`) по умолчанию: `enqueue` ставит
     отправку, задание её не трогает, отправку закрывает отметка «передано» человека
     (`EdmsSends.markSent`).

## Альтернативы

- **Счётчики в `api_tokens`.** Отклонено: суток в строке токена нет, каналы без токена не
  учитываются, горячая строка под блокировкой.
- **Учёт из журнала доступа обратного прокси.** Отклонено: шлюз DMZ не единственный вход, а строки
  и ошибки синхронизаций в журнале прокси не видны.
- **Ключ журнала как UUID исходной установки.** Отклонено: человеку такой ключ ничего не говорит,
  а журнал, заведённый вручную в обоих контурах, не совпадёт.
- **Каталог каналов кодом платформы, отдельной страницей.** Отклонено: паспорт правит Комитет —
  ответственные, условия доступа, адреса. Это страницы базы знаний с владельцем и сроком
  пересмотра.
- **Реализация адаптера ЭДО по предположительному протоколу.** Отклонено: без интерфейса это
  угадывание. Порт и очередь фиксируют то, что известно уже сейчас.

## Последствия

- Показатель «партнёров на уровнях 0–2» считается дашбордом «Интеграции». Уровень партнёра
  (0–2) — оценка Комитета, в данных его нет. Вопрос владельцу задан в отчёте.
- Новый системный датасет `connections` добавлен в `SYSTEM_DATASETS`.
- События `source.synced` и `source.failed` получили необязательное поле `kind`.
- Добавлены разделы пакета `journals` и `documentTemplates` и домен событий `edms`.
- Контракты совместимы с main.
- Порядок разделов в `CONFIG_SECTIONS` стал порядком применения пакета.
- Шаблон страницы `channel_passport` появился в списке «Создать страницу» базы знаний.
- Датасет и дашборд показывают данные через минуту после запроса — это задержка сброса.
