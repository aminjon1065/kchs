# 0220. Надёжность и скорость горячих путей: outbox, пределы базы, кэш, дерево, видимость, шина, старт

Статус: Принято
Дата: 2026-10-14

## Контекст

Владелец прогнал проект через внешний разбор. Каждое утверждение сверено с кодом и записано в
`04-delivery/07-architecture-hardening.md` §3.4а. Все они подтвердились. Ошибки веб-клиента на
HTML-ответе прокси исправлены отдельно. Остальное делается одной веткой `phase/10-perf`.

Надёжность:
- outbox без предела попыток: одно битое событие держит весь поток;
- у основного пула базы нет пределов времени;
- кэш результатов без предела размера;
- у движка нет общего предела времени задания;
- скачивание копии Parquet идёт под одним замком на процесс;
- отмена задания не останавливает тяжёлый SQL.

Производительность:
- запрос API ждёт строку пользователя, набор принципалов, способности и политику по очереди;
- замыкание дерева пересчитывается по узлу;
- в предикате видимости граница наследования считается дважды;
- группы подписчиков стоят на всех потоках;
- SQL-лаборатория разбирает запрос дважды;
- worker при старте гоняет миграции и DDL;
- движок преобразует значения по одному.

## Решение

### Надёжность

1. **Outbox** (`kernel/events/dispatcher.ts`).
   - Пачка событий уходит в Redis одним `pipeline()`. Все принятые события отмечаются
     опубликованными: pipeline их уже отправил, иначе были бы дубли.
   - Событие, которое Redis отверг само по себе, получает `attempts + 1`. После 10 попыток ставится
     `quarantined_at`: событие уходит из очереди публикации и больше её не держит.
   - Системная ошибка Redis (`OOM`, `LOADING`, `READONLY`, `NOAUTH` и т. п.) попытку не
     расходует.
   - Видно в трёх местах: метрика `kchs.outbox.quarantined`, оповещение
     `KchsOutboxQuarantined`, «Здоровье системы».
   - Миграция `20261014035249_outbox-quarantine.sql`.
2. **Пределы основного пула базы** (`shared/db/client.ts`).
   - `statement_timeout` и `idle_in_transaction_session_timeout` задаются при подключении.
     - `ROLE=api`: 60 с и 60 с.
     - Worker и `all`: 30 мин и 10 мин.
   - `connect_timeout` — 10 с.
   - Переменные: `DATABASE_STATEMENT_TIMEOUT_MS`, `DATABASE_IDLE_IN_TX_TIMEOUT_MS`,
     `DATABASE_WORKER_*`, `DATABASE_CONNECT_TIMEOUT_S`. Они есть в compose, Helm и `.env.example`.
   - Отмена по пределу (57014) — ответ `504 query_timeout`.
   - Миграции идут своим клиентом без пределов.
3. **Кэш результата запроса.** В Redis попадает результат не больше 2000 строк и не больше
   1 МБ JSON (`fitsCache`). Большие выборки читаются из базы.
4. **Отмена задания TS доходит до базы.**
   - `readAsQueryRole` принимает `signal` и по нему вызывает `pg_cancel_backend` своего
     соединения.
   - Сигнал задания передают выгрузка, пайплайн и анализ (`QueryService.stream`).
5. **Движок.**
   - Предел времени задания по очереди: импорт и преобразования — 120 мин, отрисовка — 30,
     медиа — 180, остальное — 60. Выход за предел — `JobTimeoutError`.
   - Копия Parquet скачивается под замком своего ключа. Общий замок держится только на проверку и
     вытеснение кэша.

### Производительность

6. **Способности ролей** хранятся в кэше набора принципалов (`PrincipalSet.capabilities`).
   - Набор сбрасывается уже существующими путями: смена ролей и правка способностей роли.
   - Новая версия платформы со способностями системной роли сбрасывает его в `bootstrap`.
   - Пользователь, набор и политика читаются параллельно.
   - `buildUserCtx`: 1,80 → 0,98 мс (500 вызовов).
7. **Замыкание дерева.**
   - Перенос поддерева — два запроса при любом размере. Удаляются связи узлов поддерева с внешними
     предками, добавляется произведение «новые предки × поддерево».
   - Окончательное удаление читает потомков одним запросом, от самых глубоких.
   - Перенос папки с 585 объектами: 1,1–2,0 с → 17 мс.
8. **Видимость и вложения.**
   - В предикате списков прямой ACL вынесен отдельной веткой.
   - Роль в пространстве и ACL предков читают одну границу наследования, посчитанную один раз на
     строку.
   - На 10 тыс. объектов: посторонний — 87 → 75 мс, участник и читатель без изменений (≈ 75 и
     58 мс).
   - Хост даёт вложению не выше `edit`. С этим уровнем остальные хосты не проверяются, но
     «Объяснить доступ» (`explain`) по-прежнему перечисляет все.
   - Хосты по-прежнему ищутся для всех типов (N158).
9. **Шина событий.**
   - Группа подписчика стоит только на потоках доменов его типов. Со звёздочкой в домене — на всех.
   - Прежние группы на чужих потоках удаляются при старте. Их события подписчик подтверждал не
     глядя, а такая группа держала обрезку потока и копила отставание. До удаления их не учитывают
     обрезка и «Отставание».
   - Служебные записи пачки подтверждаются одним `XACK`, отметки обработки пачки читаются одним
     `SELECT`. Отметка по-прежнему ставится после обработки (N158).
   - `NOGROUP` при чтении пересоздаёт группы.
10. **SQL-лаборатория.**
    - `prepareRawSql` (`@kchs/query`): разбор передаётся в `rawSqlTables` и `compileRawSql`.
    - Справочники подписей читаются параллельно.
    - Разбор обычного запроса — около 0,05 мс, поэтому выигрыш заметен на длинном тексте, не на
      типичном.
11. **Старт.**
    - `ROLE=worker` не гоняет миграции, системные роли и DDL таблиц модулей. Он регистрирует типы,
      ждёт, пока все миграции этой версии будут применены (до 10 мин, затем ошибка и перезапуск
      оркестратором), и готовит настройки поискового индекса.
    - Таблицы `ds.*` обновляются, только пока `data.storage_version` в системных настройках
      старее кода (сейчас 2). Сканирования каталога на каждом старте больше нет.
12. **Колоночная копия.**
    - Выборка уже была потоковой: именованный курсор, пачки по 100 тыс. строк.
    - Теперь пачка преобразуется по столбцам с заранее известным типом Arrow. Значения, которые
      psycopg отдаёт готовыми, не преобразуются: 223 → 166 мс на 100 тыс. строк × 6 столбцов.
    - Результат DuckDB забирается `fetchmany` по 10 тыс., а не `fetchall`.

## Альтернативы

- **Outbox: отмечать только события до первой ошибки.** Отклонено: принятые после ошибки уже
  в потоке, следующий проход опубликовал бы их второй раз.
- **Хосты вложения только для «вложимых» типов.** Отклонено: через общий
  `POST /objects/{id}/links` вложением бывает любой объект, и гриф хоста перестал бы его
  ограничивать. Это ослабление доступа.
- **Идемпотентность через `INSERT … ON CONFLICT DO NOTHING RETURNING` до обработки.** Отклонено:
  если процесс упадёт между отметкой и обработкой, событие потеряется (ADR-0027 — «как
  минимум один раз»). Отметка после обработки остаётся. Сокращён `SELECT`: один на пачку.
- **Arrow прямо из Postgres (ADBC или `COPY` в бинарном виде).** Отклонено: нужна новая
  зависимость движка, а выборка и так потоковая.
- **DuckDB `fetch_arrow_table` для результата.** Отклонено: другие типы значений. Например,
  `HUGEINT` из `sum()` стал бы десятичным, и api получил бы строку вместо числа.

## Последствия

- При обновлении S2 старые поды worker могут получить `NOGROUP` на чужих потоках, пока их не
  заменили. События за это время читают новые поды тех же групп.
- Новый домен у существующего подписчика начинает с новых событий, как новый подписчик
  (ADR-0171).
- Новое обновление вида таблиц `ds.*` повышает `DATA_STORAGE_VERSION`.
- Worker больше не стартует раньше схемы. Compose ждёт здоровый api, Helm — задание миграций
  или api.
