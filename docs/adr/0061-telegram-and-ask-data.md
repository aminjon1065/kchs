# 0061. Telegram-бот и «Спросить данные»: канал уведомлений модуля, модуль ИИ, план вместо QuerySpec

Статус: Принято
Дата: 2026-09-19

## Контекст

P1-E09 «Каналы и ИИ» и сценарии приёмки фазы 1: №6 (исполнитель получает уведомление в
Telegram и открывает объект по ссылке) и №7 (вопрос на русском → график и показанный запрос,
запрос правится вручную). Открытыми оставались:

- как ядро доставляет в Telegram, не завися от модуля;
- режим бота — вебхук или долгий опрос;
- как устроены провайдер ИИ, лимиты и аудит;
- в какой форме модель возвращает запрос;
- что уходит во внешний провайдер (вопросы Q7 и N6 в `05-risks-and-open-questions.md`).

Токен бота и переменные провайдера (`TELEGRAM_BOT_TOKEN`, `AI_PROVIDER`, `ANTHROPIC_API_KEY`,
`OPENAI_COMPAT_URL`) были в конфигурации с фазы 0, но нигде не использовались.

## Решение

1. **Канал уведомлений как порт ядра.**
   - Ядро объявляет `NotificationChannelAdapter` (`kernel/notifications/channels.ts`), модуль
     `telegram` регистрирует реализацию при старте — так же, как справочник людей (ADR-0031).
   - `NotificationService.notify` включает Telegram в каналы уведомления только у тех, кому он
     доступен: бот настроен и чат привязан. Остальным он не пишется в `channels`.
   - Правила по умолчанию: в Telegram сразу идут `inbox`, `mention` и `meetings` («действия и
     упоминания — везде», 12-calendar-notifications-home.md §2). Остальные категории
     включаются в настройках.
   - Дайджеста у внешних каналов нет: любой режим, кроме `off`, означает «сразу». Слитые
     повторы (агрегация за 5 минут) не отправляются, как и письма.
   - Текст и ссылку строит ядро одной функцией для писем и каналов: язык получателя, ссылка
     `KCHS_BASE_URL + /o/{id}` открывает вкладку объекта.
   - Ответ настроек уведомлений дополнен полем `defaults` — действующие режимы по умолчанию,
     чтобы экран показывал фактическое состояние.
2. **Привязка Telegram.**
   - Таблица `telegram_links`: один чат на пользователя и один пользователь на чат.
   - Профиль выдаёт одноразовую ссылку `t.me/<бот>?start=<токен>`. Токен — 24 случайных байта,
     живёт 15 минут, в Redis хранится хеш токена, гасится при первом предъявлении.
   - Бот принимает `/start <токен>` только в личном чате; группы игнорируются.
   - Отвязка: в профиле, командой `/stop` или сама, когда Bot API отвечает 403 (бот
     заблокирован).
   - События `user.telegram_linked` и `user.telegram_unlinked` (с причиной `user` или
     `blocked`) пишутся в outbox вместе с изменением. Действия попадают в аудит как
     `integration.telegram_*`; chat_id в событие не попадает.
3. **Долгий опрос, не вебхук.**
   - Установка S1 on-prem обычно не принимает входящих соединений из интернета. Вебхуку нужен
     публичный HTTPS, а Caddy получает сертификат только при публичном домене.
   - Бот (grammY) опрашивает `getUpdates` в роли worker. Читатель должен быть один, поэтому
     несколько worker делят блокировку в Redis с продлением. После сбоя (неверный токен,
     конфликт) опрос делает паузу на минуту.
   - `TELEGRAM_POLLING=false` оставляет только отправку. Адрес Bot API задаёт
     `TELEGRAM_API_URL`: для тестов с поддельным сервером или для локального Bot API.
   - Вебхук можно добавить позже как второй вход, не меняя обработчиков.
4. **Модуль `ai`.**
   - Провайдер за интерфейсом (`modules/ai/providers`):
     - Anthropic через официальный SDK. Структурированный ответ задаётся `output_config.format`
       по zod-схеме, системный промпт кэшируется. Модель по умолчанию — `claude-sonnet-5`,
       переопределяется `AI_MODEL`; `ANTHROPIC_BASE_URL` задаёт шлюз организации или
       поддельный сервер.
     - OpenAI-совместимый сервер (vLLM, Ollama) через `response_format: json_schema` — вариант
       on-prem.
   - Для любой функции ИИ нужна способность `ai.use`.
   - Суточные лимиты на пользователя: `AI_DAILY_REQUESTS` и `AI_DAILY_TOKENS`, счётчики в
     Redis, сутки считаются по поясу установки. Запрос резервируется до вызова провайдера.
   - Каждое обращение пишется в аудит `ai.request`: функция, провайдер, модель, исход, токены,
     длительность, вопрос и ответ модели (план). Строки данных и результат в аудит не
     попадают.
   - Без провайдера `GET /ai/status` отвечает `enabled: false`, а функции скрыты в интерфейсе.
     API отвечает 503 с `data.reason = ai_not_configured`.
   - Остальные ошибки — 429 `ai_limit`, 424 `ai_provider` (подробности только в журнале, ключ
     клиенту не уходит) и 422 `ai_invalid` / `ai_unanswerable`.
   - Промпт — константа в коде с версией, версия записывается в аудит. Файлов
     `prompts/*.md` (13-search-knowledge-ai.md §6) пока нет: бандл api собирает только
     TypeScript.
5. **«Спросить данные» v1 — модель возвращает не QuerySpec, а плоский план.**
   - План: условия через И (одно значение, список, пара или относительный период), разрезы с
     интервалом для дат, меры (`count`, `count_distinct`, `sum`, `avg`, `min`, `max`,
     `median`), сортировка, лимит, тип графика, заголовок, объяснение, признак «ответить
     нельзя» с причиной.
   - Рекурсивный `FilterNode` и выражения недоступны: структурированный вывод провайдеров не
     поддерживает рекурсивные схемы, а план «Исследования» покрывает вопросы v1.
   - Сервер переводит ответ в `ExplorePlan` (новый контракт `data/explore.ts`). Поля — только
     из схемы, видимой пользователю: скрытые и маскированные политикой поля модель не видит.
     Имя такого поля в ответе даёт «нет поля», без подсказки, что оно существует.
   - Типы мер проверяются. Исправимое чинится: интервал у не-даты убирается, сортировка по
     имени поля меры заменяется алиасом, лимит обрезается.
   - Дальше `explorePlanSpec` строит QuerySpec, а QueryService компилирует его с политиками
     строк и столбцов пользователя и выполняет.
   - Ошибка компиляции — ответ модели не годится (422 `ai_invalid` с проблемами); ничего
     невалидного не выполняется.
   - `explorePlanSpec` — одна функция для сервера и конструктора на экране. Поэтому ответ
     ложится в «Исследование» как обычное состояние: фильтры, разрезы, меры и сортировка
     видны и правятся, запрос показывается, а результат сервера попадает в кэш клиента под
     тем же запросом без повторного выполнения.
6. **Что уходит во внешний провайдер (Q7, N6).**
   - Уходят инструкция, вопрос, название и описание датасета и видимые пользователю поля:
     ключ, подпись, тип, семантика, единица, описание и варианты списков (у полей с
     `sensitive` варианты не отправляются). Уходит и сегодняшняя дата.
   - Строки, профили столбцов и результаты не уходят.
   - По умолчанию ИИ выключен. Включить облачного провайдера или свой сервер решает
     администратор установки, и каждое обращение видно в аудите. Политика «что можно
     отправлять» по грифу и пространству остаётся за фазой 5.

## Альтернативы

- **Модель пишет QuerySpec целиком:** нужна рекурсивная схема фильтров и выражений. Её не
  поддерживает структурированный вывод, модель ошибалась бы чаще, а проверять пришлось бы
  больше.
- **Модель пишет SQL:** отдельный путь с парсером и ролью `kchs_query` есть в SQL-лаборатории,
  но ответ нельзя положить в конструктор для ручной правки. Кроме того, для него нужна
  способность `data.sql`.
- **Вебхук Telegram:** нужен публичный HTTPS, которого на типичной установке нет.
- **Отдельное задание очереди на каждое сообщение Telegram:** даёт повторы, но запись задания
  на каждое уведомление дороже самой отправки. Сейчас доставка идёт сразу, как письмо
  «немедленно», а ошибки попадают в журнал.
- **Схема с примерами значений из профиля столбцов:** точнее фильтры по тексту, но профиль
  считается без политики строк и раскрыл бы значения чужих строк.

## Последствия

- Для шага Telegram в сценарии №6 уведомление о поручении должно идти в категории `inbox`
  (или `mention`): тогда оно уйдёт в Telegram без настройки. Для категории `tasks` канал
  включается в профиле. Кнопок действий в сообщениях пока нет: принять можно по ссылке в
  вебе.
- Интеграционные тесты используют поддельные Bot API и провайдера (Anthropic и
  OpenAI-совместимый). Настоящие Telegram и модели не вызываются.
- Контракты: `data/explore.ts`, `data/ask.ts`, `ai`, `integrations/telegram.ts`, поле
  `NotificationPreferences.defaults`, события `user.telegram_linked` и
  `user.telegram_unlinked`.
- Позже:
  - повторная доставка в Telegram;
  - кнопки действий (реестр обработчиков в модуле `telegram`);
  - вебхук;
  - промпты в файлах с golden-тестами на модели;
  - политика данных для внешнего провайдера по грифу и пространству.
