# 0085. Печатные формы и штампы — реестр форм с HTML api и рендером движка, шаблоны DOCX в песочнице, водяной знак на копии, сравнение версий по словам

Статус: Принято
Дата: 2026-09-20

## Контекст

Вторая волна фазы 3 (P3-E02 S03 — штампы и печатные формы, S08 — шаблоны DOCX, §13 — водяные
знаки, §8 — сравнение версий). ADR-0080 оставил у типа документа только ключи `printForms` и
отложил штампы, печатные формы, водяные знаки и шаблоны. `08-documents.md` требует:

- печатные формы — регистрационная карточка, штамп, лист согласования, лист ознакомления,
  реестр отправки — «HTML-шаблоны → PDF (Playwright)» (§5, ADR-0022); листы согласования,
  подписи и ознакомления, опись дела делают параллельные ветки — им нужен общий шов;
- штамп регистрации на PDF-представлении (§5);
- шаблоны DOCX с плейсхолдерами (`{{doc.subject}}`, `{{doc.fields.addressee}}`,
  `{{author.position}}`, таблицы и циклы docxtpl), «Создать по шаблону» (§8);
- водяные знаки на вложениях конфиденциальных документов при просмотре, экспорт — с аудитом
  (§13, «Водяные знаки — не реализованы», ADR-0080);
- сравнение версий: текстовый diff и визуальное — PDF рядом (§8).

Открытые вопросы: где собирается HTML формы и кто проверяет права; куда кладётся штампованный
PDF; кто ведёт шаблоны; чем исполнять шаблон, который пишет не разработчик; как выдавать
исходник файла с грифом.

## Решение

1. **Реестр печатных форм — шов для всех модулей.** Форма — `PrintFormDefinition`
   (`modules/documents/domain/print/registry.ts`): ключ, подпись (ключ словаря), тип объекта
   (`document`, `journal`, в будущем `case`), параметры (`period`), `unavailable(subject)` —
   причина недоступности, и `build(pc, subject, params)` — сборка с правами того, кто печатает
   (`pc.ctx`, язык, пояс, название организации `brand.name`). Результат сборки — страница
   (`kind: 'html'`) или наложение на PDF (`kind: 'overlay'`). Разметка собирается только
   шаблонной строкой `html` (`print/html.ts`): каждая подстановка экранируется, как есть
   вставляются лишь фрагменты, собранные той же `html`.

   **Как добавить форму** (лист согласования, лист ознакомления, опись дела):
   1. описать `PrintFormDefinition` — данные читать с правами `pc.ctx`, разметку собирать
      через `html`/`multiline` (`DocumentsPrint` из `modules/documents/public.ts` для
      других модулей);
   2. зарегистрировать при старте модуля: `DocumentsPrint.register(форма)` (встроенные —
      `registerBuiltinPrintForms` в `print/forms/index.ts`);
   3. документу форма видна, если её ключ есть в `printForms` его типа (`typeListed: false` —
      всем документам); журналу и другим объектам — всегда; подпись — ключ словаря
      `documents.print.forms.<ключ>`.

   Встроенные формы: регистрационно-контрольная карточка (реквизиты, корреспондент, поля типа,
   участники, срок, контроль, поля резолюции и отметки об исполнении), PDF со штампом
   регистрации, реестр отправки журнала за период (строки — только видимые печатающему:
   права и допуск через `visibleObjectsSql`; аннулированные — нет; до 2000 строк, период — до
   года).

2. **Рендер — строка `document_renders` и задание движка.** Заказ (`POST /documents/prints`)
   проверяет `authorize(view)`, форму и параметры, кладёт строку (`print | fill | inspect |
   watermark`, статус `queued → running → ready | failed`) и задание `render:document.render`
   с одним `renderId` — в той же транзакции, событие `document.render_queued`. Движок берёт
   план у api (`POST /internal/documents/renders/{id}/start`, сервисный токен): api
   пересобирает контекст заказчика и снова проверяет доступ — права и допуск действуют **на
   момент рендера**, а не заказа; нет доступа, объект удалён, форма стала недоступной — рендер
   `failed`, движок ничего не делает. Результат (`…/done`) принимается только для
   `running`-рендера и только под ключом, который api выдало в плане (ключ в отчёте движка не
   читается). Файл печати — объект `file` под заранее выданными идентификаторами,
   прикреплённый к объекту (`registerGeneratedFile`): доступ и гриф — объекта, как у
   PDF-представления версии (ADR-0080). Печать объекта с грифом от «конфиденциально» — аудит
   `document.printed`. Повторное нажатие «Печать» в течение двух минут, пока рендер идёт,
   возвращает тот же рендер. Окончательный сбой задания (`job.failed`) переводит рендер в
   `failed`.

3. **Штамп регистрации — копия, а не правка версии.** Штамп накладывается на копию
   PDF-представления текущей версии и сохраняется отдельным файлом, прикреплённым к
   документу; версия, её PDF и SHA-256 не меняются. Причина: хэш версии фиксирует то, что
   согласовали и подписали (§9); новое «представление» версии подменило бы подписанное
   содержимое, а новая версия ради штампа засорила бы историю. Штамп ставится сам: подписчик
   `documents-stamp` на `document.registered` и `document.version_pdf_ready` (PDF ещё строился в
   момент регистрации) — для типов с `registration_stamp` в `printForms`; ключ идемпотентности
   `stamp:<документ>:<версия>:<номер>` — один штамп на регистрацию и версию. Место — правый
   нижний угол первого листа (ГОСТ Р 7.0.97, реквизит «отметка о поступлении»): организация,
   «Вх. № …», дата.

4. **Движок: HTML в PDF и наложение.** Страница формы печатается Chromium (Playwright,
   ADR-0022) без скриптов и с закрытой сетью (все запросы страницы отклоняются), A4 с
   колонтитулом «организация · напечатал …, дата» и «Лист N из M». Наложение (штамп, водяной
   знак) — страница с прозрачным фоном, напечатанная под размер каждого листа (поворот листа
   переносится в содержимое, одна печать на каждый размер), pypdf накладывает её на копию PDF;
   не-PDF (офисный файл, скан) сначала переводится в PDF, как PDF-представление версии.
   Страниц печати одновременно — не больше, чем у рендера отчётов (общий семафор).
   Зашифрованный или битый PDF, ошибка шаблона — рендер `failed` с причиной, без повторов.

5. **Шаблоны DOCX — объект реестра `template`, справочник.** Тип объекта `template` и таблица
   `templates` (модель данных, 05-data-model.md): вид `docx`, тип документа (или любой),
   файл — вложение шаблона, карточка по умолчанию, найденные и неизвестные плейсхолдеры,
   состояние разбора. Лежат в системном пространстве `documents`, видны всем сотрудникам
   (`everyone: view`), ведут владельцы `documents.journals.manage` (политика типа `manage`) —
   как типы документов и журналы: шаблон — часть справочника документооборота, отдельная
   способность дала бы ещё одну роль без отдельной ответственности. Загрузка файла
   (`POST /document-templates/{id}/file`) ставит разбор: движок возвращает пути
   плейсхолдеров — самые длинные цепочки атрибутов от корня контекста, без переменных
   циклов и присваиваний; api делит их на известные (`templatePlaceholders()` и поля
   карточки типа) и неизвестные — автор видит их до первого использования. Пока шаблон не
   разобран, в «Создать по шаблону» он не предлагается.

   **Заполнение.** Контекст собирает api с правами заказчика: `doc.*` (реквизиты, корреспондент,
   `doc.fields.<ключ>` — значения, отформатированные по полю), `author`/`signer`/`responsible`/
   `controller` (`name`, `short_name` «Фамилия И. О.», `position`, `unit`, `email`, `phone`),
   `doc.attachments[]`, `org.name`, `today` — готовые строки на языке заказчика. Движок
   исполняет шаблон docxtpl в **песочнице Jinja** (`SandboxedEnvironment`, автоэкранирование XML,
   неизвестный путь — пустая строка): шаблон пишет администратор справочника, но из шаблона
   нельзя добраться до объектов Python. «Создать по шаблону» (`POST /documents/from-template`)
   создаёт черновик с карточкой шаблона и введённой (в одной транзакции со строкой рендера);
   файл, построенный движком, становится вложением документа и **версией** (`DocumentVersionService.add`
   системным контекстом), дальше — обычное PDF-представление. Перезаполнение из текущей карточки
   (`POST /documents/{id}/fill`) — новая версия. Стартовый бланк исходящего письма (ГОСТ
   Р 7.0.97: поля, Times New Roman 14, реквизиты «Исп.») собирается из XML в коде
   (`starter-template.ts`) и заводится `DocumentsSeed.ensureStarterSet` (`kchs init`, сид)
   идемпотентно по названию; его плейсхолдеры известны заранее — разбор движком не нужен.

6. **Водяной знак — у ядра файлов, копия — у документов.** Файл, действующий гриф которого
   (свой или объектов, к которым он прикреплён, ADR-0080) не ниже «конфиденциально»:
   - превью (`GET /files/{id}/previews`) несут строки знака — гриф, имя смотрящего, время в
     его поясе; просмотрщики рисуют их поверх страниц;
   - исходник (`GET /files/{id}/download`) отдаётся только в режиме администратора — аудит
     `file.downloaded` с уровнем `warning` и признаком `original`; остальным — `403` с
     `data.reason: watermark_required`;
   - копия (`POST /documents/watermarked`) — рендер `watermark`: движок печатает строки знака
     плиткой по диагонали на каждом листе PDF-копии (не-PDF — через перевод в PDF) и кладёт
     её во временный бакет выгрузок (`documents/watermarks/<рендер>/copy.pdf`, не объект
     реестра); ссылку получает только заказчик, пока он видит файл. Заказ — аудит
     `document.file_exported`.

   Знак на просмотре — оверлей клиента, а не перерисованные превью: превью общие для всех
   смотрящих, персональный растр на каждого смотрящего размножил бы хранилище. Защита от снимка
   экрана не цель; цель — установить источник утечки распечатки или файла.

7. **Сравнение версий.** `GET /documents/{id}/versions/compare?from&to`: текст основного файла
   версии (или её PDF-представления), извлечённый движком при обработке файла; сравнение по
   словам (Майерс с отбрасыванием общих начала и конца, предел 2000 правок — дальше середина
   целиком «удалено/добавлено», текст — до 300 тыс. символов); соседние правки через пробел
   сливаются. `pending` — текст ещё извлекается, `unavailable` — у версии нет текста.
   Визуальное сравнение — PDF-представления двух версий рядом в клиенте.

8. **События и интерфейс.** `document.render_queued`, `document.render_finished` (объект —
   документ, журнал, шаблон или файл), `template.created`, `template.updated`; домен
   `template` — в потоках событий. Клиент: меню «Печать» в карточке документа и в журнале
   (форма с периодом — диалог), ожидание движка, готовый PDF открывается вкладкой; справочник
   «Шаблоны документов»; «Создать» — с выбором шаблона типа; во вкладке «Файлы и версии» —
   «Печатные формы и шаблоны», «По шаблону», «Сравнить».

## Альтернативы

- **Страница печати веба, как у отчётов (ADR-0078).** Отклонено для форм: отчёту нужны графики
  и карты, которые рисует браузер; форме — только текст и таблицы. HTML в api проще проверить
  тестом (экранирование, права, состав строк) и не требует служебного токена страницы.
- **Штамп — новое PDF-представление версии.** Отклонено: меняет содержимое, которое фиксирует
  хэш версии и подпись (п. 3).
- **Шаблоны — `jinja2.Environment` без песочницы.** Отклонено: выражение шаблона
  (`''.__class__.__mro__…`) исполнило бы произвольный Python в движке.
- **Отдельная способность «Шаблоны документов».** Отклонено: те же люди ведут типы и журналы
  (п. 5); при необходимости отделить — способность добавляется без изменения данных.
- **Водяной знак — персональные растровые превью.** Отклонено: хранилище × число смотрящих, а
  кэш превью перестал бы быть общим (п. 6).
- **Копия со знаком — объект `file`.** Отклонено: копия персональна и временна; объект реестра
  с грифом документа появился бы в списках и поиске у других.

## Последствия

- Миграция `documents_print_templates`: `templates`, `document_renders`.
- Образ движка: зависимость `pypdf` (группа `render`), обработчик `render:document.render`;
  контракт `document_render.json`. К релизу — пересобрать `kchs/engine`.
- `LinkService.attachments` принимает исполнителя транзакции (видит несохранённые связи).
- Ветки второй волны добавляют формы регистрацией (п. 1): листы согласования и подписи — с
  маршрутом (R), лист ознакомления — с ознакомлением (E), опись дела — с делами (A); ключи
  `approval_sheet`, `acknowledgment_sheet` уже есть в `printForms` стартовых типов.
- Не сделано: редактирование в ONLYOFFICE (§8), штамп исходящего и «Вх.» на бумажном
  оригинале (печать штампа отдельно от PDF), шаблоны с картинками и подписью, объединение
  нескольких форм в один PDF, регистрационная карточка из списка документов пачкой.
- Вопросы владельцу: N18 (реквизиты и место штампа регистрации), N19 (кто может скачать
  исходник файла с грифом).
