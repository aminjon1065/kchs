# 0051. Строки датасета: чтение через компилятор, правка с версией строки

Статус: Принято
Дата: 2026-09-18

## Контекст

Таблица датасета (`06-analytics-engine.md` §3) читает строки с серверными сортировкой,
фильтрами и поиском «через QuerySpec», а политики строк и столбцов действуют для всех путей
к данным (`03-access-model.md`). Бэклог P1-E01 S03 требует правку строк с историей и
оптимистичной блокировкой: конфликт `_ver` — 409 с разницей. Кэш результатов запросов
(`05-data-model.md`) инвалидируется по версиям датасетов. Открытыми оставались: как
версия датасета отражает правки строк, как правка уживается с политикой строк и как
клиент получает состояние строки при конфликте.

## Решение

1. **Чтение — только через компилятор** `packages/query` в режиме таблицы (`rowMeta`: `_id` и
   `_ver` первыми): `POST /datasets/{id}/rows/query` строит QuerySpec из фильтра, быстрого
   поиска (`contains` по видимым текстовым полям через OR), сортировки с `_id` в конце для
   стабильных страниц и `limit/offset`. Строка по идентификатору — тот же путь с фильтром по
   `_id`. Выполнение — `QueryService`: роль `kchs_query`, транзакция только для чтения,
   `statement_timeout` через `set_config`, кэш Redis по ключу компилятора и версиям схемы.
2. **Правка** (`POST /rows`, `PATCH /rows/{rowId}`, `POST /rows/delete`) — роль приложения, в
   одной транзакции: строки таблицы, история `ds.h_*` (что стало и что было), версия датасета
   с происхождением `edit`, событие `dataset.rows_changed`. Каждая операция правки — новая
   версия: так кэш результатов инвалидируется без отдельного счётчика. Объединение подряд
   идущих правок в одну версию отложено до экрана версий.
3. **Оптимистичная блокировка.** Правка передаёт `ver`, который видел пользователь. Если
   строку уже изменили — 409, в `data` ответа текущая строка и поля, изменённые после его
   версии (по истории; без истории — поля правки, расходящиеся с текущими значениями).
   Правка без фактических изменений версию строки не меняет.
4. **Правка при политике строк не выполняется** (403): вставка или правка могли бы создать
   или изменить строки, которых пользователь не видит, а проверка политики над значениями
   новой строки требует отдельного механизма. Маскируемые и скрытые поля не правятся;
   история строки — только тем, кто видит все строки и столбцы (в ней прежние значения).
5. **Удаление** при включённой истории — мягкое (`_deleted_at`), иначе окончательное.
6. **Данные ошибки для клиента.** `ProblemDetails` получает необязательное поле `data`
   (состояние строки при конфликте, проблемы запроса с позицией в выражении); `AppError`
   отдаёт его из отдельного поля `data`, а `details` остаются только в журнале.

## Альтернативы

- Отдельный счётчик ревизий данных для ключа кэша и версии «сеансами правки» — ещё один
  столбец и правила объединения, пока экрана версий с объединением нет.
- Проверка политики строк над новыми значениями через встроенный источник компилятора —
  отложена до форм сбора данных (фаза 3), где правка по политике нужна.

## Последствия

- Список версий растёт с каждой правкой; экран версий будет группировать правки подряд.
- Правка строк управляющим датасета под политикой строк не ограничивается (уровень `manage`
  видит все строки).
