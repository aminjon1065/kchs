# 0132. Ленты по адресу и исходящий прокси: источник вида `feed`, запись строк по ключу, один исходящий клиент

Статус: Принято
Дата: 2026-09-24

## Контекст

Пакет «Чрезвычайные ситуации» (P5-E08, `01-product/04-domain-pack-emergency.md`)
и компонент «Мониторинг опасных явлений и агрегация предупреждений» концепт-ноты
КЧСиГО требуют: сообщения мировых служб — GDACS, USGS, EMSC, NASA FIRMS —
сами попадают на карту и в ленту дежурной смены, привязываются к району по
координатам, правило уведомляет назначенных, дежурный фиксирует решение, всё
остаётся в архиве. Ответы владельца (24.09.2026, `05-risks-and-open-questions.md`
§5): ленты входят в пакет уже для демонстрации; у серверов Комитета есть
**исходящий доступ в интернет только через прокси** (A6).

К этому моменту в платформе были источники внешних БД (ADR-0107: объект
`source`, запись через staging снимком или по ключу), ГИС-службы (ADR-0108)
и ICS-подписки (ADR-0081) со своими клиентами исходящих запросов на
`node:http` и проверкой адреса, но без прокси. Ленты по URL (REST/JSON) в
`06-analytics-engine.md` §2 значились «позже».

Открытые развилки:

1. Модуль ЧС со своими сущностями или платформенный источник данных, который
   пакет только настраивает.
2. Как писать записи ленты: staging-загрузкой, как у внешней БД, или правкой
   строк.
3. Как не затирать решение дежурного, когда служба уточняет событие (USGS
   пересчитывает магнитуду).
4. Как привязать запись к району и отбросить чужие страны.
5. Где хранить ключ API (у FIRMS он бывает нужен) и как не показать его в
   настройке, ответах и ошибках.
6. Как ходить наружу через прокси, не открыв ход во внутреннюю сеть.

## Решение

### Лента — вид источника `feed`, а не модуль предметной области

Платформа предметно-нейтральна: лента — **вид источника `feed`** (объект
`source`, ADR-0107) с настройкой `feed`: адрес, формат (`geojson`, `csv`,
`json` с путём к массиву), область отбора (`bbox`), «только внутри территорий»,
сопоставление полей, геометрия, поле района, ключ, предел записей. Пакет ЧС
заводит четыре ленты в один датасет «Сообщения об опасных явлениях» с полем
«Источник» константой. Прогоны, статусы, «Опросить сейчас», расписание,
журнал и `source.synced` — общие с источниками БД. Интеграция у ленты
необязательна: `sources.integration_id` без NOT NULL, а CHECK требует его только
у вида `database`.

### Сопоставление — путь, константа, шаблон, дата+время

Значение поля датасета берётся по пути в записи (`properties.mag`,
`geometry.coordinates.1`, у CSV — имя столбца), постоянным значением, шаблоном
из нескольких полей (`{latitude}_{longitude}_{acq_date}_{acq_time}_{satellite}` —
ключ FIRMS, у которого нет идентификатора) или датой и временем из двух полей
(FIRMS: `acq_date` + `acq_time` HHMM). Приведение по умолчанию — по типу поля:
время из ISO или числа эпохи, **ISO без пояса — всемирное время** (GDACS),
двумерная геометрия (глубину очага USGS и EMSC отбрасываем: столбец геометрии
датасета двумерный). Явные `epoch_ms`/`epoch_s`, `number`, `text` — для
неоднозначных случаев. Разбор — чистые функции (`feed-parse.ts`), проверены на
живых ответах четырёх служб.

### Запись — правкой строк по ключу, только своих полей

Лента даёт десятки или сотни записей за опрос, поэтому пишет **через
`RowService`, а не staging**: история строк, версия датасета, события
(`dataset.rows_changed` и события строк `dataset.row_*` при настройке
`rowEvents`) — как у ручной правки, и правила автоматизации видят новые
сообщения. Порядок опроса:

1. запрос и разбор; область отбора и геометрия — до сопоставления;
2. район по границе (для поля района и «только внутри территорий»);
3. значения проверяются схемой поля; запись с плохим значением или без ключа
   пропускается с причиной в журнале прогона, остальные пишутся;
4. строки ищутся по ключу — **вместе с удалёнными**: удалённую вручную строку
   лента заново не заводит;
5. новые — одной вставкой, у знакомых — только поля ленты и **только
   изменившиеся** (время сравнивается моментом, числа — числом, геометрия —
   с округлением хранения): повторный опрос без изменений не даёт ни версий, ни
   событий;
6. поля, которых нет в сопоставлении (статус, решение дежурного), лента не
   трогает; начальное значение им даёт значение по умолчанию поля датасета.

Строка, которую дежурный правит в этот момент, пропускается и обновится
следующим опросом (конфликт версии). Пишет запустивший — по расписанию владелец
источника, как у источников БД; права — как у правки строк (`edit`, датасет
правится, без политики строк). `_import_id` строки — идентификатор ленты:
счётчик «строк ленты» в общем датасете считается по нему.

### Район — по границе, одним запросом

`TerritoryLocator.locate` в публичном API модуля ГИС: пачка геометрий → единица
уровня `district`, границе которой принадлежит точка на поверхности
(`ST_PointOnSurface`, `ST_Covers`, как обратный геокодер ADR-0067); одноимённое
наложение решается меньшим кодом. «Только внутри территорий» отбрасывает
записи без района — события соседних стран.

### Ключ API — у интеграции HTTP

Адрес и заголовки ленты ссылаются на секрет: `{secret:mapKey}`. Подставляет его
модуль интеграций (`HttpIntegration.get`) прямо перед запросом; в настройке
источника, ответах API и сообщениях об ошибке ключа нет. Ссылка без интеграции
отклоняется при сохранении.

### Один исходящий клиент с прокси

`shared/net/outbound.ts` (undici) — единственный путь запросов по адресу,
который задают люди: ленты, растровые подложки и ГИС-службы (переведены с
`node:http`), ICS-подписки (переведены).

- Напрямую — адрес проверяется **после разрешения имени, в момент соединения**:
  служебные сети (loopback, link-local, multicast, «этот узел») закрыты всегда,
  частные — по политике вызова (подписки ICS их закрывают, ленты и подложки —
  нет: серверы закрытого контура обычно в них).
- Через прокси `HTTP_PROXY`/`HTTPS_PROXY` (`HTTPS_PROXY` без значения берёт
  `HTTP_PROXY`) имя разрешает прокси, поэтому закрыты адреса-литералы служебных
  сетей и `localhost`. `NO_PROXY` — по правилам undici (имя точно, `.домен` —
  поддомены, `*` — никогда, порт по желанию); **службы установки** (api,
  хранилище, поиск, движок, офисный сервер, медиасервер) идут мимо прокси сами.
- Адрес http через прокси — обычным запросом, https — туннелем CONNECT: Squid и
  подобные туннели на порт 80 обычно не пускают.
- Перенаправления — по разрешению вызова, каждый шаг проверяется заново; ответ
  ограничен временем, размером и типом; в сообщении об ошибке нет адреса.
- Глобальный `fetch` процесса (вебхуки, провайдеры ИИ, проверка интеграций) при
  заданном прокси тоже идёт через него (`setGlobalDispatcher` при старте).
- `OUTBOUND_ALLOW_LOOPBACK` — только для локальной отладки (лента с машины
  разработчика); в тестовой среде loopback открыт, как и раньше.

Маршрутизатор написан поверх стабильных `Agent` и `ProxyAgent`:
`EnvHttpProxyAgent` undici помечен экспериментальным и пишет предупреждение при
каждом старте. Зависимость `undici` закреплена на 6.x — той же ветке, что
встроена в Node 22: глобальный `fetch` принимает диспетчер той же версии.

## Альтернативы

- **Модуль «Опасные явления» со своей сущностью сообщения.** Отклонено: второй
  путь данных рядом с датасетами — без карты, дашбордов, показателей, политик и
  правил, которые у датасета есть; пакет ЧС реализуется конфигурацией
  (`04-domain-pack-emergency.md` §Принцип).
- **Staging-загрузка, как у внешней БД.** Отклонено: снимок затёр бы решение
  дежурного, `upsert` по ключу меняет строку целиком, а загрузка не пишет
  истории строк и событий строк — правило не узнало бы о новом землетрясении.
- **Ключ API в адресе источника.** Отклонено: адрес виден в настройке, журнале
  прогонов и ошибках; секреты платформы живут в интеграциях (ADR-0097).
- **`HTTPS_PROXY` через переменную окружения Node (`NODE_USE_ENV_PROXY`).**
  Отклонено: ветка Node установки его не гарантирует, и прокси действовал бы на
  все запросы процесса, включая внутренние службы, без проверки адреса.
- **Проверка адреса до запроса (разрешить имя и сравнить).** Отклонено для
  прямых соединений: подмена DNS между проверкой и соединением её обходит;
  проверка в момент соединения — та же, что у прокси подложек (ADR-0066).

## Последствия

- Миграция `feed-sources`: `sources.integration_id` допускает NULL, CHECK
  `sources_integration_check` требует интеграцию у вида `database`.
- Контракт `SourceRecord`: `integrationId` и `query` — nullable, новое поле
  `feed`; `SourceUpdateInput` принимает `feed` и `integrationId` (только у ленты).
  Маршруты `POST /sources/feeds` и `POST /sources/feed/preview` (способность
  `data.sources.manage`). Событие `source.created` допускает `integrationId: null`.
- Новые переменные окружения: `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`,
  `OUTBOUND_ALLOW_LOOPBACK` (compose `x-app-env`, `.env.example`; в Helm адреса
  прокси — ключами Secret, в них бывают логин и пароль; `NO_PROXY` —
  `app.outbound.noProxy`).
- Сообщения об ошибках растрового прокси, ГИС-служб и ICS-подписок стали общими:
  «Нет соединения: …», «Адрес закрыт для исходящих запросов: …» — без рода
  прилагательного, который раньше не сходился с названием службы.
- Ограничения: ленты RSS/GeoRSS и CAP (XML) не разбираются — GDACS отдаёт тот же
  набор GeoJSON-API, остальные службы — GeoJSON и CSV; разбор XML — когда
  понадобится национальная служба с одним XML. Клиенты вне общего — драйверы
  внешних БД (ADR-0107: соединение с проверенным адресом), SMTP, IMAP, Telegram
  (grammy на своём `node-fetch`), web-push — ходят мимо прокси: это протоколы не
  HTTP или своя библиотека со своим агентом. Боту и web-push прокси можно дать их
  собственным параметром агента — отдельной правкой, когда установке без прямого
  выхода понадобится Telegram.
- Удаление ленты оставляет строки в датасете: это данные, а не кэш ленты.
