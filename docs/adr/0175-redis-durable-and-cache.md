# 0175. Redis — долговечный и кэш; путь запроса падает быстро

Статус: Принято
Дата: 2026-10-05

## Контекст

Один Redis с `noeviction` и пределом 1 ГБ держал очереди BullMQ, потоки событий и outbox вместе
с кэшами: тайлы (24 ч, без предела по объёму), результаты запросов, геосводки, наборы прав.
`noeviction` для очередей обязателен (ADR-0014, ADR-0015): вытеснение потеряло бы задания. Но
тогда заполненный кэш доходит до предела, Redis отказывает в записи — и встают очереди, outbox
и realtime, то есть вся платформа (находка 6 разбора, `04-delivery/07-architecture-hardening.md`).

Вдобавок у всех клиентов было `maxRetriesPerRequest: null`: при сбое Redis команды ждали
переподключения вечно, и запросы api зависали (каждый запрос читает версию прав в Redis), а не
падали быстро.

## Решение

**Два экземпляра.**
- Долговечный Redis (`REDIS_URL`, `noeviction`, AOF) — то, что нельзя потерять или пересчитать.
- Кэш (`REDIS_CACHE_URL`, `allkeys-lru`, без RDB и AOF) — то, что можно пересчитать. У предела
  он вытесняет давно не читанное и ничего не останавливает.
- Без `REDIS_CACHE_URL` кэш живёт в основном Redis: разработка и тесты не меняются.

В установке (`infra/compose`) служба `redis-cache` запущена всегда, как и основной Redis.
api и worker в контейнерах получают её адрес через `x-app-env`. Пароль — `REDIS_CACHE_PASSWORD`;
если его нет, берётся пароль основного Redis, поэтому прежние `.env` стенда показа работают.
В чарте: `redisCache.embedded` (Deployment без тома) или `redisCache.host`, ключ секрета
`REDIS_CACHE_PASSWORD`. Движку кэш не передаётся — он им не пользуется.

**Классификация ключей.**

| Ключ | Где | Почему |
|---|---|---|
| `bull:*` — очереди BullMQ | долговечный | задания нельзя терять |
| `events:*`, `events:dlq`, группы потребителей, `events:groups:initialized` | долговечный | шина событий (ADR-0171) |
| каналы `rt:relay`, `rt:job`, `rt:collab`, адаптер Socket.IO | долговечный | pub/sub; памяти не занимает |
| `kchs:job:cancel:*` | долговечный | флаг отмены — его читает и движок (ADR-0172) |
| `kchs:share:grant:*` | долговечный | доступ гостя: вытеснение оборвало бы просмотр |
| `kchs:print:grant:*`, `kchs:print:scope:*` | долговечный | токен рендера печатной формы (ADR-0078) |
| `kchs:users-import:*:credentials` | долговечный | одноразовые пароли до выгрузки (ADR-0041) |
| `kchs:telegram:poller` | долговечный | лидерство опроса: потеря — два опрашивающих |
| `kchs:telegram:link:*`, `kchs:telegram:pending:*`, `kchs:meeting:knocks:*` | долговечный | состояние сценария пользователя, а не кэш |
| `kchs:rl:*`, `kchs-rl:*` (плагин частоты) | долговечный | защита от подбора: вытеснение сбросило бы счётчик |
| `kchs:ai:usage:*` | долговечный | квота ИИ за сутки |
| `kchs:principals:version`, `kchs:territories:version` | долговечный | отметки версий кэшей — ниже |
| `kchs:principals:<user>` — набор принципалов | кэш | пересчитывается, сверяется с версией |
| `kchs:inbox:counts:*` | кэш | пересчитываются из базы, живут 60 с |
| `kchs:presence:*` | кэш | присутствие; пропажа — «никто не смотрит» до следующей отметки |
| `kchs:tile:*`, `kchs:gis:territory-tile:*`, `kchs:service-layer:*` | кэш | тайлы и объекты служб |
| `kchs:query:*` | кэш | результаты запросов; ключ включает версии источников |
| `kchs:layer-stats:*`, `kchs:geo:*`, `kchs:data:profile:*` | кэш | сводки слоёв, геометрии, профили полей |
| `kchs:job:<id>` — последний прогресс задания | кэш | запись без читателя; кандидат на удаление |

Кэш читается и пишется только через `cache` (`shared/redis`). Его сбой — промах: чтение
возвращает пустоту, запись пропускается, предупреждение в журнал не чаще раза в минуту.
Неиспользуемые ключи `sessionTouch` и `objectSummary` удалены из `cacheKeys`.

**Отметки версий.** Версия наборов принципалов была счётчиком: пропавший ключ читался как `1`,
а `INCR` после потери снова давал `1`. Набор прав, посчитанный до изменения членства, совпал бы
по версии — устаревшие права. Теперь версия — случайное число в долговечном Redis:
- пропавшая версия заменяется новой случайной (`SET NX`);
- смена версии — новое случайное значение.

Ни один набор, посчитанный до потери или до смены, с новой версией не совпадёт. Версия
справочника территорий — та же схема: прежде пропавшая метка читалась как общая `none`, и
тайлы границ из отдельного кэша могли вернуться прежними. Если удалить набор одного
пользователя из кэша не удалось (кэш недоступен), меняется общая версия: устаревший набор не
доживёт до возвращения кэша.

**Быстрая ошибка.**
- Основной клиент и публикация outbox: `maxRetriesPerRequest: 2`, `commandTimeout: 5 с`.
- Кэш: `enableOfflineQueue: false`, `commandTimeout: 1 с`.
- BullMQ, блокирующие чтения потоков и подписки — по-прежнему `maxRetriesPerRequest: null`,
  без тайм-аута (этого требует BullMQ; блокирующее чтение тайм-аут бы обрывал).

Недоступный основной Redis даёт `503 service_unavailable` с `Retry-After: 5`, а не зависший
запрос.

**Наблюдаемость.** Экспортёр кэша и задание `redis-cache` в Prometheus. Правила основного Redis
ограничены `job="redis"`: полная память кэша — норма, и тревоги «очереди стоят» она не
поднимает. Свои правила кэша:
- `KchsRedisCacheDown` — кэш не отвечает, платформа медленнее;
- `KchsRedisCacheUnbounded` — у кэша нет предела памяти;
- `KchsRedisCacheThrashing` — вытесняет больше 200 ключей в секунду, мал для рабочего набора.

«Здоровье системы» показывает кэш отдельной строкой, если он свой.

## Альтернативы

- **Один Redis с `volatile-lru` и TTL у кэшей.** Вытеснение затронуло бы и долговечные ключи с
  TTL — гостевые доступы, флаги отмены, пароли импорта. Очереди и потоки без TTL упирались бы в
  предел так же.
- **Логические базы одного Redis (`SELECT n`).** Память и политика вытеснения у экземпляра
  общие: кэш в своей базе всё равно останавливал бы очереди.
- **Кэш тайлов и запросов в Postgres или на диске api.** Та же нагрузка на основную базу или
  кэш на каждой реплике api отдельно. Redis-кэш общий для реплик и уже знаком эксплуатации.

## Последствия

- Принцип «один Redis» (`00-start-here.md` §6) уточнён: один долговечный Redis и кэш рядом.
  Сервер S1 держит ещё одну небольшую службу (512 МБ по умолчанию).
- После перезапуска кэша платформа первые минуты медленнее: тайлы и запросы считаются заново.
- Новый ключ Redis относят к одной из двух групп: вытесняемое — через `cache`, долговечное —
  через `redis()`. Строку в таблицу выше добавляют вместе с ключом.
- В тестах кэш живёт в той же базе Redis слота. `test/redis-cache.test.ts` проверяет:
  - работу без кэша (адрес без Redis);
  - что кэшевые ключи не попадают в долговечный Redis — проверка ловит регрессию, если вернуть
    запись тайла в `redis()`;
  - отметку версии;
  - строку кэша в «Здоровье системы».
- `src/shared/redis/redis.test.ts` проверяет умолчания соединений, `problem.test.ts` — ответ
  503 при сбое Redis.
