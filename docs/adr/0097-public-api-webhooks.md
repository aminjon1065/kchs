# 0097. Публичный API: токены с областями, вебхуки, интеграции и перенос конфигурации

Статус: Принято
Дата: 2026-09-20

## Контекст

`14-automation-integrations.md` §3–§6 описывает публичный API с токенами
интеграций, исходящие и входящие вебхуки, объект `integration` и перенос
конфигурации между контурами. К фазе 5 из этого было сделано только основание:
пустая таблица `api_tokens`, способность `api_tokens.create`, типы объектов
`integration` и `webhook` в перечне контрактов, `/api/openapi.json`. Ни
аутентификации токеном, ни областей доступа, ни доставки вебхуков, ни
страницы `/api/docs` не было.

Главная трудность — не механика, а безопасность. Токен машины живёт дольше
сессии, его нельзя подтвердить вторым фактором и он легко утекает в чужой
журнал. Значит, он не должен ни расширять прав человека, ни открывать
поверхность, на которой этих прав не спрашивают. Отдельный риск — входящий
вебхук: точка без аутентификации внутри защищённого периметра.

Открытые развилки, которые пришлось закрыть:

1. Как определять требуемую область на каждом из ~470 маршрутов, не
   расставляя её руками (и не забывая при добавлении нового маршрута).
2. Чем показывать документацию API при строгом CSP установки (`script-src
   'self'`, стили только с nonce, который Caddy подставляет лишь в `index.html`).
3. Что делать со встроенными SMTP и Telegram, которые настроены переменными
   окружения и работают с фазы 0/1, — переносить в таблицу интеграций или нет.
4. Как понимать «конфликт» при импорте пакета конфигурации.

## Решение

### Токен — учётные данные, а не объект реестра

Токен хранится как сессия: строка `api_tokens` с хэшем. Объектом реестра он не
становится — у него нет ни обсуждения, ни связей, ни прав, а «сущность вне
реестра» здесь такая же, как `sessions`, `telegram_links` и
`push_subscriptions`. Объектами реестра стали `integration` и `webhook`: у них
есть владелец, права и место в карточке.

Формат токена — `kchs_<16 hex>_<43 символа base64url>`. Первая часть —
видимый префикс: по нему находится строка (индекс, а не перебор), сравнение
идёт по SHA-256 в постоянное время. Префикс показывается в списках и в
аудите — по нему узнают токен, не зная его.

Токен строит контекст своего владельца обычным `buildUserCtx` и дальше
проходит те же `authorize()` и политики строк. Дополнительно:

- режим администратора живёт в сессии браузера и токену не достаётся;
- `x-kchs-on-behalf-of` с токеном не принимается: замещение — право человека;
- незавершённая настройка входа владельца (временный пароль, обязательный
  второй фактор) закрывает токен целиком;
- у токена свой счётчик запросов (`API_TOKEN_RATE_LIMIT_PER_MINUTE` или
  собственный потолок строки);
- CSRF для Bearer не проверяется — он к нему неприменим (17-security.md §5).

### Область доступа выводится из тега маршрута

Ресурс области — первый известный тег маршрута. Теги уже расставлены у всех
маршрутов, попадают в OpenAPI и проверяются тестом, поэтому таблица
«тег → ресурс» одна и не расходится с действительностью; отдельная разметка
маршрутов областями разошлась бы с ними на первом же добавлении.

Правило действия: `GET`/`HEAD` — чтение; `POST` с признаком `readOnly` (тем
самым, которым помечены POST без изменения данных для страницы печати,
ADR-0078) — тоже чтение; остальное — запись. `write:x` включает `read:x`.

Список закрыт по умолчанию: незнакомый тег, отсутствие тега и вывод области,
которой нет в справочнике (`write:search`, `write:jobs`), означают «токенам
недоступно». Новый модуль сам решает, открывать ли свои маршруты, и до этого
решения его API для токенов не существует.

Безусловно закрыты пути `/me`, `/auth`, `/internal`, `/admin`, `/share`,
`/hooks` и теги `auth`, `me`, `internal`, `admin`, `ai`. Токен не меняет
пароль, не входит в режим администратора и не выпускает второй токен.

### `/api/docs` — страница, собранная на сервере

Документацию отдаёт сам api: HTML по текущему OpenAPI, со стилем отдельным
файлом `/api/docs/style.css` того же происхождения и без единого скрипта
(разделы раскрывает `<details>`). Готовые просмотрщики (Swagger UI, Scalar,
Redoc) требуют скрипта и inline-стилей, которых CSP установки не допускает, а
ослаблять CSP ради документации неразумно. Заодно это снимает зависимость и
её обновления.

Спецификация приведена в порядок: описания разделов, обе схемы аутентификации
объявлены по умолчанию, служебные маршруты вне `/api/v1` из неё убраны, а тест
требует у каждой операции тега, краткого описания и ответов.

### Вебхуки

Исходящий вебхук — объект `webhook` с фильтром по типам событий и
пространствам и владельцем `run_as`. Подписчик шины (`webhooks-dispatch`,
подписка `*`) заводит запись доставки и ставит задание; запись уникальна по
паре (вебхук, событие), поэтому повторная обработка события не задваивает
отправку.

Наружу не уходят домены `job`, `webhook` и `token`: первый порождается самой
доставкой и зациклил бы очередь, остальные описывают устройство доставки и
выпуск ключей. События с `visibility.principals` уходят, только если владелец
подписки входит в этот список: подписка не показывает наружу больше, чем видит
её владелец.

Подпись — `x-kchs-signature: sha256=HMAC(секрет, "<x-kchs-timestamp>.<тело>")`.
Отметка времени в подписываемой строке не даёт переиграть старую доставку.
Повторы — 30 с, 1, 5, 15, 30 мин, 1, 2, 6 ч и дальше по 6 ч, пока не истекут
сутки от первой попытки (`WEBHOOK_RETRY_WINDOW_HOURS`). Серия отказов
(`disableAfterFailures`, по умолчанию 20) отключает подписку с событием
`webhook.disabled`. Есть ручной повтор из журнала.

Адрес проверяется до запроса: только `http`/`https`, имя разрешается и не
должно указывать во внутреннюю сеть (loopback, 10/8, 172.16/12, 192.168/16,
169.254/16, CGNAT, ULA, link-local). Перенаправления не выполняются. Иначе
вебхук стал бы способом ходить по внутреннему периметру чужими руками.
`WEBHOOKS_ALLOW_PRIVATE_ADDRESSES=true` снимает запрет на стенде.

Входящий вебхук `POST /api/v1/hooks/{integrationId}/{secret}` только публикует
факт `webhook.received` и ничего не меняет. Это и есть ответ на вопрос «не
обход ли это авторизации»: знание секрета не даёт доступа к данным, а действия
выполняют правила автоматизации от имени своего `run_as`. Неизвестная
интеграция, выключенный вход и неверный секрет отвечают одинаково (404),
секрет сравнивается по хэшу в постоянное время, частота ограничена по
интеграции.

### Интеграции: встроенные остаются в окружении

Объект `integration` держит конфигурацию, зашифрованные секреты (AES-256-GCM
мастер-ключом), статус, журнал синхронизаций и кнопку «Проверить соединение».
Наружу отдаются только имена заданных секретов, но не значения; в событиях и
аудите — только имена изменённых полей.

SMTP и Telegram-бот настроены переменными окружения и работают с фазы 0/1.
Переносить их в таблицу — значит переделывать работающее и заводить второй
источник правды о той же службе. Вместо этого они показываются в общем списке
как `source: 'env'`: только для чтения, с тем же статусом и той же проверкой
связи. Общий учёт получен, работа не сломана.

### Пакет конфигурации

Раздел пакета даёт модуль через реестр ядра (`kernel/config-package`) — так же,
как тип объекта или канал уведомлений; иначе перенос читал бы чужие таблицы.
Реализованы разделы `integrations`, `webhooks` и `processDefinitions`
(маршруты). Секреты в пакет не едут: переносится настройка, а не учётные
данные чужого контура — вместо значений едет список имён, и новая интеграция
приезжает выключенной.

Различие считается по телу записи; «конфликт» — это запись, которую правили
здесь **после** выгрузки пакета (`updatedAt` записи новее `exportedAt`
пакета): именно её импорт затёр бы молча. Конфликт применяется только с
явным `overwriteConflicts`.

Раздел `documentTypes` объявлен в контракте, но поставщика не имеет и в
предпросмотре честно помечается `unsupported`: карточка типа ссылается на
журнал регистрации по UUID, а у журналов стабильного ключа нет (вопрос N42).

## Альтернативы

- **Область доступа отдельным полем маршрута.** Честнее по замыслу, но требует
  разметить ~470 маршрутов и не забывать про новые; расхождение разметки с
  действительностью — это дыра, а не неудобство. Тег уже обязателен и
  проверяется тестом.
- **Готовый просмотрщик OpenAPI.** Отклонён из-за CSP: пришлось бы разрешить
  сторонний скрипт или inline-стили на всей установке.
- **Токен как объект реестра.** Дал бы «поделиться токеном» и обсуждение —
  ровно то, чего у учётных данных быть не должно.
- **Перенос SMTP и Telegram в таблицу интеграций.** Второй источник правды о
  тех же службах и риск сломать работающие уведомления ради единообразия
  списка.
- **Доставка вебхука повторами BullMQ.** Экспоненциальная задержка без потолка
  не укладывается в сутки: либо не добирает, либо сильно перебирает. Свой
  список задержек с проверкой окна нагляднее и предсказуемее.
- **Отдавать в вебхук полный объект.** Противоречит правилу каталога событий
  («идентификаторы и минимальный снимок») и увеличило бы утечку при
  неправильно настроенной подписке. Получатель забирает подробности API
  своим токеном, под своими правами.

## Последствия

- Появился модуль `apps/api/src/modules/integrations` (токены, интеграции,
  вебхуки, пакет конфигурации) и реестр разделов пакета в ядре.
- `Authorization: Bearer` обрабатывается раньше cookie-сессии; новый маршрут
  автоматически недоступен токенам, пока его тег не отображён на ресурс.
- Домены событий пополнились: `token`, `integration`, `webhook`, `config`.
- Новые переменные окружения: `API_TOKEN_RATE_LIMIT_PER_MINUTE`,
  `WEBHOOKS_ALLOW_PRIVATE_ADDRESSES`, `WEBHOOK_RETRY_WINDOW_HOURS`.
- `POST /objects/batch-get` помечен `readOnly`; добавлен
  `POST /datasets/{id}/rows/batch` с ответом `202 + jobId` на большой пачке.
  Задание пачки выполняется правами поставившего (`buildUserCtxFor`), а не
  системы — иначе массовая правка обходила бы политики строк.
- Способность `api_tokens.create` есть только у администратора системы: пока
  она не выдана роли, сотрудник токен не выпустит. Это сознательно строгая
  отправная точка (вопрос N40).
- Журнал доставок чистится заданием обслуживания раз в сутки (30 дней).
