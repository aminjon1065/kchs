# 0089. Встречи: объект реестра с комнатой LiveKit, токены по правам участника, гость по ссылке

Статус: Принято
Дата: 2026-09-20

## Контекст

Фаза 4 (P4-E02 S01–S02, сценарии приёмки №1–4) строит звонки и встречи:
11-communications-meetings.md §3 задаёт личный и групповой звонок из беседы, встречу по
расписанию рядом с событием календаря, клиента комнаты с демонстрацией экрана и комнатой
ожидания, гостей по ссылке, запись через Egress и масштаб «один узел LiveKit на S1». В фазе 0
уже заведены заготовки: сервис `livekit` профиля `media` в compose, переменные
`LIVEKIT_URL`/`LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET`, колонка `events.meeting_id`, способность
`meetings.record`, тип объекта и иконка «Встреча».

Открытыми были вопросы основания, от которого зависят остальные части фазы (клиент комнаты,
звонки из чата, запись, расшифровка, протокол):

- чем встреча является в системе и как участники получают к ней доступ, не ломая правила
  доступа (только `authorize()` и предикаты видимости);
- кто выпускает токен медиасервера и что в него попадает: медиапоток идёт мимо api, поэтому
  права участника в токене — единственная граница;
- где живут встречи (пространство), чтобы роль в пространстве не давала доступ к чужим
  звонкам;
- как встреча связывается с событием календаря и беседой чата, не нарушая границы модулей
  (правило 4: модули не читают чужие таблицы, циклы запрещены);
- что происходит, когда медиасервер не настроен (установка без встреч).

## Решение

1. **Модуль `meetings`, объект `meeting`.** Встреча — объект реестра: организатор — владелец,
   уровни view…owner, действия `view`, `comment` (чат встречи — обсуждение объекта), `join`
   (`comment`), `edit`, `end` и `manage` (ведёт встречу), `share`, `delete`. Таблицы модуля —
   `meetings` (вид `call`/`scheduled`, статус, имя комнаты, ссылки на событие и беседу,
   организатор, плановое и фактическое время) и `meeting_participants` (роль, вход и выход).
2. **Системное пространство «Встречи»** (`space.key = meetings`, как документооборот в
   ADR-0080): роль в пространстве доступа не даёт, объекты — `accessMode: restricted`.
   Видимость — только участием и явными записями ACL.
3. **Права участников — тихими записями ACL ядра** (как поручения, ADR-0060): приглашённый
   получает уровень `comment` на объект встречи. Поэтому встречу одинаково показывают списки,
   поиск, realtime и `authorize()`, а «посторонний» получает 404, а не 403.
4. **Токен комнаты выпускает api** (`POST /meetings/{id}/join`) после `authorize(ctx, 'join')`:
   `identity` — идентификатор пользователя, `name` — его отображаемое имя, грант — только на
   комнату этой встречи (`roomJoin`, `canPublish`, `canSubscribe`, `canPublishData`), право
   записи `roomRecord` — только при способности `meetings.record`. Срок — час; клиент
   запрашивает новый токен при переподключении. Медиасервер проверяет подпись ключом
   установки, поэтому api в медиапотоке не участвует.
5. **Гость по ссылке** получает токен с `identity = guest:<uuid>`, сроком 15 минут и
   метаданными `{meetingId, guest: true}`: комната — единственное, что ему доступно,
   пользователем системы он не становится и в участниках не сохраняется.
6. **Первый вход поднимает встречу** (`planned → live`, событие `meeting.started`), выход
   отмечается в участниках, `end` закрывает встречу для всех (`meeting.ended` с причиной и
   длительностью). Отмена события календаря завершает встречу с причиной `cancelled`.
7. **Границы модулей — только в одну сторону.** Встречу заводит тот, кто ею распоряжается:
   календарь для события (`ensureMeetingForEvent`, `setMeetingParticipants`, `endMeeting`),
   чат для звонка (`startCall`). Модуль встреч не импортирует календарь и чат и не читает их
   таблиц: событие и беседа приходят идентификаторами и хранятся как ссылки без внешнего
   ключа. Обратная ссылка `events.meeting_id` остаётся у календаря.
8. **Без ключей медиасервера встречи выключены**: `GET /meetings/status` отвечает
   `enabled: false`, карточка встречи приходит с `can.join = false`, вход отвечает 503
   `service_unavailable`. Ключи генерирует `generate-secrets.sh`, compose передаёт их и
   медиасерверу (`LIVEKIT_KEYS`), и api с worker.

## Альтернативы

- **Комната на каждый объект без объекта встречи** (звонок — эфемерная комната по имени
  беседы): нет истории, прав, записи и протокола; запись и расшифровка потом некуда положить.
- **Токен выпускает медиасервер по своему списку пользователей**: второй источник правды о
  людях и правах; LiveKit такого и не умеет — токены подписывает приложение.
- **Встречи в пространстве беседы или события**: роль в пространстве давала бы доступ к чужим
  звонкам, а встреча события личного календаря вообще не имеет пространства.
- **Гость как временный пользователь системы**: лишние учётные записи, риск доступа к
  объектам; токен комнаты решает задачу без этого.
- **Хранить участие только в медиасервере**: после перезапуска и для завершившихся встреч
  данных нет; список участников нужен протоколу и записи.

## Последствия

- Ядро: без изменений; встречи используют реестр объектов, ACL, события и обсуждения.
- Контракты: `packages/contracts/src/meetings` (`MeetingRecord`, `MeetingJoin`,
  `MeetingCreateInput`, `MeetingsStatus`), события `meeting.scheduled`, `meeting.started`,
  `meeting.participant_joined`, `meeting.participant_left`, `meeting.ended`, `call.incoming`.
- API: `/meetings` (список и звонок), `/meetings/{id}`, `/meetings/{id}/join|leave|end`,
  `/meetings/status`.
- Инфраструктура: профиль `media` с ключами из `.env`, порт медиасервера настраивается
  (`LIVEKIT_PORT`), `.env.example` описывает выключенное состояние.
- Публичный API модуля: `ensureMeetingForEvent`, `setMeetingParticipants`, `endMeeting`,
  `startCall`, `meetingBrief` — для календаря и чата.
- Не сделано здесь (следующие ветки фазы 4): клиент комнаты и демонстрация экрана, входящий
  звонок и комната ожидания, ссылка для гостя, запись через Egress и вебхуки медиасервера,
  расшифровка и протокол, нагрузочная проверка 20×30 и push.
