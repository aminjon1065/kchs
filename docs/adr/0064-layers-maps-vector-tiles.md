# 0064. Слои, карты и векторные тайлы: объекты реестра, MVT через компилятор с политиками, кэш по версиям

Статус: Принято
Дата: 2026-09-19

## Контекст

Фаза 2 начинается с P2-E01 «Слои, стили, тайлы». В 07-gis-engine.md со статусом «Решено» записаны
модель (объект карты — строка датасета; слой — представление датасета; карта — композиция) и тайлы
`GET /gis/layers/{id}/tiles/{z}/{x}/{y}.pbf?v=&f=&t=` из PostGIS (`ST_AsMVT`) с политиками строк
внутри SQL, кэшем Redis на 24 ч и тайм-аутом 5 с. Контракты стиля, слоя и карты уже есть
(`packages/contracts/src/gis`, `docs/contracts/layer-style.md`). Открытыми оставались:

- как тайл получает права и политики строк и столбцов: отдельный SQL рядом с компилятором
  запросов или сам компилятор;
- как кластеризовать точки, чтобы уложиться в бюджет 04-verification.md §4 (500 тыс. точек:
  p95 ≤ 300 мс без кэша, ≤ 50 мс из кэша);
- как политика строк сочетается с индексом GIST. Базовый подзапрос датасета под политикой —
  барьер `OFFSET 0` (06-analytics-engine.md, ADR-0048): условия пользователя не опускаются ниже
  политики и не вычисляются на чужих строках. Из-за барьера и охват тайла не доходил бы до индекса.

## Решение

1. **Слой и карта — объекты реестра** `layer` и `map` (модуль `gis`, уровни view…owner,
   обсуждения, связи, дерево папок, поиск по названию). Таблицы `layers` (датасет, поле геометрии,
   тип геометрии, стиль `LayerStyle`, поля тайла, правка, модерация) и `maps` (`MapSpec`).
   Создание — через `ObjectService` в транзакции, зависимости «Используется в» (слой → датасет,
   карта → слои), события `layer.published`, `layer.style_changed`, `map.updated`. У `layers`
   нет внешнего ключа на датасет, как у графиков: слой удалённого датасета остаётся объектом и
   открывается с «нет доступа к данным».
2. **Права на слой не открывают данные.** Тайлы, объекты GeoJSON и карточка объекта читаются с
   правами смотрящего на датасет: без доступа к датасету — 404, как для невидимого объекта.
   `GET /gis/layers/{id}` отдаёт `dataAccess`: без доступа студия показывает «нет доступа» и
   тайлы не запрашивает, экстент и число объектов не раскрываются. Скрытая политикой столбцов
   геометрия — 403 для тайлов и объектов; скрытые поля в тайл не попадают; маскированная
   геометрия пуста.
3. **Тайл — обёртка над компилятором запросов.** Спецификация тайла: фильтр слоя, фильтр карты
   `f` (FilterNode в base64url — связанные представления, дашборд), время `t=from/to`, выбор
   полей (геометрия + поля стиля и `tileFields`, видимые смотрящему). Компилятор с `rowMeta` и
   новым режимом `geometryOutput: 'raw'` отдаёт геометрию как есть; сервис оборачивает запрос в
   `ST_AsMVT(…, 'layer', 4096, 'geom', '_id')`. Числа в тайле — числами, даты — миллисекундами
   эпохи, списки — через «|». Выполнение — под ролью `kchs_query`, `read only`, тайм-аут 5 с;
   не уложился — 204 с заголовком `x-kchs-tile: timeout` (студия предложит кластеры или фильтр).
4. **Пространственное окно компилятора** `spatialWindow` (`CompileContext`, `RunOptions`):
   доверенная рамка сервера — условие `&&` на физическом столбце геометрии в базовом подзапросе,
   рядом с политикой строк, до барьера. Барьер для условий пользователя сохраняется. В окне —
   только числа рамки и видимое поле геометрии: скрытое — ошибка компиляции, маскированное —
   `FALSE`. Окно входит в ключ кэша. Им же пользуются объекты GeoJSON по `bbox`.
5. **Кластеры точек** — на масштабах до `cluster.maxZoom` (по умолчанию 11): сетка в градусах
   с ячейкой ≈ радиусу кластера в пикселях, по широте — с поправкой Меркатора. Координаты
   извлекаются один раз (подзапрос с `OFFSET 0`), группировка — по целым номерам ячеек,
   центр — среднее координат, `point_count`, значения полей — у одиночной точки (`any_value`,
   PostgreSQL 16+). Против первого варианта (`ST_SnapToGrid`, `ST_Collect`, `array_agg`) —
   вдвое быстрее. Линии и полигоны — `ST_SimplifyPreserveTopology` на полпикселя масштаба.
6. **Кэш.** Redis `kchs:tile:{layer}:{sha256}`, 24 ч, тайл хранится сжатым gzip (отдаётся с
   `content-encoding: gzip`, остальным — распакованным). Ключ — ключ компиляции (версия данных,
   отпечаток политик, спецификация, окно, пользовательские значения) + версия схемы + версия
   слоя + z/x/y: новая версия данных, стиль или политика дают новые ключи, старые истекают.
   Браузеру — `ETag` (304 по `If-None-Match`) и `Cache-Control: private, max-age=300`; клиент
   добавляет к адресу версию данных `v` и версию слоя.
7. **Маршруты** `/gis/layers` (создать, список слоёв датасета), `/gis/layers/{id}` (прочитать,
   изменить), `/gis/layers/{id}/tiles/{z}/{x}/{y}.pbf`, `/gis/layers/{id}/features?bbox=&limit=`
   (до 5 000 объектов, мелкие слои и правка), `/gis/layers/{id}/features/{rowId}` (карточка),
   `/gis/maps`, `/gis/maps/{id}`. У тайлов свой счётчик частоты — 12 000 в минуту на
   пользователя: быстрый пролёт карты — несколько экранов по 12–20 тайлов в секунду.
8. **Бюджет проверяется** тестом `apps/api/test/gis-tiles-perf.test.ts` (500 тыс. точек в своём
   слоте, `KCHS_PERF=1`, замер на стороне сервера) и профилем k6 `infra/perf/k6/gis-tiles.js`
   (слой на «Происшествиях» с временем, окно в три месяца ≈ 500 тыс. точек, у каждого холодного
   запроса свой интервал).

## Альтернативы

- **Отдельный SQL тайлов с политиками** (как в эскизе 07-gis-engine.md §3) — второй путь к данным
  в обход компилятора: политики строк и столбцов, маски, макросы пользователя и справочники
  пришлось бы повторять и держать согласованными.
- **Martin или pg_tileserv** — тайлы без политик смотрящего; оставлены для «тяжёлых»
  статичных слоёв в S2 (ADR-0010).
- **Условие охвата снаружи скомпилированного запроса** — планировщик опускает его к таблице
  только без политики строк; под политикой барьер оставлял полный просмотр строк политики
  (100 мс на z14 для 500 тыс. строк и секунды для 5 млн).
- **Охват фильтром `intersects` в спецификации** — то же: условие пользователя вычисляется
  после барьера, индекс GIST не работает.
- **Кластеры на клиенте (supercluster по GeoJSON)** — не масштабируется за десятки тысяч точек
  и отдаёт браузеру все строки.
- **Заранее посчитанные пирамиды кластеров** — нужны на каждую версию данных и каждый отпечаток
  политик; отложено до замеров на S2.

## Последствия

- Замер `gis-tiles-perf` на ноутбуке разработки (500 тыс. точек, 8 городов-скоплений):
  без кэша p95 186 мс (z5–z6 ≈ 200 мс, z8+ ≤ 70 мс), из кэша p95 35 мс; читатель с политикой
  строк — p95 107 мс; точки без кластеров на z10+ — p95 68 мс. Под нагрузкой соседних процессов
  цифры кратно хуже — бюджет проверяется на спокойной машине или стенде.
- Самые дорогие — холодные тайлы z5–z6 со всеми точками страны: на 5 млн точек кластеризация
  одного тайла — около 2 с. Бюджет фазы — 500 тыс.; для десятков миллионов нужны пирамиды или
  фильтр слоя.
- Условия пользователя под политикой строк по-прежнему не используют индексы (барьер); окно
  снимает это ограничение только для охвата.
- Пул роли `kchs_query` (8 соединений) общий для запросов к данным и тайлов; при нехватке —
  отдельный пул тайлов.
- Клиент (студия карт, фаза 2) строит адреса тайлов с `v` и версией слоя, обрабатывает 204 и
  `x-kchs-tile: timeout`, а без `dataAccess` показывает слой как недоступный.
