# 0141. Адресаты правил автоматизации: белый список доменов в политике безопасности

Статус: Принято
Дата: 2026-09-25

## Контекст

Действие правила `send_email` принимало и выражения назначений, и явные адреса почты, а
`webhook` — любой http(s)-адрес (ADR-0096). Правила ведёт владелец способности
`automation.manage`, поэтому правило могло отправлять данные системы на произвольный ящик или
сервер вне Комитета. Журнал запусков это фиксировал, но не предотвращал.

Владелец 24.09.2026 решил (N38, `05-risks-and-open-questions.md` §5): письма из правил — только
на адреса организации и домены белого списка, вебхуки — только на разрешённые домены, список
ведёт администратор.

## Решение

1. **Два списка в политике безопасности** (`SecurityPolicy`, системные настройки `security.*`):
   `ruleEmailDomains` и `ruleWebhookDomains`. Их ведёт администратор системы в консоли
   («Безопасность» → «Адресаты правил автоматизации»), каждое изменение — запись аудита. Здесь уже
   есть кэш процесса, аудит «до/после» и экран, поэтому второй механизм настроек не нужен.
2. **Домен нормализуется.** Нижний регистр, без схемы, `@`, `*.`, пути и точки в конце:
   вставленный `https://Hooks.Partner.tj/in` сохранится как `hooks.partner.tj`. Не похожее на
   домен отклоняется с 400. Совпадает сам домен и его поддомены (`hooks.kchs.tj` под `kchs.tj`).
3. **«Адреса организации» — сотрудники из справочника.** Письмо человеку, найденному выражением
   назначения (`user:`, `role:`, `unit_head(…)`…), разрешено всегда. Явный адрес — только из
   `ruleEmailDomains`: общий ящик Комитета попадает сюда внесением домена Комитета, ведомства —
   их доменами.
4. **Запрет по умолчанию.** Пустой список писем — только сотрудникам; пустой список вебхуков —
   вебхуки правилам запрещены. Так понимается «только на разрешённые домены».
5. **Проверка в трёх местах.**
   - при сохранении и проверке правила (`checkRule`) — ошибка с путём к адресу и подсказкой, где
     ведётся список;
   - при включении (`setEnabled`): список мог сузиться, пока правило было выключено;
   - при исполнении — действие отказывает (`forbidden`) с той же причиной, запуск получает
     статус «Ошибка», и владелец правила получает уведомление.

## Альтернативы

- **Отдельный раздел консоли для списков.** Правильнее по теме, но потребовал бы своих настроек,
  аудита и экрана. Политика безопасности уже отвечает на вопрос «куда можно выносить данные»,
  рядом с гостевыми ссылками.
- **Проверка только при исполнении.** Автор узнавал бы об ошибке по сбою запуска, а не при
  сохранении, и правило молча не работало бы до первого события.
- **Пропускать запрещённые адреса и отправлять остальным.** Письмо части адресатов выглядит
  выполненным, и расхождение легко не заметить. Отказ действия виден в истории запусков сразу.
- **Распространить список на подписки-вебхуки интеграций (ADR-0097).** У них своя защита:
  запрет внутренней сети, подпись, способность `integrations.manage`. Вопрос N38 был о правилах.

## Последствия

- Существующие правила с явными адресами или вебхуками после обновления не включаются и не
  выполняются, пока администратор не внесёт домены. Нужно предупредить при обновлении.
- Контракт `automation-rule.md` описывает ограничение; тест `automation.test.ts` проверяет
  сохранение, включение и запуск, `security-policy.test.ts` — нормализацию.
- Сквозной сценарий `owner-decisions-platform.spec.ts` проверяет карточку «Адресаты правил
  автоматизации».
