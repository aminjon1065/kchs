# 0153. Входящие по группам и массовые действия; настройки уведомлений по категориям и каналам

Статус: Принято
Дата: 2026-09-25

## Контекст

Владелец решил 25.09.2026 закончить разработку до переноса на VPS. В доработку входят
«Входящие» и уведомления: группы, фильтры, массовые действия, настройки уведомлений.

До этого:
- список дел был плоским: группа видна только бейджем в карточке, фильтр — одна область
  «все / мои / замещаемые». API уже понимало фильтры `kind` и `due`, экран — нет;
- массовой отметки не было: у делопроизводителя и руководителя за день набираются
  десятки ознакомлений и готовых отчётов;
- настройки уведомлений хранились по категории и каналу (`notification_preferences`),
  но в интерфейсе был только список категорий Telegram;
- у push не было режимов по умолчанию. Подписанное устройство молчало у всех категорий,
  а включить их было негде;
- центр уведомлений не умел отметить прочитанным одно уведомление, хотя `POST
  /notifications/read` принимал `ids`.

## Решение

1. **Группы — в контрактах.** `INBOX_GROUPS` и `inboxGroupOf(kind)`: решения,
   ознакомиться (включая готовые отчёты), поручения, приглашения, данные и алерты.
   - Одна функция для экрана, счётчиков и фильтра `GET /inbox?group=…`.
   - Список во «всех видах» разбит по группам со счётчиками из `counts.byKind`.
   - Рядом фильтр срока: «просрочено», «сегодня», «неделя».
2. **Массовые действия** — `POST /inbox/bulk`, до 100 дел:
   - «Ознакомлен» — действие `acknowledge`;
   - «Отметить выполненным» — действие `dismiss` алертов;
   - «Отложить» — на сутки.

   Первые две проходят тем же `InboxService.act`, что одиночная кнопка, — по одному делу
   через модуль дела. События, аудит и закрытие копий заместителей работают как обычно.
   Дела, которым нужны комментарий, код второго фактора, дата или форма объекта, массово
   не выполняются. Уже закрытые и чужие тоже пропускаются. Ответ — «сделано N, пропущено
   M» с причиной у каждого.
3. **Клавиши.** A — согласовать, R — отклонить (откроется диалог комментария), X —
   отметить дело. Шпаргалка перечисляет только рабочие сочетания (N84).
4. **Настройки уведомлений** — таблица «категория × канал» в профиле.
   - Режимы: в приложении — сразу или выключено; почта — сразу, в дайджесте или
     выключено; Telegram и push — сразу или выключено.
   - Недоступный канал помечен «не подключено».
   - Тихие часы и «не беспокоить» остаются в статусе присутствия (ADR-0140). Карточка
     открывает тот же диалог, но только с загруженными данными присутствия: иначе
     «сохранить» записало бы значения по умолчанию.
   - `PUT` проверяет категорию контрактом.
5. **Push по умолчанию — как Telegram**: Входящие, упоминания, поручения, личные
   сообщения, встречи. Остальное включает сам сотрудник.
6. **Центр уведомлений.** Щелчок отмечает уведомление прочитанным и открывает объект, у
   непрочитанного есть кнопка «Отметить прочитанным», категория показана словами.
7. **Сессии.** «Завершить» у каждой, кроме текущей: `POST /me/sessions/revoke {
   sessionIds }` уже был.

## Альтернативы

- **Массовое действие одним SQL-обновлением.** Быстрее, но обходит модули дел: закрытие
  ознакомления должно отметить ознакомление документа, а алерта — срабатывание. Путь
  через `act` медленнее, зато поведение то же, что у кнопки.
- **Группа как поле строки `inbox_items`.** Потребовало бы миграции и заполнения. Группа
  однозначно выводится из вида, а вид уже проиндексирован.
- **Push выключен по умолчанию, пока сотрудник не выберет категории.** Честнее к
  согласию, но устройство подписывают, чтобы получать уведомления. Молчание после
  подписки выглядит поломкой.

## Последствия

- Контракты: `InboxGroup`, `inboxGroupOf`, `inboxKindsOf`, `InboxQuery.group`,
  `InboxBulkInput`/`InboxBulkResult`. Маршрут `POST /inbox/bulk`.
- Миграций нет: настройки уведомлений хранятся в прежней таблице.
- Подписанные на push начнут получать категории по умолчанию. Кому это лишнее, тот
  выключит их в таблице.
