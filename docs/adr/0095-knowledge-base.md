# 0095. База знаний: страница — совместный документ из блоков, версии со снимками, чанки в отдельном индексе, порт семантики

Статус: Принято
Дата: 2026-09-20

## Контекст

`13-search-knowledge-ai.md` §2 описывает базу знаний: страницы в пространствах
деревом, совместное редактирование, блоки (текст, таблицы, изображения, файлы,
встроенные объекты), шаблоны, версии с diff, статусы, владельцы и срок
пересмотра, ознакомление под подпись, комментарии к фрагментам, теги,
оглавление, печать. §1 добавляет чанки страниц отдельным документом поиска
(`page_chunk`) и гибридную выдачу со семантикой.

К фазе 5 в системе уже есть всё, на чём это стоит: реестр объектов, совместные
документы Yjs с блоками (тетрадь ADR-0071, протокол ADR-0093), ознакомление
ядра (ADR-0084), печатные формы с рендером в движке (ADR-0085), индекс
Meilisearch с фильтром по принципалам. Вопрос — что из этого переиспользовать и
где провести границы, чтобы база знаний не стала ещё одним параллельным
механизмом. Отдельно: семантический поиск (эмбеддинги, pgvector) делается
параллельно другой веткой — нужна точка стыковки, которая не ломается, пока
источника нет.

## Решение

**Страница — объект реестра `page`** в дереве пространства (`hasParentTree`),
тело — совместный документ Yjs. Раскладка блоков — контракт
`PAGE_BLOCK_LAYOUT`, документ читается и пишется тем же ядром блочных
документов (`kernel/collab/block-doc.ts`), что тетрадь и протокол: порядок в
`Y.Array`, блоки в `Y.Map`, текст — `Y.XmlFragment` Tiptap. Снимок JSON лежит в
`pages.blocks` — от него живут поиск, версии, печать и оглавление. Клиент
переиспользует функции тетради (`notebook-doc.ts`): порядок, перенос,
дублирование, удаление блоков — общий код, своя только раскладка.

**Виды блоков**: `text`, `table`, `image`, `file` и встроенные объекты реестра
`chart`, `map`, `dataset`, `metric`, `tasks`. Встроенный блок хранит только
идентификатор объекта; права проверяются при вставке (`authorize(view)`) и
рисуется он теми же представлениями, что и в остальной системе. `tasks` ссылается
на **проект**, а не на сохранённое представление: список открытых задач проекта
получается одним запросом существующего API и не тянет за собой фильтры
представления.

**Версии — снимки блоков** (`page_versions`): при публикации, по кнопке
«Сохранить версию» и перед откатом. Сравнение — по тексту версий алгоритмом
по словам, который переехал из модуля документов в общий слой
(`shared/text-diff.ts`): он нужен и версиям документа (ADR-0085), и версиям
страницы. Откат кладёт блоки версии обратно в совместный документ — у всех, кто
держит страницу открытой, текст меняется сразу; текущий текст перед этим
сохраняется версией, поэтому откат обратим.

**Состояния**: `draft` → `published` → `review`. Публикация снимает версию и
назначает срок пересмотра. Задание `knowledge.review` (очередь `maintenance`,
раз в сутки) переводит страницы с наступившим сроком в `review` и открывает
владельцу дело Входящих `review_page`; повторная публикация дело закрывает.
Дело не дублируется: в строке хранится срок, на который оно уже открывалось.

**Владелец страницы** — отдельное поле `pages.owner_id`, а не владелец объекта
в реестре: первый отвечает за пересмотр и меняется кнопкой, второй определяет
права и в ядре не переназначается. В интерфейсе это «Владелец страницы» на
вкладке «Пересмотр».

**Ознакомление** — механизм ядра (ADR-0084) без изменений: модуль только
создаёт запрос (`POST /pages/{id}/acknowledgments`), список, отметка и
напоминание — общие маршруты `/objects/{id}/acknowledgments*`. Прав получателям
не выдаётся: страница лежит в пространстве, и знакомят с ней тех, кто её видит.

**Комментарии к фрагментам** — обсуждение объекта с якорем: у сообщения
появилось поле `anchor` (ядро хранит его в `messages.meta`), у страницы якорь —
идентификатор блока. Отдельной сущности комментариев нет; контекстная панель с
якорем показывает комментарии к этому фрагменту и им же помечает новые.

**Шаблоны** (инструкция, регламент, справочник, FAQ) — заготовка блоков на
языке автора, без связи со страницей после создания. **Разделы по умолчанию**
(«Регламенты и инструкции», «Справочники», «Обучение», «Часто задаваемые
вопросы») — корневые страницы пространства «Общее» в сиде: раздел — обычная
страница с вложенными, дерево остаётся однородным, и у раздела есть своё
вступление, владелец и срок пересмотра.

**Печать** — печатная форма реестра форм (ADR-0085), а не страница печати в
Chromium (ADR-0078): api собирает разметку из блоков, движок печатает её в PDF
с закрытой сетью. Картинки вставляются данными (до 1,5 МБ); встроенные объекты
в PDF не рисуются — на их месте строка со ссылкой на объект в системе.

**Поиск** — свой индекс `page_chunk` рядом с индексом объектов: кусок страницы
находится и цитируется целиком. Чанк режется по абзацам блока (до 1200
символов), идентификатор — `<pageId>_<blockId>_<n>` (только буквы, цифры, `-` и
`_`: этого требует ключ документа Meilisearch). Права — `aclPrincipals` чанка,
их ведёт ядро (`readPrincipalsFor`); подписчик пересобирает чанки страницы и её
потомков по событиям текста, прав и переноса. Выдача всё равно проверяется
`authorize(view)` — рассинхрон индекса не может показать чужое.

**Порт семантики** (`modules/knowledge/domain/semantic-port.ts`) — по образцу
порта расшифровки протокола: интерфейс `SemanticSource` с `search`, `ready`,
`index` и `forget`; источник подключается через `KnowledgeSemantics.setSource`
в `public.ts`. Порт мягко деградирует: источника нет, он не готов или бросил
исключение — выдача остаётся словесной, а ответ честно говорит `semantic:
false`. Эмбеддинги, pgvector и RAG-ответы в этот эпик не входят.

## Альтернативы

- **Свой механизм блоков для страниц.** Отклонено: блочные документы уже есть у
  тетради и протокола, а третий вариант раскладки означал бы третий набор
  ошибок слияния Yjs.
- **Версии как полные документы Yjs.** Отклонено: снимок JSON сравнивается,
  печатается и откатывается без разбора истории Yjs, а история состояний
  документа нужна только для отладки.
- **Чанки в индексе объектов (`parentId` на страницу).** Отклонено: один
  документ на объект не даёт ни цитаты, ни якоря на блок, а ранжирование
  длинной страницы по одному полю `body` хуже.
- **Фильтр прав в `page_chunk` по списку видимых страниц (как у сообщений,
  ADR-0090).** Отклонено: у чатов список бесед короткий, а видимых страниц
  могут быть тысячи — фильтр по принципалам дешевле и уже есть в ядре.
- **Печать страницей печати в Chromium (ADR-0078).** Отклонено: странице не
  нужны живые графики в PDF, а печатная форма не требует служебного токена,
  открытой сети и headless-маршрута.
- **Разделы — папки (`folder`).** Отклонено: дерево из двух типов усложнило бы
  навигатор, а раздел-страница даёт вступление, владельца и пересмотр.
- **Владелец страницы = владелец объекта.** Отклонено: ядро не умеет
  переназначать владельца объекта (это переносит и права уровня `owner`), а
  ответственность за пересмотр меняется чаще людей.

## Последствия

- Новый домен событий `page` (`page.updated`, `page.published`,
  `page.status_changed`, `page.version_created`, `page.restored`,
  `page.review_due`), новый вид дела Входящих `review_page`.
- Ядро обсуждений получило поле `anchor` у сообщения — им может пользоваться
  любой тип объекта, у которого есть фрагменты.
- `shared/text-diff.ts` — общий слой; модуль документов импортирует его оттуда.
- Индекс `page_chunk` создаётся при старте воркера (`scheduleKnowledgeJobs`);
  Meilisearch недоступен — это предупреждение, а не отказ старта.
- Семантический поиск и RAG-ответы («Спросить по базе знаний») остаются
  открытыми: порт готов, источник подключается отдельно.
- В PDF страницы нет графиков, карт и таблиц датасетов — только ссылки на них
  (вопрос N36).
