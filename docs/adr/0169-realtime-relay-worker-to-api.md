# 0169. Ретрансляция realtime из worker в узлы api каналом Redis

Статус: Принято
Дата: 2026-10-05

## Контекст

Подписчики событий работают в процессе worker (`main.ts`: `startConsumers` только в роли
`worker` или `all`), а сокеты открыты на узлах api (`startRealtime` — только в роли `api`
или `all`). Отправка в комнату была вызовом `io?.to(room).emit(…)`: в worker шлюза нет, и
вызов ничего не делал. Так же молча выходили отзыв прав из комнат (`revokeRoomAccess`) и их
перепроверка (`recheckUserRooms`). Через Redis уходил только прогресс заданий (`rt:job`).

Профиль `app`, стенд показа (`demo-stand.sh`) и чарт S2 запускают api и worker разными
контейнерами. Там не доходили уведомления, счётчик «Входящих», сообщения чатов, входящий
звонок и `object.updated` открытых вкладок. Чаты частично спасал опрос раз в 30 с. В
разработке и e2e (`ROLE=all`) всё работало, а `verify-stack.sh` realtime не проверял, поэтому
дефект нашёл только архитектурный разбор (`04-delivery/07-architecture-hardening.md`).
`01-overview.md` §Realtime описывает правильную схему: worker → Redis pub/sub → api.

## Решение

- Процесс без шлюза кладёт команду в канал Redis `rt:relay` (`kernel/realtime/gateway.ts`):
  `emit {room, event, payload}`, `revoke {objectId}`, `recheck {userId}`. Каждый узел api
  подписан на канал и выполняет команду только над своими сокетами (`io.local`). Поэтому при
  нескольких репликах сообщение не задваивается.
- На узле api отправка идёт напрямую, `io.to(room)`: адаптер Redis доставит её и на другие
  узлы.
- Отзыв и перепроверка комнат всегда идут через канал, в том числе с узла api. Каждый узел
  перепроверяет права по настоящему контексту своих сокетов. Копия сокета через адаптер
  (`fetchSockets` по всем узлам) приходит сериализованной и может потерять поля контекста,
  которые сериализация не переносит, например `Set` способностей.
- Прогресс заданий из `rt:job` тоже уходит только своим сокетам (`io.local`). Канал слушает
  каждый узел, и при двух репликах api клиент получал сообщение дважды.
- Браузерная проверка установки (`apps/web/scripts/stack-check.mjs`, её запускает
  `verify-stack.sh` и задание CI «Установка в контейнерах») получила шаг «живые обновления».
  Переименование файла через API должно дойти до его открытой вкладки сообщением
  `object.updated` за 15 с. На образах до этого решения шаг падает.

## Альтернативы

- **`@socket.io/redis-emitter` в worker.** Официальный способ отправки из процесса без
  сервера, но он покрывает только отправку. Отзыв и перепроверка требуют `authorize` над
  каждым сокетом, то есть своего канала всё равно. Это ещё одна зависимость ради половины
  задачи.
- **Подписчик realtime в процессе api.** Обработка событий делила бы цикл событий с HTTP.
  Каждой реплике api понадобилась бы своя группа потребителей, иначе событие получит только
  одна из них, а значит отдельная схема доставки.
- **Сервер Socket.IO в worker поверх адаптера.** У worker нет HTTP-сервера, и держать его
  ради отправки дороже, чем одна подписка на канал.

## Последствия

- Pub/sub доставляет «не более одного раза»: узел api, перезапущенный в момент публикации,
  сообщение пропустит. Его клиенты переподключаются, заново подписываются на комнаты и
  перечитывают открытые вкладки, как и раньше при разрыве (`16-api-and-events.md` §3).
- Каналы pub/sub общие для всего экземпляра Redis, не для его базы. Тестовые слоты и стенд
  разработки видят команды друг друга, но комнаты адресуются UUID, поэтому чужие команды не
  находят сокетов.
- Тест `apps/api/test/realtime-relay.test.ts`: отправка из процесса без шлюза уходит в
  канал, узел api доставляет команду сокету и по отзыву прав исключает его из комнаты.
