# 0109. Колоночный tier: копия версии датасета в Parquet, тяжёлые агрегаты — DuckDB в движке

Статус: Принято
Дата: 2026-09-20

## Контекст

`06-analytics-engine.md` §19 и ADR-0002 (Решено): для крупных датасетов добавляется колоночный
tier — Parquet в S3 и DuckDB в движке, «QuerySpec компилируется в диалект DuckDB» за тем же
интерфейсом `Dialect`, а горячие срезы остаются в Postgres. Бюджет `04-verification.md`:
агрегация с фильтром на датасете до 10 млн строк — p95 ≤ 2 с. На демо-датасете «Происшествия»
(5 млн строк, ADR-0063) Postgres в этот бюджет упирается: месячная сводка по районам —
p95 около 2,0 с, сводка с фильтром — около 2,4 с.

Главное требование к колоночному пути — доступ. Политики строк и столбцов (03-access-model.md)
в Postgres-пути живут внутри SQL, который пишет компилятор: подзапрос датасета отбирает
видимые строки, скрывает и маскирует столбцы и ставит барьер оптимизатора. Если колоночный
путь получит данные другим способом, политика может не примениться — это утечка.

## Решение

1. **Один компилятор, два диалекта.** `packages/query` пишет запрос только через примитивы
   `Dialect`; добавлен `duckdbDialect`. Приведения с вычисляемым именем типа, которые раньше
   собирались строкой (`NULL::${type}`, `::numeric`, `::jsonb`), теперь идут через
   `Dialect.cast`: текст Postgres не изменился (эталоны `golden.test.ts` те же), а DuckDB
   получает свои имена типов. Так политики строк, маскирование столбцов и барьер
   `OFFSET 0` в колоночном пути — тот же код, что в Postgres-пути.
2. **Чего DuckDB не умеет — не считает.** Геометрия в колоночной копии не хранится:
   `geoJson`, `geography` и неизвестные типы бросают `UnsupportedByDialectError`, вызывающий
   молча возвращается в Postgres. Там же оказываются сырой SQL, системные датасеты, режим
   таблицы (`_id`/`_ver`), тайлы и пространственное окно.
3. **Копия — снимок версии датасета.** Задание движка `transform:columnar.build` читает
   таблицу строк ролью только для чтения `kchs_query` (ADR-0048) и пишет Parquet (zstd)
   в бакет `kchs-columnar` под ключом `columnar/<датасет>/v<версия>.parquet`. План столбцов
   (физические имена и типы полей) готовит api — движок не знает реестра полей. Метаданные
   копии (версия, строки, размер, время сборки, ошибка) — таблица `dataset_columnar_copies`,
   одна строка на датасет; они видны в карточке датасета и в администрировании.
4. **Выбор исполнителя — в сервисе запросов, а не в компиляторе.** `packages/query` остаётся
   чистым. `QueryService.plan` берёт колоночный путь, если: tier включён, у всех датасетов
   запроса есть копия текущей версии, в спецификации есть шаг `aggregate` или `pivot`
   (`executor: 'auto'`) и хотя бы один датасет крупнее порога. Явный переключатель —
   `options.executor` (`auto` | `postgres` | `columnar`). Компиляция в диалекте DuckDB не
   удалась — считает Postgres, и ошибка спецификации всплывёт там обычным сообщением.
5. **Честный ответ.** `QueryResult.executedOn` (`postgres` | `columnar`) входит в контракт;
   рядом с результатом в конструкторе и в тетради написано, что считал движок.
6. **Кэш — прежний,** по версиям датасетов и политикам; исполнитель входит в ключ, поэтому
   переключение показывает настоящие числа, а новая версия данных обесценивает и копию,
   и кэш.
7. **Копия на диске движка.** DuckDB читает локальный файл, а не S3: расширение `httpfs`
   пришлось бы скачивать при первом запросе, а установка бывает без выхода в интернет.
   Файл скачивается один раз и живёт в кэше с вытеснением по объёму
   (`ENGINE_COLUMNAR_CACHE_MB`); ключ содержит версию, поэтому устаревший файл не
   переиспользуется.
8. **Типы копии.** Ссылки (`user`, `unit`, `territory`, `object_ref`, `file`) и JSON лежат
   строками: сравнение канонических идентификаторов посимвольное, а приведения на миллионах
   строк не происходит. Длительность хранится минутами — так её читает компилятор. Точные
   числа — `DECIMAL(38,12)`, как и в диалекте.

## Альтернативы

- **ClickHouse** (`18-tech-stack.md`) — отдельная служба и эксплуатация ради одного сценария;
  DuckDB встраивается в уже существующий движок.
- **DuckDB читает Postgres напрямую (`postgres_scanner`) или S3 (`httpfs`)** — расширения
  скачиваются при первом обращении; установка без интернета переставала бы работать.
- **Переписать политики отдельно для колоночного пути** — второй источник правды о доступе,
  то есть постоянный риск утечки. Отвергнуто.
- **Отдавать DuckDB готовые строки из Postgres** — теряется весь смысл: чтение строк и есть
  дорогая часть.
- **Копия на каждую версию, история копий** — место в хранилище без спроса; прежний файл
  удаляется после успешной сборки новой копии.

## Последствия

- Замеры на 5 млн строк (одна машина, DuckDB 4 потока, 9 повторов; Postgres — та же таблица
  с индексами по времени, району и виду):

  | Запрос | Postgres p95 | DuckDB p95 | Выигрыш |
  |---|---|---|---|
  | Сводка по виду (count, sum, avg) | 684 мс | 42 мс | 16× |
  | То же с политикой строк | 1553 мс | 139 мс | 11× |
  | Месяц × район (count, sum) | 2051 мс | 234 мс | 8,8× |
  | То же с политикой строк | 2235 мс | 471 мс | 4,7× |
  | Фильтр + p95 + count_distinct | 2382 мс | 60 мс | 40× |
  | То же с политикой строк | 2349 мс | 104 мс | 23× |

  Копия 5 млн строк: 82,9 МБ Parquet против 1076 МБ таблицы с индексами; сборка — 28 с.
- Новая версия данных делает копию устаревшей; датасет крупнее порога пересобирается сам
  заданием, остальные — по кнопке в карточке или в администрировании.
- Движку нужны `DATABASE_QUERY_URL` и место на диске под кэш копий.
- Образ движка нужно пересобрать: добавлены модуль колоночного tier и явная зависимость
  `pytz` (она и так приходила с `pandas`; DuckDB без неё не отдаёт значения с поясом).
- Соблюдение политик в колоночном пути проверяется с двух сторон: интеграционный тест api
  (`apps/api/test/data-columnar.test.ts`) смотрит, что уходит в движок — политика строк
  до барьера, скрытые столбцы отсутствуют, маски на месте, у администратора и сотрудника
  запросы разные; тест движка (`apps/engine/tests/test_columnar.py`) выполняет этот SQL
  настоящей DuckDB поверх Parquet и проверяет, что он отбирает ровно разрешённые строки и
  даёт те же маски, что Postgres.
