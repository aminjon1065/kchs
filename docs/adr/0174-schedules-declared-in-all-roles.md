# 0174. Расписания объявляются во всех ролях процесса

Статус: Принято
Дата: 2026-10-05

## Контекст

Единый планировщик (ADR-0096) держит объявления регулярных заданий в реестре процесса.
Экран «Расписания» читает этот реестр и поставщиков расписаний сущностей (правила,
пайплайны, источники). Объявляли их функции `scheduleMaintenance`, `scheduleProcessTimers` и
`schedule*Jobs` модулей, а вызывались они только в роли worker.

Профиль `app`, стенд показа и Helm запускают api и worker раздельно. В процессе api экран
«Расписания» не видел ни системных заданий, ни расписаний правил, пайплайнов и источников, а
«Выполнить сейчас» и «Выключить» отвечали 404. В разработке (`ROLE=all`) всё работало. Нашёл
это форк обслуживания шины событий (ADR-0171) — второй дефект того же рода, что ADR-0169.

Вдобавок функции модулей смешивали объявления с работой при старте: синхронизацию расписаний
сущностей с BullMQ, служебные записи (календари подразделений, каналы, индексы), снятие
прежних повторяемых записей.

## Решение

- **Объявления — отдельно и во всех ролях.** `declareMaintenanceSchedules`,
  `declareProcessSchedules` и `declareModuleSchedules` (`declare<Модуль>Schedules` каждого
  модуля) вызываются в `main.ts` до выбора роли. Они только объявляют: `declareSchedule` и
  `registerEntityScheduleProvider`, без обращений к базе и очередям. `declareSchedule`
  идемпотентен.
- **Работа при старте — только в worker.** В `schedule<Модуль>Jobs` остаются синхронизация
  расписаний сущностей, служебные записи и уборка прежних повторяемых записей. В очередь
  расписания ставит `syncSchedules`.
- **Группы событий раньше публикации.** Worker создаёт группы потребителей до запуска
  диспетчера outbox. События, накопленные за время обновления, попадают и в потоки новых
  доменов, у которых групп ещё не было (дополнение к ADR-0171).
- **Проверка.** Браузерная проверка установки (`stack-check.mjs`, где api и worker — разные
  контейнеры) запрашивает `GET /schedules` и ждёт задание ядра (`maintenance:outbox.prune`) и
  задание модуля (`maintenance:tasks.deadlines`).

## Альтернативы

- **Вызывать `schedule*Jobs` во всех ролях.** Каждая реплика api синхронизировала бы
  расписания сущностей и создавала служебные записи при каждом старте. Это лишняя работа и
  гонки между репликами.
- **Читать экран из BullMQ.** В очереди нет подписей, поставщиков сущностей и выключенных
  расписаний — экран потерял бы смысл.

## Последствия

- Новый модуль объявляет расписания в `declare<Модуль>Schedules`, а работу при старте
  держит в `schedule<Модуль>Jobs`.
- Тесты автоматизации вызывают `declareAutomationSchedules` перед `scheduleAutomationJobs`,
  как и `main.ts`.
