# ADR-0131. Сроки шагов маршрута в календарных часах

Статус: **Принято** · Дата: 2026-09-24 · Фаза 5 (P5-E08, пакет ЧС)

## Контекст

По решению N14 (`04-delivery/05-risks-and-open-questions.md` §5) в предметный
пакет ЧС входит экстренный маршрут донесения со сроками в часах: донесение о
происшествии рассматривают за часы, а не за рабочие дни, и в выходной тоже.

Движок процессов (ADR-0012, ADR-0079) знал один вид срока — `dueWorkingDays`:
конец N-го рабочего дня по производственному календарю от активации шага. Так
же считалось ожидание `wait.durationWorkingDays`. Точный момент можно было
задать только ожиданием `until`, а у шагов с решением такого способа не было.
Контракт `contracts/process-definition.md` прямо говорил: «сроки — в рабочих
днях». Значит, нужен второй способ задать срок и запись этого решения.

## Решение

1. **Второе поле, а не единица при числе.** У `approval`, `sign`, `register`,
   `acknowledge`, `task` и `return` рядом с `dueWorkingDays` — `dueHours`
   (1–720), у `wait` рядом с `durationWorkingDays` — `durationHours`. Так
   изменение совместимо: опубликованные определения, запущенные экземпляры и
   пакеты конфигурации не меняются, миграция данных не нужна.
2. **Часы — календарные.** Срок — момент активации плюс N часов, без
   производственного календаря: экстренный шаг не ждёт выходных и праздников.
   Рабочие часы («только с 9 до 18») сознательно не вводятся — для них есть
   рабочие дни.
3. **Одним способом.** Оба поля сразу — ошибка проверки `due_conflict`:
   определение с ней не публикуется. `deadlineOf(step)` читает срок одной
   записью `{ unit: 'working_days' | 'hours', value }`; всё ядро (исполнение,
   предпросмотр назначений, ожидание) считает момент через неё.
4. **Свои напоминания у часового срока.** Утренние напоминания «за рабочий
   день» и «в день срока» для часов бессмысленны. У часового срока одно
   напоминание: за час до срока, а у срока короче двух часов — посередине
   (`remindSoon` в таймерах шага, `process.step_due_soon` с `when: 'soon'`).
   Просрочка и эскалация по `timers` определения — в момент срока, как у
   дневных. Восстановление после перезапуска — прежнее: задание на ближайший
   момент и обход таймеров раз в пять минут.
5. **Конструктор маршрутов** показывает срок полем и единицей «рабочие дни /
   часы»; смена единицы переносит число в другое поле определения.

## Альтернативы

- **`due: { value, unit }` вместо двух полей.** Отклонено: ломает
  опубликованные определения, пакеты конфигурации и конструктор ради
  симметрии, которая пользователю не видна.
- **Часы по производственному календарю (рабочие часы).** Отклонено:
  экстренный маршрут должен идти круглосуточно, а внутренние сроки в пределах
  рабочего дня хорошо выражаются рабочими днями.
- **Срок через `wait.until` перед шагом.** Отклонено: ожидание не создаёт
  элементов Входящих и не просрочивает решение, а эскалация по `timers`
  работает только у шагов со сроком.

## Последствия

- `@kchs/process`: поля `dueHours` и `durationHours`, функции `deadlineOf`,
  `waitDurationOf`, `hoursDeadline`, `hoursReminder`; `dueOf` снята.
- Контракт `contracts/process-definition.md` дополнен разделом «Сроки».
- `process.step_due_soon.when` получил значение `soon`, уведомление —
  «Скоро срок».
- Во Входящих и в карточке документа срок шага и раньше показывался с
  временем: момент хранится в `timestamptz`.
