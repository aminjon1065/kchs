# 0143. Смена мастер-ключа без простоя: прежний ключ на время перехода и `kchs secrets rotate`

Статус: Принято
Дата: 2026-09-25

## Контекст

`17-security.md` §4 обещал «ротацию с перешифрованием» мастер-ключа `KCHS_MASTER_KEY`. Средств
перешифрования в установке не было (вопрос N81). Смена ключа делала нечитаемыми:

- секреты TOTP;
- пароль учётной записи каталога и секрет клиента IdP;
- секреты интеграций и подписи вебхуков;
- ключи ГИС-служб и подложек;
- адреса подписок на календари.

Сотрудникам пришлось бы заново подключать второй фактор, а администратору — вводить все секреты.
Поэтому ключ, скорее всего, не меняли бы вовсе. Владелец решил: команда нужна до пилота.

Шифротекст — `iv(12) | tag(16) | данные`, AES-256-GCM, без номера ключа. Тег GCM проверяет ключ:
чужим ключом расшифровка не проходит, а не выдаёт мусор.

## Решение

1. **Прежний ключ на время перехода.** Новая переменная `KCHS_MASTER_KEY_PREVIOUS`.
   Расшифровка пробует текущий ключ, при неудаче — прежний. Шифрование всегда идёт текущим.
   Номер ключа в шифротекст не вводится: тег GCM и так отличает ключи, а формат хранимых
   значений не меняется.
2. **`kchs secrets rotate [--dry-run]`** проходит по списку зашифрованных колонок
   (`shared/crypto/rotation.ts`: восемь таблиц). Каждое значение:
   - уже зашифрованное текущим ключом — не трогается;
   - зашифрованное прежним — перешифровывается;
   - не читаемое ни одним ключом — не меняется и попадает в отчёт, код выхода 1.

   Строки обновляются по одной пачками по первичному ключу, поэтому прерванный прогон
   безопасно повторить.
3. **Порядок смены без простоя** (`infra/runbooks/secret-leak.md` §3):
   1. новый ключ ставится в `KCHS_MASTER_KEY`, прежний — в `KCHS_MASTER_KEY_PREVIOUS`,
      перезапуск;
   2. пробный прогон, затем перешифрование;
   3. прежний ключ убирается и хранится офлайн — для восстановления старых резервных копий.
4. **Полнота списка** проверяется тестом: каждая колонка `bytea` схемы `public` либо есть в
   списке, либо явно названа не секретной (публичный ключ входа). Новая зашифрованная колонка
   без записи в список роняет тест.
5. Временные пароли импорта сотрудников живут в Redis часы и не перешифровываются: их читает
   прежний ключ, пока он задан.

## Альтернативы

- **Номер ключа в шифротексте** (`v2:…`) и связка ключей в окружении. Это честнее при
  нескольких сменах подряд, но меняет формат хранимых значений и требует миграции всех
  колонок. Двух ключей на время перехода достаточно: смена — событие редкое.
- **Перешифровывать при остановленной установке одним ключом «старый → новый»** в параметрах
  команды. Это простой на время прогона и риск остаться с базой, которую не читает ни
  окружение, ни команда, если прогон прервался.
- **Внешний KMS.** Верное направление для S2. На S1 без KMS у Комитета мастер-ключ живёт в
  окружении, и смена должна работать там.

## Последствия

- Смена ключа больше не требует ни повторного ввода секретов, ни повторного подключения
  второго фактора.
- При утечке ключа вместе с копией базы одного перешифрования мало: секреты меняются у
  поставщиков. Runbook разделяет эти случаи.
- Резервная копия, снятая до смены, читается только с прежним ключом. Его хранят офлайн и при
  восстановлении задают в `KCHS_MASTER_KEY_PREVIOUS`.
- Переменная попала в `x-app-env` compose.
