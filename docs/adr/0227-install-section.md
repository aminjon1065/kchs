# Черновик раздела ADR-0227 — рабочая установка, обновление, сторож, пределы ресурсов

> Для вклейки в общий ADR-0227 этапа Б. Без сценариев атак.

## Контекст

Пилот — один сервер с реальными данными Комитета. До этого единственным путём установки в
контейнерах был стенд показа (`demo-stand.sh`, ADR-0148): каждый `up` загружал демо-данные,
`reset` без вопроса удалял тома, а руководство предлагало обновляться через `reset --build`.
Хранилище файлов публиковалось на порту 9443, который типовой прокси организации не пропускает.
Пределов памяти у служб не было, а о сбоях без профиля наблюдаемости никто не узнавал.
Образы `kchs/*` назывались без реестра, и `docker compose pull` из руководств пошёл бы в чужое
пространство имён на Docker Hub.

Решения владельца (04.11.2026): хранилище — на своём имени и порту 443; оповещения — в
Telegram; сервер ещё не выбран, поэтому два профиля пределов, 16 и 32 ГБ.

## Решение

- **`infra/scripts/pilot.sh` — рабочая установка.** Команды `install`, `update`, `status`,
  `profile`, `watchdog-install`, `history`, `basemap`, `kchs`, `logs`. Скрипт никогда не
  удаляет тома и не загружает демо-данные. В `.env` ставится признак
  `KCHS_INSTALL_KIND=pilot`.
  - `install` заводит администратора (`kchs init`). Справочники (`kchs seed --profile base
    --pack emergency`) ставит один раз и только в пустую базу, где init только что завёл
    администратора, с отметкой `KCHS_PILOT_REFERENCES`. На базе с данными seed заново
    вставил бы оргструктуру и должности.
  - `update`: сначала свежая резервная копия скриптом копий (`KCHS_BACKUP_SCRIPT`, по
    умолчанию `infra/scripts/backup.sh run`). Без скрипта обновление отказывается работать;
    обход — только явным `--skip-backup`. Затем `generate-secrets.sh --add-missing`, сборка,
    `up --wait`, `kchs migrate`, проверка `/health`, уборка кэша сборки старше недели и
    висячих образов.
  - `--no-build` — образы уже есть, например привезены `docker load` в закрытый контур.
- **`demo-stand.sh` на рабочей установке ничего не делает.** `up`, `reset`, `down` и
  `basemap` отказывают с отсылкой к `pilot.sh`; `status` работает. `reset` на стенде показа
  требует `--yes` или ввод имени проекта. Руководства больше не предлагают `kchs seed` для
  пилота.
- **Хранилище — на своём имени и порту 443** (`storage-subdomain.yml`,
  `caddy/sites-available/storage-subdomain.caddy`). Имя хранилища — `KCHS_STORAGE_DOMAIN`, по
  умолчанию `files.<домен портала>`. `S3_PUBLIC_ENDPOINT` и `KCHS_STORAGE_ORIGIN` указывают
  на это имя. Caddy выпускает сертификат и на него и передаёт заголовок Host в MinIO как есть,
  поэтому подпись ссылок сходится. Порт 9443 (`storage-https.yml`) остаётся у стенда показа
  для прежних установок.
- **Образы `kchs/*` — `pull_policy: never`** (postgres, api, worker, engine, web). Compose
  собирает образ, если его нет, и никогда не тянет его из реестра; `compose pull` его
  пропускает. Из руководств убран `pull`.
- **Пределы ресурсов** — переменные `*_MEM_LIMIT` и `*_CPUS`; по умолчанию `0`, то есть без
  предела, и у разработки, CI и стенда показа ничего не меняется. Профиль пишет
  `pilot.sh install|profile` под сервер на 16 или 32 ГБ. Пределы ставятся на api, worker,
  движок, Meilisearch, ONLYOFFICE, web и наблюдаемость. Процессор не превышает числа ядер
  сервера, иначе Docker не запустит контейнер.
  - Postgres предела не получает, у него `oom_score_adj: -800`: при нехватке памяти ядро
    убивает сначала другие процессы.
  - `shared_buffers` и `effective_cache_size` берутся из профиля.
  - `MEILI_MAX_INDEXING_MEMORY` — 2 ГиБ по умолчанию, без него индексация берёт до двух
    третей памяти; у профилей — 1 и 2 ГиБ.
  - `ENGINE_CONCURRENCY` у движка — 2 и 4.
  - `MEILI_ENV=production` в режиме `generate-secrets.sh --mode app` и на рабочей установке.
- **Сторож** — `infra/scripts/watchdog.sh` и таймер systemd (`infra/systemd/`), раз в 5
  минут, без профиля наблюдаемости.
  - Проверки: занятость диска выше 85 %; служба `unhealthy` — перезапуск и сообщение;
    перезапуск по кругу или остановка службы; копия (`KCHS_BACKUP_DIR/last-success`)
    старше 26 часов или её нет; `/health` api не отвечает.
  - Сообщения уходят в Telegram ботом платформы (`TELEGRAM_BOT_TOKEN`) в
    `KCHS_ALERT_TELEGRAM_CHAT`, при его отсутствии — в `ALERTMANAGER_TELEGRAM_CHAT_ID`.
    Одно и то же сообщение — не чаще раза в час; когда беда прошла, приходит «снова в
    порядке».
  - `--dry-run` — без отправки и перезапусков.
  - Проверка `watchdog.test.sh` с поддельным API Telegram запускается в CI (задание
    «Правила оповещений»).
- **Руководство** — `docs/06-guides/32-pilot-install.md` для неинженера: профили и требования
  к серверу, два имени DNS, установка, обновление, таблица «сообщение сторожа → что делать».

## Альтернативы

- **`pull_policy: build`.** Пересобирает образ при каждом `up`: на движке это десятки минут
  без сети, и это затирало бы привезённые образы. `never` собирает только отсутствующий образ.
- **Хранилище по пути портала (`/s3/…`).** Подпись SigV4 включает путь, и префикс прокси её
  ломает; своё имя на 443 работает с подписанными ссылками без правок api.
- **Пределы по умолчанию в compose.** Ограничили бы стенд разработки и CI на тяжёлых
  демо-данных. Пределы задаёт профиль рабочей установки.
- **Сторож внутри контейнера.** Видеть и перезапускать контейнеры можно только через
  `docker.sock`, а это права root на хосте. Таймер хоста проще и не расширяет права служб.

## Последствия

- Владелец заводит две DNS-записи вместо одной.
- Обновление рабочей установки без настроенных резервных копий не идёт — это намеренно.
- Сторожу нужен systemd. Без него `pilot.sh` печатает строку для cron.
- Пароль временного администратора печатается один раз, как у `demo-stand.sh`.

## Проверки

Временная установка (проект compose со своими портами, режим `--domain localhost`, внутренний
УЦ Caddy): установка, повторный `update`, подписанные ссылки загрузки и скачивания через
`files.localhost`, CSP портала с origin хранилища. Затем установка удалена. Сторож —
`watchdog.test.sh`.
