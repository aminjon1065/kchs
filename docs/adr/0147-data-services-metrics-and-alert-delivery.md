# 0147. Метрики служб данных и доставка оповещений: экспортёры, учётки только для метрик, Alertmanager

Статус: Принято
Дата: 2026-09-25

## Контекст

ADR-0045 дал профиль `observability`: метрики api и worker, трассы, журналы и правила алертов.
В разделе «Не сделано» остались три вещи, без которых оповещения на пилоте бесполезны:

- **Метрики служб данных.** Postgres, Redis, MinIO и Meilisearch метрик не отдавали. Упавшая
  база была видна только по ошибкам api, заполненный диск — никак.
- **Доставка.** Правила срабатывали в Prometheus, но письма и сообщения никто не отправлял:
  узнать о сбое можно было, только открыв Grafana.
- **Доступ.** У служб данных нет «анонимных» метрик. Отдавать Prometheus пароль
  суперпользователя, root MinIO или мастер-ключ Meilisearch нельзя: Prometheus читает много и
  отовсюду, его конфигурация лежит в репозитории.

Владелец включил этот пункт в доводку к пилоту.

## Решение

1. **Учётные записи только для метрик**, одна на службу. При каждом запуске профиля их
   заводят одноразовые контейнеры `metrics-init-*`, поэтому для существующей установки
   ничего не надо делать руками:
   - **Postgres** — роль `kchs_monitor`: `pg_monitor`, `CONNECT` к рабочей базе, только
     чтение, предел 5 соединений. Пароль — `KCHS_MONITOR_PASSWORD` (`generate-secrets.sh`);
     в старом `.env` его нет — тогда пароль придумывается один раз и хранится в томе
     `prometheussecrets`. Экспортёр читает пароль из файла тома. Смена пароля в `.env`
     пересоздаёт контейнер роли, а `depends_on.restart` перезапускает экспортёр.
   - **MinIO** — пользователь `kchs-prometheus` с политикой только на `admin:Prometheus` и его
     JWT для `/minio/v2/metrics/cluster`. Секрет пользователя придумывается при каждом
     запуске, токен выпускается заново: хранить в `.env` нечего.
     `MINIO_PROMETHEUS_AUTH_TYPE=public` отвергнут: порт S3 опубликован наружу, и размеры
     бакетов и состав узлов стали бы видны любому, а сервис MinIO пришлось бы пересоздать.
   - **Meilisearch** — ключ с постоянным `uid` и действием `metrics.get`. Значение ключа
     выводится из мастер-ключа, после его смены ключ обновляется сам. Экспериментальные
     метрики (`MEILI_EXPERIMENTAL_ENABLE_METRICS`) уже включены в основном сервисе; правило
     «Meilisearch не отвечает» — только предупреждение: данные целы, индекс восстанавливает
     переиндексация.

   Токены лежат в томе `prometheussecrets` (владелец — `nobody`, права 0400), Prometheus
   читает их при каждом опросе (`credentials_file`).
2. **Экспортёры**:
   - `prometheuscommunity/postgres-exporter` — активность и длинные транзакции, соединения,
     размер баз, блокировки, WAL, контрольные точки, возраст транзакций. Потабличные
     сборщики выключены: у каждого датасета своя таблица в схеме `ds`, и метрики росли бы
     вместе с данными;
   - `oliver006/redis_exporter`.

   Порты наружу не публикуются. У целей в метке `instance` — имя службы (`postgres`,
   `redis`, `minio`, `meilisearch`), а не адрес экспортёра. Так оно читается в письме, и по
   нему подавляются предупреждения.
3. **Правила** (`alerts.yml`, группы по службам). Postgres:
   - не отвечает;
   - соединений больше 80 % `max_connections`;
   - транзакция дольше 30 минут — ночной `pg_dump` большой базы короче;
   - `idle in transaction` дольше 5 минут;
   - взаимные блокировки вне тестовых баз;
   - возраст транзакций выше миллиарда;
   - отставание реплики — срабатывает только на реплике.

   Redis:
   - не отвечает;
   - память у `maxmemory` или больше 2 ГБ без предела;
   - отказ соединений;
   - отказ записи (OOM, MISCONF);
   - сбой сохранения на диск.

   MinIO:
   - не отвечает;
   - узлы или диски вне сети;
   - свободно меньше 10 % (предупреждение) и 5 % (критично). В S1 тома всех служб обычно на
     одном диске, так что это место всей установки.

   Meilisearch: не отвечает, индексирование отстаёт, очередь задач почти заполнена. Сама
   наблюдаемость: метрики службы не собираются, Alertmanager не доставил оповещение.
4. **Alertmanager** в профиле `observability`. Интерфейс — только на `KCHS_BIND`, как у
   Grafana. Конфигурация собирается из переменных окружения при каждом старте контейнера
   (`infra/observability/alertmanager/entrypoint.sh`):
   - **почта** — через тот же SMTP, что у api и worker в контейнерах (`SMTP_URL_INTERNAL`,
     в разработке — mailpit), или отдельный `ALERTMANAGER_SMTP_URL`:
     - адрес `smtp[s]://логин:пароль@узел:порт` разбирается сам, `%XX` в логине и пароле
       раскодируются;
     - `smtp` с логином требует STARTTLS, чтобы пароль не ушёл открытым;
     - `smtps` — порт 465 с TLS сразу;

     Получатели — `ALERTMANAGER_EMAIL_TO`, адреса через запятую;
   - **Telegram** — если задан `ALERTMANAGER_TELEGRAM_CHAT_ID`. Бот по умолчанию тот же, что
     у платформы: Alertmanager только отправляет сообщения, долгому опросу worker это не
     мешает. Из закрытого контура — через исходящий прокси (ADR-0132) или свой Bot API;
   - **шаблоны по-русски** (`templates/kchs.tmpl`): тема «[Портал КЧС] ТРЕВОГА: правило —
     суть», текст и HTML письма, сообщение Telegram, местное время (`TZ`). Название установки
     задаётся в `ALERTMANAGER_INSTALLATION`;
   - **ритм**: группировка по правилу и заданию; первое письмо через 30 с; новые в группе —
     не чаще раза в 5 минут; повтор — раз в 4 часа; письмо «Восстановлено», когда правило
     перестаёт срабатывать;
   - **подавление**: critical подавляет warning того же `instance`. Упал Postgres — его
     «соединения» отдельно не шлются.

   Без получателей Alertmanager работает «в пустоту», оповещения видны в его интерфейсе и в
   Prometheus, при старте в журнал пишется предупреждение.
5. **Дашборд** «kchs — инфраструктура» (`kchs-infrastructure.json`): Postgres, Redis, MinIO,
   Meilisearch, доставка оповещений.

## Альтернативы

- **Экспортёры для MinIO и Meilisearch.** Обе службы отдают метрики сами. Лишний контейнер
  ничего бы не добавил, кроме ещё одной учётки.
- **Пароли и токены метрик в `.env`.** Для MinIO и Meilisearch их можно выпускать заново при
  каждом запуске, храня только в томе; меньше секретов для ротации и утечки. Для Postgres
  пароль в `.env` оставлен: он нужен экспортёру стабильно между перезапусками.
- **Роль мониторинга в `postgres/init`.** Скрипт инициализации выполняется только на пустом
  кластере: существующие установки остались бы без роли. Он потребовал бы ещё и новую
  переменную в сервисе postgres, то есть его пересоздание.
- **Шаблон конфигурации через `configs.content` compose.** Подстановка переменных есть, но
  блок Telegram по условию и разбор адреса SMTP в ней не выразить.
- **Оповещения через саму платформу** (вебхук в api → уведомления администраторам).
  Удобные каналы, но когда лежит база или api, оповещение не дойдёт, а именно тогда оно и
  нужно.
- **Node exporter для места на диске.** Смотрит на корень хоста, требует монтирования `/` и
  на Docker Desktop показывает диск виртуальной машины. В S1 место томов видно по MinIO;
  отдельные диски под тома — повод добавить node exporter.

## Последствия

- Новые сервисы профиля `observability`:
  - `metrics-init-postgres`, `metrics-init-minio`, `metrics-init-meilisearch` — одноразовые;
  - `postgres-exporter`, `redis-exporter`, `alertmanager`;
  - тома `prometheussecrets` и `alertmanagerdata`.

  Сервисы основного стека не менялись и не пересоздаются.
- Новые переменные: `KCHS_MONITOR_PASSWORD` (`generate-secrets.sh`), `ALERTMANAGER_PORT`,
  `ALERTMANAGER_EMAIL_TO`, `ALERTMANAGER_SMTP_URL`, `ALERTMANAGER_SMTP_FROM`,
  `ALERTMANAGER_SMTP_REQUIRE_TLS`, `ALERTMANAGER_TELEGRAM_CHAT_ID`,
  `ALERTMANAGER_TELEGRAM_BOT_TOKEN`, `ALERTMANAGER_TELEGRAM_API_URL`,
  `ALERTMANAGER_INSTALLATION`, `ALERTMANAGER_EXTERNAL_URL`. Все необязательны: без них
  профиль поднимается, но писем нет.
- Что делать по каждому оповещению — `infra/runbooks/incident.md`, раздел «Оповещения
  наблюдаемости»; настройка получателей и проверка доставки — руководство 28.
- Не сделано:
  - трассы движка;
  - метрики диска сервера;
  - предел памяти Redis (`maxmemory`) — это изменение основного сервиса, до него
    срабатывает только порог 2 ГБ;
  - экран «Здоровье системы» из метрик;
  - чарт S2 оповещений не содержит: в кластере Prometheus и Alertmanager ставит
    администратор (ADR-0118), правила переносятся в `PrometheusRule`.

  Всё, кроме метрик диска, сделано в ADR-0167 (25.09.2026).
