# 0192. Протокол realtime в контрактах: события в обе стороны, типы на обеих сторонах, тест «у каждого события есть обработчик»

Статус: Принято
Дата: 2026-10-05

## Контекст

Часть 3Д этапа 3 плана укрепления (`07-architecture-hardening.md` §5.0а; проверка этапа 3 в §6).

- **Протокол описан частично.**
  - Перечень `RT_SERVER_EVENTS` знал 12 событий сервера из 20, схемы были у 4 нагрузок.
  - Из сообщений клиента описано одно — `subscribe`. Его поле `since` никто не читал.
- **Типов нет.**
  - `emitToRoom(room, event: string, payload: unknown)` и
    `onRealtimeEvent(event: string, handler: (payload: unknown) => void)` не проверяли ни имя, ни
    нагрузку.
  - Обработчики приводили нагрузку руками (`payload as {…}`).
  - Шлюз читал сообщения клиента как `payload?.rooms ?? []`.
- **Сверка отправок и подписок нашла мёртвые события.**
  - `meeting.knock`: ведущий видел заявку гостя только опросом раз в 15 с. Копию организатору в
    `user:{id}` не слушал никто.
  - `call.declined`: звонящему не показывалось ничего.
  - `presence.changed`: свой статус «на встрече» обновлялся только при перезапросе.
- **Ход заданий не доставлялся.** `job.progress` и `job.finished` шли в комнату `job:{id}`, а в неё
  клиент не входит ни на одном экране. Строка состояния «Мои задания» не двигалась. Прогресс в
  `rt:job` уходил необрезанным, хотя запись хранит 0…1.
- **Комнаты терялись.**
  - После переподключения сокет на сервере новый и без комнат, а клиент заново не подписывался.
    Открытая беседа и вкладки не в фокусе переставали получать события до смены набора вкладок.
    Видимые вкладки возвращала отметка присутствия.
  - Подписка экрана, сделанная до подключения сокета, терялась.
  - При смене набора вкладок клиент отписывался от всех комнат и подписывался снова, поэтому общие
    комнаты на миг выпадали.

## Решение

### 1. Протокол — `packages/contracts/src/realtime/protocol.ts`

- **`RT_SERVER_PAYLOADS`** — 19 событий сервера, имя → zod-схема нагрузки. Таблица — в
  `16-api-and-events.md` §3. Схемы доменов переиспользуются: `IncomingCall`, `InboxCounts`.
- **`RT_CLIENT_PAYLOADS`** — 5 сообщений клиента:
  - `subscribe` и `unsubscribe` — `{rooms}`, до `ROOMS_PER_SUBSCRIBE` = 64 комнат;
  - `presence.view` и `presence.leave` — `{objectId}`;
  - `typing` — `{conversationId}`.
- **Что убрано из описания.**
  - Поле `since`: повтора пропущенного нет (см. «Последствия»).
  - Сообщение `ping` из документа: в коде его не было, пульс у Socket.IO свой.
- **Типы.** `RtServerEvent`, `RtServerPayload<E>`, `RtServerEvents` и `RtClientEvents` — карты
  событий для Socket.IO на обеих сторонах.
- **`ROOMS_PER_SUBSCRIBE`** лежит в `limits.ts`, без схем: оболочка web берёт предел, не таща схемы
  в свой чанк (бюджет ADR-0166).

### 2. Сервер

- **Отправка.** `emitToRoom<E>(room, event: E, payload: RtServerPayload<E>)` и `emitToUser` так же.
  Socket.IO шлюза типизирован картами протокола, поэтому прямые отправки шлюза тоже проверяются:
  `presence`, `typing`, `acl.revoked`, ход заданий.
- **Сообщения клиента.** До разбора их нагрузка — `unknown`, шлюз разбирает её схемами контракта.
  Подписку не по схеме он отклоняет целиком (`{granted: [], denied: []}`). Прежде каждая комната
  проверялась отдельно, но клиент шлёт только верные имена.
- **Ретрансляция (ADR-0169).**
  - Схема команды принимает только имя из протокола. Команду не по схеме узел api не выполняет и
    пишет предупреждение.
  - Нагрузку на канале не проверяем: её проверил тип в процессе-отправителе. Потерять сообщение в
    работе из-за формата идентификатора хуже, чем доставить его.
- **Ход заданий** — сигнал `rt:job` со схемой (`kernel/jobs/signal.ts`) и инициатором.
  - Узел api доставляет его в комнату задания и в комнату `user:{инициатор}`: «Мои задания»
    (`GET /jobs`) — это задания инициатора.
  - Клиенту инициатор не передаётся.
  - Прогресс обрезается до 0…1, как в записи.
- **Подписчики.** Нагрузки событий шины они берут по каталогу (`EventPayload<…>`). `meeting.changed`
  строится по таблице событий встречи, а не срезом имени.

### 3. Клиент

- **Сокет** — `Socket<RtServerEvents, RtClientEvents>`. Он не выходит из
  `shared/realtime/client.ts`: `connectRealtime` его больше не возвращает. Неиспользуемые
  обработчики `connectRealtime` (`onObjectUpdated` и другие) убраны.
- **`onRealtimeEvent<E>(event, handler: (payload: RtServerPayload<E>) => void)`.** Тип нагрузки
  выводится из имени, ручные приведения в чате и встречах убраны.
- **Комнаты экранов — со счётчиком.**
  - `subscribeRooms` и `unsubscribeRooms` удерживают и отпускают комнаты.
  - Отписка уходит после такта, поэтому комнаты, общие для старого и нового набора, не выпадают.
  - При подключении и после каждого переподключения клиент подписывается на все удерживаемые
    комнаты.
  - Подписка уходит пачками по 64.
- **Схемы нагрузок клиент не исполняет — только типы.** Сервер и клиент — одна сборка, проверку
  даёт компилятор, а схемы в оболочке стоили бы бюджета.

### 4. Мёртвые события

| Событие | Решение |
|---|---|
| `meeting.knock` | Комната встречи ведущего (`meeting-view`) сразу перечитывает заявки. Опрос раз в 15 с остаётся страховкой: пропущенное при переподключении сообщение шлюз не повторяет, а гость без ответа ждёт. Копия организатору в `user:{id}` убрана: заявки показывает только комната встречи, а ведущий в ней подписан на комнату объекта. |
| `presence.changed` | Клиент сразу перечитывает свой статус — только `['chats', 'presence']`. Вход в комнату и выход из неё видны и с другой вкладки. |
| `call.declined` | Сообщение звонящему убрано, событие шины осталось (журнал, автоматизация). Отказ можно показать только текстом («… отклонил звонок»), а словари на этапе 3 разносятся по модулям (3В, ADR-0191). Строка появится в словаре модуля встреч вместе с обработчиком; до тех пор отправка без обработчика уронила бы тест. **Возвращено ADR-0193.** |
| `job.progress`, `job.finished` | Доставка в комнату инициатора (п. 2). Клиент правит ход в кэше «Моих заданий» на месте, а если задания в списке ещё нет — перечитывает список, не чаще раза в секунду: прогресс приходит часто. |

### 5. Тест «у каждого события есть обработчик»

`packages/contracts/src/realtime/__tests__/handlers.test.ts` обходит исходники компилятором
TypeScript.

- **Что считается отправкой и подпиской.**
  - Сервер шлёт: `emitToRoom` и `emitToUser` (весь `apps/api/src`), `.emit` шлюза
    (`kernel/realtime`).
  - Клиент слушает: `socket.on` (`shared/realtime`) и `onRealtimeEvent` (весь `apps/web/src`).
  - Клиент шлёт `socket.emit` (`shared/realtime`), шлюз слушает `socket.on` (`kernel/realtime`).
- **Когда тест падает** — в обоих направлениях:
  - событие вне протокола;
  - событие шлют, но не слушают, или слушают, но не шлют;
  - событие протокола не шлют и не слушают.
- **Исключения.**
  - События транспорта Socket.IO (`connect`, `connect_error`, `disconnect`, `disconnecting`) — не
    протокол.
  - Вычисляемое имя допускается только в двух местах шлюза: `emitToUser` (обёртка над `emitToRoom`)
    и `emitVia` (общая отправка). Другое вычисляемое имя роняет тест, устаревшее исключение — тоже.
    Приведение (`'a' as 'b'`) считается вычисляемым именем.
- **Что не обходится.** `.emit` и `.on` в других местах — карта, редактор, Redis: сокет есть только у
  шлюза и у клиента realtime.
- **Где живёт тест.** Рядом с протоколом, как сверка ACL Redis
  (`jobs/__tests__/engine-access.test.ts`). Он читает обе стороны, а сами стороны друг друга не
  видят.

## Альтернативы

- **Две половины теста — в api и web.** Каждая сверяла бы свою сторону с протоколом. Вместе это то
  же условие, но «шлют, но не слушают» распалось бы на два теста в разных пакетах.
- **Регулярные выражения вместо компилятора.** Они ломаются на переносах аргументов, комментариях и
  условном имени. Разбор компилятором уже используется для литералов i18n.
- **Проверка нагрузки на клиенте схемами.** Отсекла бы чужие сообщения, но схемы протокола тянут
  схемы доменов в чанк оболочки.
- **Проверка нагрузки на канале ретрансляции.** Ошибка формата (например, идентификатор не UUID)
  в работе молча теряла бы сообщение. Тип отправителя ловит расхождение раньше.
- **Восстановление состояния соединения Socket.IO (`connectionStateRecovery`).** Вернуло бы комнаты
  и пропущенные пакеты при коротком разрыве, но `@socket.io/redis-adapter` его не поддерживает —
  нужен адаптер на Redis Streams.
- **Снимок протокола в `contracts:snapshot` (ADR-0189).**
  - Сервер и клиент выкатываются одной сборкой, внешних потребителей у realtime нет.
  - Совместимость между версиями протокол не обещает. Вкладка старой сборки после выката
    доживает на обработчиках, которые только перечитывают кэш.

## Последствия

- **Новое событие realtime:** схема в `RT_SERVER_PAYLOADS` → отправка через `emitToRoom` или
  `emitToUser` → обработчик в клиенте. Имя вне протокола не пропустит компилятор, забытый
  обработчик или забытую отправку — тест.
- **Пропущенные за разрыв сообщения не повторяются** — `since` нет и не было. Экран, где пропуск
  недопустим, держит опрос-страховку или перечитывает данные при подключении.
