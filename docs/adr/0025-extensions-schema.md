# 0025. Расширения PostgreSQL в схеме `extensions`

Статус: Принято

Контекст: критерий приёмки P0-E02 требует, чтобы роль `kchs_query` не имела прав
на схему `public`. Но пользовательские запросы к датасетам используют функции
PostGIS (`ST_*`) и операторные классы `pg_trgm`, которые при установке по
умолчанию создаются в `public`. Дать `USAGE` на `public` — значит открыть путь
к платформенным таблицам, если где-то будет забыт `REVOKE`.

Решение: все расширения (`postgis`, `vector`, `pg_trgm`, `btree_gist`,
`unaccent`, `pgcrypto`) устанавливаются в выделенную схему `extensions`.
`search_path` базы — `public, extensions`; для роли `kchs_query` — `ds, extensions`.
`USAGE` на `extensions` выдан всем ролям, на `public` — только приложению,
мигратору, аудиту и read-only.

Альтернативы:
- Расширения в `public` + `GRANT USAGE ON SCHEMA public TO kchs_query` с ручными
  `REVOKE` на каждую таблицу — хрупко, ошибка одной миграции открывает данные.
- `SECURITY DEFINER`-функции-обёртки для чтения `ds` — избыточная сложность,
  теряется планирование запросов.

Последствия: индексы в миграциях указывают операторный класс с квалификатором
(`extensions.gin_trgm_ops`). Резервное копирование и обновление PostGIS не
меняются. Роль `kchs_query` физически не видит ни одной таблицы `public`.
