# 0190. Контракт движка: схемы заданий и обратных вызовов, реестр хранения полей; компилятор на Postgres и mypy в CI

Статус: Принято
Дата: 2026-10-05

## Контекст

Часть 3Г этапа 3 плана укрепления (`07-architecture-hardening.md` §5.0а; находка 13 и
«Тесты» в §3.4).

- **С движком общие только константы.**
  - `gen:engine` выгружал перечни и пределы: форматы, коды ошибок, очереди.
  - Нагрузку задания api собирало словарём в месте постановки, движок читал её как
    `data["…"]`. Опечатка или новое поле проявлялись только на стенде.
  - Тело статуса задания и `NormalizedReport` жили в api: во внутреннем маршруте и в сервисе
    импорта. Ответы обратных вызовов были встроены в маршруты.
- **Расхождения, найденные при сверке.**
  - api слал в `imports:dataset.normalize` поле `onError`, движок его не читал: как грузить
    строки с ошибками, решает загрузка воркером по записи импорта.
  - Движок читал в `transform:columnar.build` поле `timeoutS`, api его не слал.
  - Предел примеров ошибок импорта (50) жил в api и в движке отдельно. Профили демо-данных —
    списком в api и словарём в движке.
  - Запись задания движок брал как `jobRecordId or job.id`: задание без конверта api
    исполнялось бы, а отчитываться было бы некому.
- **Типы полей повторены в пяти местах и разошлись.**
  - Тип столбца Postgres — `data/infra/physical.ts`; приведения DuckDB — `query/dialect.ts`;
    типы Arrow копии — `columnar.py`; семейства геовыгрузки — `geo_export.py`; перечень типов
    копии — `columnar-service.ts`.
  - Слова «да/нет»: вставка в таблицу (`@kchs/fields`) понимала `on`, `off`, `-`, импорт файла
    (`values.py`) — `t`, `f`, `вкл`, `выкл`, `ха`, `✔`. Одна и та же ячейка давала «да» или
    ошибку в зависимости от пути.
- **CI.**
  - 51 тест исполнения SQL компилятора на Postgres (`execute`, `spatial-execute`,
    `raw-sql-execute`) в задании unit пропускался: базы там нет.
  - mypy движка в CI не было.
  - Очередь `ai` числилась за движком, но её никто не ставил и не читал: модель зовёт api
    (ADR-0061), векторы движок считает синхронным вызовом (ADR-0099). ACL Redis при этом
    открывал движку `bull:ai:*`.

## Решение

### 1. Задания движка — схемы в `packages/contracts/src/engine`

- **`ENGINE_JOBS`** (`jobs.ts`) — все 10 заданий движка, ключ `<очередь>:<имя>`, у каждого
  zod-схема нагрузки и результата: `transform:engine.echo`, `transform:demo.generate`,
  `transform:columnar.build`, `render:file.process`, `render:document.pdf`,
  `render:document.render`, `render:report.render`, `media:media.transcribe`,
  `imports:users.parse`, `imports:dataset.normalize`.
- **`EngineJobEnvelope`** — поля, которые добавляет `JobService.dispatch`: `jobRecordId`,
  `initiatorId`, `callbackToken`, `callbackScope`.
- **`ENGINE_CALLBACKS`** (`callbacks.ts`) — 10 обратных вызовов: путь маршрута api, тело и
  ответ.
  - Сюда перенесены `JobStatusReport` (статус задания) и `NormalizedReport`.
  - Остальные тела и ответы уже были в контрактах доменов: `FileProcessedInput`,
    `DocumentPdfResult`, `TranscriptResult`, `UsersImportParsed`, `ReportRenderResult`,
    `DocumentRenderResult`, `ReportRenderStart`, `DocumentRenderStart`.
- **`gen:engine`** пишет `kchs_engine/contracts/jobs.json` — JSON Schema каждой нагрузки,
  результата, тела и ответа.
  - Без `unrepresentable: 'any'`: тип, которого нет в JSON Schema, роняет генерацию.
  - То, что движок получает (нагрузка, ответ), — в форме `output`: после разбора, со
    значениями по умолчанию. То, что движок отправляет (результат, тело), — в форме `input`:
    как это примет api.
- **Тест контрактов**: ключ — очередь и имя, очередь исполняет движок, схемы выражаются JSON
  Schema, путь — внутренний маршрут с одним параметром.

### 2. Api ставит задание по схеме

- **Постановка.** `engineJob(key, data)` (`kernel/jobs/engine.ts`) берёт тип нагрузки из
  схемы. Все постановки заданий движка идут через него, константы заданий модулей —
  `engineJobRef(key)`.
- **Разбор до записи.** `JobService.schedule` разбирает нагрузку задания движка его схемой до
  записи в реестр. В реестр и очередь попадает разобранное значение: без лишних полей, со
  значениями по умолчанию. Расхождение — `internal_error` с путями полей: это ошибка кода, а
  не данных пользователя.
- **Маршруты.** Маршрут статуса задания и `/internal/data/imports/:id/normalized` берут тела
  из контрактов. Интеграционный тест (`engine-callbacks.test.ts`) сверяет каждый маршрут
  обратного вызова с `ENGINE_CALLBACKS` по JSON Schema тела и ответа и проверяет, что других
  маршрутов с токеном задания нет.
- **Результат.** Подписчик сборки колоночной копии читает результат схемой
  `ColumnarBuildJobResult`. Импорт пользователей читает свою нагрузку схемой задания.

### 3. Движок проверяет нагрузку на входе

- **Модели, а не JSON Schema.** Модели pydantic (`TypedDict` с `with_config`) — в
  `kchs_engine/contracts/jobs.py` и `callbacks.py`. pydantic уже в зависимостях движка;
  валидатор JSON Schema — новая зависимость и пересборка слоя зависимостей образа. Поля
  моделей названы как в JSON: обработчики читают словари по тем же ключам, `NotRequired`
  точно выражает «поля может не быть».
- **Вход и выход.**
  - Вход (нагрузка, ответ api) — `extra="ignore"`: конверт задания и поле новой версии api не
    мешают. Обязательны только поля, без которых движок не работает.
  - Выход (результат, тело) — `extra="forbid"` и `strict=True`.
- **Обработчик.** `@handler` регистрирует только задание из контракта и возвращает
  обработчик с проверкой. Нагрузка или результат не по контракту — `PermanentJobError`:
  повтор не поможет.
- **Воркер** требует конверт api. Без `jobRecordId` задание отклоняется
  (`UnrecoverableError`): отчитываться некому.
- **Обратные вызовы** (`api.py`): путь — из `jobs.json`, тело проверяется до отправки, ответ
  api — до чтения обработчиком (`CallbackContractError`).
- **Сверка моделей со схемами** — `tests/test_engine_contracts.py`:
  - у объектов те же поля;
  - то, что движок получает, модель принимает целиком: обязательное в модели api присылает
    всегда, перечни и `null` в модели не уже, чем в схеме;
  - то, что движок отправляет, api примет: обязательное в схеме обязательно в модели, типы и
    перечни модели — подмножество схемы;
  - пределы длины и диапазоны проверяет api своей схемой, здесь сверяется форма;
  - сама проверка покрыта тестом на расхождения, которые она обязана находить.

### 4. Реестр хранения полей

- **`FIELD_STORAGE`** (`packages/contracts/src/data/field-storage.ts`) — для каждого хранимого
  типа: тип столбца Postgres, тип Arrow колоночной копии, тип DuckDB, семейство геовыгрузки.
  Рядом — `COLUMNAR_DECIMAL` (38, 12), `DURATION_UNIT` (минуты), `COLUMNAR_FIELD_TYPES`.
  Движок получает реестр в `field_types.json`.
- **Читатели**: `physical.ts` (`pgColumnType`), `query/dialect.ts`, `columnar-service.ts`,
  `columnar.py`, `geo_export.py`.
- **`BOOLEAN_WORDS`** (`fields/values.ts`) — одно множество слов «да/нет» для `@kchs/fields` и
  `values.py`, объединение прежних двух. Импорт файла теперь понимает `on`, `off`, `-` (прежде
  — ошибка значения), вставка — `t`, `f`, `вкл`, `выкл`, `ха`, `✔`.
- **Тесты с обеих сторон**: `packages/query/test/field-storage.test.ts` (приведения
  компилятора = типы столбцов Postgres и копии), `apps/engine/tests/test_field_types.py`,
  тест `@kchs/fields`. Описание — `contracts/field-types.md`, «Реестр хранения».

### 5. CI

- **Интеграционное задание** запускает тесты исполнения `@kchs/query` на базе стека
  (`KCHS_QUERY_TEST_DATABASE_URL` из `.env`).
- **Задание «Тесты движка»** запускает `uv run mypy`, настройки — в `pyproject.toml`.
  - Библиотеки без типов — `ignore_missing_imports`.
  - База исключений — `ignore_errors` для четырёх модулей с прежними ошибками:
    `demo.boundaries`, `render.documents`, `render.docx_report`, `render.report`. Модуль уходит
    из списка, когда его ошибки исправлены; новые модули в список не добавляются.

### 6. Очередь `ai` убрана

- Очередь удалена из `QUEUES` и `QUEUE_RUNTIME` и из ACL Redis движка (compose и чарт).
- Строка `ai` в таблице ADR-0035 больше не действует.
- Миграция не нужна: `jobs.queue` — текст, заданий этой очереди не было.

## Альтернативы

- **Проверка в движке по JSON Schema** (`jsonschema`, `fastjsonschema`). Один источник без
  моделей, но новая зависимость движка, пересборка слоя зависимостей образа и словари без
  типов для mypy. Сверка моделей тестом находит те же расхождения.
- **Генерация моделей pydantic из JSON Schema** (`datamodel-code-generator`). Ещё один
  генератор и зависимость, сгенерированные модели хуже читаются.
- **`BaseModel` с алиасами вместо `TypedDict`.** Чтобы поле могло отсутствовать, нужны
  значения по умолчанию, а нагрузка перестаёт быть словарём обработчика.
- **Отклонять в api любое незнакомое задание очереди движка.** Тест надёжности ставит в
  очередь движка свои задания. Движок без контракта обработчик не зарегистрирует, так что
  незнакомое задание всё равно не исполнится.

## Последствия

- **Новое задание или поле**: схема в `packages/contracts` → `gen:engine` → модель движка →
  тест контракта. Забытая модель роняет тесты движка, забытая пересборка — CI статики.
- **Форма тел внутренних маршрутов не изменилась** — снимок OpenAPI (ADR-0189) тот же.
- **Синхронные вызовы api → движок** — анализ файла, геовыгрузка, запрос к копии, векторы —
  в контракт не вошли: это по-прежнему модели FastAPI и схемы zod на стороне api.
- **После 3А-1** (ADR-0188) маршруты обратных вызовов можно описать в таблице маршрутов,
  ссылаясь на `ENGINE_CALLBACKS`.
