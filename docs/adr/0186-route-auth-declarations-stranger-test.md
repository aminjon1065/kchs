# 0186. Маршрут с параметром пути объявляет, кто проверяет доступ; тест «посторонний не видит»

Статус: Принято
Дата: 2026-10-06

## Контекст

`route()` не регистрирует маршрут без `auth` (17-security.md §3). Политика `{ action }`
проверяет право на объект в ядре до обработчика. Но из 685 маршрутов API 338 объявлены
`auth: 'session'`, и у 168 из них в пути есть параметр — id задачи, документа, сообщения,
запуска. Права в них проверяет сервис внутри обработчика. Выборочная проверка нашла
`authorize` везде, где смотрели, но гарантии на уровне маршрута не было: новый маршрут
`'session'` мог молча пропустить проверку. Негативные тесты по типам объектов
(`test/access-matrix.test.ts`) ходили только по маршрутам, перечисленным в фикстурах.

## Решение

**Явное объявление.** Маршрут `auth: 'session'` с параметром пути не регистрируется, ошибка
возникает на старте (`assertRouteAuth` в `shared/http/route.ts`). Вместо него — один из трёх
вариантов:

| Вариант | Что в пути | Кто проверяет | Маршрутов |
|---|---|---|---|
| `{ delegated, objectType }` | объект реестра (`any` — любой тип) | названный сервис: `TaskService.get`, `authorize(view)` | 125 |
| `{ delegated, resource }` | вложенный ресурс объекта: сообщение, ход маршрута, запуск, ответ формы, задание | названный сервис | 26 |
| `{ owned }` | свой ресурс пользователя вне реестра: сессия загрузки, ключ входа, токен, дело «Входящих», замещение | сервис ищет только среди ресурсов вошедшего | 12 |
| `{ open }` | общий справочник: карточка сотрудника, глифы и значки карты, тайлы границ, схема системного датасета | никто; строка объявления — причина | 5 |

Плагин аутентификации обращается с ними как с `'session'`. Страница офисного редактора
(`/office/editor/:id`) регистрируется вне реестра API, но объявляется тем же способом.
Регистратор держит реестр маршрутов процесса (`registeredRoutes()`), и тесты проверяют по
нему каждый маршрут.

**Тест «посторонний не видит»** — в `test/access-matrix.test.ts`, на объектах матрицы типов.

- **Объектные маршруты.** Тест обходит реестр и вызывает от постороннего каждый маршрут
  `{ action }` (189) и каждый делегированный маршрут с типом объекта (125): объект матрицы
  нужного типа, остальные параметры, тело и строка запроса собираются из zod-схемы маршрута
  (`z.toJSONSchema`, минимальные значения). Ждётся 403 или 404.
  - Тела, которые схема не даёт собрать из-за уточнений (`refine`), — в `PAYLOADS`: срок
    «датой или числом», непустой список получателей, хотя бы одно изменение.
  - Пачка правок строк проверяется в обеих ветках: сразу и заданием.
  - Маршрут, до проверки прав которого не дойти, — в `CHECKED_MANUALLY` с причиной. Сейчас
    список пуст, а строка, ставшая лишней, роняет тест.
- **Вложенные ресурсы.** Сообщение обсуждения, задание и служебная учётная запись — со
  своими фикстурами, это 8 маршрутов. Ход маршрута, ответ формы, импорт, запуск отчёта,
  рендер документа и запуск правила (18 маршрутов) проверены в профильных тестах:
  `RESOURCES_ELSEWHERE` называет, в каких. Новый ресурс без фикстуры и без строки там —
  падение.
- **Свои ресурсы.** Сессия загрузки, токен API и шаблон резолюции создаются администратору,
  и посторонний получает 403 или 404. Отмена чужой загрузки идемпотентна и ничего не меняет;
  тест проверяет, что сессия администратора не отменена. Остальные свои ресурсы — в
  `OWNED_ELSEWHERE` со ссылкой на тест. Справочники — явным списком `OPEN_ROUTES`: новый
  справочник проходит через ревью.

**Что нашлось и исправлено:**
- `POST /datasets/:id/rows/batch` с `async: true` или больше 500 операций ставил задание без
  проверки прав: посторонний получал 202. Правку задание не делало — оно выполняется правами
  инициатора, — но проверка в момент действия (ADR-0123) была нарушена, и очередь можно было
  засыпать. Теперь до постановки проверяется уровень edit.
- `POST /meetings/:id/leave` отвечал постороннему 200 по чужой встрече и публиковал
  `meeting.participant_left` с её названием. Теперь сначала право view, а событие — только
  если участник действительно вышел.
- `GET /documents/territory/:id` проверял только, что территория есть в индексе: документы
  были отфильтрованы, но посторонний узнавал о существовании невидимой ему территории.
  Теперь, как у паспорта территории, — `TerritoryService.get`.

## Альтернативы

- **Перевести все делегированные маршруты на `{ action }`.** Проверку делало бы ядро, но
  часть сервисов различает 403 и 404 по смыслу, допускает участников шага маршрута или
  проверяет вложенный ресурс. Это переписывание обработчиков без выигрыша в гарантии.
- **Только статический линтер, что обработчик зовёт `authorize`.** Он не видит проверку
  внутри сервиса и не доказывает поведение; тест по реестру проверяет ответ.
- **Перебор всех объектов матрицы для каждого маршрута.** Чужой тип даёт 404 «не найдено» и
  ничего не доказывает. Поэтому объявление называет тип или ресурс.

## Последствия

- Новый маршрут с объектом в пути объявляет проверяющего, и генерируемый тест сразу
  проверяет его на постороннем. Без фикстуры, тела или строки в списках тест падает.
- Имя проверяющего в объявлении — документация. Поведение доказывает тест, а не строка.
- Ограничения:
  - вложенный параметр, кроме главного, подставляется случайным UUID: сервис, который ищет
    вложенный ресурс раньше родителя, ответит 404 и пройдёт;
  - маршруты `{ capability }` с параметром пути тест не обходит — у них нет объекта, а
    способности выдаются ролями;
  - отзыв замещения чужим отвечает 403, а не 404, и выдаёт существование замещения — мелочь,
    записана для этапа 2В.
