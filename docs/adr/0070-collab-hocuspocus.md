# 0070. Совместное редактирование: Hocuspocus в процессе api на `/collab`

Статус: Принято
Дата: 2026-09-19

## Контекст

ADR-0018 выбрал Tiptap + Yjs/Hocuspocus и требует прав на уровне collab-сервера;
16-api-and-events.md §3 задаёт путь `/collab`, имя документа = `objectId`, вход по токену
сессии и режимы `edit`/`view`. Caddy (ADR-0044) и dev-прокси Vite уже отдают `/collab/*`
процессу api, таблица `yjs.documents` создана в фазе 0. Открытыми оставались:

- где работает сервер: процесс, порт, путь;
- как проверять вход, чтобы сокет с cookie пользователя не открыла чужая страница;
- что делать с правами, которые меняются, пока документ открыт часами;
- как хранить состояние, не терять правки и не ломаться при нескольких процессах;
- как тело документа попадает в поиск, экспорт и ленту событий.

Первый потребитель — тетради (P2-E05 S02, ADR-0071); дальше — страницы знаний, протоколы,
описания объектов.

## Решение

1. **Процесс, порт, путь.**
   - Hocuspocus 4 работает внутри процесса api (роли `api` и `all`) на том же HTTP-сервере и
     порту, что REST и realtime (3000). Апгрейды на `/collab` и `/collab/…` обслуживает
     crossws — так же, как `Server` самого Hocuspocus; остальные апгрейды остаются
     realtime-шлюзу `/ws`.
   - Клиент подключается к `/collab/ws`: один сокет на вкладку браузера, документы
     мультиплексируются по имени.
   - Рукопожатие завершается сразу, права проверяются уже в протоколе. Иначе engine.io закрыл
     бы «чужой» для него апгрейд через секунду.
   - Сообщение — не больше 16 МБ (первая синхронизация большого документа). Пинг — crossws
     (30 с) и Hocuspocus (60 с).
2. **Вход.**
   - Сессия — из cookie запроса апгрейда (`SESSION_COOKIE_NAME`).
   - При входе в каждый документ сверяется CSRF-токен сессии, который клиент кладёт в поле
     `token` протокола. Чужая страница может открыть сокет с cookie пользователя (CSWSH), но
     токена не знает. Проверка Origin не нужна и не ломается при входе по другому имени хоста.
   - Пока не сменён временный пароль или не подключён обязательный второй фактор, вход
     отклоняется с причиной `setup_required`, как в realtime.
   - Причины отказа уходят клиенту (`onAuthenticationFailed`): `unauthorized`,
     `setup_required`, `not_found`. Последняя — и когда объекта нет, и когда нет права `view`,
     и когда тип без совместной правки: существование объекта не раскрывается.
3. **Права.**
   - `authorize(view)` открывает документ, `authorize(edit)` — открывает для правки. Иначе
     подключение только для чтения (`readOnly`): сервер не применяет обновления клиента и
     отвечает `SyncStatus false`. Присутствие и курсоры (awareness) разрешены всем.
   - Объект в архиве — только чтение: так решает `authorize`.
4. **Права меняются, пока документ открыт.**
   - Подключение перепроверяется при сообщении клиента, если с прошлой проверки прошло
     60 с: сессия жива, `view` и `edit` те же. Awareness клиента обновляется каждые 15–30 с,
     поэтому проверка не ждёт правки.
   - Сразу — по событиям `acl.changed`, `object.shared`, `object.moved`, `object.archived`,
     `object.restored`, `object.trashed`, `object.deleted`. Подписчик ядра `kernel-collab`
     (роль worker) публикует идентификатор объекта в канал Redis `rt:collab`, процесс api
     перепроверяет подключения к открытому документу.
   - Если доступ пропал или изменился, документ закрывается для подключения с причиной
     `access_changed`. Клиент переподключается и получает отказ или новый режим.
5. **Хранение.**
   - `yjs.documents` хранит полное состояние (`encodeStateAsUpdate`). Строка удаляется вместе с
     объектом: внешний ключ на `objects` с каскадом (миграция `notebooks_collab`).
   - Запись — через 2 с после последней правки, не реже раза в 10 с и сразу, когда уходит
     последний клиент. При остановке процесса отложенные записи сбрасываются до закрытия
     сокетов.
   - Запись идёт в транзакции с блокировкой строки. Если другой процесс записал то, чего нет в
     открытом документе, эта часть сначала применяется к документу (без повторного
     сохранения), затем пишется объединённое состояние.
6. **Реестр типов.**
   - Модуль регистрирует тип как тип объекта: `registerCollabType({type, initialState?,
     snapshot})`. Ядро хранит состояние и проверяет права; раскладку документа знает модуль.
   - `snapshot` пишет JSON-снимок тела в той же транзакции, что и состояние: таблицу модуля,
     версию объекта и доменное событие модуля (у тетради — `notebook.updated`).
   - Версия меняется через `ObjectService.update(…, {silent: true})`: `object.updated` на
     каждое сохранение засорил бы ленту активности. Поиск обновляет подписчик модуля на своё
     событие.
   - Документ пишут клиенты, поэтому снимок не доверяет содержимому. Если снимок всё же не
     записан, состояние Yjs сохраняется отдельно (правки важнее), а снимок догонит при
     следующей записи.
   - `initialState` строит документ для объекта без состояния в базе. Он детерминирован:
     одинаковые операции у двух процессов при слиянии не удваиваются.
7. **Правка сервером.** `CollabService.change(ctx, object, edit)` открывает прямое подключение
   Hocuspocus. Изменение сразу приходит всем, кто открыл документ, а снимок записан к возврату.
   Первый потребитель — `POST /notebooks/{id}/cells`.
8. **Богатый текст.**
   - Текст Tiptap в документе — `Y.XmlFragment` в раскладке y-prosemirror (@tiptap/y-tiptap).
   - Сервер переводит его в Tiptap JSON и обратно без ProseMirror и только в пределах белого
     списка контракта `common/rich-text.ts` (`RICH_TEXT_NODES`, `RICH_TEXT_MARKS`,
     `RICH_TEXT_ATTRS`). Ссылки — только http(s), почта, телефон и пути приложения
     (`safeHref`).
9. **Наблюдаемость.** Метрики `kchs.collab.documents` и `kchs.collab.connections`; `/collab`, как
   и `/ws`, не трассируется (ADR-0045).

## Альтернативы

- **Отдельный процесс и порт (`Server` Hocuspocus).** Лишний контейнер и маршрут прокси,
  вторая копия проверки сессии и реестра типов. На S1 выгоды нет.
- **Токен сессии в адресе сокета.** Попадает в журналы прокси и историю браузера.
- **Только cookie с проверкой Origin.** Ломается при входе по другому имени хоста; CSRF-токен
  уже есть у клиента и проверяется одинаково везде.
- **y-websocket.** Нет хуков авторизации и хранения — пришлось бы написать то же, что даёт
  Hocuspocus.
- **Журнал инкрементальных обновлений вместо полного состояния.** Запись быстрее, но нужна
  периодическая компакция. Документы тетрадей и страниц малы, полное состояние проще.

## Последствия

- Несколько экземпляров api (S2): документ, открытый в двух процессах, сходится только при
  записи (слияние из базы). Для S2 нужен `@hocuspocus/extension-redis` или маршрутизация по
  имени документа. Отложено до S2.
- Выход из системы без действий клиента закрывает документ при следующей проверке — до минуты;
  отдельного события `session.revoked` в шине нет, веб-клиент закрывает сокеты при выходе сам.
- Гость по ссылке через `/collab` документ не открывает (нет сессии). Гостевой просмотр — по
  REST-снимку, когда он понадобится.
- Новых переменных окружения нет. Зависимости api — `@hocuspocus/server`, `crossws`, `yjs`,
  `y-protocols` (peer Hocuspocus); веб — `@hocuspocus/provider`, `yjs`, `y-protocols`;
  дизайн-система — Tiptap 3 и `yjs`.
