# 0121. Проверки безопасности в CI: ZAP baseline со списком разобранных правил, Trivy по образам, жёсткий порог `pnpm audit`

Статус: Принято
Дата: 2026-09-20

## Контекст

`17-security.md` §8 требует «ZAP baseline в CI на staging» и «обзор зависимостей
ежемесячно», `04-verification.md` §1 — «зависимости, образы, ZAP baseline» на
уровне «Безопасность», а критерий приёмки фазы 5 — «ZAP без high». К этой истории
в CI было задание «Безопасность», которое выполняло `pnpm audit --audit-level
high` с `continue-on-error: true` и Trivy по файловой системе с `exit-code: '0'`.
То есть обе проверки печатали отчёт и никогда не падали: они существовали, но
ничего не запрещали. ZAP не было вовсе.

Развилки, которые пришлось закрыть:

1. Где брать цель для ZAP. Стенд разработки — это vite на `:5173` и api на
   `:3000` напрямую; заголовки безопасности в установке ставит Caddy (ADR-0043),
   и на стенде их нет по устройству стенда. Прогон по стенду показывал бы
   отсутствие CSP, `X-Frame-Options`, `nosniff` и `Permissions-Policy` —
   то есть врал бы о продукте.
2. Что делать с предупреждениями ZAP. «Падать только на FAIL» — это ровно
   «ZAP без high» из критерия, но почти все находки пассивного сканирования
   приходят как WARN, и такой порог пропускает всё, что нас беспокоит.
3. Что делать с пятью уже имеющимися находками `pnpm audit` уровня high:
   включить порог значило бы сломать сборку в тот же день.
4. Куда ставить прогон: каждый PR или по расписанию.

## Решение

### Цель ZAP — установка целиком, а не стенд разработки

Сканируется поднятая установка за Caddy: `verify-stack.sh` с `KEEP=1` оставляет
её на отдельном проекте compose с чистыми томами, ZAP обходит `/` и `/api/docs`,
после чего установка убирается. Только там заголовки настоящие.

Скрипт `infra/security/zap-baseline.sh` умеет и профиль `dev` — он добавляет к
списку правила тех заголовков, которых на стенде разработки нет, и тем самым
оставляет прогон по стенду осмысленным для разработчика. Профиль `app`
(по умолчанию) этого дополнения не подключает: в установке те же правила обязаны
проходить.

Сканирование только пассивное. Активные атаки по общей базе портят данные, а на
чистой установке дают мало: поверхность закрыта аутентификацией, и настоящие
проверки доступа делают негативные интеграционные тесты (`04-verification.md` §2).

### Порог ZAP — «всё, чего нет в списке»

Прогон роняет сборку и на FAIL, и на WARN. Каждое ожидаемое замечание внесено в
`infra/security/zap-baseline.conf` с объяснением, почему оно не про нас:

- `10027` Suspicious Comments — слова из строковых литералов минифицированных
  библиотек;
- `10049` Non-Storable Content — `Cache-Control: no-store` на страницах с nonce
  стоит намеренно (ADR-0043);
- `10096` Timestamp Disclosure — число в чанке сборки;
- `10109` Modern Web Application — описание SPA, а не замечание;
- `90004` Cross-Origin-Embedder-Policy — см. ниже.

Это строже критерия «ZAP без high» и точнее: новое замечание любого уровня
требует разбора, а не молча копится под порогом.

**COEP не включается.** `require-corp` потребовал бы заголовка
`Cross-Origin-Resource-Policy` от каждого стороннего происхождения — подписанных
ссылок S3, превью и медиасервера встреч; ни MinIO, ни LiveKit его не ставят, и
включение сломало бы загрузки и запись встреч. Вместо него добавлен
`Cross-Origin-Opener-Policy: same-origin` (все `window.open` в web идут с
`noopener`, так что терять нечего), а ресурсы api уже закрыты
`Cross-Origin-Resource-Policy: same-site`.

### Порог зависимостей и образов — high и critical, с разобранным списком

`pnpm audit --audit-level high` и Trivy по файловой системе ломают сборку на
каждом PR. Пять сегодняшних находок внесены в `auditConfig.ignoreGhsas`
(`pnpm-workspace.yaml`) — каждая со строкой о том, почему уязвимый путь в kchs
недостижим (`sql.identifier()` drizzle мы не вызываем; `image-size` приезжает с
текстурами glTF, которых мы не грузим; `raw` nodemailer не передаём). Это не
«выключить проверку», а «разобрать и записать разбор»: список короткий, читается
глазами и обсуждается при обновлении (вопрос N80).

Trivy по образам api, web и engine — `ignore-unfixed: true`: уязвимость без
выпущенного исправления сборку не ломает, потому что чинить её нечем; она видна
в отчёте и ждёт обновления базового образа.

### Место в CI — отдельный workflow по расписанию

ZAP и Trivy по образам требуют собранной установки: это около получаса, столько
же, сколько «Установка в контейнерах» (`stack.yml`), и по той же причине они
вынесены в `security.yml` — ночью на `main`, вручную и на PR с меткой `security`.
Быстрые проверки (`pnpm audit`, Trivy по файловой системе) остаются в `ci.yml`
на каждом PR, а заголовки на каждом PR проверяет `csp:check` — он поднимает тот
же Caddy с тем же Caddyfile.

## Альтернативы

- **ZAP по стенду разработки на каждом PR.** Быстро, но проверяет не тот
  периметр: половина находок — отсутствие того, что в установке есть.
- **Падать только на FAIL (`-I`).** Буквальное прочтение критерия «ZAP без
  high», но пассивные правила почти всё сообщают как WARN — порог оказался бы
  декоративным, как прежние `continue-on-error` и `exit-code: '0'`.
- **Активное сканирование (zap-full-scan).** Часы работы, изменение данных и
  поток находок на формах, которые всё равно закрыты аутентификацией.
  Не для каждой ночи; при необходимости запускается руками по отдельной
  установке.
- **Сначала обновить уязвимые пакеты, потом включать порог.** Правильно по сути,
  но это смена мажорных версий `nodemailer` и минорной `drizzle-orm` в ветке
  аудита безопасности — чужая работа и чужие риски. Порог включён сразу, а
  обновление записано вопросом N80.
- **Аутентифицированный прогон ZAP.** Даёт больше поверхности, но требует
  держать в CI учётные данные и контекст ZAP, а найденное дублирует негативные
  тесты доступа, которые точнее и идут на каждом PR.

## Последствия

- Появились `infra/security/zap-baseline.sh`, `zap-baseline.conf`,
  `zap-baseline-dev.conf` и workflow «Безопасность: образы и ZAP».
- `pnpm audit --audit-level high` и Trivy теперь ломают сборку; новая находка
  high или critical требует либо обновления, либо строки разбора в
  `auditConfig.ignoreGhsas`.
- В Caddyfile добавлен `Cross-Origin-Opener-Policy: same-origin`.
- `verify-stack.sh` принимает `KCHS_VERIFY_ENV_FILE`: стенд, оставленный
  `KEEP=1`, убирает следующий шаг workflow.
- Прогон на стенде разработки 2026-09-20 (профили `dev` и `app`) не нашёл ничего
  за пределами списка: 0 FAIL, 0 WARN.
