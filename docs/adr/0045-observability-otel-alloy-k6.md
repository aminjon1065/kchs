# 0045. Наблюдаемость: OpenTelemetry по запросу, агент Alloy, бюджеты API профилем k6

Статус: Принято
Дата: 2026-09-18

## Контекст

`15-admin-operations.md` §4 (состав мониторинга — Рекомендовано): метрики OpenTelemetry →
Prometheus, журналы pino → Loki с корреляцией `requestId`, трассы Tempo «запрос → SQL →
задание», дашборды Grafana из `infra/observability/dashboards`, алерты; профиль compose
`observability` — prometheus, grafana, loki, promtail, tempo. Бэклог P0-E01 S02/S03 требует
этот профиль и OpenTelemetry в каркасе api, критерий фазы 0 — «p95 API ≤ 200 мс на базовых
операциях», измеряемый k6 (`04-verification.md` §4). На момент решения не было ни трасс, ни
метрик, ни сервисов профиля, ни профиля k6.

Ограничения:

- драйвер postgres.js не имеет готового инструментирования OpenTelemetry, встроенный
  трассировщик drizzle в поставке выключен;
- приложение — ESM (бандл esbuild, ADR-0044): модули `http` и `ioredis` перехватываются
  только загрузчиком ESM (import-in-the-middle), зарегистрированным до импорта приложения;
- задание уходит в BullMQ не из запроса, а из подписчика outbox после коммита (ADR-0036) —
  активного контекста запроса к этому моменту нет;
- конверт события — контракт (`docs/contracts`), поля для контекста трассы в нём нет;
- promtail снят с поддержки (Grafana, март 2026); его преемник — Grafana Alloy, он же
  дистрибутив коллектора OpenTelemetry;
- тесты и разработка не должны платить за телеметрию, которую никто не читает.

## Решение

**Трассы — только при заданном адресе OTLP.** Предзагрузка `src/instrument.ts` — отдельная
точка входа бандла: `node --import ./dist/instrument.js dist/main.js` (CMD образа api/worker,
`pnpm start`, в `pnpm dev` — через tsx). Если задан `OTEL_EXPORTER_OTLP_ENDPOINT` (или
`…_TRACES_ENDPOINT`), она поднимает SDK (`@opentelemetry/sdk-trace-node`, экспорт OTLP/HTTP
пакетами, выборка — стандартные `OTEL_TRACES_SAMPLER*`) и регистрирует загрузчик ESM только
для `http`, `https`, `ioredis`. Без адреса SDK не загружается, модули не перехватываются, а
помощники (`withSpan`, `traceMetadata`) просто вызывают функцию. Модуль телеметрии лежит в
общем чанке бандла: флаг «трассы включены» у предзагрузки и `main` один.

- Инструментирование: `http` — входящие запросы и исходящие вызовы S3; `undici` — `fetch`
  (Meilisearch, движок); `ioredis` — BullMQ и кэши, в спане только имя команды (в ключах и
  аргументах бывают токены сессий). Исходящие вызовы и Redis записываются только внутри
  запроса, задания или события — фоновые опросы трасс не порождают; `/health`, `/metrics`,
  `/ws`, `/collab` не трассируются.
- SQL: обёртка `execute`/`all` подготовленного запроса drizzle для postgres.js — через неё идут
  и пул, и транзакции. Спан `SELECT objects` с параметризованным текстом (`$1`, без значений).
- HTTP: плагин Fastify даёт спану сервера имя по шаблону маршрута (`GET /api/v1/objects/:id`),
  `http.route`, `kchs.request_id`, `enduser.id`; для 5xx — исключение в спане.
- Корреляция: pino добавляет `trace_id`/`span_id` в каждую строку; обработка события
  подписчиком — свой спан с `kchs.correlation_id` (он же `requestId` запроса, конверт не
  меняется); задание продолжает трассу запроса: `JobService.schedule` сохраняет контекст в
  `jobs.options.telemetry.metadata` в той же транзакции, диспетчер передаёт его в BullMQ как
  `opts.telemetry.metadata` (формат телеметрии BullMQ), воркер открывает спан задания дочерним.
- Персональные данные: процессор перед экспортом убирает строку запроса из адресов и адрес
  клиента (`17-security.md` §4).

**Метрики — OpenTelemetry → Prometheus на отдельном порту.** `METRICS_PORT` (в compose —
9464 для api и worker, `x-app-env`) поднимает `MeterProvider` с экспортёром Prometheus;
порт не пробрасывается и не проксируется web (Caddy отдаёт наружу только `/api`, `/ws`,
`/collab`), его читает Prometheus во внутренней сети. Без `METRICS_PORT` провайдер не
создаётся и плагин не вешает хуков. Состав: `http_server_request_duration` (гистограмма по
методу, шаблону маршрута и коду, граница на 200 мс), процесс (RSS, куча, CPU, задержка и
загрузка цикла событий), outbox (`kchs_outbox_pending`, `kchs_outbox_oldest_age`), очереди
BullMQ по состояниям (процесс с воркерами), длительность заданий и обработки событий,
подключения WebSocket.

**Профиль compose `observability`**: Alloy (приём OTLP → Tempo; журналы контейнеров своего
проекта через API Docker → Loki с уровнем pino и `trace_id`), Tempo, Loki, Prometheus
(DNS-обнаружение api/worker, `alerts.yml`), Grafana (источники с переходами трасса ↔ журнал,
дашборд `kchs-overview` из репозитория). Alloy заменяет promtail и отдельный коллектор: один
агент на обе задачи, поддерживаемый. Grafana и приём OTLP публикуются только на `KCHS_BIND`
(127.0.0.1), пароль Grafana — `GRAFANA_ADMIN_PASSWORD` из `generate-secrets.sh`. Хранение:
трассы и журналы — 7 дней, метрики — 15 дней. Алерты — правила Prometheus: ошибки > 1 %, p95 >
200 мс, outbox старше минуты, очередь растёт 15 минут, RSS > 1 ГБ, экземпляр недоступен.

**Бюджеты — профиль k6** `infra/perf/k6/api-basic.js`: 5 рабочих циклов в секунду (≈ 50
запросов/с — ~300 одновременно работающих, предел S1) сотрудниками демо-данных; пороги p95
по операциям — базовые (профиль, список 50, карточка, Входящие, папка, сессия загрузки,
обсуждение) ≤ 200 мс, поиск ≤ 100 мс, вход ≤ 500 мс (argon2id намеренно дорог). Запуск —
`infra/perf/run-k6.sh` (k6 в Docker) на стенде разработки; в CI — ночью и вручную в задании
«Установка в контейнерах» через web (пара минут к уже поднятому стенду), на PR — нет.

## Альтернативы

- `@opentelemetry/sdk-node` с автоинструментированием — тянет экспортёры gRPC/protobuf и
  десятки инструментирований, а нужны три; своя сборка из `sdk-trace-node` меньше и понятнее.
- Трассы всегда включены с выборкой 0 — SDK всё равно загружается и перехватывает модули;
  тесты и разработка платили бы за телеметрию.
- `prom-client` — `15-admin-operations.md` предписывает OpenTelemetry → Prometheus; метрики
  процесса — несколько датчиков без `host-metrics`/`runtime-node`.
- `/metrics` на основном порту за служебным токеном — секрет в конфигурации Prometheus, а
  worker без HTTP-сервера всё равно потребовал бы отдельного порта.
- promtail + коллектор OpenTelemetry — два агента, один из них без поддержки.
- `bullmq-otel` (встроенная телеметрия BullMQ) — спаны на каждую внутреннюю операцию
  очереди; контекст запроса до постановки всё равно пришлось бы хранить в реестре заданий.
- Контекст трассы в конверте события — изменение контракта; корреляции по `requestId`
  достаточно, чтобы найти обработку событий запроса (`{span.kchs.correlation_id = "req_…"}`).

## Последствия

- api и worker запускаются с `--import ./dist/instrument.js`; если адрес OTLP задан, а
  предзагрузки нет, `main` пишет предупреждение.
- Новые переменные: `METRICS_PORT`, `METRICS_HOST`, стандартные `OTEL_*`,
  `OTEL_EXPORTER_OTLP_ENDPOINT_INTERNAL` (для контейнеров), `GRAFANA_PORT`,
  `GRAFANA_ADMIN_PASSWORD`, `OTLP_HTTP_PORT`.
- Alloy монтирует `docker.sock` только на чтение — это доступ к API Docker; профиль
  включается осознанно (`17-security.md` §6).
- Замер на стенде разработки (Mac mini M-серии, инфраструктура в Docker, 5 циклов/с, 2 мин,
  трассы и метрики включены): p95 базовых операций 7–25 мс, поиск 12 мс, вход 83 мс, ошибок
  0 %, RSS ≤ 381 МБ; без телеметрии медианы ниже на 0,2–0,5 мс.
- Не сделано: метрики Postgres/Redis/MinIO/Meilisearch (экспортёры), доставка алертов
  (Alertmanager), трассы движка (Python), экран «Здоровье» из метрик, спаны сырых запросов
  postgres.js (диспетчер outbox).
