# 0209. Тесты компонентов web: Testing Library и happy-dom в vitest

Статус: Принято
Дата: 2026-10-13

## Контекст

У web были unit-тесты чистой логики (`*.test.ts`, Node) и сквозные сценарии Playwright, но
не было тестов компонентов (`07-architecture-hardening.md` §3.4). Регрессия этапа 8 показала
цену пробела: баннер «Вы замещаете» держал выбор «от имени» вне React и менялся, только пока
оболочка перерисовывалась на каждый ответ `/me`. Поймал её только полный e2e на общем
стенде — медленно и не на каждой правке.

## Решение

1. **Два проекта vitest в `apps/web/vitest.config.ts`:** `unit` — `src/**/*.test.ts` в Node,
   как раньше; `components` — `src/**/*.test.tsx` в happy-dom с Testing Library
   (`@testing-library/react`, `user-event`, `jest-dom`). Оба входят в `pnpm test` и в CI.
2. **Окружение — `src/test/setup.ts`:** все неймспейсы словаря `ru` загружены, DOM и
   заглушки сбрасываются после каждого теста, у happy-dom есть то, чего ждут примитивы Radix
   (захват указателя, прокрутка к пункту).
3. **Помощники — `src/test/render.tsx`:** `renderWithClient` рисует компонент в окружении
   оболочки (`app/providers.tsx`: запросы без повторов, язык, подсказки, тосты), `stubApi`
   отвечает на `fetch` по пути таблицы маршрутов и ведёт журнал запросов, `meFixture` и
   `delegationFixture` — `/me` по контракту. Сеть, сервер и стенд не нужны.
4. **Что тестируем компонентно:** поведение, которое зависит от состояния React, ответа
   сервера и прав, — выбор режима, видимость кнопок по `can` и способностям, проверка ввода
   до отправки, тело запроса. Внешний вид — снимки Storybook (`test:visual`), путь
   пользователя через несколько экранов — Playwright.
5. **Первые тесты** (8 компонентов, 33 теста): баннер замещения (проверен поломкой —
   возврат выбора в переменную модуля роняет тест), строка состояния с офлайн-очередью,
   подписанный экземпляр и место факсимиле, действия шага документа, письма исходящего,
   факсимиле в профиле, токены API, «Работает от имени».

## Альтернативы

- **jsdom.** Работает так же, но медленнее при старте; happy-dom достаточно для Radix при
  двух заглушках.
- **Storybook interaction tests.** Требуют Docker и браузер на каждый прогон; для логики
  компонента избыточны.
- **Только e2e.** Отклонено: регрессия этапа 8 стоила полного прогона на общем стенде.

## Последствия

- Новые devDependencies web: `@testing-library/react`, `@testing-library/dom`,
  `@testing-library/user-event`, `@testing-library/jest-dom`, `happy-dom`
  (`18-tech-stack.md`, строка «Тесты»).
- Компонент с логикой получает тест `*.test.tsx` рядом с собой; тест импортирует
  `~/test/render.js`, правила dependency-cruiser тестовые файлы не проверяют.
