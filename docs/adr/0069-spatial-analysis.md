# 0069. Пространственный анализ: шаг `spatial` компилятора и объект «анализ»

Статус: Принято
Дата: 2026-09-19

## Контекст

07-gis-engine.md §10 (Рекомендовано): лёгкие операции выполняются шагом `spatial` в QuerySpec
и дают виртуальный слой, тяжёлые — объектом `analysis` с воспроизводимыми параметрами и
материализацией в новый датасет; происхождение фиксируется. Контракт query-spec.md перечислял
операции шага (`buffer … clip`), но не их параметры и формы цели; компилятор фазы 1 шаг
отклонял. 05-data-model.md задаёт таблицу `analyses(id → objects, kind, params,
input_dataset_ids, output_dataset_id, status, job_id)`. Справочник территорий (ADR-0057) —
таблица `public.territories`, которую роль пользовательских запросов не читает (ADR-0048).

## Решение

1. **Шаг `spatial` компилируется в CTE на PostGIS** (`packages/query`, `compiler/spatial.ts`).
   Геометрии — WGS 84; метрические величины — через `geography`: расстояния и размеры —
   метры, площадь — км², длина — км; все значения — параметрами `$n`, `@param:имя` — для
   чисел. У каждой операции свой набор параметров (таблица — в contracts/query-spec.md),
   неизвестный параметр — ошибка с путём. Поле геометрии — `params.field` или единственное.
   - `buffer`, `centroid` заменяют геометрию строки; `area`, `length`, `assign_territory` и
     `nearest` добавляют поля (имя по умолчанию при совпадении получает номер, явное
     `params.as` совпадать с полем не может); `intersects`, `within`, `dwithin` отбирают
     строки (`negate` — наоборот, строки без геометрии не входят ни туда, ни туда).
   - `nearest`: кандидаты — KNN-индекс `<->` (плоские градусы, `max(16, 4·limit)`), точный
     порядок и расстояние — по geography; для цели-геометрии — расстояние до неё.
   - `assign_territory`: территория уровня, покрывающая точку на поверхности объекта
     (`ST_PointOnSurface` + `ST_Intersects` — граница не теряется); на общей границе —
     первая по коду; поле `<уровень>_id` типа `territory`.
   - `spatial_join`: меры `count | count_distinct | sum | avg | min | max` по объектам цели,
     связанным со строкой (`intersects | contains | within | dwithin`), — LATERAL на строку.
   - `grid` / `hexgrid`: ячейки `ST_SquareGrid` / `ST_HexagonGrid` в зоне UTM центра охвата
     данных (метры без искажения широты), только непустые; `cell` = `i:j`, граница, меры.
   - `dissolve`: `ST_Multi(ST_Union)` по полям `by` с мерами; `clip`: пересечение с
     объединением цели той же размерности (`ST_CollectionExtract`), пустые части отбрасываются.
   Сетка и растворение меняют строки (как сводка): порядок сбрасывается, режима таблицы нет.
2. **Цель** — `{kind: dataset|query, id, alias?, field?, filter?}` (политики смотрящего, как у
   соединения; `filter` — в формате фильтра), `{kind: system, name}`, `{kind: territory,
   id | ids | level}` или геометрия GeoJSON (`{kind: geometry, geometry}` или без обёртки).
   `collectSources` собирает цели, вызывающий загружает их с правами до компиляции. Слой как
   цель — со слоями: API раскроет его в `{kind: dataset, id, filter}`.
3. **Справочник территорий — системный датасет `territories`** (`SYSTEM_DATASETS`): модуль
   GIS регистрирует представление `ds.sys_territories` (ручной хвост миграции `gis_analysis`,
   чтение — `kchs_query`; поля `id, code, level, parent_id, name, name_tg, name_en, geom,
   area_km2`, удалённые единицы не видны). Сотрудникам — все строки, гостю по ссылке — ни
   одной. Он же источник запросов `{kind: system, name: territories}`; такие запросы, как и
   прочие с системными датасетами, не кэшируются.
4. **Объект `analysis` — в модуле data**: анализ — это запрос и материализация в датасет;
   модуль GIS даёт справочник. Таблица `analyses` по модели данных и поля состояния
   последнего запуска (`row_count`, `error`, `last_run_at`); `params = {query, outputName}`;
   `kind` — операция последнего шага `spatial` (без шага — 400). Создание проверяет запрос
   компилятором с правами автора, объект — через `ObjectService`, зависимости `uses` на
   источники. API: `POST /analyses` (`run: true` — сразу в очередь), `GET /analyses/:id`,
   `POST /analyses/:id/run` (право `run` = `edit`; пока задание в работе — 409).
5. **Запуск — задание `data:analysis.run`** (очередь `data`, воркер). Права — запустившего на
   момент выполнения, как у экспорта (ADR-0056): `authorize(run)`, компиляция с его
   политиками, запрос потоком под `kchs_query`, строки пачками через `jsonb_to_recordset` в
   таблицу датасета — в одной транзакции с созданием датасета или заменой строк, версией и
   событиями. Первый запуск и смена набора полей — новый датасет в пространстве анализа
   (право `create_child`; снимок: без правки строк и истории). **Результат закрыт**
   (`accessMode: restricted`, владелец — запустивший): его строки посчитаны с политиками
   запустившего, и наследование прав пространства раскрыло бы их участникам, которым
   политики строк этих строк не открывают; поделиться результатом — решение владельца.
   Повтор с тем же набором полей заменяет строки прежнего результата новой версией с
   происхождением `analysis`, если у запустившего есть право `edit` на него; иначе (чужой
   результат) — новый датасет запустившего, и анализ указывает на него. Больше 1 млн строк —
   ошибка без частичного результата; тайм-аут запроса — 10 минут.
6. **Происхождение:** зависимости датасета-результата `derives_from` на анализ и источники,
   связь «Источник» (`source`) датасета с анализом — видна в панели «Связи».
7. **События** (раздел gis каталога): `analysis.created`, `analysis.queued`, `analysis.started`,
   `analysis.finished {status, datasetId, rows, error}`, у датасета — `dataset.version_created
   {origin: analysis}`. Окончательный сбой задания (`job.failed`) подписчик переводит в
   `failed` с причиной.
8. **Клиент:** на экране датасета с геометрией — кнопка «Анализ» и диалог (операция,
   параметры, цель — датасет или территории, имена анализа и результата); карточка анализа —
   состояние запуска, результат, параметры, источники, перезапуск. Мастер анализа на карте и
   предпросмотр на выборке — вместе со студией карт.

## Альтернативы

- **Задание в движке Python** (07-gis-engine.md §10: «заданием engine»): у движка нет
  компилятора запросов и политик доступа — их пришлось бы повторить; SQL на PostGIS база
  выполняет одинаково из любого процесса.
- **`INSERT … SELECT` под ролью `kchs_query`:** роли понадобилась бы запись в схему `ds`, что
  противоречит ADR-0048; поток через приложение дороже, но роль и права не расширяются.
- **Точный «ближайший» перебором по geography:** без индекса, O(строк × объектов цели);
  кандидаты по KNN ошибаются только при плотном скоплении объектов на краю круга кандидатов.
- **Сетка в EPSG:3857 с поправкой масштаба:** проще, но на широтах Таджикистана ячейки
  искажены на несколько процентов; зона UTM даёт метры.

## Последствия

- Изменения контрактов: `SYSTEM_DATASETS` + `territories`, `DATASET_VERSION_ORIGINS` +
  `analysis`, четыре события анализа; параметры шага — в contracts/query-spec.md.
- Представление `ds.sys_territories` зависит от столбцов `territories`: изменение их типа
  требует пересоздать представление в той же миграции.
- Предел строк и тайм-аут ограничивают анализ интерактивным классом данных; большие
  объёмы — с колоночным слоем (фаза 3).
- Участники пространства видят карточку анализа, но не его результат, пока владелец
  результата им не поделится; перезапуск другим редактором даёт ему собственный датасет.
- Территории без границ не участвуют в присвоении и отборе — результат для них пуст.
