# 0055. Политики строк и столбцов: общий формат фильтра, проверка компилятором, связь со схемой

Статус: Принято
Дата: 2026-09-19

## Контекст

`03-access-model.md` («Строки и столбцы датасетов») описывает политику строк как «фильтр в
языке выражений платформы над полями датасета и атрибутами пользователя (`user.unit_codes`,
`user.territory_codes`, `user.attributes.<key>`)», а `contracts/field-types.md` называет общий
формат фильтра форматом «политик строк». Таблицы `dataset_row_policies(filter jsonb)` и
`dataset_column_policies(mode, fields[])` и слой `DatasetAccess` появились в первом срезе фазы 1;
не было API для их ведения, правил проверки и поведения при правке схемы. Кроме того, ключ
принципала политики сравнивался с множеством принципалов в неверной форме: политика для
«всех сотрудников» (`everyone`) не совпадала с ключом `everyone:*` и ни к кому не применялась.

## Решение

1. **Формат — общий фильтр** (`FilterNode`), как в `contracts/field-types.md`. Атрибуты
   пользователя — макросами значений (`@me`, `@my_unit`, `@my_units`, `@my_territories`) и
   операторами `is_me`, `is_my_subordinate`, `in_my_unit`, `within`. Условия на языке выражений
   (`user_attr('…')`) компилятор уже поддерживает (`RowPolicy.kind = 'expr'`), но API их пока не
   принимает: конструктор фильтра покрывает сценарии фазы 1, а выражение в политике трудно
   проверить глазами. Вернёмся к этому вместе с атрибутами пользователей (фаза 5, LDAP).
2. **Проверка при сохранении — компилятором запросов**: фильтр компилируется так же, как при
   чтении (поля датасета включая скрытые, макросы, без параметров запроса `@param:*`). Сохранить
   можно только политику, которая выполнится; ошибка — 400 с путём и сообщением компилятора.
3. **Принципалы** — все типы ACL, кроме гостевой ссылки; ключ сравнивается в форме множества
   принципалов ядра (`type:id`: `everyone:*`, `space_role:<пространство>:<роль>` с иерархией ролей).
4. **API** (действие `manage`): `GET /datasets/{id}/policies`, `POST|PATCH|DELETE
   /datasets/{id}/policies/rows[/{policyId}]` и то же для `columns`. Не больше 200 политик каждого
   вида на датасет (их объединение компилируется в каждый запрос); правки одного датасета идут
   по очереди (advisory-блокировка транзакции). Каждое изменение — событие
   `dataset.policies_changed {kind, op, policyId}` в той же транзакции. Кэш результатов запросов
   отдельно не сбрасывается: политики пользователя входят в ключ кэша компилятора.
5. **Связь со схемой.** Поле, на которое ссылается политика строк, удалить нельзя (409), а смена
   его типа проверяется компиляцией политик с новым типом до перезаписи таблицы (409, если
   политика станет некорректной): иначе политика перестала бы компилироваться и закрыла бы
   строки всем. Из политик столбцов удаляемое поле убирается, опустевшая политика удаляется.
6. **Интерфейс** — вкладка «Доступ» датасета для `manage+`: выбор принципала (поиск и быстрый
   выбор «все сотрудники» и ролей пространства), конструктор фильтра, режим «скрыть/маскировать»
   с выбором полей; условие показывается сводкой `FilterSummary` дизайн-системы.

## Альтернативы

- Политика строк выражением на языке платформы — гибче, но без конструктора и с проверкой только
  при сохранении; отложено (п. 1).
- Удалять или отключать политики строк при удалении поля — тихо меняет видимость данных; явный
  конфликт безопаснее.

## Последствия

- Руководитель «только своей области» задаётся политикой строк на пользователя, подразделение
  или роль пространства; числа на дашбордах, в графиках, таблице и (далее) в экспорте и
  SQL-лаборатории считаются с ней — всё идёт через `DatasetAccess`.
- Политики для «всех сотрудников» начали применяться (раньше такие пользователи не видели строк).
- Атрибутные политики через `user.attributes.<key>` появятся вместе с синхронизацией атрибутов.
