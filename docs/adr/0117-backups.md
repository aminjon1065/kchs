# ADR-0117. Резервные копии S1: `pg_dump` заданием платформы

Статус: **Принято** · Дата: 2026-09-20 · Фаза 5 (P5-E06)

## Контекст

`15-admin-operations.md` §5 назначает для PostgreSQL pgBackRest с непрерывным
архивом WAL (RPO 15 минут), а §1 требует «бэкап-статуса» в консоли
администрирования. pgBackRest — отдельная служба со своим хранилищем и
расписанием: в установке S1 (`docker compose`, ADR-0044) это ещё один контейнер,
который некому обслуживать, и консоль всё равно не сможет ни запустить копию, ни
показать её итог — приложение не управляет соседними контейнерами.

## Решение

1. **Копия — задание платформы**: `pg_dump --format=custom` пишет потоком прямо в
   бакет `kchs-backups` (multipart-выгрузка, размер заранее неизвестен). Запись о
   прогоне — `ops.backups`: начало, конец, размер, ключ архива, кто заказал,
   ошибка.
2. **Расписание — единое** (ADR-0096): `backup.run` в 02:50, видно и выключается
   на экране «Расписания». Кнопка «Сделать копию» в консоли запускает то же самое.
3. **Ошибка остаётся в записи прогона**, а не летит наружу заданием: иначе повтор
   задания бил бы по базе раз за разом. Прерванный прогон (процесс остановили
   посреди дампа) помечается ошибкой при следующем запуске.
4. **Хранение — семь удачных копий**, лишние удаляются вместе с архивами.
5. **Проверку восстановлением отмечает человек** (`POST /admin/backups/{id}/verified`):
   платформа не может доказать, что дамп разворачивается — это делает
   администратор по `infra/runbooks/restore.md`, а отметка с датой остаётся в
   списке и в аудите.
6. **`pg_dump` версии сервера** ставится в образ api из репозитория PGDG: в
   Debian bookworm клиент 15-й, а сервер 17-й, и 15-й такой дамп не снимет. Там,
   где клиента нет (машина разработчика), прогон честно отвечает «pg_dump не
   найден» — молчать об этом нельзя.

## Альтернативы

- **pgBackRest сразу.** Остаётся планом для S2 (Kubernetes, Helm): там сайдкар и
  архив WAL уместны, а RPO 15 минут без непрерывного архива не выдержать. Для S1
  суточный дамп с проверкой — честная граница, и она записана в runbook.
- **Отдельный контейнер-бэкапер с cron.** Консоль не смогла бы ни запустить
  копию, ни показать итог — пришлось бы читать манифесты из бакета и доверять им.
- **Дамп во временный файл, затем выгрузка.** Требует места на диск размером с
  базу; поток частями его не требует.

## Последствия

- RPO S1 — сутки (или интервал расписания), RTO — по runbook. Это записано в
  `15-admin-operations.md` и в runbook; переход на pgBackRest — вопрос S2.
- Файлы (MinIO) и поиск (Meilisearch) этой копией не резервируются: у первых своё
  версионирование и зеркало, второй перестраивается из Postgres.
- Бакет копий создаётся при первой копии, если его нет: установка, поднятая до
  появления этой истории, не требует ручных шагов.
