# Черновик раздела ADR-0228 — фоновые задания, автоматизация, поиск, сокеты

> Для вклейки в сводный ADR-0228 этапа В. Без сценариев атак.

## Контекст

Подписчики, задания и правила рассчитывали на одного исполнителя, а исполнитель этого
не обеспечивал:

- воркер очереди брал наибольший `concurrency` её обработчиков, и задания с
  `concurrency: 1` (обслуживание, дайджест, проверка алертов, разбор почты) шли до
  четырёх копий сразу; «Выполнить сейчас» и предел времени давали ещё наложение;
- дайджест и немедленная доставка писем выбирали одни и те же уведомления, проверка
  алертов — одни и те же алерты, без захвата строк;
- обход «зависших» запусков правил считал запуск зависшим по времени создания и
  исполнял живой запуск второй раз, а позиция продолжения сохранялась только при `wait`;
- исключение разбора одного правила в цикле подписчика уводило каждое событие в DLQ;
- подписчик поиска после пяти неудач терял событие до ручного повтора, удаление из
  индекса глушило ошибки;
- сокет realtime жил по снимку контекста и после выхода, отзыва сессии и блокировки.

## Решение

- **Одиночные задания.** `concurrency: 1` у обработчика значит «одно исполнение на всю
  установку». Исполнитель берёт сессионную advisory-блокировку
  (`pg_try_advisory_lock(singleJob, hashtext(ключ))`) на отдельном соединении и держит её,
  пока обработчик действительно работает, — и после того, как предел времени освободил
  слот очереди. Процесс упал — соединение закрыто, блокировка снята.
  - Занято — регулярная проверка пропускается (`result.skipped = 'busy'`): её сделает
    следующий тик.
  - Задание с полезной нагрузкой не теряется: `exclusive.whenBusy: 'defer'` откладывает
    его в очереди (импорт сотрудников, удаление файлов из хранилища, выгрузка объектов
    службы, переиндексация пространства).
  - Одиночность может быть по своему объекту (`exclusive.key`): источник данных,
    пайплайн, пространство — разные объекты идут параллельно.
  - `exclusive: false` — без одиночности, если `concurrency: 1` означает только слот.
- **Захват строк.** Письмо уведомлений: уведомления захватываются условным
  `UPDATE … SET emailed_at = now() WHERE emailed_at IS NULL RETURNING` до отправки;
  письмо не ушло — захват снимается. Проверка алерта: срок следующей проверки ставится
  условным `UPDATE … WHERE next_run_at <= now()` — параллельный тик алерт не проверит.
- **Запуск правила — с арендой.** `rule_runs.leased_until` и `lease_owner` (миграция
  `rule_runs_lease`, столбцы с NULL). Исполнитель захватывает запуск условным UPDATE; второй
  исполнитель — повтор задания, обход `automation.resume` — получает отказ, пока аренда жива.
  - Аренда — 20 минут (предел очереди `automation` — 15) и продлевается каждым шагом.
  - Позиция продолжения (`resume_at`) пишется вместе с каждым выполненным шагом: повтор
    после сбоя процесса сделанное не повторяет. Действие, выполненное, но не записанное до
    сбоя, может выполниться ещё раз — доставка «как минимум один раз».
  - Сбой вне шагов снимает аренду — повтор задания продолжает сразу.
  - Обход берёт исполняемый запуск только по истёкшей аренде.
- **Битое правило.** Сохранённое определение разбирается `safeParse`
  (`automation/domain/stored-rule.ts`): правило, которое не проходит текущую схему,
  пропускается с записью в своём журнале (не чаще раза в минуту), остальные работают — в
  подписчике событий, в запусках по расписанию и вебхуку, в исполнителе.
- **Поисковая проекция.**
  - Признак подписчика `redrive`: его события из DLQ задание `events.redrive` раз в 10
    минут возвращает в поток адресно, когда они отлежались 5 минут. События старше 7
    дней остаются администратору.
  - Удаление из индекса ошибки не глушит: подписчик повторит.
  - Ночная сверка `search.reconcile`: переиндексация реестра по текущим правам и удаление
    документов, которых в реестре нет.
- **Сокет и сессия.** Сокет входит в комнату `session:<id>`. Выход, отзыв сессий и
  `revokeAllExcept` (блокировка учётной записи, смена и сброс пароля) после фиксации
  публикуют команду ретранслятора `end-sessions` — сокеты этих сессий закрываются на всех
  узлах api. Перепроверка комнат (`recheck`) проверяет и живость сессии.

## Альтернативы

- **Своя очередь с одним слотом на каждое одиночное задание.** Не спасает при нескольких
  процессах worker и при «Выполнить сейчас»; блокировка в базе — общая для всех процессов.
- **Блокировка в Redis с продлением.** Требует сторожа продления и не снимается сама при
  падении процесса так надёжно, как сессионная блокировка Postgres.
- **Захват запуска на время всего исполнения без продления.** Долгое правило потеряло бы
  аренду посередине; продление шагом — проще сторожа по таймеру.
- **Бесконечные повторы проекции без DLQ.** Битое событие держало бы обрезку потока;
  возврат из DLQ с паузой и пределом возраста не мешает обрезке.

## Последствия

- Задание с `concurrency: 1` больше не исполняется параллельно с собой на установке. Если
  обработчику нужен только один слот без одиночности — `exclusive: false`.
- Регулярная проверка, пропущенная из-за занятости, видна в журнале заданий как
  выполненная с `skipped: 'busy'`.
- Каждое выполняемое одиночное задание держит одно соединение пула.
- Ночная сверка поиска проходит весь реестр — на пилотном объёме это минуты.

## Проверки

Интеграционные тесты (каждый падает на прежнем коде): одиночное задание не идёт
параллельно при свободных слотах; отложенные выполняются все по очереди; после предела
времени второе исполнение ждёт конца первого; два одновременных вызова доставки дают одно
письмо; три параллельных тика — одно срабатывание алерта; живой запуск правила не
исполняется повтором и обходом, а с истёкшей арендой доходит до конца; продолжение с
записанной позиции не повторяет сделанное; битое правило рядом с рабочим; возврат событий
поиска из DLQ только у проекций; сверка восстанавливает читателей и удаляет сирот;
выход, отзыв сессий и перепроверка закрывают сокет.
