# 0046. Импорт датасета: движок нормализует файл, воркер загружает его в таблицу

Статус: Принято
Дата: 2026-09-18

## Контекст

`06-analytics-engine.md` §2 описывает конвейер импорта файла: анализ в движке, сопоставление
в интерфейсе, выполнение «в движке» — чтение потоком, приведение типов, staging-таблица через
`COPY`, валидация, коммит (`swap`/`INSERT`/`MERGE`), новая `dataset_version`, событие
`dataset.imported`. Одновременно `05-data-model.md` (Решено) требует, чтобы вся DDL таблиц
датасетов была инкапсулирована в `modules/data/infra/physical.ts`, а правило 3 `CLAUDE.md` —
чтобы каждое изменение состояния публиковало событие через outbox в той же транзакции.

У движка сейчас нет подключения к базе: он читает S3 и Redis (BullMQ) и сообщает результаты
внутренними маршрутами API (импорт пользователей, ADR-0041). Дать ему роль с правом DDL и DML
в схеме `ds` значило бы разнести знание о физических таблицах по двум языкам, а коммит
(метаданные в `public`, версия, outbox) движок всё равно выполнить не может.

## Решение

Выполнение импорта делится на два задания:

1. **`imports:dataset.normalize`** (движок, ADR-0035): скачивает файл, читает его потоком по
   параметрам анализа, приводит значения к типам сопоставления с учётом локали (десятичная
   запятая, разделители тысяч, форматы дат, логические значения, геометрия из широты/долготы,
   WKT или GeoJSON) и пишет в S3 **нормализованный CSV** — формат описан в
   `packages/contracts/src/data/import.ts` (`NORMALIZED_VALUE_FORMATS`) и передаётся движку
   сгенерированным `data_import.json` — и **файл ошибок** (строка, поле, значение, код
   причины). Итог сообщает внутренним маршрутом API.
2. **`data:dataset.load`** (TypeScript-воркер, новая очередь `data`): создаёт staging-таблицу
   через `physical.ts`, загружает нормализованный CSV потоком `COPY … FROM STDIN`, проверяет
   ключ и обязательность, применяет режим (`replace` — `swap` таблиц, `append`, `upsert`,
   `sync`) и в одной транзакции пишет новую версию, счётчики и событие `dataset.imported`.

Анализ файла — синхронный HTTP-вызов движка по выборке (`IMPORT_LIMITS.analyzeSampleRows`),
как в §2 п. 2.

Очередь `data` добавлена в `QUEUE_RUNTIME` с исполнителем `worker`: её же используют
последующие операции над таблицами датасетов (профили столбцов, пересчёт индексов), которым
нужны `physical.ts` и компилятор запросов на TypeScript.

## Альтернативы

- Движок пишет в staging сам (роль с DML в `ds`), API только коммитит: DDL staging-таблиц
  окажется в Python, типы столбцов придётся согласовывать между двумя реализациями.
- Воркер TypeScript разбирает файлы сам: нет зрелых потоковых читателей XLSX, распознавания
  кодировок и форматов дат, которые есть в Python (pandas, openpyxl, charset-normalizer).
- Движок отдаёт строки JSON через внутренний маршрут: для миллионов строк — лишняя сериализация
  и память; файл в S3 дешевле и позволяет повторить загрузку без повторного разбора.

## Последствия

- Движок остаётся без доступа к базе; DDL и транзакции с событиями — только в TypeScript.
- Нормализованный CSV — договор: изменение формата — правка контракта и `gen:engine`.
- Повтор загрузки (сбой воркера) не требует повторного разбора файла.
- Промежуточные файлы импорта удаляются заданием обслуживания вместе с устаревшими импортами.
