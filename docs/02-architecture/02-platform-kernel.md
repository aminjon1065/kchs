# Ядро платформы

Ядро — набор общих механизмов, на которых стоят все модули. Именно ядро превращает тринадцать областей в один продукт. Статус всего документа: **Решено**, если не указано иное.

## 1. Реестр объектов

### Идея
Каждая значимая сущность (датасет, график, дашборд, карта, слой, документ, файл, папка, задача, проект, встреча, событие, страница, тетрадь, отчёт, показатель, территория, форма, правило, беседа…) — **объект** с записью в таблице `objects`. Таблица модуля хранит специфичные поля и разделяет с `objects` тот же UUID (`datasets.id = objects.id`).

### Что даёт
Единые для всех типов: открытие во вкладке по `/o/{id}`, права, связи, обсуждение, активность, избранное, недавние, теги, поиск, выбор объекта в любом поле (`ObjectPicker`), карточка при наведении, корзина и восстановление, архив, перенос между пространствами.

### Таблица `objects` (ключевые поля)
`id uuid`, `type text`, `space_id`, `parent_id` (иерархия: папка→файл, проект→задача, датасет→слой не является родителем — слой ссылается на датасет связью), `title`, `subtitle`, `icon`, `owner_id`, `created_by`, `created_at`, `updated_at`, `archived_at`, `deleted_at` (корзина), `access_mode` (`inherit`|`restricted`), `meta jsonb` (лёгкие сводные поля для карточек: статус, срок, исполнитель — денормализация для списков и поиска), `search_version` (для инкрементальной индексации).

Закрытие таблицы предков `object_ancestors(object_id, ancestor_id, depth)` поддерживается ядром при создании/переносе — для наследования прав и быстрых выборок.

### Реестр типов (в коде)
Модуль регистрирует `ObjectTypeDefinition`:

```ts
interface ObjectTypeDefinition {
  type: 'dataset' | 'document' | ...;
  labels: { ru: {one, many}, tg, en };
  icon: string;
  routes: { open: (id) => string };                 // URL вкладки
  levels: PermissionLevel[];                         // какие уровни доступа имеют смысл
  actions: Record<string, { minLevel; capability? }>; // 'dataset.export' → 'view' + capability
  policy: TypePolicy;                                // производные права и предикат видимости (см. 03-access-model.md)
  searchable: (id) => Promise<SearchDocument | null>; // как индексировать
  summary: (ids) => Promise<ObjectSummary[]>;        // для карточек, пикеров, чипов
  lifecycle: { onArchive?, onRestore?, onDelete?, onMove? };
  discussable: boolean; linkable: boolean; hasParentTree: boolean;
}
```

Ядро ничего не знает о конкретных типах, кроме этого описания.

### Жизненный цикл
`active` → `archived` (скрыт из списков, доступен по ссылке, только чтение) → `trashed` (корзина, 30 дней, восстановление) → удалён (задание физического удаления вызывает `lifecycle.onDelete` модуля и удаляет файлы из S3). Удаление объекта каскадно затрагивает дочерние по `parent_id`.

## 2. Пространства

Пространство — контейнер совместной работы и единица «где это лежит». Каждый объект принадлежит ровно одному пространству.

| Тип | Кто создаёт | Пример |
|---|---|---|
| `personal` | автоматически для каждого пользователя | «Моё пространство» |
| `unit` | автоматически или администратором для подразделения | «Управление анализа рисков» |
| `team` | пользователи со способностью `spaces.create` | «Паводок-2026», «Проект цифровой карты» |
| `org` | одно на инсталляцию | «Общее» — справочники, регламенты, общие датасеты |

Поля: `key` (короткий код), `name`, `type`, `unit_id?`, `settings jsonb` (модули включены, видимость по умолчанию, шаблон навигации, цвет/иконка), `members` (роль: `viewer|member|editor|admin`). Пространства — тоже объекты (тип `space`), поэтому у них есть обсуждение и активность.

Навигация внутри пространства организуется **разделами** (папки-контейнеры для любых объектов, `parent_id`), а не по типам объектов. Модуль «Данные» показывает только датасеты/дашборды всех пространств, а пространство показывает всё своё вместе.

## 3. Связи

`links(id, source_id, target_id, kind, created_by, created_at, meta)`; связь двунаправленная по чтению, `kind` фиксирует смысл:

| kind | Смысл | Кто создаёт |
|---|---|---|
| `related` | «см. также» | пользователь |
| `attachment` | объект → файл | вложение |
| `source` | результат ← исходный объект (поручение из документа, документ из отчёта, отчёт из дашборда) | модули |
| `mention` | объект упомянут в тексте (документ, сообщение, страница) | парсер упоминаний |
| `reply_to`, `in_execution_of`, `cancels`, `amends` | связи документов | модуль документов |
| `about_territory`, `about_feature` | объект относится к территории/объекту карты | модули, пользователь |

Отдельно ядро хранит **зависимости** `dependencies(from_id, to_id, kind)` — вычисляемые связи «использует» (дашборд→график→запрос→датасет→источник; слой→датасет; отчёт→график). Их пересчитывают модули при сохранении объекта. На их основе строятся происхождение (lineage), анализ влияния и предупреждения при удалении.

Панель «Связи» в контекстной панели показывает обе группы, сгруппированные по типу, с карточками объектов.

## 4. События и outbox

Любое изменение состояния пишет запись в `ops.outbox` **в той же транзакции**, что и данные. Диспетчер (в `worker`, с блокировкой `SELECT ... FOR UPDATE SKIP LOCKED`) публикует записи в Redis Streams (`events:<domain>`), помечает отправленными. Потребители — идемпотентные подписчики с consumer groups и повторами.

Конверт события (контракт `docs/contracts/events.md`):

```json
{
  "id": "01J...", "type": "document.registered", "version": 1,
  "occurredAt": "2026-09-17T08:15:00Z",
  "actor": {"userId": "...", "onBehalfOf": null, "kind": "user|system|automation|integration"},
  "object": {"id": "...", "type": "document", "spaceId": "..."},
  "target": {"id": "...", "type": "..."},
  "payload": {...}, "correlationId": "...", "causationId": "..."
}
```

Потребители ядра: `activity` (лента), `notifications` (правила уведомлений), `search` (переиндексация), `realtime` (рассылка в комнаты), `automation` (правила), `webhooks`, `audit`. Потребители модулей — по подписке в `module.ts`.

Каталог событий — в `16-api-and-events.md`.

## 5. Активность и аудит

- **Активность** — человекочитаемая лента изменений объекта («Иванов изменил срок с 12.09 на 15.09», «добавлено вложение»), строится из событий подписчиком; хранится в `activities` с ссылкой на событие; показывается в контекстной панели и в ленте пользователя (по объектам, на которые он подписан).
- **Аудит** — `audit_log`: события безопасности и значимых действий (вход, MFA, смена пароля, изменение прав, экспорт данных, доступ к конфиденциальному документу, действия администратора, действия «от имени»). Неизменяемая таблица (только INSERT, отдельная роль БД), экспорт в SIEM через syslog/HTTP.

## 6. Обсуждения (единые с чатами)

Комментарии к объектам и сообщения в чатах — **одна сущность**: `conversations` и `messages`. У каждого обсуждаемого объекта — беседа `kind='object'`, создаваемая при первом сообщении. Личные чаты, группы и каналы — беседы других видов (см. `11-communications-meetings.md`). Это даёт одинаковые упоминания, вложения, реакции, треды, поиск и уведомления везде, а обсуждение документа появляется и в модуле «Чаты» как лента «Обсуждения».

Специальные сообщения: системные (`kind='system'`: «документ отправлен на согласование»), решения по согласованию (`kind='decision'`), сообщения с быстрыми действиями (создать задачу, прикрепить).

## 7. Уведомления и Входящие

Два разных механизма:

| | Уведомление | Элемент Входящих |
|---|---|---|
| Что это | «что-то произошло» | «от вас требуется действие» |
| Состояние | прочитано/нет | открыт → выполнен/отклонён/отложен; закрывается **автоматически**, когда действие сделано (согласовал, принял поручение, ознакомился) |
| Примеры | упоминание, изменение объекта, ответ в треде | согласование, подпись, резолюция, ознакомление, назначение поручения, приёмка результата, приглашение, запрос доступа, алерт |

Конвейер: событие → правило уведомления (кому, шаблон, срочность, каналы) → агрегация/дедупликация (несколько правок одного объекта за 5 минут = одно уведомление) → доставка по каналам с учётом предпочтений и тихих часов → `notifications`. Элементы Входящих создают модули явно (`InboxService.open(user, kind, object, due)`) и закрывают по событиям.

Каналы: в приложении (realtime + центр уведомлений), e-mail (немедленно/дайджест), Telegram-бот (с кнопками действий: согласовать/отклонить/принять), Web Push. E-mail: режим `immediate` отправляется сразу, `digest` — заданием `notifications.digest` раз в 15 минут одним письмом на пользователя; отправленное помечается `notifications.emailed_at`, прочитанное в приложении в дайджест не попадает (ADR-0034). Настройки по категориям × каналам, «тихие часы», режим «не беспокоить», делегирование уведомлений заместителю.

## 8. Поиск

Индекс `SearchDocument`: `{id, type, spaceId, title, body, tags, ownerId, updatedAt, meta (статус, срок, исполнитель…), aclPrincipals[]}`. Каждое изменение объекта ставит задание переиндексации (дебаунс). Текст файлов и сообщений индексируется отдельными документами с `parentId`. Права применяются **фильтром `aclPrincipals`** (список принципалов с правом чтения, пересчитывается при изменении ACL; для объектов с наследованием — от предка) плюс пост-проверкой `authorize` для чувствительных типов.

Движок: Meilisearch (ADR-0017). Семантический поиск: эмбеддинги в `pgvector` для страниц, документов, сообщений, описаний датасетов; гибридная выдача. Палитра команд использует тот же индекс с ограничением по типам и ранжированием по недавним.

## 9. Задания

BullMQ-очереди: `imports`, `exports`, `transform`, `render`, `media`, `ai`, `index`, `notify`, `automation`, `process-timers`, `maintenance`, `data` (загрузка импорта и операции над таблицами датасетов, ADR-0046). Реестр заданий в Postgres (`jobs`: тип, объект, инициатор, статус, прогресс, результат, ошибка, попытки) — для экрана «Процессы» и истории. Правила: идемпотентность по ключу, повторы с экспоненциальной задержкой, тайм-ауты, отмена, прогресс через Redis pub/sub → realtime. У каждой очереди ровно один исполнитель — TypeScript-воркер или Python-движок (через `bullmq` для Python); соответствие задаёт `QUEUE_RUNTIME` в `packages/contracts` (ADR-0035). Задание ставится в транзакции вызывающего кода (запись реестра + событие `job.queued`) и попадает в BullMQ после коммита (ADR-0036).

## 10. Движок процессов

Декларативный движок для маршрутов документов, жизненных циклов задач, ознакомлений и автоматизаций с ожиданием. **Не** BPMN и **не** Temporal (ADR-0012): достаточно шагов, условий, параллельных ветвей, таймеров и назначений через выражения над оргструктурой.

Определение процесса (контракт `docs/contracts/process-definition.md`): список шагов типов `approval`, `sign`, `register`, `task`, `acknowledge`, `condition`, `parallel`, `wait`, `notify`, `set`, `call` (действие модуля), `end`. Назначения — выражения: `user:<id>`, `group:<id>`, `unit_head(author.unit)`, `manager(author)`, `role_in_space('legal')`, `chosen_by_initiator`, `field('responsible')`.

Экземпляр: `process_instances` (определение, версия, объект, статус, контекст), `process_steps` (шаг, статус, назначенные, решения, сроки), таймеры — отложенные задания. Каждое изменение — событие `process.step.*`, шаги-действия создают элементы Входящих. Версионирование определений: запущенные экземпляры продолжаются по своей версии.

Реализация (ADR-0079):
- **Модель и исполнение.** `@kchs/process` — чистый пакет: схема, проверка определения, выражения назначений и их резолвер, модель экземпляра и переходы (кворумы, режимы, ветви, условия, возврат с повторным согласованием `full|rejecters_only`). `kernel/process` исполняет переходы в транзакции под блокировкой строки экземпляра: определяет назначенных (порт справочника, участники пространств), выполняет шаги модулей, сохраняет разницу состояний, открывает и закрывает Входящие (копии заместителям), ставит таймеры, публикует события, вызывает хуки модуля.
- **Запуск и решения.** `ProcessService.start(tx, ctx, {objectId, definitionKey|definitionId, variables, assignees})` — в транзакции вызывающего модуля; решения (`act`), добавление согласующего, передача и переназначение шага, отмена, `completeStep` для шагов модулей. Кнопки шагов — `registerInboxActionHandler` (Входящие, Telegram, API; копия заместителя действует от имени получателя). Подпись с `requireMfa` подтверждается кодом через порт `kernel/second-factor` (реализация — identity).
- **Сроки и таймеры.** Срок шага — `BusinessCalendar.deadline(активация, dueWorkingDays)` или активация плюс `dueHours` календарных часов (ADR-0131); напоминания (за рабочий день и в день срока, у часового срока — одно, за час до срока), просрочка с эскалацией по `timers`, ожидание `wait` — моменты в строке шага (`timers`, `next_timer_at`), одно отложенное задание очереди `process-timers` на ближайший момент и обход по расписанию: состояние только в базе, перезапуск worker ничего не теряет.
- **Расширения модулей.** `registerProcessObjectProvider` (данные объекта для назначений и условий, изменение поля, хуки активации, решения, завершения шага и маршрута), `registerProcessStepHandler` (`register`, `task`, `call`), `registerProcessWaitEvent`. Право участников шагов видеть объект — `withProcessParticipants` в политике типа (с принципалами для поиска).
- **API.** `/process-definitions` (способность `processes.manage`: черновики, версии, проверка, публикация, предпросмотр назначений), `/processes` (запуск, если тип разрешает; маршруты объекта; линия шагов с решениями и действиями смотрящего; решения, состав назначенных, отмена).

## 11. Realtime

WebSocket-шлюз (Socket.IO с Redis-адаптером). Комнаты: `user:{id}`, `space:{id}`, `object:{id}`, `conversation:{id}`, `job:{id}`. Вход в комнату объекта проверяет `authorize(view)`; при изменении ACL пользователи без прав исключаются. Сообщения: `object.updated {id, type, version, changedFields}`, `message.posted`, `notification.new`, `inbox.changed`, `job.progress`, `presence` (кто смотрит объект), `typing`. Клиент по `object.updated` инвалидирует кэш запросов и мягко обновляет представление без скачков.

Совместное редактирование (страницы, тетради, протоколы, описания): Yjs-документы через Hocuspocus на `/collab`, персистентность в Postgres (`yjs_documents`), права по объекту.

## 12. Поля и формы

Единая система типов полей (`docs/contracts/field-types.md`) используется: в схемах датасетов, карточках документов, пользовательских полях задач/проектов, формах сбора, атрибутах объектов карты, параметрах отчётов. Один рендерер форм `SchemaForm` (валидация zod, зависимости полей, условная видимость, справочники, объекты, территории, геометрия, файлы). Один `FilterBuilder` и один набор форматтеров.

## 13. Представления

`views(id, owner|space, object_type, filters, sort, group_by, columns, mode, params)` — сохранённые представления списков любого типа (задачи, документы, датасеты, файлы, объекты слоя). Один компонент `CollectionView` с режимами таблица/доска/список/календарь/таймлайн/карта/галерея. Модули описывают схему фильтруемых полей типа.

## 14. Прочее

- **Хранилище**: S3-ключи `{{space}}/{{objectType}}/{{objectId}}/{{versionId}}/{{filename}}`; подписанные URL с коротким TTL; загрузка напрямую в S3 по подписанным URL (multipart, докачка); антивирусная проверка (ClamAV, опционально) заданием.
- **Настройки**: трёхуровневые (система → пространство → пользователь) с типизированными ключами.
- **Бизнес-календарь**: `calendars_business(country, year, days)` — рабочие/выходные/праздники/сокращённые; функция `addWorkingDays(date, n)`; используется задачами, документами, формами.
- **Теги**: глобальный словарь по пространствам; `object_tags`.
- **Избранное/недавние**: `favorites`, `recent_views` (последние 200 на пользователя).
- **Корзина**: единая для всех типов, 30 дней, восстановление с восстановлением связей.
- **Локализация**: все строки через `packages/i18n`; данные пользователей (названия объектов) — в исходном виде; справочники — с многоязычными подписями (`label jsonb {ru,tg,en}`).
