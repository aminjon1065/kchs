# Модель доступа

Статус: **Решено** (ADR-0004). Одна модель для всех модулей, строк данных, документов, файлов, чатов и карт.

## Цели

1. Понятность: пользователь и администратор всегда могут ответить, **почему** кто-то видит объект.
2. Единообразие: один диалог «Поделиться», один способ проверки, одинаковые уровни во всех модулях.
3. Оргструктура как источник прав: подразделения, руководители, должности, замещения.
4. Данные: ограничение по строкам и столбцам без возможности обхода из любого пути запроса.
5. Проверяемость: аудит и «негативные» тесты на каждый тип объекта.

## Принципалы

Кто может получать права:

| Принципал | Пример | Раскрытие |
|---|---|---|
| `user:<id>` | конкретный сотрудник | — |
| `group:<id>` | «Юристы», «Оперативный штаб» | статичное членство |
| `unit:<id>` | подразделение | все сотрудники подразделения **и вложенных** подразделений |
| `position:<id>` | должность (например, «Начальник управления») | занимающие должность |
| `space:<id>:<role>` | участники пространства с ролью не ниже | членство в пространстве |
| `role:<key>` | системная роль | назначение роли |
| `everyone` | все аутентифицированные | — |
| `link:<token>` | гостевая ссылка | предъявитель токена (ограничения: срок, пароль, только просмотр) |

**Множество принципалов пользователя** (`PrincipalSet`) = сам пользователь + группы + подразделение и все его предки + должности + пространства с ролями + роли + `everyone` + активные делегирования. Вычисляется при входе, кэшируется в Redis с версией; инвалидируется при изменении членства.

## Уровни доступа к объекту

Упорядоченные уровни: `none < view < comment < edit < manage < owner`.

| Уровень | Что можно |
|---|---|
| `view` | видеть объект, читать содержимое, скачивать (если тип не запрещает), обсуждать нельзя |
| `comment` | + писать в обсуждении, ставить реакции, предлагать правки (где применимо) |
| `edit` | + изменять содержимое и поля, добавлять вложения, менять статус в рамках роли |
| `manage` | + менять права (кроме владельца), переносить, архивировать, настраивать |
| `owner` | всё, включая удаление и передачу владения; ровно один владелец |

Модули объявляют **действия** с минимальным уровнем и, при необходимости, способностью: `dataset.export → view + cap:data.export`, `document.register → cap:documents.register`, `document.sign → назначен подписантом текущего шага`, `layer.edit_features → edit`, `map.publish → manage`.

## Источники прав (в порядке проверки)

1. **Системная роль.** `system_admin` — полный доступ с аудитом (все действия помечаются, доступ к конфиденциальным документам требует явного «режима администратора» с указанием причины). `security_auditor` — чтение всего и аудита, без изменений. Остальные роли дают только **способности** (`capabilities`), не доступ к объектам.
2. **Владелец** объекта — `owner`.
3. **Явные записи ACL** `acl_entries(object_id, principal, level, inherited_from?, expires_at?, granted_by)` на объекте **или его предках** до ближайшей границы `restricted` включительно (см. «Наследование»). Берётся максимум.
4. **Роль в пространстве** объекта: настройка пространства сопоставляет роль пространства уровню по умолчанию (по умолчанию: `viewer→view`, `member→comment`, `editor→edit`, `admin→manage`). Объект с `access_mode='restricted'` и всё его поддерево игнорируют этот источник: у закрытого объекта — только явные записи и владелец, у его потомков — ещё записи предков до границы.
5. **Политика типа** (`TypePolicy`) — производные права из отношений: участник согласования видит версию; исполнитель/соисполнитель/контролёр поручения — `edit`/`view`; руководитель видит поручения подчинённых (цепочка руководства, транзитивно, только `view`); участник беседы — `view/comment`; участник встречи; автор резолюции; регистратор видит журналы; «делопроизводитель подразделения» видит документы подразделения. Каждая политика — функция `derive(userCtx, object) → level` и SQL-предикат `visibleSql(userCtx)` для списков.
6. **Вложение** (ADR-0042): объект, прикреплённый связью `attachment`, видит тот, кто видит объект-хост, и правит тот, кто правит хост, — не выше `edit`; делиться вложением может только его владелец. Хост проверяется без этого шага.
7. **Атрибутные ограничения** (после определения уровня, могут только понижать): гриф конфиденциальности документа выше допуска пользователя → `none`; политики строк и столбцов датасета; ограничение по территориям пользователя.

Итог: `effectiveLevel = min(max(1..5), attributeCaps)`.

## Наследование

`objects.parent_id` образует деревья (папки, разделы пространства, проект→задачи, страница→подстраницы). ACL наследуется вниз, пока объект не переключён в `restricted` («разорвать наследование»). При разрыве текущие эффективные записи копируются явно (как в файловых системах), чтобы ничего не «исчезло» неожиданно. Разрыв действует на всё поддерево: потомки закрытого объекта наследуют записи только от предков до ближайшей границы `restricted` включительно, роль в пространстве к ним не применяется (новый участник пространства не видит содержимое закрытой папки, пока ему не выдали доступ). При разрыве копируются только действовавшие права — с максимальным уровнем на принципала; разрыв вложенного объекта не возвращает доступ, закрытый границей выше. Изменение доступа или перенос объекта пересчитывает фильтр прав в поисковом индексе для всего поддерева (задание `search.reindex-subtree`). Ссылочные отношения (слой→датасет, дашборд→график) **не** наследуют права: дашборд может быть виден, а его плитка — показать «нет доступа к данным». Диалог «Поделиться» предлагает «также дать доступ к используемым данным» с перечислением.

## Строки и столбцы датасетов

- **Политика строк** `dataset_row_policies(dataset_id, principal, filter)`: фильтр в языке выражений платформы над полями датасета и атрибутами пользователя (`user.unit_codes`, `user.territory_codes`, `user.attributes.<key>`). Несколько политик для пользователя объединяются через OR; отсутствие политик для датасета = все строки; наличие хотя бы одной политики для датасета включает режим «по умолчанию ничего» для тех, кто ни под одну не попал, кроме `manage+`.
- **Политика столбцов** `dataset_column_policies(dataset_id, principal, mode: hide|mask, fields[])`: скрытие или маскирование (`***`, последние 4 символа, округление).
- Формат политики строк, проверка компилятором при сохранении, API и поведение при правке схемы — ADR-0055 (в v1 фильтр общего формата с макросами пользователя; `user.attributes.<key>` — позже).
- Применение: компилятор запросов оборачивает каждый источник-датасет в подзапрос с политиками **для текущего пользователя**; сырой SQL проходит через парсер `libpg-query`, ссылки на таблицы заменяются на такие же подзапросы; экспорт, тайлы, GeoJSON, формы, API — всё проходит через один и тот же слой `DatasetAccess`. Обход невозможен, потому что физические таблицы `ds.*` недоступны роли приложения напрямую при выполнении пользовательских запросов: используется отдельная роль `kchs_query` с правами только на представления, создаваемые компилятором (см. `17-security.md`).

## Организационная структура

`org_units` (дерево, `head_user_id`, `deputy_user_ids`), `positions`, `employments(user_id, unit_id, position_id, is_primary, from, to)`. Из них выводятся: `manager(user)` — руководитель основного подразделения (если пользователь сам руководитель — руководитель родительского подразделения), `subordinates(user)` — транзитивно, `unit_head(unit)`. Кэшируется в `org_closure`.

Синхронизация из LDAP/AD: сопоставление OU → подразделения, `manager` атрибут → руководители; локальные правки помечаются как «переопределено вручную».

## Делегирование (замещение)

`delegations(from_user, to_user, scope: all|approvals|instructions|documents|meetings, starts_at, ends_at, note, status)`. Активное делегирование добавляет в `PrincipalSet` заместителя виртуальный принципал `acting_as:<from_user>` в указанной области; шаги процессов и элементы Входящих делегирующего дублируются заместителю; действия записываются с `actor.onBehalfOf`. Интерфейс: баннер «Вы замещаете …» с переключателем режима, фильтр «Только мои». Технически режим — заголовок `x-kchs-on-behalf-of` (ADR-0033). Делегирование не передаёт `owner` и права администратора.

## Способности (capabilities)

Глобальные разрешения действий, не привязанные к объекту. Присваиваются ролями (`roles`, `role_capabilities`, `user_roles`; роли можно ограничить пространством). Примеры: `spaces.create`, `users.manage`, `org.manage`, `documents.register`, `documents.journals.manage`, `data.sources.manage`, `data.export`, `gis.basemaps.manage`, `automation.manage`, `admin.audit.read`, `admin.system`, `ai.use`, `meetings.record`, `api_tokens.create`.

Стартовые роли: `system_admin`, `security_auditor`, `org_admin` (структура и пользователи), `registrar` (канцелярия), `data_steward`, `gis_admin`, `employee` (по умолчанию).

Кто назначает роли и обслуживает учётные записи (сброс пароля и MFA, блокировка):
- `system_admin` и `security_auditor` назначает, снимает и обслуживает только администратор системы;
- способность `roles.manage` даёт управление остальными ролями;
- `users.manage` без `roles.manage` (администратор оргструктуры) работает только с сотрудниками на базовой роли `employee` и назначает только её;
- свои роли и статус через администрирование не меняют; последнего активного администратора системы отключить или разжаловать нельзя;
- смена ролей действует со следующего запроса: кэш `PrincipalSet` сбрасывается сразу после коммита и событием `user.roles_changed`.

## Гостевые ссылки

`share_links(object_id, token, level: view, password_hash?, expires_at, max_uses, created_by)`. Доступ только к конкретному объекту (и его вложениям по явному флагу), без входа, с водяным знаком в предпросмотре, аудит открытий. Отключаемо политикой безопасности.

Открытие: `POST /share/{token}/open` (публичный маршрут, при необходимости с паролем) → короткоживущий токен доступа для заголовка `x-kchs-share-token`; открытие увеличивает `uses` и пишется в аудит как `share_link.opened` (ADR-0032). У гостя нет личного состояния: избранное, недавние, подписки и прочитанность не ведутся.

## Проверка доступа: интерфейс

```ts
authorize(ctx: UserCtx, action: string, objectRef: ObjectRef | ObjectRow, opts?): Promise<Decision>
// Decision = { allowed: boolean; level: Level; reasons: Reason[] }  // reasons — для «объяснить доступ»

visibleObjectsSql(ctx, objectType): SqlFragment  // предикат для списков и поиска
datasetAccess(ctx, datasetId): { rowFilter: Expr | null; hiddenFields: string[]; masks: Mask[] }
```

Правила использования: каждый HTTP-обработчик вызывает `authorize` до чтения данных; списки используют `visibleObjectsSql`; батчевые операции проверяют каждый объект; ошибки — `403` с кодом причины (без раскрытия существования объекта для тех, кто не имеет `view`: возвращается `404`).

## Диалог «Поделиться» и «Кто имеет доступ»

Единый диалог для любого объекта: поиск людей/групп/подразделений/должностей, уровень, срок, сообщение; переключатель «доступ по ссылке»; вкладка «Кто имеет доступ» показывает эффективные права всех с источником («участник пространства», «наследуется от папки „Регламенты“», «исполнитель поручения»). Кнопка «Проверить доступ пользователя» показывает `Decision.reasons`.

## Аудит и тесты

Каждое изменение прав — событие `acl.changed` и запись аудита. Для каждого типа объекта обязательны негативные тесты: пользователь без прав не видит объект в списках, поиске, по прямому URL, через связи, через realtime-комнату, через экспорт, через тайлы/GeoJSON и через API-токен.

## Как это выглядит для сценариев

| Сценарий | Как работает |
|---|---|
| Руководитель видит поручения подчинённых | политика типа `task`: `view`, если исполнитель ∈ `subordinates(user)` |
| Аналитик из региона видит только свои районы | политика строк датасета по `user.territory_codes`; хороплет и тайлы фильтруются автоматически |
| Юрист согласует документ | шаг процесса даёт `acting_in_step` → `view` версии + действие `approve`; после завершения остаётся `view` (настраивается типом документа) |
| Документ с грифом «Конфиденциально» | атрибутная проверка допуска; попытка доступа записывается в аудит |
| Заместитель на неделю | делегирование `approvals+instructions`; входящие дублируются; действия «от имени» |
| Дашборд для всех сотрудников | ACL `everyone: view` на дашборд и на датасеты-источники (или показатели с агрегатами, разрешёнными «всем» отдельной политикой `aggregate_only`) |

Политика `aggregate_only` (Рекомендовано, фаза 2): разрешает выполнять по датасету только агрегирующие запросы без доступа к строкам — для дашбордов «для всех» над чувствительными данными.
