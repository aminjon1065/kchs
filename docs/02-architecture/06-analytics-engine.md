# Аналитический движок: данные, запросы, показатели, визуализация

Главный модуль продукта. Статус: **Решено** для модели датасета, компилятора запросов, показателей и дашбордов; **Рекомендовано** для тетрадей, отчётов, форм и качества данных.

## 1. Центральная идея

**Датасет** — единица данных с владельцем, схемой, версиями, правами и историей. Всё остальное — представления и производные:

```
источник → импорт/синхронизация → ДАТАСЕТ ─┬─ таблица (grid)
                                            ├─ слой карты (если есть геометрия)
                                            ├─ запросы → графики → дашборды → отчёты
                                            ├─ показатели → алерты
                                            ├─ формы сбора (пишут в датасет)
                                            └─ преобразования → новые датасеты
```

Один компилятор запросов обслуживает: таблицу, конструктор, SQL-лабораторию, графики, показатели, тайлы карты (атрибутивные фильтры), экспорт, формы и API. Политики доступа применяются в одном месте.

## 2. Источники и импорт

### Поддерживаемые источники
| Вид | Фаза | Реализация |
|---|---|---|
| Файлы: CSV/TSV, XLSX/XLS, JSON/NDJSON, Parquet | 1 | engine: pandas/pyarrow, openpyxl; распознавание кодировки (chardet), разделителя, десятичного знака (`,`/`.`), форматов дат (`dd.mm.yyyy` и др.), листов Excel и диапазонов, заголовков в несколько строк |
| Геоданные: GeoJSON, Shapefile (zip), GeoPackage, KML/KMZ, GPX, CSV с координатами | 1–2 | engine: pyogrio/GDAL; перепроецирование в EPSG:4326; валидация геометрий |
| Внешние БД: PostgreSQL, MySQL/MariaDB, MS SQL, ClickHouse | 2 | engine: SQLAlchemy-коннекторы; синхронизация снимком/инкрементом по ключу и полю времени; расписание |
| REST/JSON API, S3/папка, Google Sheets | 3 | engine: коннекторы с маппингом |
| WFS / ArcGIS Feature Service / WMS | 3 | engine (GDAL) — как источник слоя |
| Формы сбора, редактирование, анализ, пайплайны | 1–2 | внутренние источники строк |

### Конвейер импорта файла
1. **Загрузка**: клиент получает подписанный URL, загружает файл в S3 напрямую (multipart, докачка); создаётся `file` и `import` в статусе `uploaded`.
2. **Анализ** (engine, синхронный вызов ≤ 5 с на выборке первых N строк): кодировка, разделитель, листы, заголовки, типы, семантика (дата/число/координаты/код территории/e-mail/ссылка), примеры значений, число строк (оценка).
3. **Сопоставление** (UI): для нового датасета — правка схемы (тип, подпись, семантика, ключ, гео-поля из lat/lon или WKT, территория по коду/имени); для существующего — сопоставление столбцов с полями, режим: `replace` (заменить всё), `append` (добавить), `upsert` (обновить по ключу), `sync` (upsert + пометить отсутствующие удалёнными).
4. **Выполнение** (engine, задание): чтение потоком → приведение типов с учётом локали → staging-таблица (`COPY`) → валидация (типы, обязательность, уникальность ключа, справочники, геометрии) → отчёт об ошибках (строка, столбец, причина; файл ошибок) → политика: «остановить при ошибках» или «загрузить валидные» → коммит (транзакция: `swap`/`INSERT`/`MERGE`) → новая `dataset_version` с diff → индексы/`ANALYZE`/генерализованные геометрии → событие `dataset.imported`. Для `upsert`/`sync` в существующий датасет — по выбору пользователя **предпросмотр изменений**: после разбора файл сравнивается с датасетом по ключу, импорт ждёт публикации или отмены со сводкой «добавится / изменится / удалится» и примерами (ADR-0068).
5. **Итог** в UI: сводка (добавлено/обновлено/удалено/ошибок), ссылки на ошибки, «повторить с теми же настройками», сохранение настроек как **шаблона импорта** (для регулярных файлов).

Крупные файлы (≥ 1 ГБ) обрабатываются потоково; прогресс — через `job.progress`.

## 3. Датасет

### Схема и семантика полей
Тип поля (контракт `contracts/field-types.md`) + **семантика**: `dimension` (разрез), `measure` (мера), `identifier`, `time`, `geometry`, `territory`, `category`, `text`, `lookup`. Семантика определяет поведение по умолчанию в конструкторе (что предлагать в группировках/мерах), форматирование, роль на карте и в показателях.

### Возможности экрана датасета
- **Таблица**: виртуализированная сетка, сортировка/фильтры/группировка на сервере (через QuerySpec), быстрый поиск, закрепление столбцов, форматирование по типам, редактирование ячеек (если `editable`), массовые операции над выделением, копирование, экспорт выделения.
- **Профиль столбцов**: тип, пустые %, уникальные, мин/макс, распределение (гистограмма/топ-значения), выбросы — считается заданием при новой версии и кэшируется.
- **Схема**: редактор полей; изменение типа с предпросмотром ошибок приведения; вычисляемые поля (формулы на языке выражений); справочники; чувствительность.
- **Версии**: список версий с diff; просмотр строк «как было»; откат (создаёт новую версию из старой).
- **История строк**: при `track_history` — кто/когда/что изменил (из `ds.h_*`).
- **Связи**: с другими датасетами, справочниками; «связанные строки» в карточке строки.
- **Карта** (если геометрия): вкладка карты с автослоем; связанное выделение.
- **Качество**: правила и последние результаты; флажки на строках.
- **Доступ**: политики строк/столбцов и обычный шаринг.
- **Происхождение**: откуда пришли данные и кто их использует.
- **Формы и расписания**: какие формы пишут, когда обновляется.

### Карточка строки
Универсальный экран строки (`/o/dataset/{id}/rows/{rowId}`): поля по схеме, геометрия на мини-карте, связанные строки, обсуждение (строка — адресуемый под-объект: `objectId#row=…`), документы/поручения «об этом объекте» (связи `about_feature`), история изменений.

## 4. Связи между датасетами и справочники

`dataset_relations` объявляют соединения (ключ → ключ, кардинальность). Конструктор запросов предлагает «добавить поля из связанного датасета» без ручного join. Поле типа `lookup` показывает подпись из справочника вместо кода. **Справочники** (`kind='reference'`): версионируемые датасеты с UI ведения (НСИ), используемые в полях `select`, картах документов, формах. Территории — специальный справочник (см. `07-gis-engine.md`).

## 5. Компилятор запросов

### QuerySpec
Декларативная спецификация (контракт `contracts/query-spec.md`): источник + упорядоченные шаги `filter`, `join`, `compute`, `aggregate`, `sort`, `limit`, `spatial`, `window`, `pivot` + параметры. Строится визуальным конструктором, тетрадями, графиками, показателями, таблицей датасета, тайлами (только `filter`) и ИИ.

### Язык выражений
Небольшой безопасный язык (`packages/query/expr`): арифметика, сравнения, логика, `if()/case`, строковые (`concat, lower, trim, substr, regex_match`), даты (`date_trunc, date_add, date_diff, year, month, now`), агрегаты (`sum, count, count_distinct, avg, min, max, median, percentile`), окно (`lag, lead, running_sum, rank`), гео (`distance, within, intersects, area, length, buffer, centroid, lat, lon`), справочники (`lookup(field)`), пользовательские атрибуты (`user.unit_codes`). Парсер — Pratt; AST типизируется по схеме датасета; ошибки — с позицией и подсказкой. Тот же язык — в политиках строк, вычисляемых полях, условиях правил автоматизации и показателях.

### Конвейер компиляции
```
QuerySpec ─validate(zod)─▶ resolve (схемы датасетов, связи, справочники, параметры)
  ─▶ authorize (доступ к каждому датасету; политики строк → фильтры; столбцов → исключение/маски)
  ─▶ plan (порядок шагов, pushdown фильтров, выбор генерализации гео, лимиты)
  ─▶ emit SQL (диалект Postgres; параметризация; подзапросы на источники с политиками)
  ─▶ execute (роль kchs_query, SET LOCAL statement_timeout, max rows, отмена по запросу клиента)
  ─▶ shape (колоночный результат {fields, rows}, типы, форматы) ─▶ cache (Redis; ключ включает версии датасетов и хэш политик)
```
Диалект DuckDB добавляется для колоночного tier (фаза 5) за тем же интерфейсом `Dialect`.

### Ограничения выполнения
Тайм-аут по умолчанию 30 с (интерактив), 10 мин (задание/экспорт); максимум строк для интерактива 50 000 (далее — пагинация/экспорт); `work_mem` ограничен для роли; параллельность запросов на пользователя ≤ 4; тяжёлые запросы можно «отправить в фон» (результат в файл).

### Результаты
Колоночный JSON для интерактива; NDJSON-поток для больших; CSV/XLSX/Parquet/GeoJSON для экспорта (задание). В фазе 5 — Arrow IPC для гридов и карт.

## 6. SQL-лаборатория

Редактор (CodeMirror 6) с подсветкой, автодополнением по датасетам (по подписям **и** ключам: пользователь пишет `Происшествия.Дата`, компилятор подставляет физические имена — «человеческие» имена таблиц как представления `ds_names`), параметрами `{{param}}`, историей, сохранением как `query`. Выполнение: парсинг `libpg-query` → проверка: только `SELECT`/`WITH`, только датасеты, к которым есть доступ, без функций записи и системных каталогов → переписывание ссылок на подзапросы с политиками → выполнение под `kchs_query`. Ошибки Postgres переводятся в понятные сообщения с позицией.

## 7. Показатели

Показатель = именованная мера над датасетом с определением (агрегат, фильтры), допустимыми измерениями, временным полем, единицей и форматом, целями и порогами, владельцем и описанием. Вычисление — генерация QuerySpec: `aggregate(measure) by (dimensions ⊆ allowed, time bucket) where (filters ∧ user filters)`. Значение показателя на дашборде, в отчёте, в алерте и в паспорте территории — **всегда** один и тот же код пути. Сравнения: предыдущий период, тот же период прошлого года, план/цель. Каталог показателей с поиском, деревом по областям, «где используется».

Предагрегаты (Рекомендовано, фаза 5): для показателей с большими датасетами — материализованные свёртки по `time × territory` при новой версии датасета.

## 8. Графики

ChartSpec (контракт `contracts/chart-spec.md`) — независимое от библиотеки описание: тип, кодировки (x, y[], color, size, tooltip, facet), опции (стек, сглаживание, оси/форматы, легенда, пороги, референс-линии, аннотации, сравнение периодов), цветовая схема из дизайн-системы. Рендер — ECharts через `packages/chart-spec` (тема из токенов, тёмная/светлая). Взаимодействие: наведение с синхронизацией по времени между графиками, выделение (brush) → фильтр связанным представлениям, клик по элементу → детализация (строки/карта), экспорт PNG/SVG/CSV. Большие данные — агрегация на сервере до ≤ 5 000 точек (даунсэмплинг по времени, top-N категорий + «прочее»).

## 9. Дашборды

- **Сетка** 12 колонок, плитки: график, показатель (с искрой и сравнением), карта, таблица, текст/заголовок, изображение, фильтр, кнопка-действие (открыть объект/создать задачу).
- **Фильтры и параметры**: глобальные (период, территория, подразделение, произвольные поля) с привязкой к полям плиток; URL-состояние; значения по умолчанию по пользователю (его территория).
- **Перекрёстная фильтрация**: клик/brush на плитке фильтрует другие (настраивается), карта фильтрует по экстенту/выделению.
- **Плитка-карта** (ADR-0074): сохранённая карта со своим видом; фильтры дашборда привязываются к полям датасетов её слоёв и уходят тайлам условием `f`; живых карт на экране — не больше четырёх (остальные — заглушки до прокрутки).
- **Детализация**: путь детализации у плитки (→ таблица строк → карточка строки → карта/документы).
- **Обновление**: по расписанию/интервалу; realtime при новой версии датасета (плитки перерисовываются мягко).
- **TV-режим**: полноэкранный, авто-переключение страниц дашборда, крупные шрифты, тёмная тема.
- **Подписки**: снимок PDF/PNG по расписанию в почту/Telegram/канал.
- **Версии** и черновик/публикация; **снимки** (зафиксированные значения на дату для отчётности).
- **Права**: плитка без доступа к данным показывает «нет доступа» с запросом доступа; диалог шаринга предлагает выдать доступ к источникам или включить `aggregate_only`.

## 10. Исследование (конструктор)

Экран `Explore`: слева шаги (источник → фильтры → соединения → вычисления → сводка → сортировка/лимит → пространственные операции), справа результат (таблица/график/карта, переключаемые) с мгновенным пересчётом (дебаунс, отмена предыдущего). Из любой таблицы датасета кнопка «Исследовать» переносит текущие фильтры. Сохранение: как график, в тетрадь, на дашборд, как новый датасет (материализация), как показатель. Режим SQL — переключение с сохранением (визуал → SQL с показом сгенерированного кода; обратно — только если SQL не менялся).

## 11. Тетради

Ячейки: текст (Tiptap, совместное редактирование), запрос (визуальный/SQL) с результатом-таблицей, график, карта (карта или слой со своим видом, ADR-0074), датасет (встроенный grid), показатель, изображение, ИИ (вопрос → ответ с сгенерированным запросом/графиком, редактируемым как обычная ячейка). Параметры тетради (период, территория) применяются ко всем ячейкам. Результаты кэшируются по версии датасета; «пересчитать всё». Экспорт: в отчёт (тетрадь → шаблон отчёта), в PDF, в страницу базы знаний. Шаринг как любого объекта; версии.

## 12. Отчёты

Шаблон отчёта — документоподобная структура: страницы/секции (заголовок, оглавление, текст с переменными `{{metric:...}}`, график, таблица (с ограничением строк и итогами), карта (экстент, слои, легенда), сетка показателей, разрыв страницы, приложение), параметры (период, территория), колонтитулы, титульный лист, стили (из дизайн-системы для печати). Генерация — задание `render`: engine поднимает Playwright, рендерит специальный маршрут `web /print/report/{runId}` (те же компоненты графиков и карт, что в UI) → PDF; DOCX — по шаблону docxtpl с вставкой изображений графиков/карт и таблиц. Результат — файлы в S3, `report_run`. Расписание и распространение (почта, Telegram, канал, папка). **Регистрация как документа**: `report.register_as_type_id` → создаётся документ выбранного типа с PDF как основной версией и запускается маршрут.

Реализация фазы 2 (ADR-0078): шаблон — совместный документ из блоков (текст, запрос, график, показатели, карта, разрыв страницы) с параметрами тетради и настройками печати; «В отчёт» из тетради; движок открывает страницу печати со служебным токеном (cookie) пользователя, под чьими правами строится запуск; файлы — в бакете экспортов, скачивает их только этот пользователь; рассылка по расписанию (BullMQ, пояс IANA) — отдельный рендер под правами каждого получателя, каналы — Входящие, почта с файлом, документ от бота Telegram. Регистрация как документа, канал чата и папка — позже.

## 13. Формы сбора данных

Форма привязана к датасету: схема формы ⊆ полей датасета (+ скрытые авто-поля: подразделение, период, автор). Назначения: кому (подразделения/пользователи), период (ежедневно к 08:00, еженедельно…), контроль сдачи (элементы Входящих «Сдать сводку», просрочка → эскалация). Отправка = вставка/обновление строк с `_import_id` = отправка; статус отправки (черновик/сдано/принято/возвращено); проверка ответственным (опционально). Экран «Контроль сдачи»: матрица подразделения × периоды. Заполнение — из веба, Telegram (простые формы) и мобильного веба с геопривязкой и фото.

## 14. Алерты

Правило на показатель: условие (порог, изменение %, аномалия по z-score/сезонности — фаза 5), разрез (по территориям), расписание проверки, каналы, cooldown. Срабатывание — событие `alert.fired` → уведомления/Входящие/правила автоматизации (например, создать задачу). История срабатываний на графике показателя.

## 15. Качество данных и происхождение

Правила качества: `not_null`, `unique`, `range`, `regex`, `in_set/lookup`, `referential`, `geometry_valid`, `freshness`, `row_count_delta`, `custom_expr`. Выполняются при новой версии; результаты в карточке датасета, бейдж качества в каталоге, флаги на строках, алерт при ухудшении. Происхождение строится из `dependencies` и `imports/pipelines`: граф «источник → датасет → пайплайн → запрос → график → дашборд → отчёт» с анализом влияния при изменении схемы (подсветка сломанных ссылок на поля, «мягкое» поведение графиков при отсутствии поля).

## 16. Преобразования (пайплайны)

Определение: цепочка шагов над входными датасетами → выходной датасет: `select/rename`, `cast`, `filter`, `dedupe`, `fill`, `split`, `merge_columns`, `compute`, `join`, `union`, `aggregate`, `unpivot/pivot`, `geocode`, `assign_territory`, `spatial_join`, `custom_sql` (в рамках компилятора). Выполняется engine (pandas/DuckDB для тяжёлых, SQL для лёгких) как задание, по расписанию или по событию `dataset.imported` входа. Результат — новая версия выходного датасета; происхождение сохраняется.

## 17. Связанные представления (ViewContext)

В рабочем пространстве панели (таблица, график, карта, тетрадь) могут быть **связаны**: у группы панелей общий `ViewContext = {filters, selection, timeRange, extent, highlight}`. Изменение в одной панели (brush на графике, выделение строк, перемещение карты с включённым «фильтр по экстенту») обновляет остальные. Связь показывается цветной меткой; отключается. Реализация — в `apps/web/app/workspace/view-context` (Zustand-хранилище на группу панелей) — общий механизм для аналитики и GIS.

Фаза 2 (ADR-0073): связь — по датасету внутри группы панелей (выделенные `_id`, фильтр кисти графика, охват карты); новая панель при разделении входит в группу исходной; охват у таблицы — пространственное окно компилятора (`DatasetRowsQuery.bbox`).

## 18. Интеллектуальные функции в аналитике

- «Спросить данные»: вопрос → QuerySpec (LLM с описанием схем, семантик, справочников и примерами) → выполнение → таблица/график + показ запроса; пользователь правит как обычный запрос. Никакого «скрытого SQL».
- Объяснение графика/аномалии, авто-описание датасета, предложение семантики полей и типов при импорте, предложения визуализации, генерация нарратива отчёта с цитатами значений.
- Все вызовы через `modules/ai` с политикой провайдера и аудитом; данные для контекста ограничиваются агрегатами и выборками по правам пользователя.

## 19. Производительность

| Задача | Приём |
|---|---|
| Таблица на миллионах строк | серверная пагинация по курсору `_id`, `count` приблизительный (`reltuples`) с точным по запросу, индексы по сортируемым полям |
| Графики | агрегация на сервере, лимит точек, кэш результатов по версии |
| Показатели на дашборде | один батч-запрос на дашборд (группировка плиток по датасету) + кэш |
| Импорт | `COPY`, staging, индексы после загрузки |
| Гео | GIST, генерализация по зумам, тайл-кэш (см. GIS) |
| Большие датасеты (S2+) | колоночный tier: Parquet в S3 + DuckDB в engine; QuerySpec компилируется в диалект DuckDB; горячие срезы — в Postgres |
