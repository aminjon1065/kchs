# Безопасность

Статус: **Решено**.

## 1. Модель угроз (кратко)

Активы: персональные данные сотрудников, служебные и конфиденциальные документы, пространственные данные об инфраструктуре, учётные данные интеграций, записи встреч. Угрозы: несанкционированный доступ (внешний и внутренний), утечка через экспорт/ссылки/ИИ-провайдера, инъекции (SQL, XSS, шаблоны), подделка запросов (CSRF), компрометация сессий, злоупотребление администратора, потеря данных, отказ в обслуживании (тяжёлые запросы).

## 2. Аутентификация

- Пароли: Argon2id (память 64 МБ, итерации 3), политика (длина ≥ 12, проверка по словарю утечек — локальный список), история паролей (5), блокировка после 10 неудачных попыток на 15 минут с прогрессией, защита от перебора по IP и логину (rate limit).
- MFA: TOTP (обязательность по роли/политике), коды восстановления, WebAuthn/passkeys (фаза 5, ADR-0098); шаг-вверх (повторное подтверждение) для подписи документов, изменения прав администратора, экспорта конфиденциального. Ключ TOTP — 160 бит (RFC 4226 §4). Обязательность задаёт политика `security.requireMfaRoles` (ADR-0040): пока второй фактор не подключён, сервер отвечает `403 mfa_enrollment_required` на всё, кроме `GET /me`, подключения TOTP или ключа входа и выхода, realtime-шлюз не принимает подключение; отключить обязательный для роли фактор нельзя. Сначала сменяется временный пароль, затем подключается MFA.
- Сессии: серверные (`sessions`), cookie `HttpOnly; Secure; SameSite=Lax`, ротация идентификатора при входе и повышении привилегий, абсолютный срок (30 дней) и бездействие (12 ч, настраивается политикой `security.sessionIdleHours`), список устройств и принудительное завершение, привязка к `User-Agent`-семейству.
- SSO OIDC: PKCE, проверка `iss/aud/nonce`, JIT-создание с правилами сопоставления групп; LDAP bind по TLS. Реализовано в фазе 5 (ADR-0098): состояние незавершённого входа — одноразовая строка в базе (`state` хэшем, проверочный код PKCE зашифрован, срок 10 минут); секреты поставщиков (пароль учётной записи чтения каталога, секрет клиента) — в зашифрованной колонке `auth_providers.secret_enc`, наружу не возвращаются и в журналы не пишутся. Учётная запись каталога проверяет пароль привязкой в каталоге и локального пароля не имеет; блокировка после серии неудач, аудит и политика сессий у неё те же. Политика `security.requireMfaRoles` применяется и ко входу через IdP: гарантия организации не зависит от настройки провайдера (вопрос N44).
- Ключи входа (WebAuthn, ADR-0098): ключ с подтверждением личности (`UV`) входит самостоятельно и засчитывается как второй фактор наравне с TOTP; ключ без подтверждения служит только вторым фактором после пароля. Вызов одноразовый, счётчик подписи только растёт, отозванный ключ не находится. Подключение ключа разрешено и при незакрытом требовании второго фактора — наравне с подключением TOTP.
- Восстановление доступа: одноразовые ссылки (15 минут), уведомление на все каналы, отмена активных сессий по выбору; администратор может выдать временный пароль с обязательной сменой. Временные пароли импорта из Excel не сохраняются ни в отчёте, ни в журнале задания, ни в аудите: они зашифрованы в Redis не дольше двух часов и выдаются инициатору одним файлом один раз (ADR-0041). Пока временный пароль не сменён, сервер отвечает `403 password_change_required` на всё, кроме `GET /me`, смены пароля и выхода. Ссылка восстановления не действует для отключённой учётной записи.
- Вход не раскрывает существование учётной записи: для неизвестного логина хеш всё равно считается (время ответа одинаково), о блокировке сообщается только при верном пароле. Код TOTP принимается один раз: шаг последнего кода хранится в `mfa_factors.last_step`.
- Гости (ссылки, встречи): токены с коротким сроком, ограниченный контекст, без доступа к API вне объекта. Гостевой токен допускается только на чтение маршрутов объекта; маршруты сессии, способностей и любые изменения для гостя отвечают `404`. Ссылку с паролем или лимитом открытий нельзя предъявить напрямую — только через `POST /share/{token}/open`, где считаются открытия. Политика `security.allowShareLinks = false` запрещает создание ссылок и приостанавливает выданные (ADR-0040).
- Пароль не может содержать логин — при создании, смене и восстановлении по ссылке одинаково.

## 3. Авторизация

См. `03-access-model.md`. Дополнительно: принцип «404 вместо 403» для отсутствия `view`; проверка на каждом маршруте (интеграционный тест с автоматической проверкой, что все маршруты объявляют `auth` политику — маршрут без объявления не регистрируется); негативные тесты по типам объектов; действия «от имени» с двойной записью в аудит; администратор входит в «режим администратора» для доступа к чужим конфиденциальным объектам с обязательным обоснованием.

## 4. Данные и запросы

- Все обращения к БД через Drizzle с параметрами; динамический SQL компилятора использует только идентификаторы из метаданных (экранирование `quoteIdentifier`) и параметры для значений.
- Сырой SQL: парсер `libpg-query` → белый список узлов (SELECT/WITH/JOIN/функции из списка), запрет `COPY`, DDL/DML, `pg_*`/`information_schema`, `SET`, `dblink`; таблицы только `ds.*` с проверкой прав; переписывание в подзапросы с политиками; выполнение под ролью `kchs_query` с `statement_timeout`, `work_mem`, `temp_file_limit`, `SET LOCAL` в транзакции `READ ONLY`.
- Роли БД с минимальными привилегиями; пароли БД в секретах; соединения по TLS в S2.
- Шифрование: диски/тома (LUKS или на уровне облака), S3 SSE, секреты интеграций — AES-256-GCM с мастер-ключом из окружения/KMS (`KCHS_MASTER_KEY`, ротация с перешифрованием), TOTP-секреты — так же.
- Персональные данные: минимизация в логах, маскирование в ошибках, право на экспорт/удаление профиля (в рамках трудовых отношений — по политике).
- Телеметрия (ADR-0045): в трассах SQL — параметризованный текст без значений, Redis — только имя команды (ключи содержат токены сессий), из адресов вычищаются строка запроса (поисковые фразы, токены ссылок) и адрес клиента; пользователь — только идентификатором. Метрики — на отдельном порту 9464 во внутренней сети compose (не публикуется, web его не проксирует); Grafana и приём OTLP — только на `KCHS_BIND` (127.0.0.1), пароль Grafana — из `generate-secrets.sh`.

## 5. Веб-безопасность

- CSP строгий (`default-src 'self'`; для карт — `blob:`/`worker-src`; без `unsafe-inline` — стили через nonce), `X-Frame-Options: DENY` (кроме маршрутов печати), HSTS, `Referrer-Policy`, `Permissions-Policy` (камера/микрофон только для своего origin).
  Как устроено (ADR-0043): заголовки ставит Caddy (`infra/compose/caddy/Caddyfile`, им же отдаёт SPA образ web). Скрипты — только свои файлы (`script-src 'self'`): тема до первой отрисовки применяется внешним `public/theme-init.js`, eval запрещён (zod работает в режиме `jitless`). Стили — свои файлы и элементы `<style>` с nonce запроса: Caddy берёт `{http.request.uuid}` и для `'nonce-…'` в CSP, и для `<meta name="csp-nonce">` в `index.html` (шаблон `templates`, только HTML); приложение при старте передаёт его библиотекам, которые вставляют `<style>` во время работы (`setCspNonce` в `@kchs/ui`: Radix ScrollArea/Select — проп `nonce`, react-remove-scroll — get-nonce, react-resizable-panels — свой `setNonce`). Страницы с nonce не кешируются (`no-store`), файлы `/assets/*` с хешем — навсегда. Загрузка и превью идут в S3 по подписанным ссылкам — его origin (`KCHS_STORAGE_ORIGIN`) разрешён в `connect-src`/`img-src`/`media-src`. Проверка `pnpm --filter @kchs/web csp:check` собирает web, поднимает Caddy с этим же Caddyfile и обходит ключевые экраны Playwright, падая на любом `securitypolicyviolation` (CI, задание «Сквозные сценарии»).
- XSS: React экранирует; rich-text (Tiptap JSON) рендерится через безопасный рендерер с белым списком узлов; HTML-шаблоны печатных форм — через `DOMPurify` + песочница; загруженные SVG — санитизация или отдача как `attachment`.
- CSRF: SameSite + токен в заголовке (`X-CSRF-Token`) для cookie-аутентификации; Bearer-запросы не подвержены.
- Файлы: проверка типов по содержимому (magic bytes), ограничение размеров, антивирус (ClamAV, опц.), отдача через подписанные URL с `Content-Disposition`, отдельный домен/путь для пользовательского контента (S2: отдельный origin для превью).
- Зависимости: `pnpm audit`/`uv`-аудит в CI, lockfile, Renovate; образы — сканирование (Trivy).
- Rate limiting: вход, восстановление, поиск, запросы, тайлы, API-токены; защита от тяжёлых запросов — тайм-ауты и лимиты параллельности на пользователя. Лимит считается по пользователю (после аутентификации) или по адресу клиента. Организация обычно выходит в сеть через один NAT, поэтому формы входа считают попытки по адресу и учётной записи: вход — адрес + логин (10 в минуту) и общий потолок адреса (`LOGIN_RATE_LIMIT_PER_IP_PER_MINUTE`, по умолчанию 300 — утренний вход всей организации); второй фактор — адрес + вызов входа (сам вызов допускает 5 попыток); запрос восстановления — адрес + логин (5 за 10 минут) и потолок адреса (50 за 10 минут); установка пароля по ссылке — адрес + токен. Логины и токены в ключах счётчиков хешируются. Открытие гостевой ссылки ограничено для каждой ссылки отдельно (адрес + ссылка, 20 в минуту): подбор пароля к одной ссылке не блокирует гостей других, выходящих через тот же NAT. Ответ 429 — обычная проблема API (`rate_limited`, `retryAfter`, заголовок `Retry-After`); экран входа показывает время ожидания. Адрес берётся из `X-Forwarded-For` только от доверенного прокси (`TRUST_PROXY`: `loopback` в разработке, `uniquelocal` за Caddy в Docker; значение `true` запрещено — иначе адрес подменяется заголовком).
- Периметр: наружу открыт только Caddy (и MinIO для подписанных ссылок); api слушает порт лишь на `127.0.0.1` сервера, внутренние маршруты `/api/v1/internal/*` на прокси отвечают `404`, сервисный токен движка сравнивается за постоянное время.
- Исходящие запросы по адресу, который задают люди (ADR-0132): ленты, растровые подложки, ГИС-службы и ICS-подписки идут одним клиентом `shared/net/outbound.ts`. Напрямую адрес проверяется после разрешения имени, в момент соединения (подмена DNS проверку не обходит): служебные сети — loopback, link-local с метаданными облака, «этот узел», multicast — закрыты всегда, частные — по политике вызова (ICS-подписки закрывают их, пока не включён `CALENDAR_FEEDS_ALLOW_PRIVATE`; ленты и подложки — нет: серверы закрытого контура обычно в них). Перенаправления проверяются на каждом шаге, ответ ограничен временем, размером и типом, в сообщении об ошибке нет адреса — в нём бывает ключ API; сам ключ хранит интеграция HTTP и подставляет его перед запросом. Исходящий прокси задают `HTTP_PROXY`/`HTTPS_PROXY`: через него идут эти запросы и глобальный `fetch` процесса (вебхуки, провайдеры ИИ); имя разрешает прокси, поэтому клиент закрывает адреса-литералы служебных сетей и `localhost`, а `NO_PROXY` и службы установки идут напрямую — с той же проверкой. `OUTBOUND_ALLOW_LOOPBACK` открывает loopback только для локальной отладки. Вебхуки проверяют адрес по своему правилу до отправки (ADR-0097): частные сети им закрыты.

## 6. Аудит и мониторинг безопасности

Агент журналов Alloy (профиль `observability`) читает журналы контейнеров через `docker.sock`, смонтированный только на чтение, — это всё равно доступ к API Docker: профиль включает администратор сервера, а сам Alloy не публикует портов, кроме приёма OTLP на `KCHS_BIND`.

`audit_log` неизменяем (роль `kchs_audit` только INSERT; периодический экспорт в WORM-хранилище/SIEM). Обязательные события: аутентификация, изменения прав/ролей/структуры, доступ к конфиденциальному, экспорты, подписи, «от имени», действия администратора, изменения политик, интеграции, API-токены. Алерты: всплеск неудачных входов, вход из новой страны/устройства (уведомление пользователю), массовый экспорт, изменение ролей администраторов. Отчёты соответствия в администрировании.

## 7. ИИ-безопасность

Политика передачи данных провайдеру (по грифу/пространству; on-prem без ограничений), запрет включения секретов и паролей в промпты (фильтр), инструменты ассистента через обычный `authorize`, защита от prompt-injection в данных: содержимое документов/сообщений передаётся как **данные**, инструкции — только системные; результаты извлечения помечаются как «предложение ИИ» и требуют подтверждения.

## 8. Процесс

Чек-лист безопасности при завершении каждой фазы (`04-delivery/04-verification.md`), ZAP baseline в CI на staging, обзор зависимостей ежемесячно, план реагирования на инциденты (runbook), тестовое восстановление из бэкапа ежемесячно, обновления образов по расписанию.
