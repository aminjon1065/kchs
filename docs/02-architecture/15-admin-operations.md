# Администрирование, эксплуатация, развёртывание

Статус: **Решено** — Docker Compose для S1, единая точка правды в Postgres, стратегия резервирования; **Рекомендовано** — состав мониторинга и Kubernetes-профиль для S2.

## 1. Консоль администрирования

Разделы (доступ по способностям):
- **Пользователи**: список/поиск, создание/приглашение, блокировка, сброс MFA, сессии и устройства, атрибуты для политик, импорт из Excel/LDAP, массовые операции. Импорт из Excel (ADR-0041): шаблон со справочниками ролей и подразделений → «Проверить» без записи → импорт годных строк; строки с существующим логином пропускаются, отчёт по строкам — на экране и в CSV, временные пароли созданных — одноразовым файлом инициатору.
- **Структура**: дерево подразделений (drag-and-drop), должности, назначения, руководители/заместители, территория подразделения, синхронизация с каталогом и «переопределено вручную».
- **Роли и способности**: матрица, назначение пользователям (глобально/в пространстве).
- **Пространства**: список, участники, квоты, архивирование, передача.
- **Документооборот**: типы документов и карточки, журналы, маршруты, шаблоны, номенклатура дел, корреспонденты, грифы.
- **Данные**: источники, реестр датасетов (владельцы, размер, свежесть, качество), справочники, показатели, политики строк, расписания, колоночный tier.
- **GIS**: базовые карты, территории (загрузка/обновление границ), геокодер, тайл-кэш.
- **Интеграции и правила**: см. `14-automation-integrations.md`.
- **Уведомления**: правила по умолчанию, шаблоны писем/сообщений, тестовая отправка.
- **Процессы и задания**: очереди, активные/ошибочные задания, повтор/отмена, расписания.
- **Безопасность**: политики (пароли, MFA-обязательность, тайм-ауты сессий, IP-списки, публичные ссылки, экспорт), аудит с фильтрами и экспортом, активные сессии, API-токены.
- **Система**: здоровье сервисов, версии, размеры БД/хранилища, резервные копии (последние, проверка восстановления), флаги функций, объявления, брендирование (логотип, название, акцентный цвет), локали и календарь, лицензии/лимиты, обслуживание (переиндексация, пересчёт кэшей, очистка корзины).

## 2. Развёртывание S1 (Docker Compose)

Состав `infra/compose/docker-compose.yml`:

```
web (caddy + SPA)   :80/:443 — TLS, статика, /api → api, /ws → api, /collab → api, CSP; /livekit → livekit (фаза 4) — ADR-0044
api ×2              ROLE=api
worker ×1           ROLE=worker
engine ×1           python; тома для моделей (whisper, bge-m3, tesseract data)
postgres            postgis/postgis:17-3.5 + pgvector; том данных; pgbackrest sidecar
redis               redis:7 (AOF)
minio               бакеты создаются init-контейнером
meilisearch         том индекса
livekit + egress    UDP 50000-60000, TCP 7881, TURN/TLS 443 (через proxy или отдельный IP)
alloy, tempo, loki, prometheus, grafana      (профиль `observability`, ADR-0045)
onlyoffice          (профиль `office`, опционально)
titiler, photon     (профили `raster`, `geocoder`, опционально)
```

Требования S1: 16 vCPU, 64 ГБ RAM, NVMe 1 ТБ (БД) + хранилище файлов по объёму (или внешний S3), ОС Linux, Docker 27+. Установка: `git clone`, `.env` из `.env.example` (секреты генерируются скриптом `infra/scripts/generate-secrets.sh --mode app`), `docker compose --profile app up -d`, `docker compose exec api kchs init` (миграции, первый администратор с временным паролем, базовые справочники; PMTiles-базовая карта — загрузка/генерация, с фазы 2). Порядок и проверка — ADR-0044, `infra/scripts/verify-stack.sh`.

Обновление: `docker compose pull && docker compose up -d` — миграции применяются при старте `api` с advisory lock; обратная совместимость миграций на одну версию назад (blue-green без простоя для S2).

## 3. S2 (Kubernetes)

Helm-чарт `infra/helm/kchs`: Deployments `api` (HPA по CPU/RPS), `worker` (по глубине очередей, KEDA), `engine` (по очередям; GPU-node pool опционально для whisper/эмбеддингов), `web` (nginx). Данные: PostgreSQL через оператор (CloudNativePG/Patroni) с репликой и PgBouncer, Redis Sentinel/оператор, MinIO distributed (4+ узла) или внешний S3, Meilisearch (одиночный с PVC; репликация — перестроением), LiveKit multi-node с Redis. Ingress с TLS, отдельный сервис для UDP LiveKit. Кэш тайлов — nginx/Varnish перед API или Martin. Secrets — внешний менеджер (Vault/SealedSecrets).

## 4. Наблюдаемость

- Метрики (OpenTelemetry → Prometheus): HTTP (RPS, латентность по маршрутам, ошибки), очереди (глубина, длительность, ошибки), запросы датасетов (p95, тайм-ауты, кэш-хиты), тайлы, WebSocket-подключения, LiveKit, БД (pg_exporter), Redis, MinIO, Meilisearch.
- Логи (pino JSON → Loki): корреляция `requestId`/`correlationId`, уровни, без персональных данных в логах (маскирование).
- Трассы (Tempo): запрос → SQL → задание.
- Ошибки: Sentry-совместимый (GlitchTip self-hosted или Sentry) для web и api/engine.
- Дашборды Grafana из репозитория (`infra/observability/dashboards`), алерты: ошибки > 1 %, p95 > бюджета, очередь растёт > 15 мин, диск > 80 %, бэкап не выполнен, репликация отстаёт.
- Экран «Здоровье» в администрировании — сводка из тех же метрик.

Как устроено в S1 (ADR-0045):

- **Включение.** `docker compose --profile observability up -d` поднимает Alloy (агент: приём
  OTLP и журналы контейнеров своего проекта), Tempo, Loki, Prometheus и Grafana
  (`http://127.0.0.1:3001`, пароль `GRAFANA_ADMIN_PASSWORD`). Метрики api и worker включены в
  контейнерах всегда (`METRICS_PORT=9464` в `x-app-env`); трассы — адресом коллектора:
  `OTEL_EXPORTER_OTLP_ENDPOINT_INTERNAL=http://alloy:4318` в `.env` для профиля `app`, для api на
  хосте — `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` (и `METRICS_PORT=9464`, чтобы
  Prometheus опрашивал `host.docker.internal:9464`). Без адреса трассы выключены полностью:
  SDK не загружается и модули не перехватываются. Доля трасс — `OTEL_TRACES_SAMPLER=
  parentbased_traceidratio` и `OTEL_TRACES_SAMPLER_ARG`.
- **Метрики** (`/metrics` на порту 9464, только внутренняя сеть): `http_server_request_duration`
  по методу, шаблону маршрута и коду; процесс — `process_memory_usage` (RSS),
  `process_cpu_time_total`, `nodejs_eventloop_delay_p99`, `nodejs_eventloop_utilization`;
  `kchs_outbox_pending`, `kchs_outbox_oldest_age`; `kchs_queue_jobs{queue,state}`;
  `kchs_job_duration`, `kchs_event_duration` (по исходу); `kchs_realtime_connections`.
- **Трассы**: спан запроса по шаблону маршрута с `kchs.request_id` и `enduser.id`, внутри — SQL
  (параметризованный текст), Redis (имя команды), исходящие HTTP (S3, Meilisearch, движок).
  Задание — дочерний спан трассы запроса, поставившего его (через outbox и BullMQ). Обработка
  события подписчиком — своя трасса с `kchs.correlation_id` = `requestId`: поиск в Tempo
  `{span.kchs.correlation_id = "req_…"}`.
- **Журналы**: строки pino несут `trace_id`/`span_id`; в Grafana поле `trace_id` открывает
  трассу, из спана — журналы с тем же `trace_id`.
- **Дашборд** «kchs — обзор» (`infra/observability/dashboards/kchs-overview.json`): запросы,
  p95 по маршрутам с линией бюджета, ошибки, память, CPU, цикл событий, outbox, очереди,
  задания, события, журналы предупреждений. **Алерты** — `infra/observability/prometheus/
  alerts.yml`; доставка (Alertmanager, почта/Telegram) — следующий шаг.
- **Бюджеты** (`04-verification.md` §4) — `bash infra/perf/run-k6.sh` на стенде с демо-данными
  (профиль `infra/perf/k6/api-basic.js`); ночью в CI — в задании «Установка в контейнерах».
- Пока нет: экспортёров Postgres/Redis/MinIO/Meilisearch, трасс движка, Alertmanager.

## 5. Резервирование и восстановление

| Компонент | Метод | Частота | Проверка |
|---|---|---|---|
| PostgreSQL | pgBackRest: полный + инкрементальный + WAL-архив в S3/отдельный том | полный еженедельно, инкремент ежедневно, WAL непрерывно | ежемесячное восстановление в тестовый контур (автоматизированное задание с отчётом) |
| MinIO | версионирование объектов + репликация в резервный бакет/узел (mc mirror) | непрерывно | выборочная проверка контрольных сумм |
| Meilisearch | дамп ежедневно; полностью восстанавливается переиндексацией из Postgres | ежедневно | переиндексация в тесте |
| Redis | AOF; потери допустимы (очереди восстанавливаются из `jobs`/outbox) | — | — |
| Конфигурация | `.env`/секреты в менеджере, Compose/Helm в git | при изменении | — |

Целевые RPO 15 мин, RTO 1 ч (S1). Runbook восстановления — в `infra/runbooks/restore.md` (создаёт исполнитель на фазе 0).

## 6. Обслуживание

Ежедневные задания: очистка корзины (30 дней), экспорты (30 дней), истёкшие сессии/ссылки, партиции, `VACUUM` тяжёлых таблиц, проверка сирот в S3, пересчёт денормализованных счётчиков, дайджесты. Еженедельно: отчёт о здоровье (размеры, рост, медленные запросы), проверка бэкапов. Обновление PMTiles — ежеквартально (скрипт Planetiler на отдельной машине → загрузка в MinIO → переключение версии).

## 7. Окружения

`dev` (compose с hot-reload, seed), `test` (CI: testcontainers), `staging` (копия prod-конфигурации, анонимизированные данные), `prod`. Флаги функций — таблица `settings` scope `system` + локальные переопределения; новые модули включаются флагом.

## 8. Ограничения S1, при которых переходить к S2

Более 300 одновременных пользователей, суммарный размер датасетов > 500 ГБ, p95 запросов стабильно > бюджета при верных индексах, тайлы > 200 RPS, > 20 одновременных конференций, требование 99.9 %.
