# Автоматизация и интеграции

Статус: **Решено** — правила «триггер → условия → действия» на шине событий; публичный REST API и вебхуки; **Рекомендовано** — набор интеграций и порядок их появления.

## 1. Правила автоматизации

Правило ★ (`rules`): `trigger` (событие из каталога, расписание cron, вебхук-вход, ручной запуск), `conditions` (выражения языка платформы над полезной нагрузкой события и объектом: `object.type == 'document' && object.fields.amount > 100000`), `actions` (список): создать задачу/поручение, изменить поле/статус, назначить, уведомить (пользователей/канал/Telegram/почта), создать документ по шаблону, запустить пайплайн/импорт, запустить процесс, вызвать вебхук, добавить связь/тег, запустить ИИ-задачу (с записью результата в поле/комментарий), создать событие календаря, отложить (`wait`) и продолжить. Выполняются в worker очередью `automation` от имени `run_as` (служебный пользователь правила с ограниченными правами — **не** от имени администратора), с журналом `rule_runs`, идемпотентностью по `(rule, event)` и защитой от циклов (глубина каузальной цепочки ≤ 5, событие с `causationId` от правила не запускает то же правило).

Конструктор: список правил по пространствам, форма «когда / если / то» с подсказками полей из схем событий и типов, тестовый прогон на последних событиях («что бы произошло»), шаблоны правил (галерея), включение/выключение, история запусков с диагностикой.

Реализовано (ADR-0096): правило — объект реестра `rule` в модуле `automation`; `run_as` —
идентификатор служебного пользователя (администратор системы недопустим), и запуск пропускается,
если `run_as` не видит объект события; условия и шаблоны — язык выражений платформы, получатели
и исполнители — язык назначений маршрутов; ручной запуск — кнопки в контекст-панели карточки
объекта. Действия `run_pipeline` и `run_import` ждут пайплайнов (P5-E03).

Контракт: `contracts/automation-rule.md`.

## 2. Расписания

Единый планировщик (BullMQ repeatable jobs) для: правил по cron, обновлений источников, пайплайнов, рассылок дашбордов/отчётов, проверок алертов, форм сбора (создание элементов Входящих), обслуживания. Экран «Расписания» в администрировании с ближайшими запусками и историей.

Реализовано (ADR-0096): регулярные задания объявляются через `declareSchedule` в ядре и ставятся
одним проходом `syncSchedules()` при старте воркера (обслуживание, таймеры маршрутов, задания
модулей); правила по cron — свои планировщики по состоянию правила. Экран показывает и то, и
другое: ближайший запуск, последний результат, история, переключатель и «выполнить сейчас».
Рассылки отчётов ведут собственные планировщики на карточке отчёта (ADR-0078).

## 3. Публичный API

- REST `/api/v1`, OpenAPI генерируется из zod-контрактов; документация на `/api/docs`.
- Аутентификация: cookie-сессия (браузер) или `Authorization: Bearer <api_token>` (интеграции; токены со scopes: `read:datasets`, `write:datasets`, `read:documents`, …, привязаны к пользователю или служебной учётной записи, срок действия, аудит).
- Всё, что умеет UI, доступно через API (UI использует тот же API).
- Массовые операции: `POST /datasets/{id}/rows:batch`, `POST /objects:batch-get`; длительные — задания (`202 + jobId`).
- Лимиты: rate limit по токену/пользователю, квоты на экспорт.

Реализовано (ADR-0097): токен `kchs_<префикс>_<секрет>` — учётные данные, как сессия (в базе только хэш; видимый префикс ищет строку, сравнение по SHA-256 в постоянное время). Область доступа выводится из тега маршрута: `GET` и `POST` с признаком `readOnly` — чтение, остальное — запись; `write:x` включает `read:x`. Список закрыт по умолчанию: незнакомый тег и маршрут без тега токенам недоступны, безусловно закрыты `/me`, `/auth`, `/internal`, `/admin`, `/share`, `/hooks` и теги `auth`, `me`, `internal`, `admin`, `ai`. Токен строит контекст владельца и дальше проходит обычный `authorize()`; режим администратора и замещение (`x-kchs-on-behalf-of`) ему недоступны, незавершённая настройка входа владельца закрывает токен целиком. У токена свой счётчик запросов (`API_TOKEN_RATE_LIMIT_PER_MINUTE` или собственный потолок). Документация — `/api/docs`: страница собирается на сервере по текущему OpenAPI, без скриптов (CSP установки разрешает только свои файлы, ADR-0043). Массовые операции — `POST /objects/batch-get` и `POST /datasets/{id}/rows/batch` (вставка, изменение и удаление одной транзакцией; больше 500 операций или `async` — `202` с `jobId`, задание выполняется правами поставившего). Экраны: «Мои токены» в профиле, «Токены API» в администрировании.

## 4. Вебхуки

Исходящие: подписка на события (фильтр по типам/пространствам), доставка `POST` с подписью HMAC-SHA256, повторы с экспоненциальной задержкой (до 24 ч), журнал доставок, ручной повтор. Входящие: `POST /api/v1/hooks/{integrationId}/{secret}` → событие `webhook.received` → правила.

Реализовано (ADR-0097): вебхук — объект реестра с владельцем `run_as`; наружу уходит только то, что видит владелец подписки (события с `visibility.principals` фильтруются), и никогда — домены `job`, `webhook`, `token`. Подпись — `x-kchs-signature: sha256=HMAC(секрет, "<x-kchs-timestamp>.<тело>")`; заголовки доставки — `x-kchs-event`, `x-kchs-delivery`, `x-kchs-timestamp`. Повторы: 30 с, 1, 5, 15, 30 мин, 1, 2, 6 ч и дальше по 6 ч, пока не истекут сутки от первой попытки; серия отказов (по умолчанию 20) отключает подписку событием `webhook.disabled`. Адрес проверяется до запроса — только `http`/`https` и не во внутреннюю сеть, перенаправления не выполняются (`WEBHOOKS_ALLOW_PRIVATE_ADDRESSES` снимает запрет на стенде). Входящий вебхук только публикует факт и ничего не меняет: знание секрета не даёт доступа к данным; неизвестная интеграция, выключенный вход и неверный секрет отвечают одинаково (404).

## 5. Интеграции

| Интеграция | Что даёт | Фаза |
|---|---|---|
| SMTP (исходящая почта) | уведомления, дайджесты, рассылки, отправка исходящих документов | 0 |
| Telegram-бот (grammY) | привязка аккаунта по коду, уведомления, кнопки действий (согласовать/принять/ознакомлен), быстрые ответы, простые формы, получение дашборд-снимков; при необходимости — команды `/inbox`, `/tasks` | 1 |
| IMAP (входящая почта) | регистрация входящих из почтового ящика канцелярии, ответы в обсуждения (опц.) | 5 (P5-E04, ADR-0113) |
| LDAP / Active Directory | синхронизация пользователей, подразделений и должностей по расписанию, предпросмотр «что изменится», журнал синхронизаций, вход по паролю каталога (bind), сопоставление групп → роли | 5 (P5-E04, ADR-0098) |
| OIDC SSO | вход через корпоративный IdP (Keycloak, ADFS, Entra ID) по Authorization Code + PKCE, JIT-создание пользователей, сопоставление claims и групп, выход из сессии провайдера | 5 (P5-E04, ADR-0098) |
| Внешние БД | источники датасетов (снимки/инкременты) | 2 |
| Внешние ГИС-сервисы (WMS/WMTS/WFS/ArcGIS REST) | базовые карты и слои-ссылки, импорт | 2–3 |
| S3/папки/SFTP | файлы-источники по расписанию (сводки от регионов) | 3 |
| Google Sheets / REST-источники | датасеты из внешних API | 3 |
| CalDAV / Google / Microsoft календарь | двусторонняя синхронизация событий | 5 |
| ONLYOFFICE / Collabora | совместное редактирование офисных файлов | 5 (P5-E04, ADR-0112) |
| SMS-шлюз | оповещения (предметный пакет) | по требованию |
| Гидрометео/сейсмо-фиды | источники датасетов с расписанием (предметный пакет) | по требованию |
| 1С / бухгалтерия | обмен справочниками, документами | Открыто |

Каждая интеграция — объект `integration` с конфигурацией, зашифрованными секретами, статусом, журналом синхронизаций, кнопкой «Проверить соединение», правами администратора интеграций.

Поставщики входа (каталог, единый вход) — исключение (ADR-0098): установка обслуживает одну организацию (ADR-0020), поэтому их по одному на вид, и они живут не в реестре объектов, а в таблице `auth_providers` со своим разделом администрирования. Всё остальное сохраняется: зашифрованный секрет, который наружу не возвращается, «Проверить соединение», журнал синхронизаций и способность `admin.system`.
Реализовано (ADR-0113): ящик канцелярии — интеграция `imap` с настоящей проверкой связи (вход и открытие папки); опрос объявлен в общем планировщике (раз в пять минут, свой период у каждого ящика), каждый проход пишет в журнал синхронизаций. Письма становятся черновиками входящих — 08-documents.md §5.
Реализовано (ADR-0112): сервер документов ONLYOFFICE — профиль `office` в compose, подпись запросов и колбэков общим секретом; правка возвращается обычной новой версией файла — 09-files.md §7.
Реализовано (ADR-0097): секреты — AES-256-GCM мастер-ключом; наружу отдаются только имена заданных секретов, в события и аудит попадают лишь имена изменённых полей. Права — способность `automation.manage` (политика типа), экран — «Интеграции» в администрировании. Встроенные службы установки (SMTP, Telegram-бот) настроены переменными окружения и остаются в них: в общем списке они показываются как `source: 'env'` — только для чтения, с тем же статусом и той же проверкой связи.

## 6. Импорт/экспорт конфигурации

Типы документов, маршруты, шаблоны, правила, справочники, показатели, дашборды и карты экспортируются в JSON-пакет и импортируются в другую инсталляцию (перенос между тестовым и рабочим контуром; распространение предметного пакета). Идентификаторы — стабильные ключи (`key`), не UUID.

Реализовано (ADR-0097): раздел пакета даёт модуль через реестр ядра (`kernel/config-package`) — перенос не читает чужие таблицы. Разделы первой волны: `integrations`, `webhooks`, `processDefinitions`. Импорт идёт через предпросмотр различий: `new`, `changed`, `same`, `conflict` (запись правили здесь после выгрузки пакета — применяется только с явным согласием), `unsupported`. Секреты в пакет не едут: вместо значений — список имён, новая интеграция приезжает выключенной. Раздел `documentTypes` объявлен, но поставщика не имеет: карточка типа ссылается на журнал регистрации по UUID, а стабильного ключа у журналов нет (вопрос N42). Экран — «Конфигурация» в администрировании; маршруты `GET /config/sections`, `POST /config/export`, `POST /config/import/preview`, `POST /config/import`.
