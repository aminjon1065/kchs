# Укрепление архитектуры

Статус: план согласован владельцем 05.10.2026. Этап 0 сделан в ветке `phase/7-arch-stage0`,
этапы 1–5 идут по порядку, каждый своей веткой от `main`.

Источник — архитектурный разбор 05.10.2026 по `main` 7884c5b5 (v0.7.0). Пять независимых
проверок: инварианты ядра, границы модулей, web, пакеты и движок, рантайм и данные. Ключевые
находки сверены по коду вручную.

## 1. Вердикт

Макроархитектура выбрана и реализована правильно, переписывать ничего не нужно:
- модульный монолит и движок на Python;
- один Postgres;
- ядро с реестром объектов;
- единый `authorize()`;
- outbox в той же транзакции;
- компилятор запросов `@kchs/query`.

Слабое место в другом: многие правила из `docs/` держатся на дисциплине, а не на проверках, и
в нескольких местах она уже дала сбой. План — укрепление по этапам. Каждый этап заканчивается
работающим продуктом (правило 8), а нарушения правил после него ловит CI.

## 2. Что сделано правильно

- **Реестр закреплён базой.**
  - У 40 таблиц `id` — внешний ключ на `objects`.
  - Вставка в `objects` — только в `ObjectService` (`kernel/objects/service.ts`).
  - `ObjectService.create` вызывается в 47 местах, всегда с `tx`.
- **Маршрут без политики доступа не регистрируется** (`shared/http/route.ts`), `onRequest` отказывает ещё раз (`auth-plugin.ts`). Всего 683 маршрута.
- **Outbox пишется в транзакции.**
  - Около 300 вызовов `publishEvent`, все с `tx`.
  - У каждого подписчика своя группа и отметка обработки (ADR-0027).
  - Повторная доставка дубля не даёт.
- **`@kchs/query`:**
  - параметры только `$n`;
  - идентификаторы экранируются;
  - белые списки функций;
  - политики строк — CTE с барьером;
  - сырой SQL — разбор libpg-query и повторный разбор после переписывания;
  - исполнение под `kchs_query`, `read only`, `statement_timeout`.
- **Движок без доменной логики и решений о правах.** Строки датасетов пишет TS-воркер через COPY (ADR-0046). `QUEUE_RUNTIME` проверяется при старте обеими сторонами.
- **Циклов нет** между файлами api, файлами web и пакетами. `deps:check` проходит (909 модулей).
- **Web:**
  - один HTTP-клиент;
  - TanStack Query;
  - zustand только для состояния интерфейса;
  - дизайн-система и i18n соблюдаются, литералов вне словарей нет.

Подробности к пунктам 5–9:

- **5. Шина событий.**
  - Находки:
    - `ops.event_consumptions` не чистится никогда;
    - нет метрик отставания групп и DLQ;
    - поток обрезается `MAXLEN ~100000` без учёта отстающих;
    - новая группа создаётся с позиции `'0'` и после обновления проигрывает всю историю;
    - повторная доставка срочного уведомления даёт дубль тревоги.
  - Что сделать:
    - очищать отметки по сроку, больше срока жизни потока;
    - метрики XINFO GROUPS (lag, pending), длина DLQ, оповещения на них;
    - экран DLQ с повтором;
    - стартовая позиция группы — полем подписчика: `$` для побочных эффектов, `0` для проекций;
    - ключ идемпотентности срочных уведомлений по `event.id`;
    - обрезка по отстающей группе.
- **6. Redis.**
  - Очереди BullMQ, потоки событий, кэш тайлов (24 ч без предела) и кэш запросов живут в одном экземпляре с `noeviction` и пределом 1 ГБ. Заполненный кэш останавливает запись очередей и outbox.
  - `maxRetriesPerRequest: null` у всех клиентов: при сбое Redis запросы зависают.
- **7. Движок и задания.**
  - Находки:
    - движок, разбирающий недоверенные файлы, получает роль `kchs_app`, полные ключи S3, пароль Redis и общий сервисный токен;
    - дочерние процессы (LibreOffice, tesseract) наследуют окружение;
    - `_post` проглатывает ошибку отправки статуса, и задание остаётся «в работе»;
    - отмена не останавливает выполняющееся задание, а `finish()` перезаписывает `cancelled`;
    - у обработчиков нет тайм-аутов.
  - Что сделать:
    - движку — `kchs_query` и узкую роль вместо `kchs_app`;
    - свой пользователь MinIO с доступом по префиксам;
    - ACL Redis на `bull:<очереди движка>:*`;
    - `env` у subprocess — только нужное;
    - песочница DuckDB (`enable_external_access=false`);
    - токен обратного вызова на задание (HMAC jobId+маршрут+срок) и режим `auth: 'service'` в `route()`;
    - статусы через `QueueEvents` BullMQ со сверкой зависших `running`;
    - отмена через AbortSignal, `finish()` с проверкой статуса, тайм-ауты обработчиков.
- **8. Вход и права.**
  - `disableMfa` — два DELETE, аудит и событие тремя шагами.
  - Группы и должности меняются без событий.
  - `bumpPrincipalsVersion` вызывается до коммита: исключённый из группы до 5 минут сохраняет доступ.
  - Аудит пишется вне транзакции в 67 из 122 мест.
- **9. Данные.**
  - Партиции `audit_log` созданы только миграцией (±3 месяца от установки), дальше всё уходит в `audit_log_default`.
  - `ALTER COLUMN TYPE` без `lock_timeout` блокирует датасет на 5 млн строк.
  - `ds.h_*` без срока хранения.
  - Хэш миграций пишется, но не сверяется.
  - Пакет ЧС обновляется только переустановкой (N90).

### 3.3. Структурные долги — этапы 2–3

Почему сбоит дисциплина: правила описаны, но инструменты их не видят.

- **10. Владение таблицами не проверяется (В).**
  - Все 165 таблиц лежат в `shared/db/schema` и подключаются одним реэкспортом (257 импортов). dependency-cruiser не видит, чья таблица.
  - Нарушения:
    - chat сам пишет `conversations`, `conversation_members`, `messages` ядра мимо `DiscussionService`;
    - ядро читает 11 таблиц identity — пользователи, оргструктура, группы, роли, замещения; по смыслу это таблицы ядра;
    - `reports*` лежат в `schema/data.ts`, `api_tokens` — в identity, `schedules` — в automation;
    - модули читают `users`, `acl_entries`, `integrations` мимо `directory()` и публичных API.
- **11. У модулей нет слоёв (В).**
  - 11 из 20 модулей — одна компонента сильной связности: ai, calendar, data, documents, files, gis, identity, integrations, mail, meetings, tasks. Кольцо calendar → meetings → documents → calendar; пары ai⇄data, data⇄gis, files⇄identity, gis⇄tasks.
  - `no-circular` ищет циклы между файлами, а не между модулями.
  - Пять разрезов дают слои:
    - территории — отдельным базовым модулем (ADR, заменяющий п. 1 ADR-0057);
    - files → `directory()` вместо identity;
    - integrations → порт `kernel/second-factor`;
    - календарь объявляет порт «поставщик онлайн-встречи», meetings в нём регистрируется;
    - ai — шлюз к модели без зависимостей, ассистент над data и files — отдельным модулем.
- **12. Ядро и оболочка знают модули по именам, центральные файлы правятся в каждой фиче (В).**
  - В ядре — `KNOWN_DOMAINS` (`kernel/events/consumer.ts`), словари аудита и категорий уведомлений.
  - `events/catalog.ts` — 285 событий, 72 коммита.
  - `ru.ts` — 8829 строк, 195 из 704 коммитов, целиком в основном чанке.
  - В web ни у одной из 29 фич нет `module.ts`: `app/modules.tsx` подключает фичи 68 раз, ещё rail, палитра, контекстная панель, shell и мобильная навигация знают их по именам.
- **13. Контракты формальные (В).**
  - Клиент `api<T>(path)` не связывает путь с типом, тело запроса `unknown` (ADR-0030 выполнен на бумаге). Около 100 схем zod сервера лежат вне `contracts`, клиент переписывает их вручную.
  - С движком общие только константы (`gen:engine`).
  - Система типов полей повторена в 5+ местах и уже разошлась: слова «да/нет» в `packages/fields/src/parse.ts` и `apps/engine/kchs_engine/data/values.py` различаются.
  - Снимков OpenAPI и событий в git нет, совместимость не проверяется.
- **14. В web нет границ (С).**
  - 237 импортов между фичами, 7 взаимных пар.
  - Сквозные компоненты лежат в чужих фичах: `access/share-dialog`, `files/upload`, `tasks/user-picker`, `notebooks/collab`.
  - `entities/` пуст.
  - dependency-cruiser для web не запускается.

  - mypy для движка в CI нет;
  - тестов компонентов web нет.

### 3.5. S2 — этап 5

- Hocuspocus не синхронизируется между репликами api.
- Транспорт `polling` работает без привязки к поду.
- Нужно около 500 соединений при `max_connections: 200`.
- Аналитика идёт на primary.
- RLS нет: `kchs_query` читает все `ds.t_*`, строки защищает только переписывание SQL.

## 4. Целевая архитектура

Общее устройство остаётся прежним. Меняется одно: правила проверяют инструменты.

1. **Слои модулей без колец** (проверка в CI по графу `depcruise --output-type json`):
   - L0 — ядро, files, territories, ai;
   - L1 — identity, integrations;
   - L2 — calendar, data, mail;
   - L3 — alerts, assistant, forms, tasks;
   - L4 — documents, gis;
   - L5 — automation, knowledge, meetings, reports;
   - L6 — chat.
2. **У каждой таблицы один владелец.**
   - Схема лежит рядом с владельцем: `kernel/<область>/schema.ts`, `modules/<m>/schema.ts`. `shared/db/schema/index.ts` остаётся только сборщиком для drizzle-kit, миграций, сида и тестов.
   - Модулям на чтение открыты `objects` и `object_ancestors`; запись в таблицы ядра — только сервисами ядра.
   - Принципалы и оргструктура — в `kernel/directory`, identity отвечает только за вход.
3. **Ядро без словаря модулей.**
   - Реестры по образцу реестра типов объектов: действия аудита, категории уведомлений, домены событий выводятся из каталога, переиндексация по событиям модуля объявляется в типе объекта.
   - Новый модуль — это папка и одна строка в точке сборки.
4. **Сквозные контракты.**
   - Таблица маршрутов `'POST /tasks': {body, response}` в contracts и типизированный `http` в web.
   - Каталог событий и словари i18n разложены по модулям, словарь модуля грузится с его чанком.
   - JSON Schema заданий и обратных вызовов и единый реестр типов полей — для движка.
   - Снимки OpenAPI и событий в git с проверкой ломающих изменений.
5. **Рантайм с обслуживанием.**
   - Ретрансляция realtime (ADR-0169).
   - У шины — очистка, метрики и повтор DLQ.
   - Redis разделён на долговечный и кэш.
   - У движка минимум прав.
   - У заданий надёжные статусы, отмена и тайм-ауты.
6. **Web.**
   - У каждой фичи публичный вход `features/<m>/index.ts` и регистрация `registerModule` (экраны, представления объектов, пункты навигации, команды, разделы контекстной панели).
   - Общие компоненты лежат в `entities/`, `useT` и `useLocale` — в `shared/`.
   - Границы проверяет dependency-cruiser с базой текущих нарушений.
