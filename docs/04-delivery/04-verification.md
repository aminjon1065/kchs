Статус: **Решено** для уровней тестирования, негативных тестов доступа и бюджетов; **Рекомендовано** для инструментов.

## 2. Обязательные негативные тесты доступа

Для **каждого** типа объекта, начиная с фазы, в которой он появляется: пользователь без прав (и пользователь с `view`, но без `edit`) проверяется на путях:

1. список/представление (объект отсутствует);
2. прямой `GET /objects/{id}` и маршрут модуля (404);
3. поиск и палитра (не выдаётся);
4. связи из доступного объекта (сводка «нет доступа», без названия);
5. realtime-комната (подписка отклонена; отзыв прав исключает);
6. экспорт/скачивание/тайлы/GeoJSON/печать;
7. API-токен со scope;
8. действие модуля (`approve`, `register`, `edit_features`) без нужного уровня/способности/шага;
9. для датасетов — строки и столбцы по политикам через: грид, экспорт, SQL, график, дашборд, тайлы, формы, ИИ-инструменты.

Тесты генерируются из реестра типов (общий тест-раннер перебирает типы и фабрики), чтобы новый тип нельзя было добавить без покрытия.

## 3. Сценарии приёмки по фазам

### Фаза 0
1. Администратор создаёт организацию (seed), входит с MFA, создаёт подразделение и пользователя, назначает роль.
2. Пользователь входит, видит «Мой день», создаёт пространство «Проект», приглашает коллегу с ролью `editor`.
3. Загружает PDF 50 МБ в папку, коллега видит превью, комментирует с упоминанием → первый получает уведомление в приложении и на почту (дайджест).
4. Владелец разрывает наследование папки, делится файлом с третьим пользователем по ссылке с паролем; третий открывает по ссылке; четвёртый не находит файл в поиске и получает 404 по URL.
5. Открывает 5 вкладок, делит экран, перезагружает страницу — состояние восстановлено.
6. Делегирует Входящие заместителю на неделю; заместитель видит элемент и действует «от имени»; аудит содержит обе записи.
7. Администратор смотрит аудит и здоровье; worker убит во время задания — задание повторяется, событие не потеряно.

### Фаза 1
1. Аналитик загружает XLSX с 3 листами и «грязными» датами/числами; мастер распознаёт; импорт 1 млн строк завершается; версия и профиль столбцов доступны.
2. Создаёт справочник «Типы», связывает поле; в гриде видны подписи; редактирует 3 ячейки, вставляет 100 строк из буфера, отменяет одну правку.
3. Исследование: фильтр по периоду, группировка по территории и месяцу, вычисляемая мера; график; сохраняет; добавляет на дашборд с фильтром «Территория» и детализацией до строк.
4. Создаёт показатель с порогом; на дашборде число с сравнением с прошлым периодом; TV-режим.
5. Руководитель с политикой строк «только своя область» открывает дашборд: числа отличаются; экспорт CSV содержит только его строки; SQL-лаборатория тоже; попытка `SELECT * FROM public.users` отклонена.
6. Руководитель создаёт поручение из строки датасета; исполнитель принимает в Telegram-уведомлении по ссылке, отчитывается; руководитель принимает; Входящие закрылись.
7. «Спросить данные»: вопрос на русском → график и показанный запрос; правка запроса вручную.

### Фаза 2
1. Импорт Shapefile (cp1251, EPSG:32642) → слой; стиль по категориям; подписи; легенда; карта сохранена; плитка на дашборде.
2. Таблица + карта рядом связаны: выделение строк подсвечивает объекты; фильтр по экстенту; brush на графике фильтрует карту.
3. Редактирование: добавлен полигон с привязкой, атрибуты по форме, история, откат; слой с модерацией — правка ждёт проверки.
4. Анализ: точки в полигонах районов → хороплет «объектов на 1 000 жителей» через мастер; результат как датасет и слой.
5. Паспорт территории: показатели, карта, документы (заглушки), поручения; переход в район.
6. Тетрадь: два аналитика одновременно редактируют, ИИ-ячейка; экспорт в отчёт; отчёт PDF с картой и графиками по расписанию в Telegram.
7. Тайлы: пользователь с политикой строк видит только свои объекты в тайлах (проверка pbf).

### Фаза 3
1. Сценарий B целиком (входящее письмо → резолюция → поручения → ответ → маршрут → подпись → регистрация → дело).
2. Маршрут с параллельным согласованием, замечаниями, новой версией и повторным согласованием только отклонивших; сроки в рабочих днях с праздником в календаре; просрочка → эскалация.
3. Согласование из Входящих и из Telegram; подпись с MFA; лист согласования/подписи в PDF.
4. Документ с грифом «конфиденциально» не виден пользователю без допуска даже с ACL; администратор входит в режим с обоснованием — аудит.
5. Календарь: встреча с повтором, приглашения, ответ, напоминание; проекции сроков поручений; ICS-подписка.
6. Worker перезапущен посреди маршрута — процесс продолжается.

### Фаза 4
1. Сценарий D (встреча → запись → расшифровка → протокол → поручения → документ → ознакомление).
2. Личный звонок из чата с экраном; канал подразделения; тред; поиск по сообщениям; задача из сообщения.
3. Нагрузка: 20 конференций × 30 участников (симулятор LiveKit) на S1-стенде без деградации API —
   `KCHS_LOAD_ROOMS=20 KCHS_LOAD_PUBLISHERS=5 KCHS_LOAD_SUBSCRIBERS=25 KCHS_LOAD_DURATION=3m bash
   infra/perf/run-livekit-load.sh` (по комнате на контейнер симулятора, в итоге — битрейт и потери
   пакетов) параллельно с `bash infra/perf/run-k6.sh` (p95 API в бюджете §4).
4. Гость по ссылке видит только комнату; запись доступна участникам, недоступна остальным.

Как проверено (фаза 4): сценарий D и критерий 2 — `e2e/acceptance-p4.spec.ts` (комната, запись
Egress, расшифровка, протокол, поручения, документ, ознакомление; канал подразделения, тред, поиск,
поручение из сообщения; звонок из беседы с демонстрацией экрана), критерий 4 —
`e2e/meeting-room.spec.ts` (гость) и `apps/api/test/meetings-recording.test.ts` (посторонний
получает 404). Сценариям с медиа нужен профиль `media` и ключи медиасервера, включает их
`KCHS_E2E_MEETINGS=1`; браузеру на хосте разработчика — `LIVEKIT_NODE_IP=<адрес хоста в сети>`,
Egress — `S3_EGRESS_ENDPOINT=http://minio:9000`.

### Фаза 5
1. Сценарии A, C, G.
2. Правило автоматизации с тестовым прогоном; вебхук с подписью и повтором; API-токен со scope.
   Сделано (ADR-0097): `apps/web/e2e/integrations.spec.ts` — токен из профиля открывает API и
   перестаёт работать после отзыва, интеграция с входящим вебхуком, доставка с проверкой подписи
   и журнал, выгрузка и предпросмотр пакета конфигурации. Негативные проверки — в
   `apps/api/test/integrations-tokens.test.ts` (область доступа, отозванный и просроченный токен,
   запрет личных и административных маршрутов, замещения и выпуска токена токеном),
   `integrations-webhooks.test.ts` (чужое событие не уходит, адрес внутренней сети запрещён,
   неверный секрет входящего вебхука неотличим от несуществующей интеграции) и
   `integrations-config.test.ts` (секреты вне ответов, событий, аудита и пакета).
3. Форма сбора по подразделениям с дедлайном; матрица сдачи; просрочка → эскалация.
4. LDAP-синхронизация 500 пользователей и структуры; вход через OIDC; passkey.
5. Восстановление из бэкапа по runbook ≤ 1 ч; Helm-развёртывание; ZAP без high; k6-профили в бюджете.
   Готово к проверке (P5-E07): Helm-чарт `infra/helm/kchs` (ADR-0118) — `helm lint` и
   `helm template` на трёх наборах значений с проверкой схем Kubernetes в CI (задание
   «Helm-чарт (S2)»); нагрузочные профили S2 — ниже, §4. Развёртывание в настоящем кластере и
   прогон нагрузки делаются на стенде S2: у исполнителя кластера нет.

## 4. Бюджеты производительности

| Метрика | Бюджет | Как измеряем |
|---|---|---|
| Первая загрузка web (кэш холодный, корпоративная сеть) | ≤ 3 с до интерактива; бандл оболочки ≤ 400 КБ gz, модули лениво | Lighthouse CI |
| API базовые операции (объект, список 50, Входящие) | p95 ≤ 200 мс | k6: `infra/perf/k6/api-basic.js` (`bash infra/perf/run-k6.sh`), ночью в CI; гистограмма `http_server_request_duration` (ADR-0045) |
| Запрос к датасету ≤ 10 млн строк (агрегация с фильтром по индексу) | p95 ≤ 2 с | k6 на демо-данных |
| Грид: прокрутка 100 столбцов × 100 тыс. строк | 60 fps, без задержек ввода > 50 мс | Playwright trace |
| Тайлы 500 тыс. точек | p95 ≤ 50 мс кэш / ≤ 300 мс без | k6 |
| Realtime доставка | ≤ 500 мс | интеграционный тест |
| Импорт 5 млн строк CSV | ≤ 5 мин на S1 | e2e ночной |
| Рендер отчёта 20 страниц с 10 графиками и 2 картами | ≤ 60 с | e2e |
| Поиск | p95 ≤ 100 мс | k6, тот же профиль |

### Нагрузка масштаба S2

Бюджеты те же — меняется масштаб (`15-admin-operations.md` §8: к S2 переходят при более чем
300 одновременных пользователях и тайлах свыше 200 RPS). Профили (ADR-0119) рассчитаны на
кластер и работают против произвольного адреса:
`KCHS_PERF_API=https://kchs.example.org/api/v1 KCHS_PERF_PROFILE=<профиль> bash infra/perf/run-k6.sh`.

| Профиль | Нагрузка по умолчанию | Бюджеты |
|---|---|---|
| `s2-workday` | 1000 одновременных сотрудников (≈ 17 рабочих циклов/с) + беседы + вход раз в секунду | «Мой день», Входящие, списки, карточка, сводка задач, беседы — p95 ≤ 200 мс; поиск объектов и сообщений — ≤ 100 мс; вход — ≤ 500 мс |
| `s2-tiles` | 200 тайлов/с (40 холодных, 160 из кэша) | ≤ 300 мс без кэша, ≤ 50 мс из кэша |
| `s2-analytics` | 10 запросов/с к «Происшествиям» (5 млн строк), включая свод по всему периоду — он уходит в колоночный tier (ADR-0109) | ≤ 2 с |
| `s2-mixed` | всё сразу: рабочий день, беседы, тайлы, тяжёлые запросы | бюджеты частей; ошибки HTTP < 1 % |

Нагрузка задаётся переменными `KCHS_PERF_CONCURRENT`, `KCHS_PERF_TILE_RATE`,
`KCHS_PERF_QUERY_RATE`, `KCHS_PERF_DURATION`; каждый прогон — разгон, плато, спад. Профили
стенда S1 (`api-basic`, `data-queries`, `gis-tiles`) остаются как есть: на одном сервере
меряют ими.

Как проверено (P5-E07): профили разобраны k6 (`k6 inspect` в Docker: сценарии, пороги,
импорты). Сам прогон на машине разработчика не делался — она не тянет ни S2-нагрузку, ни
кластер под ней; замер делается на стенде S2 при первой установке кластера.

## 5. Проверка целостности данных

- Миграции: «с нуля» и «с предыдущего релиза» в CI; проверка обратимости.
- Инварианты (`04-domain-model.md`) — SQL-проверки в ночном задании обслуживания (сироты, циклы, счётчики), отчёт в администрирование.
- Outbox: «нет неопубликованных старше 1 мин» — метрика `kchs_outbox_oldest_age` и алерт `KchsOutboxStuck` (`infra/observability/prometheus/alerts.yml`).

## 6. Чек-лист безопасности (перед закрытием фазы)

CSP без `unsafe-*`; заголовки; cookie-флаги; CSRF; rate limit; аудит обязательных событий; секреты не в логах/репозитории; роли БД проверены; SQL-песочница пройдена «атакующим» набором; загрузки — типы/размеры/санитизация; зависимости без критических уязвимостей; образы просканированы; ZAP baseline; негативные тесты доступа для всех типов фазы; ИИ-политика передачи данных соблюдена. С фазы 5 (ADR-0098) — поставщики входа: секреты каталога и IdP не возвращаются в API и не попадают в журналы; состояние входа через IdP одноразовое (чужой и повторный `state`, подменённый `nonce`, просроченный код отклоняются); отключённый в каталоге и исчезнувший из него сотрудник теряет доступ; отозванный ключ входа не пускает, повторный ответ устройства не принимается.

## 7. Демонстрационные данные

`seeds/`: организация из 5 управлений/15 отделов/60 сотрудников с ролями; территории (страна/области/районы) с геометриями (источник и лицензия — фиксируются в `seeds/README.md`); синтетические датасеты: «Происшествия» (5 млн строк, точки, время, территория, тип, ущерб), «Объекты защиты» (50 тыс. точек), «Зоны риска» (полигоны), «Уровни воды» (временной ряд), справочники; документы (200 с маршрутами в разных статусах), поручения, проекты, встречи с записями-заглушками, страницы знаний. Генератор — в engine (детерминированный seed), датасеты загружает `pnpm db:seed --data=demo` при запущенном стеке (ADR-0063; `--data=small` — 50 тыс. «Происшествий» для быстрых стендов).
