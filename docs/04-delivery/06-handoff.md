# Передача работы исполнителю

Адресат: Claude Code Opus 5 max. Этот документ — «как начать и как работать», остальное — в комплекте документов.

## 1. Что ты получаешь

- Полное продуктовое и инженерное описание kchs: видение, сценарии, функциональный состав, ядро платформы, модель доступа, модель данных, модули, стек, интерфейс, контракты, дорожная карта, бэклог, проверки, риски.
- Пустой каталог проекта (кроме `docs/`, `README.md`, `CLAUDE.md`) — ты создаёшь код с нуля.
- Свободу в локальных деталях и обязанность соблюдать решения со статусом **Решено**.

## 2. Первые шаги (фаза 0, порядок)

1. Прочитай `docs/00-start-here.md`, затем документы 1–5 из порядка чтения. Сверь понимание с `05-appendix/glossary.md` — используй канонические идентификаторы.
2. Создай `docs/progress.md` (шаблон ниже) и первый ADR `docs/adr/0025-...` только если что-то меняешь; иначе — ничего.
3. Выполни P0-E01 (монорепо, compose, каркасы, CI). Зафиксируй версии инструментов в `docs/progress.md`.
4. Выполни P0-E02 (схема ядра) — таблицы точно по `05-data-model.md`; имена не изобретай.
5. Далее по порядку `02-roadmap.md` → «Порядок внутри фазы». Дизайн-систему и оболочку начинай параллельно с бэкендом ядра, как только есть каркас web.
6. После каждой истории — DoD, обновление `docs/progress.md`, коммит с Conventional Commits.
7. По завершении фазы — прогон сценариев приёмки, чек-лист безопасности, обновление `CLAUDE.md` (реальные команды), тег `v0.<фаза>.0`.

## 3. Рабочие соглашения

- **Работай вертикальными срезами**: сначала тонкий сквозной путь (например, «загрузить файл → увидеть в списке → открыть во вкладке → прокомментировать»), затем углубление. Продукт должен запускаться всегда.
- **Не изобретай параллельные механизмы.** Если нужен комментарий — это обсуждение ядра; если нужен список с фильтрами — `CollectionView`; если нужна форма — `SchemaForm`; если нужно право — `authorize`; если нужно «уведомить» — событие.
- **Сначала контракт, потом код.** Новые маршруты — через zod-схему в `packages/contracts`; новые события — со схемой; новые типы объектов — через реестр.
- **Не блокируйся на неопределённостях.** Принимай разумный вариант из `05-risks-and-open-questions.md`, фиксируй ADR, продолжай. Вопросы владельцу складывай в раздел «Новые вопросы».
- **Тесты — часть истории**, особенно негативные тесты доступа и golden-тесты компилятора.
- **Дизайн — часть истории.** Экран без соответствия токенам, темам, клавиатуре и состояниям (пустое/загрузка/ошибка) не готов.
- **Производительность измеряй рано**: DataGrid, компилятор, тайлы — с бенчмарками при первом появлении.
- **Документируй фактическое**: если структура/имена отклонились — правь `docs/`, чтобы документация оставалась правдой.

## 4. Как оформлять ADR

`docs/adr/NNNN-kebab-title.md`:

```
# NNNN. Название
Статус: Принято | Заменено ADR-XXXX
Контекст: почему возник вопрос
Решение: что решили
Альтернативы: что рассматривали и почему отклонили
Последствия: что меняется, риски
```

Нумерация продолжается с 0025 (0001–0024 заняты проектными решениями).

## 6. Критерии, по которым владелец продукта примет работу

1. Каждая фаза демонстрируется по сценариям `04-verification.md` на чистой установке `docker compose up` + `kchs init` + `db:seed`.
2. Интерфейс соответствует `03-ui/*`: оболочка с вкладками и панелями, дизайн-система, обе темы, клавиатура, состояния.
3. Модель доступа работает единообразно и объяснима; негативные тесты есть для всех типов.
4. Данные, карты, документы, поручения и встречи связаны так, как описано в сценариях A–G.
5. Документация в `docs/` отражает реальность; `progress.md` актуален.

## 7. Что не делать

- Не заменять стек из `18-tech-stack.md` (статус Решено) без ADR с веской причиной.
- Не создавать отдельные таблицы комментариев, уведомлений, вложений, прав «для своего модуля».
- Не строить экраны из сторонних UI-китов (MUI/Ant) «чтобы быстрее».
- Не выполнять пользовательский SQL мимо компилятора/парсера.
- Не откладывать i18n, тесты, темы «на потом».
- Не пропускать фазу 0.
