# Резервные копии и восстановление

## Что резервируется

| Данные | Как | Чем проверяется |
|---|---|---|
| PostgreSQL | копия установки: `pg_dump` потоком в бакет копий, задание в 02:50 и кнопка в консоли; хранятся семь последних удачных | ручное восстановление по runbook, отметка в консоли |
| Файлы (MinIO) | версионирование бакетов и репликация средствами хранилища | выборочная проверка |
| Поиск (Meilisearch) | не резервируется — перестраивается из базы | переиндексация |
| Redis | только кэш и очереди, потери допустимы | — |
| Конфигурация | `.env` в менеджере секретов, compose в git | — |

Цель по восстановлению для установки на одном сервере: **RPO — сутки** (интервал
копии), RTO — по runbook.

## Раздел «Резервные копии»

**«Администрирование» → «Резервные копии»** (способность «Администрирование
системы»).

Наверху: «Копия базы делается ночью и по требованию: дамп уходит в хранилище,
хранятся последние семь. Файлы и поиск резервируются отдельно — см. runbook
восстановления».

- **«Сделать копию»** — запускает то же задание немедленно (не чаще трёх раз за
  десять минут).
- Строка над списком: «Последняя копия: {когда}, {размер}» либо предупреждение
  «Удачных копий пока нет».
- Список прогонов: дата, размер, бейдж **«Идёт»** / **«Готова»** /
  **«Ошибка»**; при ошибке — её текст.
- У завершённой копии — кнопка **«Отметить проверенной»**; после неё в строке
  появляется «проверена восстановлением {когда}». Отметка попадает в аудит.

Ниже — карточка **«Обслуживание»**: «Регулярные работы идут по расписанию — см.
раздел „Расписания“. Здесь то, что запускается по требованию». Единственная
кнопка — **«Переиндексировать поиск»** («Переиндексация поставлена заданием»).

## Пошагово: ежемесячная проверка восстановления

1. Выгрузите архив последней копии из бакета `kchs-backups` любым клиентом S3
   (например, `mc cp kchs/kchs-backups/pg/<файл> .`).
2. На тестовом контуре остановите приложение, оставив базу:
   ```bash
   docker compose --profile app stop api worker engine web
   ```
3. Восстановите дамп:
   ```bash
   docker compose exec -T postgres pg_restore -U postgres -d kchs --clean --if-exists < kchs.dump
   ```
4. Примените недостающие миграции, если копия старше релиза: `pnpm db:migrate`
   (или перезапуск `api` — он мигрирует сам).
5. Поднимите приложение и проверьте: `curl -fsS http://localhost:3000/health`,
   раздел **«Здоровье системы»** (все компоненты «Работает», «Неопубликованных
   событий: 0»), вход и открытие объекта.
6. Перестройте поисковый индекс — кнопка **«Переиндексировать поиск»**.
7. Вернитесь в консоль боевого контура и нажмите **«Отметить проверенной»** у
   проверенной копии.

Полный порядок восстановления после сбоя — `infra/runbooks/restore.md`;
реагирование на инцидент — `infra/runbooks/incident.md`.

## Чего в консоли нет

- Скачать копию из интерфейса нельзя — только из бакета.
- Восстановиться из копии кнопкой нельзя: восстановление всегда ручное, по
  runbook.
- Глубина хранения (семь копий), время ночного прогона (02:50) и бакет не
  настраиваются; расписание можно только выключить на экране «Расписания»
  (задание **«Резервная копия базы»**).
- Файлы и поисковый индекс этой копией не резервируются: у файлов своё
  версионирование, индекс перестраивается из базы.

## Частые вопросы

**Копия падает с ошибкой «pg_dump не найден».** Так отвечает установка, где нет
клиента PostgreSQL нужной версии (например, машина разработчика). В образе `api`
клиент есть; на боевом контуре проверьте, что вы работаете именно в нём.

**Прогон завис в состоянии «Идёт».** Прерванный прогон (процесс остановили
посреди дампа) помечается ошибкой при следующем запуске.

**Почему хранится только семь копий?** Это фиксированная глубина: лишние
удаляются вместе с архивами. Для более долгого хранения выгружайте архивы из
бакета во внешнее хранилище.

**Что делать, если потеряли и файлы?** Файлы живут отдельно, в объектном
хранилище: восстанавливайте бакеты `kchs-files`, `kchs-media`, `kchs-previews`
из реплики или снимка, затем поднимайте приложение.
