# Резервные копии и восстановление

## Что резервируется

| Данные | Как | Где лежит копия | Чем проверяется |
|---|---|---|---|
| Окружение (`.env`: пароли служб, **мастер-ключ**) | ночная копия `backup.sh` | репозиторий restic на сервере → компьютер Комитета | `backup-pull.sh verify` и `check` |
| PostgreSQL | ночная копия `backup.sh`: дамп с владельцами и правами | то же | то же; ежемесячная проверка восстановлением |
| Файлы сотрудников, записи встреч и фото, подложки карт (`kchs-files`, `kchs-media`, `kchs-tiles`) | ночная копия `backup.sh` | то же | то же |
| Файлы: прежние версии | версии в бакете `kchs-files`: перезапись или удаление оставляет прежнюю версию на 30 дней | на сервере | — |
| PostgreSQL | копия самой платформы: `pg_dump` в бакет `kchs-backups`, задание в 02:50 и кнопка в консоли, семь последних | на сервере, в хранилище | раздел «Резервные копии» |
| PostgreSQL и файлы | резервный узел на удалённой площадке, если он заведён (`failover.md`) | узел | `dr.sh restore-check` раз в месяц |
| Поиск (Meilisearch) | не копируется — перестраивается из базы | — | переиндексация |
| Redis, превью, выгрузки, колоночные копии | не копируются — очереди и кэш, превью строит движок, выгрузки временные, колоночные копии строятся из базы | — | — |

Главная копия установки без резервного узла — **ночная копия `backup.sh`**: сервер
каждую ночь складывает зашифрованную копию в свой каталог, а компьютер в Комитете
забирает её к себе. Копия на самом сервере не спасает при потере сервера — поэтому
забор обязателен.

Цель по восстановлению (концепт-нота): **RPO — не больше часа, RTO — не больше
четырёх часов**. Её даёт резервный узел (`infra/runbooks/failover.md`). Без узла —
**RPO сутки** (интервал ночной копии), RTO — по разделу «Восстановление» ниже.

## Что хранить офлайн — обязательно

Два секрета хранятся **не на сервере и не в Комитете рядом с копиями**, а у
ответственного: в сейфе, на бумаге или на отдельной флешке.

1. **Пароль репозитория копий** (`/etc/kchs/backup.pass` на сервере). Без него копии
   не расшифровать. Он показывается один раз при `backup.sh init`.
2. **Копия `.env` установки.** В нём мастер-ключ: без него не расшифровать вторые
   факторы сотрудников, секреты интеграций и ключ удостоверяющего центра — пришлось бы
   заводить новый центр и перевыпускать все сертификаты. Копия `.env` есть и внутри
   репозитория, но достать её можно только паролем из пункта 1.

Пароль нарочно не хранится в `.env`: иначе копия `.env` внутри репозитория содержала
бы ключ от самого репозитория.

## Настройка на сервере (один раз)

Команды выполняются на сервере из каталога установки, от имени `root`:

```bash
sudo bash infra/scripts/backup.sh init           # репозиторий и пароль — перепишите пароль!
sudo bash infra/scripts/backup.sh run            # первая копия — убедиться, что всё работает
sudo bash infra/scripts/backup.sh install-timer  # каждую ночь в 03:30
sudo bash infra/scripts/backup.sh status         # копии, объём, последний успех и сбой
```

- Каталог копий — `/var/lib/kchs-backup` (`KCHS_BACKUP_DIR`), вне томов Docker:
  `docker compose down -v` его не трогает. Места нужно примерно столько же, сколько
  занимают база и файлы (копии сжимаются и не повторяют неизменённое).
- Хранится: 14 ежедневных, 8 еженедельных, 6 ежемесячных копий
  (`KCHS_BACKUP_KEEP_DAILY`, `_WEEKLY`, `_MONTHLY`).
- Каждую ночь проверяется структура репозитория, по воскресеньям — ещё пятая часть
  данных: за месяц перечитывается всё.
- Итог прогона — файлы `last-success` и `last-failure` в каталоге копий: по ним
  сторож присылает оповещение «копия не сделана» или «копия старше суток».

## Забор копий в Комитет

Компьютер в Комитете (Linux или Windows с WSL) раз в сутки забирает репозиторий по
SSH. У сервера нет никакого доступа к этому компьютеру; у компьютера Комитета — только
чтение каталога копий на сервере: ни записать, ни удалить, ни выполнить команду он не
может.

**1. На компьютере Комитета — ключ:**

```bash
ssh-keygen -t ed25519 -N '' -f ~/.ssh/kchs-backup -C kchs-backup
```

Файл `~/.ssh/kchs-backup.pub` передайте администратору сервера.

**2. На сервере — доступ на чтение для этого ключа:**

```bash
sudo apt install -y rsync python3                 # rrsync из пакета rsync написан на Python
sudo bash infra/scripts/backup.sh allow-pull kchs-backup.pub
```

Команда заводит пользователя `kchs-backup`, которому разрешён только `rsync` на чтение
каталога репозитория.

**3. На компьютере Комитета — настройка и первый забор.** Скрипт
`infra/scripts/backup-pull.sh` скопируйте на компьютер (например, в `~/kchs/`) и
создайте файл `~/.config/kchs-backup-pull.env`:

```bash
KCHS_PULL_HOST=kchs.example.tj      # адрес сервера
KCHS_PULL_KEY=$HOME/.ssh/kchs-backup
KCHS_PULL_DEST=$HOME/kchs-backup    # сюда ложатся копии
KCHS_PULL_KEEP=14                   # сколько прежних поколений хранить
```

```bash
bash ~/kchs/backup-pull.sh pull     # забрать
bash ~/kchs/backup-pull.sh verify   # сверить целостность (пароль не нужен)
bash ~/kchs/backup-pull.sh status   # когда забирали и сколько занято
```

Каждый забор сохраняет прежнюю копию поколением (`generations/ДАТА`, жёсткие ссылки —
место почти не занимают): если на сервере копии испортят или удалят, последняя хорошая
останется у Комитета.

**4. Расписание забора** — днём, после ночной копии:

- Linux: `crontab -e` и строка
  `30 9 * * * bash $HOME/kchs/backup-pull.sh pull && bash $HOME/kchs/backup-pull.sh verify`;
- Windows: в WSL (Ubuntu) — то же через cron; в «Планировщике заданий» Windows —
  ежедневная задача `wsl -e bash -lc "bash ~/kchs/backup-pull.sh pull && bash ~/kchs/backup-pull.sh verify"`.
  Компьютер должен быть включён в это время. Каталог копий в WSL — на диске
  компьютера; его можно дополнительно копировать на внешний диск.

**Проверка целостности.** `verify` сверяет каждый файл копии с его контрольной суммой
(имя файла репозитория — это SHA-256 его содержимого) и не требует пароля: так ловятся
обрыв при передаче и порча диска. Полная проверка с расшифровкой — раз в месяц, с
паролем репозитория:

```bash
KCHS_PULL_PASSWORD_FILE=/путь/к/файлу-с-паролем bash ~/kchs/backup-pull.sh check
```

Файл с паролем после проверки удалите: пароль хранится офлайн.

## Восстановление

Когда: сервер потерян или его данные испорчены, а резервного узла нет. Нужны:
новый сервер с установленной копией kchs (тот же выпуск или новее), репозиторий копий
от Комитета и пароль репозитория.

1. Скопируйте забранный репозиторий (`~/kchs-backup/current`) на новый сервер, например
   в `/var/lib/kchs-backup/repo`; пароль положите в `/etc/kchs/backup.pass` (права 600).
2. Восстановите — команда сначала объясняет, что сделает, и ждёт `--yes`:

   ```bash
   sudo bash infra/scripts/backup.sh restore --repo /var/lib/kchs-backup/repo
   sudo bash infra/scripts/backup.sh restore --repo /var/lib/kchs-backup/repo --yes
   ```

   По шагам она: кладёт `.env` из копии (прежний сохраняется рядом), **стирает тома
   данных проекта**, поднимает базу и хранилище, восстанавливает базу вместе с правами
   ролей и файлы. Нужна копия на определённый день — `--snapshot ID` (номер — из
   `backup.sh status`).
3. Поднимите приложение обычной командой установки (`docker compose --profile app up -d`
   или скрипт установки).
4. **«Администрирование → Резервные копии → Переиндексировать поиск».**
5. Войдите, откройте несколько документов и файлов, проверьте «Здоровье системы».

Восстановление проверено прогоном на отдельной установке: после полного сноса томов и
`.env` вернулись база с прежними правами всех ролей, файлы (скачивание, совпадение
содержимого), пользователи и правила хранилища; вход работает.

## Раздел «Резервные копии»

**«Администрирование» → «Резервные копии»** (способность «Администрирование
системы»). Он показывает **копии самой платформы** — дамп базы в хранилище на этом же
сервере; ночная копия `backup.sh` в консоли не видна, её состояние — `backup.sh
status` и оповещения сторожа.

Наверху: «Копия базы делается ночью и по требованию: дамп уходит в хранилище,
хранятся последние семь. Файлы и поиск резервируются отдельно — см. runbook
восстановления».

- **«Сделать копию»** — запускает то же задание немедленно (не чаще трёх раз за
  десять минут).
- Строка над списком: «Последняя копия: {когда}, {размер}» либо предупреждение
  «Удачных копий пока нет».
- Список прогонов: дата, размер, бейдж **«Идёт»** / **«Готова»** /
  **«Ошибка»**; при ошибке — её текст.
- У завершённой копии — кнопка **«Отметить проверенной»**; после неё в строке
  появляется «проверена восстановлением {когда}». Отметка попадает в аудит.

Ниже — карточка **«Проверки восстановления»**: их итоги сообщает резервный узел
(`dr.sh restore-check` раз в месяц) токеном своей служебной записи. В строке —
когда, что проверялось («архив WAL резервного узла» или «копия pg_dump»), узел, «данные
копии — по {когда}» и подробности; бейдж **«Восстановление проверено»** или
**«Проверка не прошла»**. Пусто — «Проверок восстановления пока не было»: узел не
заведён или ещё не проверялся. Как завести служебную запись и токен — `failover.md`,
«Подготовка», шаг 5.

Ещё ниже — карточка **«Обслуживание»**: «Регулярные работы идут по расписанию — см.
раздел „Расписания“. Здесь то, что запускается по требованию». Единственная
кнопка — **«Переиндексировать поиск»** («Переиндексация поставлена заданием»).

## Пошагово: ежемесячная проверка восстановления

Раз в месяц проверьте, что копия действительно разворачивается, — на **отдельной**
установке (тестовый сервер или ноутбук), никогда поверх рабочей:

1. Заберите свежую копию с компьютера Комитета и пароль.
2. На тестовой установке выполните «Восстановление» выше (шаги 1–5).
3. Сверьте: количество сотрудников, документов и файлов как на рабочей установке,
   открывается последний документ за вчера.
4. В консоли рабочей установки отметьте проверку (для копии платформы — «Отметить
   проверенной»), запишите результат в журнал проверок.
5. Сотрите тестовую установку: в ней боевые данные целиком.

Порядок для копии самой платформы (дамп из бакета) — `infra/runbooks/restore.md`;
реагирование на инцидент — `infra/runbooks/incident.md`.

## Чего в консоли нет

- Скачать копию из интерфейса нельзя — только из бакета или из репозитория копий.
- Восстановиться кнопкой нельзя: восстановление всегда ручное, по этому руководству.
- Глубина хранения копий платформы (семь), время её прогона (02:50) и бакет не
  настраиваются; расписание можно только выключить на экране «Расписания»
  (задание **«Резервная копия базы»**). Хранение ночной копии `backup.sh` —
  переменными `KCHS_BACKUP_KEEP_*`.

## Частые вопросы

**Пришло оповещение «копия не сделана».** На сервере: `sudo bash infra/scripts/backup.sh
status` — в строке «Последний сбой» причина. Частые: остановлена база, нет места на
диске, нет файла пароля. Исправьте и запустите `backup.sh run` вручную.

**Потеряли пароль репозитория.** Копии этого репозитория расшифровать нельзя. Если
сервер жив: `backup.sh init` в новом каталоге (`KCHS_BACKUP_DIR`), новый пароль —
офлайн, и с завтрашнего дня копии снова есть. Старые копии в Комитете бесполезны —
сотрите их.

**Сломался основной сервер — восстанавливать из копии?** Если есть резервный узел —
нет: переключитесь на него (`failover.md`), это минуты и потеря секунд данных.
Восстановление из ночной копии — до суток данных.

**Удалили файл по ошибке.** Если прошло меньше 30 дней — прежняя версия есть в
хранилище (версии `kchs-files`); администратор сервера возвращает её командой `mc`
(`mc ls --versions`, `mc cp --version-id`). Старше — из ночной копии.

**Копия падает с ошибкой «pg_dump не найден»** (раздел консоли). Так отвечает
установка, где нет клиента PostgreSQL нужной версии (например, машина разработчика). В
образе `api` клиент есть.

**«Проверка не прошла»** (резервный узел). Подробности — в строке проверки и в журнале
узла (`/var/log/kchs-dr.log`). Частые причины: архив WAL оборвался (узел был отключён
дольше, чем основной хранит WAL для него, — засейте узел заново, `init-standby --yes`),
данные копии отстают больше часа (узел отстаёт — смотрите оповещения группы
«Резервный узел»).
