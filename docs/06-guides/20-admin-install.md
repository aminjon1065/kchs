# Установка и первый запуск

## Что понадобится

Один сервер Linux с Docker 27+ и Compose v2. Ориентир для установки на 300–1500
учётных записей: 16 vCPU, 64 ГБ RAM, NVMe 1 ТБ под базу плюс место под файлы.
Node на сервере не нужен — всё работает в контейнерах.

Состав установки (профиль `app`): `web` (Caddy со сборкой интерфейса), `api`,
`worker`, `engine` (движок: превью, геоформаты, распознавание), `postgres` с
PostGIS и pgvector, `redis`, `minio`, `meilisearch`, `mailpit`. Отдельными
профилями поднимаются `livekit` (встречи), `onlyoffice` (офисный редактор),
наблюдаемость (`alloy`, `tempo`, `loki`, `prometheus`, `grafana`).

## Установка

```bash
git clone <репозиторий> kchs && cd kchs
bash infra/scripts/generate-secrets.sh --mode app
docker compose --profile app up -d --build --wait
docker compose exec api kchs init --admin-email admin@example.org
```

1. **`generate-secrets.sh --mode app`** создаёт `.env` с правами 600 и
   случайными секретами: пароли шести ролей базы, Redis, MinIO, Meilisearch,
   мастер-ключ шифрования, служебный токен движка, пароль Grafana, ключи LiveKit,
   секрет ONLYOFFICE и ключи push. Повторный запуск без `--force` ничего не
   перезаписывает. Порты задаются переменными окружения самого скрипта
   (`WEB_PORT`, `POSTGRES_PORT`, `S3_PORT` и т. д.).
2. **`docker compose --profile app up`** собирает и поднимает всё; `--wait`
   дожидается готовности.
3. **`kchs init`** применяет миграции, заводит системные роли и поисковый индекс,
   заносит праздники Республики Таджикистан с постоянной датой на текущий и
   следующий год, регистрирует базовые карты, создаёт стартовый набор
   документооборота (журналы, типы, маршруты, шаблоны) и первого администратора.
   **Временный пароль печатается один раз** — сохраните его. Команда
   идемпотентна: повторный запуск администратора не пересоздаёт.

Логин первого администратора — `admin` (или `--admin-login`, или
`KCHS_ADMIN_LOGIN` в `.env`), почта — `--admin-email` либо `KCHS_ADMIN_EMAIL`.

Откройте `http://<сервер>:8080` (порт `WEB_PORT`), войдите под администратором —
система сразу попросит задать постоянный пароль.

Демонстрационные данные (для пилота и обучения): `docker compose exec api kchs seed`.

## Домен и HTTPS

В `.env`:

```
KCHS_DOMAIN=kchs.example.org
WEB_PORT=80
WEB_HTTPS_PORT=443
KCHS_BASE_URL=https://kchs.example.org
KCHS_API_URL=https://kchs.example.org/api
CADDY_EMAIL=admin@example.org
```

Caddy получит сертификат сам. Важно: браузер загружает и получает файлы
**напрямую из хранилища** по подписанным ссылкам, поэтому `S3_PUBLIC_ENDPOINT` и
`KCHS_STORAGE_ORIGIN` должны быть адресом, видимым браузеру; если сайт работает
по HTTPS, хранилище тоже должно быть по HTTPS.

Порты данных (Postgres, Redis, Meilisearch, консоль MinIO, mailpit) публикуются
только на самом сервере — `KCHS_BIND=127.0.0.1`.

## Проверка установки

```bash
bash infra/scripts/verify-stack.sh     # вся цепочка на чистых томах в отдельном проекте compose
bash infra/scripts/smoke-api.sh        # дымовой прогон HTTP API
bash infra/perf/run-k6.sh              # бюджеты p95 (нужны демо-данные)
```

`verify-stack.sh` разворачивает установку с нуля в отдельном проекте compose,
прогоняет `kchs init`, демо-данные, дымовой прогон через веб и браузерную
проверку — стенд, на котором вы работаете, при этом не затрагивается.

## Команда `kchs`

В установке — `docker compose exec api kchs <команда>`, при разработке —
`pnpm kchs <команда>`.

| Команда | Что делает | Ключи |
|---|---|---|
| `kchs init` | миграции, системные роли, поисковый индекс, производственный календарь, реестр базовых карт, стартовый набор документооборота, первый администратор с временным паролем; идемпотентна | `--admin-login`, `--admin-email` |
| `kchs migrate` | только миграции базы | — |
| `kchs seed` | демонстрационные данные: администратор, 60 сотрудников, оргструктура, пространства, документы, поручения, страницы базы знаний; предметный пакет ЧС ([29](29-admin-emergency-pack.md)) | `--profile demo\|minimal`, `--reset` (требует `--yes`), `--data small\|demo`, `--pack emergency\|none` |
| `kchs basemaps upload <каталог>` | загрузка сборки PMTiles в хранилище и регистрация подложки | `--key`, `--no-register` |
| `kchs basemaps sync` | перестроить реестр базовых карт по манифестам в хранилище | — |
| `kchs secrets rotate` | перешифровать секреты текущим мастер-ключом после его смены; прежний ключ — в `KCHS_MASTER_KEY_PREVIOUS` (порядок — `infra/runbooks/secret-leak.md` §3) | `--dry-run` |
| `kchs help` | справка | `-h`, `--help` |

Общий ключ `--verbose` показывает журнал выполнения.

Осторожно: `kchs seed --reset --yes` **удаляет все данные** установки. На боевом
контуре не применяется.

При разработке те же операции доступны как `pnpm db:migrate`, `pnpm db:seed`
(с ключами через знак равенства: `pnpm db:seed --profile=demo --data=small`).

## Базовая карта

Из коробки карты работают «без подложки» (фон) — векторную подложку нужно
собрать и загрузить:

1. На машине с интернетом: `KCHS_BASEMAP_UPLOAD=0 bash infra/basemaps/build-pmtiles.sh`
   (для Таджикистана ≈ 620 МБ загрузок, 4 ГБ памяти JVM, около 6 минут).
   Результат — каталог `seeds/.cache/basemaps/out`.
2. Перенесите каталог на сервер и загрузите:
   ```bash
   docker compose cp <каталог> api:/tmp/basemaps
   docker compose exec api kchs basemaps upload /tmp/basemaps
   ```
3. Проверьте в консоли: **«Администрирование» → «Базовые карты»** — версия
   сборки, размер, число тайлов, подложка по умолчанию.

Растровые подложки (спутник, государственные слои) добавляются прямо в консоли:
шаблон адреса с `{z}`, `{x}`, `{y}` и `{key}`; ключ хранится на сервере
зашифрованным и в браузер не попадает.

## Обновление версии

```bash
git fetch --tags && git checkout v<версия>
docker compose --profile app pull        # или --build при локальной сборке
docker compose --profile app up -d --wait
```

Миграции применяются автоматически при старте `api` под advisory lock —
`kchs init` повторять не нужно. Перед обновлением: прочитайте описание релиза и
новые ADR, убедитесь, что резервная копия свежая, и предупредите пользователей
через **«Объявления»**.

После обновления проверьте:

- `curl -fsS http://localhost:3000/health` → `{"status":"ok"}`;
- **«Здоровье системы»**: postgres, redis, meilisearch, storage — «Работает»;
- «Неопубликованных событий: 0»;
- вход, «Мой день», открытие объекта, обсуждение — вручную.

Откат: вернуть прежний тег образов и поднять их; если новая версия применила
необратимую миграцию — восстановить базу по `infra/runbooks/restore.md`.

Подробные порядки действий — в `infra/runbooks/upgrade.md`, `restore.md`,
`incident.md`.

## Стенд разработки

Инфраструктура в Docker, api и веб — на хосте:

```bash
bash infra/scripts/generate-secrets.sh
pnpm install
docker compose up -d --wait
pnpm db:migrate && pnpm db:seed
pnpm dev
```

Интерфейс — `http://localhost:5173`, почта разработки — mailpit на
`http://localhost:8025`. Движок поднимается отдельно:
`docker compose up -d --wait engine`.

## Частые вопросы

**Версия в «Здоровье системы» не меняется после обновления.** Поле показывает
строку, зашитую в код, а не тег образа. Ориентируйтесь на тег и на описание
релиза.

**`kchs init` выполнили дважды — что будет?** Ничего плохого: команда
идемпотентна, администратор не пересоздаётся, а календарь и справочники
дозагружаются.

**Нужно ли ставить Node на сервер?** Нет. Образ `api` — единый бандл, все команды
выполняются внутри контейнера.
