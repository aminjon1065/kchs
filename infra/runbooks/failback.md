# Возврат на основную площадку после переключения

Ситуация: узел работает основным (`failover.md`), основная площадка восстановлена — тот же
сервер или новый. Возврат идёт в два шага: бывший основной становится standby узла, затем
плановое переключение обратно. Роли серверов в `dr.sh` задаёт `.env`: у того, кто сейчас
standby, заполнен раздел «Резервный узел» (`KCHS_DR_PRIMARY_*`), у основного — нет.

Проверено на стенде 12.10.2026: переключение на узел, засев бывшего основного, обратное
переключение и повторный засев узла, проверка восстановления после всего цикла.

## 1. Бывший основной — в standby узла

1. **На бывшем основном остановить приложение**, если оно поднялось само:
   ```bash
   docker compose --profile app stop api worker engine web
   ```
   Его база после аварии — устаревшая история. Если на нём успели записать что-то после
   последней репликации, сначала выгрузите это для разбора
   (`docker compose exec -T postgres pg_dump -U postgres kchs > before-failback.dump`):
   засев ниже заменит базу целиком.
2. **На узле (сейчас основной)**, `.env`: `POSTGRES_BIND=<адрес VPN узла>`,
   `KCHS_DR_CIDR=<адрес VPN бывшего основного>/32`. Затем:
   ```bash
   docker compose --env-file .env -f infra/compose/docker-compose.yml -f infra/compose/dr.yml \
     up -d postgres
   bash infra/scripts/dr.sh primary-setup
   ```
3. **На бывшем основном**, `.env` — раздел «Резервный узел» указывает на узел:
   `KCHS_DR_PRIMARY_HOST=<адрес VPN узла>`, `KCHS_DR_PRIMARY_PG_PORT`,
   `KCHS_DR_PRIMARY_S3=http://<адрес VPN узла>:9000`. Затем:
   ```bash
   bash infra/scripts/dr.sh init-standby --yes
   bash infra/scripts/dr.sh status          # поток streaming, отставание 0
   ```
   Зеркало хранилища теперь идёт в обратную сторону — файлы, загруженные на узел, приходят
   сюда. Архив WAL и базовые копии прежней истории откладываются в `previous-<время>` своих
   томов; когда возврат закончен, их можно удалить.

## 2. Обратное переключение (окно обслуживания)

1. На узле: `dr.sh stop-app` — приложение остановлено, печатается позиция WAL.
2. На бывшем основном: `dr.sh status` — «принято» и «применено» не меньше этой позиции.
3. На бывшем основном: `dr.sh promote --yes` — он снова основной, приложение запущено.
4. DNS — обратно на основную площадку; консоль → «Переиндексировать поиск»; проверка входа и
   «Здоровья системы».

## 3. Вернуть роли

1. **Основной**, `.env`: убрать (закомментировать) `KCHS_DR_PRIMARY_*`; `POSTGRES_BIND` и
   `KCHS_DR_CIDR` — как при подготовке. Слоты при засеве не переносятся, поэтому:
   ```bash
   bash infra/scripts/dr.sh primary-setup
   ```
2. **Узел**, `.env`: `POSTGRES_BIND=127.0.0.1`, раздел «Резервный узел» — на основной.
   Остановить приложение узла и засеять его заново:
   ```bash
   docker compose --env-file .env -f infra/compose/docker-compose.yml -f infra/compose/dr.yml \
     --profile app stop api worker engine web
   bash infra/scripts/dr.sh init-standby --yes
   bash infra/scripts/dr.sh basebackup
   bash infra/scripts/dr.sh restore-check
   ```
   Если `init-standby` отвечает «на основном нет слота kchs_dr» — пропущен шаг 3.1: база
   узла при этом не тронута.

Полный засев переносит базу целиком. Для больших баз это часы по VPN; перемотка
`pg_rewind` (без полного копирования) требует `wal_log_hints` и пока не включена — ADR-0199,
«Последствия».
