# Резервный узел: подготовка и переключение

Резервный узел (ADR-0199) — второй сервер на удалённой площадке. Он держит горячую копию
базы (standby по потоковой репликации), свой архив WAL для восстановления на момент времени
и зеркало хранилища. Приложение на узле не запущено, пока узел не станет основным.

Цели концепт-ноты: потеря данных (RPO) — не больше часа, время восстановления (RTO) — не
больше четырёх часов.

| Что | Где | Как |
|---|---|---|
| База | узел, `postgres` | standby, слот `kchs_dr` на основном, отставание — секунды |
| Архив WAL | узел, том `drwal` | `pg_receivewal --synchronous`, слот `kchs_dr_wal` |
| Базовые копии | узел, том `drbase` | `dr.sh basebackup` раз в неделю, хранятся 4 |
| Файлы | узел, `minio` | `mc mirror --watch` бакетов `kchs-*`, кроме выгрузок |
| Копии `pg_dump` | бакет `kchs-backups` | приходят на узел вместе с зеркалом (ADR-0117) |
| Redis, поиск | — | при переключении: очереди — из базы, поиск — переиндексацией |

Все команды — `bash infra/scripts/dr.sh …` из каталога установки; `dr.sh` без параметров
печатает справку.

## Подготовка (один раз)

1. **Сеть.** VPN между площадками; узел ходит на основной (Postgres и хранилище), обратного
   доступа узлу не нужно. Запишите адреса VPN обоих серверов.
2. **Основной сервер**, `.env`:
   ```bash
   bash infra/scripts/generate-secrets.sh --add-missing   # POSTGRES_REPLICATION_PASSWORD, S3_DR_*
   ```
   и раздел «Резервный узел»: `POSTGRES_BIND=<адрес VPN основного>`,
   `KCHS_DR_CIDR=<адрес VPN узла>/32`. Затем:
   ```bash
   docker compose --profile app up -d          # Postgres слушает адрес VPN, minio-init заводит kchs-dr
   bash infra/scripts/dr.sh primary-setup      # роль репликации, слоты, pg_hba, роль метрик
   ```
3. **Образы на узел.** Без выхода в интернет — перенос (и так при каждом обновлении):
   ```bash
   docker save kchs/postgres:17-3.5 kchs/api:<тег> kchs/engine:<тег> kchs/web:<тег> \
     redis:7-alpine getmeili/meilisearch:v1.53 axllent/mailpit:<тег> \
     quay.io/minio/minio:<тег> quay.io/minio/mc:<тег> | ssh <узел> docker load
   ```
   Точные теги — `docker compose config --images` на основном.
4. **Узел.** Та же версия репозитория; `.env` — копия основного (`scp`, режим 600) и раздел
   «Резервный узел»: `KCHS_DR_PRIMARY_HOST`, `KCHS_DR_PRIMARY_PG_PORT`, `KCHS_DR_PRIMARY_S3`
   (`http://<адрес VPN основного>:9000`), `KCHS_DR_NAME`. `POSTGRES_BIND` на узле —
   `127.0.0.1`, `KCHS_DR_CIDR` на узле не нужен. Затем:
   ```bash
   bash infra/scripts/dr.sh init-standby
   bash infra/scripts/dr.sh basebackup
   bash infra/scripts/dr.sh status
   ```
5. **Отчёт о проверках восстановления** (без входа администратором). В консоли основного:
   «Роли» → новая роль «Резервный узел» со способностью «Отчёт о проверке восстановления»;
   «Служебные учётные записи» → «Резервный узел» с этой ролью; токен на неё с областью
   `write:backups` (выпускает администратор системы). В `.env` узла:
   `KCHS_DR_REPORT_URL=https://<домен>/api/v1`, `KCHS_DR_REPORT_TOKEN=<токен>`.
6. **Расписание на узле** (cron пользователя, который управляет Docker):
   ```cron
   15 3 * * 0  cd /opt/kchs && bash infra/scripts/dr.sh basebackup >> /var/log/kchs-dr.log 2>&1
   0  5 1 * *  cd /opt/kchs && bash infra/scripts/dr.sh restore-check >> /var/log/kchs-dr.log 2>&1
   ```
7. **Оповещения.** Профиль `observability` — на обоих серверах; на узле
   `ALERTMANAGER_INSTALLATION=Резервный узел`, адресаты те же. Правила группы `kchs-dr`:
   «узел отстаёт больше RPO», «слот узла не подключён», «запас WAL для узла кончается».

## Каждый день

- Оповещений группы `kchs-dr` нет.
- `dr.sh status` на узле: поток `streaming`, отставание 0 или секунды, архив растёт,
  `s3-mirror` и `wal-receiver` — `Up`.
- В консоли «Резервные копии» → «Проверки восстановления»: последняя — не старше месяца и
  успешная.

## Аварийное переключение: основной потерян

Решение принимает ответственный за систему по регламенту Комитета.

1. **Убедиться, что основной действительно потерян**, а не пропал VPN. Если основной жив и
   доступен хотя бы локально — остановить на нём приложение
   (`docker compose --profile app stop api worker engine web`): две работающие базы — это
   две разные истории, свести их нельзя.
2. На узле `dr.sh status` — запишите «последняя транзакция»: это фактическая потеря данных.
3. ```bash
   bash infra/scripts/dr.sh promote --yes
   ```
   Останавливаются архив и зеркало, standby становится основным, запускается приложение.
4. **Адрес.** DNS-запись домена установки (`KCHS_DOMAIN`) — на публичный адрес узла, либо
   переброска NAT у провайдера. Сертификат Caddy получит сам, если домен публичный.
5. Консоль → «Резервные копии» → «Переиндексировать поиск».
6. Проверить: вход, «Здоровье системы» (все компоненты «Работает»), ситуационный экран,
   отправку уведомления себе, загрузку файла.
7. «Процессы»: задания, которые были в очереди основного, на узел не переехали (Redis не
   копируется) — импорты и печать при необходимости запустить заново.
8. Сообщить пользователям и записать время шагов: RTO — от решения до шага 6.

Возврат на основную площадку — `failback.md`.

## Плановое переключение (учения, обслуживание)

1. На основном: `dr.sh stop-app` — приложение остановлено, печатается позиция WAL.
2. На узле: `dr.sh status` — «принято» и «применено» не меньше этой позиции.
3. На узле: `dr.sh promote --yes`, дальше — шаги 4–8 аварийного переключения.
4. Вернуться — `failback.md`.

## Логическая ошибка: удалили, и это уже на узле

Standby повторяет всё, в том числе ошибку. Нужные данные берут из архива WAL на момент до
неё — отдельной базой, рабочие серверы не трогаются:

```bash
bash infra/scripts/dr.sh pitr '2026-10-12 08:00:00+05'    # момент до ошибки, с часовым поясом
docker compose -p kchs-pitr exec -T postgres pg_dump -U postgres -d kchs -t <таблица> > lost.sql
bash infra/scripts/dr.sh pitr-down
```

Глубина — до самой старой базовой копии (4 недели при еженедельной копии). Вернуть строки в
рабочую базу — разбор с разработчиком: прямую вставку мимо приложения делать нельзя (события,
аудит, права).

## Проверка восстановления

`dr.sh restore-check` раз в месяц (cron): последняя базовая копия и архив WAL во временном
проекте, проверка базы, насколько её данные отстают от узла (не больше часа), запуск api на
ней; итог — в консоль основного («Проверки восстановления») и в аудит
(`backup.restore_checked`). На стенде с демо-данными — `--smoke`
(`KCHS_DR_SMOKE_ADMIN_PASSWORD`). Неудача — повторить вручную, посмотреть
`/var/log/kchs-dr.log`, при необходимости засеять узел заново (`init-standby --yes`).
