# Восстановление из резервной копии

Цели (концепт-нота, ADR-0199): потеря данных (RPO) — не больше часа, время восстановления
(RTO) — не больше четырёх часов. Их даёт резервный узел на удалённой площадке
(`failover.md`); без узла остаётся суточная копия `pg_dump` — RPO сутки.

## Что резервируется

| Данные | Способ | Потеря при аварии |
|---|---|---|
| PostgreSQL | standby на резервном узле по потоковой репликации (ADR-0199) | секунды |
| PostgreSQL на момент времени | базовые копии раз в неделю и архив WAL на узле: `dr.sh pitr` | ≤ 1 ч, глубина — 4 недели |
| Окружение, PostgreSQL, файлы — копия за пределами сервера | ночная копия `backup.sh` (restic): репозиторий на сервере, забор компьютером Комитета (ADR-0227) | сутки |
| PostgreSQL, переносимая копия | `pg_dump` заданием платформы раз в сутки, бакет `kchs-backups` (ADR-0117) | сутки |
| Объектное хранилище (MinIO) | зеркало бакетов `kchs-*` на узел, `mc mirror --watch` | секунды; выгрузки не копируются |
| Файлы, прежние версии | версии бакета `kchs-files`: 30 дней (ADR-0227) | — |
| Meilisearch | перестраивается из Postgres («Переиндексировать поиск») | не резервируется |
| Redis | очереди восстанавливаются из базы, кэш наполняется заново | не резервируется |

Узел потерян вместе с основным, или его нет — восстановление из ночной копии `backup.sh`
(следующий раздел); копия `pg_dump` платформы — запасной путь для одной базы.
Основной потерян, узел жив — не восстанавливать, а переключаться: `failover.md`. Логическая
ошибка (удалили, и это уже на узле) — `dr.sh pitr`, раздел в `failover.md`.

## Ночная копия `backup.sh` (ADR-0227) — основной путь без узла

Окружение (`.env` с мастер-ключом), база и файлы восстанавливаются одной командой на чистой
установке; порядок для администратора, забор в Комитет и офлайн-секреты —
`docs/06-guides/27-admin-backup.md`.

```bash
sudo bash infra/scripts/backup.sh restore --repo /var/lib/kchs-backup/repo --yes
docker compose --profile app up -d      # или скрипт установки
```

Тома данных проекта стираются, база пересоздаётся из дампа с владельцами, правами ролей и
настройками базы, файлы ложатся в хранилище, `minio-init` заново заводит версии, правила
хранения и пользователей из `.env`. Затем «Переиндексировать поиск». Проверено прогоном
(04.11.2026): права всех 211 отношений, схем и базы совпали с исходными до бита, файл
скачивается с тем же содержимым, повторная синхронизация привилегий при старте — без
изменений.

## Копии установки S1 (ADR-0117)

Помимо резервного узла установка делает переносимые копии: задание `backup.run`
(02:50) и кнопка «Сделать копию» в консоли (`Администрирование → Резервные
копии`) пишут `pg_dump --format=custom` в бакет `kchs-backups`; хранятся
последние семь. Восстановление такой копии:

```bash
docker compose --profile app stop api worker engine web
docker compose exec -T postgres pg_restore -U postgres --create --clean --if-exists -d postgres < kchs.dump
docker compose --profile app up -d
```

`--create --clean`: база пересоздаётся вместе с правами ролей и своими настройками — дамп
снят с владельцами и правами (`--create`, ADR-0227). Копии, снятые до этого выпуска
(`--no-acl`), права ролей не несут: после восстановления перезапустите api (он заново
раздаст права приложению) и верните роли запросов чтение датасетов:

```bash
docker compose exec -T postgres psql -U postgres -d kchs -c \
  "GRANT SELECT ON ALL TABLES IN SCHEMA ds TO kchs_query;
   ALTER DEFAULT PRIVILEGES FOR ROLE kchs_app IN SCHEMA ds GRANT SELECT ON TABLES TO kchs_query;"
```

Архив выгружается из бакета любым клиентом S3 (`mc cp kchs/kchs-backups/pg/<файл> .`).
После проверки отметьте копию в консоли кнопкой «Отметить проверенной» — дата и
кто проверял останутся в списке и в аудите.

### Ежемесячная проверка: восстановление в отдельную базу

Проверять копию восстановлением поверх рабочей базы нельзя — это и есть авария,
которую мы репетируем. Разворачивайте её рядом, в свежую базу того же кластера;
приложение при этом не останавливается.

```bash
# 1. Копия. Либо кнопка «Сделать копию» в консоли (и выгрузка архива из бакета),
#    либо — если нужен снимок «прямо сейчас» — тот же дамп напрямую:
docker compose exec -T postgres \
  pg_dump --format=custom --create -U postgres kchs > drill.dump

# 2. Пустая база рядом
docker compose exec -T postgres psql -U postgres -d postgres \
  -c 'CREATE DATABASE kchs_restore_drill;'

# 3. Восстановление (без --jobs: параллельный режим не читает со стандартного ввода)
docker compose exec -T postgres \
  pg_restore -U postgres -d kchs_restore_drill < drill.dump

# 4. Сверка: размер и счётчики совпадают с источником
docker compose exec -T postgres psql -U postgres -d kchs_restore_drill -tAc \
  "select pg_size_pretty(pg_database_size(current_database())),
          (select count(*) from objects), (select count(*) from audit_log),
          (select count(*) from users)"

# 5. Убрать за собой: база и архив с боевыми данными не живут дольше проверки
docker compose exec -T postgres psql -U postgres -d postgres \
  -c 'DROP DATABASE kchs_restore_drill WITH (FORCE);'
rm -f drill.dump
```

Сколько это занимает (замер 2026-09-20, стенд разработки: база 2,95 ГБ, из них
2,67 ГБ — демо-датасет «Происшествия» на 5 млн строк; Docker Desktop, NVMe):

| Шаг | Время | Примечание |
|---|---|---|
| `pg_dump -Fc` | 34 с | архив 350 МБ |
| `pg_restore` | 36 с | серийный режим, ошибок нет |
| Сверка | секунды | 6491 объект, 4559 записей аудита, 363 сотрудника — совпало |

Итого около полутора минут на 3 ГБ; в бюджет RTO ≤ 1 ч (`01-overview.md`)
установка такого размера укладывается с большим запасом, и узким местом станет
не база, а выгрузка архива из хранилища и подъём сервисов. Оценка для базы
другого размера — линейная по объёму данных.

Шаг 5 обязателен: база проверки содержит боевые данные целиком, а прав на неё
никто не ограничивал.

После удачной проверки — «Отметить проверенной» в консоли: дата, кто проверял и
примечание остаются в списке копий и в аудите (`backup.verified`).

Если копии нет вовсе — смотрите аудит: `backup.created` пишется и для копии по
расписанию, `backup.failed` — для каждого отказа. Пусто и там — значит,
выключено расписание (`Администрирование → Расписания`, задание `backup.run`).

## Порядок восстановления из копии `pg_dump`

1. **Остановить приложение**, оставив базу и хранилище:
   ```bash
   docker compose --profile app stop api worker engine web
   ```
2. **Выгрузить копию** из бакета `kchs-backups` (на узле — из его зеркала) и восстановить:
   ```bash
   mc cp kchs/kchs-backups/pg/<файл> kchs.dump
   docker compose exec -T postgres pg_restore -U postgres --create --clean --if-exists -d postgres < kchs.dump
   ```
3. **Проверить схему и целостность**:
   ```bash
   docker compose exec postgres psql -U postgres -d kchs -c "select count(*) from objects;"
   ```
   Недостающие миграции api применит при старте сам.
4. **Восстановить файлы**, если утрачено и хранилище: вернуть бакеты `kchs-files`,
   `kchs-media`, `kchs-previews`, `kchs-tiles` из зеркала узла (`mc mirror` в обратную сторону).
5. **Поднять приложение** и проверить здоровье:
   ```bash
   docker compose --profile app up -d
   curl -fsS http://localhost:3000/health
   ```
   На экране «Администрирование → Здоровье системы» все компоненты должны быть
   «Работает», очередь outbox — без отставания.
6. **Перестроить поисковый индекс** — «Администрирование → Резервные копии →
   Переиндексировать поиск».
7. **Зафиксировать инцидент**: журнал аудита сохраняется вместе с базой; проверить,
   что записи за период до сбоя на месте.

## Проверка процедуры

- **Архив WAL узла** — `dr.sh restore-check` раз в месяц по расписанию узла: итог виден в
  консоли («Резервные копии» → «Проверки восстановления») и в аудите
  (`backup.restore_checked`). Порядок — `failover.md`.
- **Копия `pg_dump`** — вручную раз в месяц, порядок и замеры выше, в разделе «Ежемесячная
  проверка». Итог — отметкой «проверено восстановлением» в консоли (аудит
  `backup.verified`) и строкой в `docs/progress.md` (раздел «Результаты проверок»).
