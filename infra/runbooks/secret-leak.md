# Утечка секрета: что отзывать и в каком порядке

Секрет считается утёкшим, если он попал куда-то за пределы менеджера секретов и
`.env` сервера: в переписку, в тикет, в скриншот, в чужой журнал, в публичный
репозиторий, на ноутбук уволившегося. Доказывать использование не нужно —
ротация дешевле расследования.

Порядок один и тот же: **сначала закрыть вход, потом менять ключ, потом
разбираться**. Каждый шаг оставляет запись в аудите — она и будет отчётом.

## 0. Первые пять минут

1. Определить, **что именно** утекло (таблица ниже) и когда.
2. Снять действующие сессии и токены, если утёк секрет, дающий вход.
3. Собрать след: `Администрирование → Аудит` с фильтром по времени, и по
   действиям `user.login`, `user.login_external`, `api_token.created`,
   `api_token.rejected`, `api_token.scope_denied`, `webhook.received`,
   `data.exported`, `document.file_exported`.
4. Записать инцидент по `incident.md` — с этого момента всё в одном месте.

## 1. Что чем отзывается

| Утёк | Где живёт | Как отозвать | Последствие для людей |
|---|---|---|---|
| Пароль сотрудника | `credentials` | `Администрирование → Пользователи → Сбросить пароль`: выдаёт временный пароль и завершает **все** его сессии | сотрудник входит заново и меняет пароль |
| Cookie сессии | `sessions` | там же; сам сотрудник — `Профиль → Устройства → Завершить остальные` (`POST /me/sessions/revoke`) | вход заново |
| Токен публичного API | `api_tokens` | `Администрирование → Безопасность → Токены API` (`DELETE /admin/api-tokens/{id}`); владелец — в профиле | интеграция встаёт до выпуска нового токена |
| Секрет подписи вебхука | `webhooks.secret` (шифром) | `Перевыпустить секрет` в карточке (`POST /webhooks/{id}/secret`) — новый показывается один раз | получатель обновляет секрет у себя; доставки с этого момента подписаны новым |
| Секрет входящего вебхука | `integrations.inbound_secret_hash` | `Новый адрес приёма` в карточке интеграции (`POST /integrations/{id}/inbound-secret`) | отправитель переходит на новый адрес; старый сразу отвечает 404 |
| Учётные данные интеграции (SMTP, IMAP, внешняя БД, ГИС-служба) | `integrations.secrets`, `service_layers.secret_enc` (шифром) | сменить у поставщика, затем вписать новое значение в карточке | интеграция работает по новому ключу |
| Ссылка на объект | `share_links` | закрыть ссылку в карточке объекта; при сомнении — `security.allowShareLinks = false` приостанавливает все | гости теряют доступ |
| Сервисный токен движка (`INTERNAL_SERVICE_TOKEN`) | `.env` | новое значение в `.env`, `docker compose --profile app up -d api worker engine` | секунды недоступности превью и геоопераций |
| Секрет сервера документов (`ONLYOFFICE_JWT_SECRET`) | `.env` и конфигурация ONLYOFFICE | сменить в обоих местах одновременно, перезапустить `api` и `onlyoffice` | открытые сессии редактора закрываются, правки сохраняются повторным открытием |
| Ключи медиасервера (`LIVEKIT_API_KEY/SECRET`) | `.env` и `livekit.yaml` | сменить в обоих, перезапустить `livekit`, `livekit-egress`, `api` | идущие конференции обрываются |
| Пароли БД, ключи S3, `MEILI_MASTER_KEY` | `.env`, роли кластера, MinIO, Meilisearch | сменить в службе, затем в `.env`, поднять стек | короткий простой |
| `KCHS_MASTER_KEY` | `.env` | **см. §3 — отдельный случай** | зависит от объёма |

Если непонятно, что именно утекло, но ясно, что утекла копия `.env`, — меняется
всё из таблицы, включая мастер-ключ.

## 2. Массовый отзыв входа

Отозвать сессии всей организации отдельной кнопкой нельзя — это сознательно: в
рабочий день такой шаг останавливает работу. Когда он всё-таки нужен (утёк дамп
базы, компрометация узла):

```sql
-- Все сессии, кроме вашей: вход заново потребуется каждому
UPDATE sessions SET revoked_at = now()
 WHERE revoked_at IS NULL AND id <> '<ваш sessionId>';

-- Все токены API установки: интеграции встанут, выпускать заново придётся руками
UPDATE api_tokens SET revoked_at = now() WHERE revoked_at IS NULL;
```

Предупредите людей через `Администрирование → Объявления` до, а не после.

Ключи входа (passkey) и второй фактор при этом не трогаются: они привязаны к
устройству, а не к сессии, и утечка базы их не раскрывает (хранятся публичные
ключи и счётчики). Если же утёк `KCHS_MASTER_KEY` — секреты TOTP считаются
раскрытыми, см. ниже.

## 3. Мастер-ключ шифрования интеграций (`KCHS_MASTER_KEY`)

Этим ключом (AES-256-GCM, `17-security.md` §4) зашифрованы:

- секреты TOTP сотрудников (`mfa_factors`);
- пароль учётной записи каталога и секрет клиента IdP (`auth_providers`);
- секреты интеграций и подписи вебхуков (`integrations`, `webhooks`);
- ключи внешних ГИС-служб и растровых подложек (`service_layers`, `basemaps`);
- адреса подписок на внешние календари (`calendars.source`);
- временные пароли импорта из Excel (в Redis, не дольше двух часов) и
  проверочные коды PKCE незавершённых входов (`sso_auth_requests`, 10 минут).

**Смена ключа без простоя** (ADR-0143). Расшифровка пробует сначала текущий ключ,
затем прежний из `KCHS_MASTER_KEY_PREVIOUS`, а команда `kchs secrets rotate`
перешифровывает всё текущим. Вводить секреты заново и переподключать второй
фактор не нужно:

1. **Новый ключ** — `openssl rand -base64 32`. В `.env`: `KCHS_MASTER_KEY=<новый>`,
   `KCHS_MASTER_KEY_PREVIOUS=<прежний>`, затем
   `docker compose --profile app up -d api worker`. С этой минуты новые секреты
   шифруются новым ключом, старые читаются прежним.
2. **Пробный прогон** — `docker compose exec api kchs secrets rotate --dry-run`:
   по каждой таблице видно, сколько строк будет перешифровано и сколько уже
   зашифровано новым ключом.
3. **Перешифрование** — `docker compose exec api kchs secrets rotate`. Прерванный
   прогон безопасно повторить. Строки, которые не читаются ни одним ключом, команда
   не трогает и называет. Тогда код выхода 1: проверьте, тот ли прежний ключ задан.
4. **Убрать прежний ключ** из `.env` и снова `up -d api worker`. Прежний ключ
   сохраните в офлайн-хранилище вместе с датой: он нужен, чтобы восстановить
   резервную копию, снятую до смены. При таком восстановлении задайте его в
   `KCHS_MASTER_KEY_PREVIOUS` и повторите шаги 3–4.

**Если ключ утёк** вместе с копией базы или резервной копией, одного
перешифрования мало: тот, у кого ключ и копия, прочитает прежние значения. Кроме
смены ключа:

1. **Сменить сами секреты у поставщиков**: пароли интеграций и учётной записи
   каталога, секрет клиента IdP, ключи ГИС-служб и подложек. Перевыпустить секреты
   подписи вебхуков.
2. **Второй фактор**: администраторам и аудиторам подключить TOTP заново
   (`Профиль → Безопасность`), остальным — по решению службы безопасности. Ключи
   входа (passkey) мастер-ключом не зашифрованы — их менять не нужно.
3. **Проверить**: «Проверить соединение» у каждой интеграции и службы, тестовая
   отправка уведомления, тестовая доставка вебхука.

Если смена не может пройти сегодня, отзовите то, что утечка раскрывает **сейчас**:
- секреты вебхуков;
- ключи служб;
- пароли интеграций — они у поставщиков, и их смена мастер-ключа не требует.

Администраторам потребуйте повторно подключить второй фактор.

## 4. После ротации

- Проверить, что старые значения нигде не остались: `.env` на всех узлах,
  менеджер секретов, конфигурации соседних служб (`livekit.yaml`, ONLYOFFICE),
  CI-переменные, резервные копии `.env`.
- Просмотреть аудит за период от утечки до ротации: `user.login` из новой
  страны, `api_token.rejected` и `api_token.scope_denied` с незнакомых адресов,
  `data.exported` и `document.file_exported` не по работе.
- Записать причину и меры в `docs/progress.md` («Известные проблемы»), решение —
  в ADR, если менялся порядок работы.
- В копиях, сделанных до ротации, зашифрованные колонки остались под прежним
  ключом: восстановление из такой копии потребует и старого значения
  `KCHS_MASTER_KEY`. Храните его в менеджере секретов, пока живы эти копии (семь
  суток, ADR-0117), и удаляйте вместе с ними.
